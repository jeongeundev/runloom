## 가장 최근의 사용자 질문 — 여기서 이어갈 것

사용자는 이미 A → B → C → D → E → F라는 업무 흐름이 있다고 가정했다. 트리거·실행 조건·조건문을 지금 설계하지 말고 다음 연결이 가능한지 물었다.

```text
A → B → C → D → E → F
    │   │
    │   └→ 다른 담당자가 쓰는 에이전트
    │       └ 그 사람이 설정한 스킬·MCP·프로젝트 환경
    └→ 내가 쓰는 Codex
        └ 내가 설정한 스킬·MCP·프로젝트 환경
```

- B는 사용자가 해야 하는 업무, C는 다른 사람이 해야 하는 업무다.
- 각자가 이미 사용하는 에이전트를 해당 단계에 연결하고 싶다. n8n 안에서 스킬·MCP를 모두 다시 구성해야 하는 것으로 가정하지 않는다.
- 이 예시는 연결 가능성을 확인하기 위한 것이다. 매 업무마다 사용자가 에이전트를 수동 지정한다는 정책이나 업무 하나가 반드시 n8n 노드 하나라는 결정을 뜻하지 않는다.
- 앞서 사용자는 작업 내용을 보고 시스템이 적합한 에이전트를 선택하는 방향을 선호했다. 이번 B·C 예시를 그 선호의 철회로 해석하지 않는다.

Assistant는 **각자의 설정을 불러오는 실행 환경에 업무를 전달하는 연결부를 두면 구현 가능하다**고 설명했다. A2A로 연결부의 요청·상태·질문·결과 형식을 통일하는 구조는 후보이며 아직 구현·검증하지 않았다.

중요한 구분:

| 구분 | 이번 대화에서 설명한 내용 |
|---|---|
| 모델 API 호출 | Claude·OpenAI 모델을 부르는 것만으로 기존 Codex·Claude Code의 스킬·MCP·대화 기록이 따라오지는 않는다 |
| 기존 에이전트 실행 환경 연결 | 올바른 사용자 설정·작업 디렉터리·인증을 읽을 수 있는 환경에서 실행하면 기존 구성을 활용할 수 있다 |
| 기존 설정과 기존 대화 | 같은 설정을 사용하는 새 실행과 이미 열린 대화를 이어가는 것은 별도다. 대화 기억의 자동 승계를 약속하지 않는다 |
| 스킬·MCP 사용 | 설정이 로드되어도 모든 스킬이 매번 실행되거나 모든 도구에 무제한 접근하는 것은 아니다 |

Codex의 `codex exec`, Claude Code의 `claude -p`처럼 외부 프로그램에서 실행할 수 있는 방법을 확인했다. 상대 에이전트 실행 환경의 접근 가능성, 인증과 설정 범위 등은 실제 연결 시 검증해야 한다. Codex나 Claude Code가 이름만 등록하면 곧바로 A2A 서버가 된다고 설명하지 않는다.

## 사용자가 설명한 목적과 방향

- **원래 문제:** A가 끝난 뒤 B가 시작되지 않아 C 이후까지 계속 밀리는 착수 대기. 전달 누락, 담당자의 다른 업무, 권한 요청 등은 가능한 원인이다. 빈도·손실 규모는 검증하지 않았다.
- **첫 대상 방향:** 다른 사람과 협업하는 팀. 비개발자도 에이전트·워크플로우의 기술적 구성을 몰라도 사용할 수 있기를 원한다. 구체적인 직무와 첫 업무는 미정이다.
- **업무 흐름:** 사람 업무·에이전트 업무·일정에 따라 진행되는 단계가 섞일 수 있다. 사람이 판단할 필요가 없는 구간은 자동으로 이어가고 싶다. 모든 업무를 에이전트만 수행한다고 좁히지 않는다.
- **목표에서 시작:** 사람이 목표를 전달하면 에이전트가 필요한 일을 나누고 Jira 등에 등록하는 단계까지 포함하고 싶다고 확인했다. 모든 단계의 에이전트 수행 가능성과 모든 작업의 무승인 실행은 다르다.
- **실행 연결 후보:** Jira 작업 등록 → n8n에서 에이전트 작업 실행 → 결과를 Jira에 반영. 여기서 나아가 다음 담당자의 에이전트로 결과와 맥락을 전달한다.
- **구성 부담 감소:** 사용자가 모델·메모리·스킬·도구를 직접 조립하지 않아도 업무를 맡길 수 있게 하려 한다. 이미 설정한 에이전트의 연결과 에이전트가 없는 사용자를 위한 생성 아이디어가 모두 있으며, 생성 기능을 임의로 제외하거나 후순위로 확정하지 않는다.
- **운영 방향:** 처음 생성된 워크플로우는 사람이 확인하고, 기존 흐름은 실행하다 필요한 순간에만 확인받는다. 무엇을 같은 흐름으로 보고 언제 질문할지는 미결이다.
- **일의 경중:** 판단 과정이 필요할 수 있다고 제안했다. 실행 우선순위인지, 사람 개입 여부를 정하는 중요도인지, 둘 모두인지는 아직 확인하지 않았다.

## n8n과 A2A에 관한 최신 정리

사용자는 n8n의 기존 개발자 기능을 활용해 필요한 기능을 추가하고, 이를 웹 데모 시나리오로 보여주면 되지 않느냐고 제안했다. 현재 구체적인 검토 방향은 **n8n 기반 확장과 웹 시연**이다. 독립 SaaS 전체의 운영 범위를 먼저 선택하도록 몰아가지 않는다.

이어 사용자는 n8n 자동화와 A2A를 아예 따로 생각할 필요 없이 **n8n에 에이전트를 등록·연결하는 방법으로 A2A를 넣으면 된다**고 설명했다. 초기 인계에 있던 ‘n8n에 에이전트를 등록하는 제품이라는 해석을 정정했다’는 문구만 근거로 최신 제안을 부정하지 않는다. 목적은 여전히 업무 간 병목 감소이며, 연결 노드는 이를 위한 수단이다.

대화에서 정리한 기술 개념:

- A2A는 에이전트의 능력 정보, 업무 요청, 추가 질문·답변, 진행 상태와 결과물을 주고받는 통신 표준이다. 각자의 내부 메모리·도구를 전부 공유할 필요는 없다.
- 병렬 실행 자체에 A2A가 필수인 것은 아니다. 순차·병렬 모두에서 다른 에이전트에 질문하거나 일을 위임할 때 사용할 수 있다.
- 작업 입력이 정해져 있으면 결과 전달만으로 후속 실행이 가능하다. 부족한 정보를 서로 질문하고 답하는 협업은 그보다 더 풍부한 상호작용이다.
- n8n 노드가 A2A 연결부 역할을 할 수 있다. 요청·상태·질문·결과를 처리하는 동작은 설계·구현해야 한다. 노드 등록만으로 대화 경로와 사람 개입 정책이 저절로 생기는 것은 아니다.
- A2A를 사용한다고 병목 감소나 성공적인 업무 완료가 보장되지는 않는다. 동시에 이 한계를 설명하려고 사용자 구상을 별도 제품 여러 개로 쪼개지 않는다.

## 확인한 기존 기능과 설명을 수정한 지점

아래는 공식 문서 조사와 읽기 전용 CLI 확인의 결과다. 이 저장소에서 서비스를 연결하거나 실험으로 검증한 결과는 아니다. 상세 비교는 [제품 개요](product/PRODUCT_BRIEF.md)를 참고한다.

| 대상 | 인계 시 유지할 사실 |
|---|---|
| n8n | 티켓 이벤트와 AI Agent 실행을 연결할 수 있다. AI Workflow Builder가 자연어로 노드 선택·배치·설정·수정을 지원하므로 ‘사람이 반드시 모두 수동 구성한다’고 말하지 않는다 |
| Devin | 티켓 실행 외에도 Automations, Managed Devins, Dynamic Workflows, Auto-triage가 있다. 작업 분해·병렬 조율·단계 간 결과 전달·재개·재사용을 지원하므로 ‘Devin은 티켓 하나만 처리한다’로 차별화하지 않는다 |
| Jira | 상태 조회와 알림에 그치지 않고 자동화와 에이전트 실행 연결도 제공한다 |
| n8n·Devin 비교 | 자동화 기능은 겹친다. 기존 도구를 활용하는 사용자 의도를 인정하면서 실제로 남는 설정·협업 부담을 확인한다. 차별성은 아직 가설이다 |

## 미결 사항과 assistant 제안의 경계

- 기존 에이전트의 연결 경험과 에이전트 자동 구성·생성 중 첫 데모에서 어디까지 보여줄지.
- 연결 대상의 실행 위치, 지원 에이전트, 연결부 방식과 기존 구현 재사용 여부.
- 기존 대화 세션을 이어야 하는지, 설정을 재사용하는 새 작업 세션이면 되는지.
- 작업 내용에 따른 에이전트 선택 기준과 선택할 수 없을 때의 행동.
- 에이전트 질문을 다른 에이전트가 답할지, 사람에게 올릴지의 기준.
- 워크플로우 재사용·재확인 조건. Assistant가 제안한 ‘최초에 허용 범위를 저장하고 차이를 비교’하는 방식은 미합의다.
- 구체적인 대표 업무, MVP 범위, 완료·리뷰 기준과 성공 지표.
- 커스텀 노드·n8n 화면 수정·별도 웹 화면 중 실제로 필요한 구현 범위.

위 질문을 한꺼번에 사용자에게 던지지 않는다. 현재는 B·C 연결의 의미를 이해하는 단계이며, 트리거·조건문 상세 설계는 보류하라는 최신 요청을 존중한다. 개발팀·긴급 버그·GitHub PR을 첫 사례로 임의 확정하지 않는다.

## 문서 간 불일치와 보관 자료 처리

[제품 개요](product/PRODUCT_BRIEF.md)는 누적 초안이다. 최신 연결 장면 외에 ‘공모전 데모 — 첫 구현 대상’ 등 이번 대화에서 근거를 확인하지 못한 내용도 들어 있다. 이번 handoff 작성에서는 해당 내용을 삭제하거나 덮어쓰지 않았다.

- 공모전 마감·제출 조건·심사 방식, 무로그인 데모, 서버 페르소나, GitHub 실연동 우선 등의 ‘사용자 결정’ 표시는 이번 대화만으로 재확인할 수 없다. 별도 대화의 결정일 수 있으므로 필요할 때 출처를 확인한다.
- ‘프로토콜은 데모 뒤에 선택’, ‘데모 확정 후 바로 구현 계획’ 같은 문구를 최신 A2A 연결 논의나 구현 금지 지시보다 우선하지 않는다.
- Devin을 티켓 하나만 처리하는 도구로 제한하는 문구는 위 추가 조사와 함께 읽는다.
- [이전 Gateless 보관 자료](archive/2026-09-16-gateless/README.md)의 freeze·스택·기한·MVP·Work Engine은 당시 맥락이다. 자동 복원하지 않는다.
- Baton·Buzz는 과거 참고 아이디어다. 이 대화에서 Baton 저장소 구현을 분석한 것으로 취급하지 않는다.

## 다음 세션의 진행 방식

1. 최신 B·C 장면을 짧게 확인한다. 기존 설정을 가진 각자의 에이전트를 연결한다는 의도를 새 모델 호출이나 단일 소유자의 에이전트 여러 개로 바꾸지 않는다.
2. 사용자의 후속 질문을 받아 연결·업무 인계 경험을 하나씩 구체화한다. 최신 설명을 매번 새로운 확정 제품 방향으로 과장하지 않는다.
3. 제품 개요의 충돌 문구는 출처를 구분해 정리하고, 구체적인 업무 장면을 정한 뒤 PRD와 MVP 범위로 이어간다.
4. 사용자 흐름 → 기술 설계 → 작은 단계의 구현 계획 순으로 작성한다. 기존 `docs/PRD.md`, `docs/ARCHITECTURE.md`는 템플릿이며 같은 역할의 문서를 중복 생성하지 않는다.
5. 별도 구현 요청 전에는 코드·실연동·배포를 시작하지 않는다.

## 수행 내용과 작업 상태

- 이번 대화에서 제품 개요 초안을 작성·갱신하고 `docs/README.md`에 연결했다. 이번 요청에서는 이 handoff를 최신 의도 중심으로 다시 정리했다.
- 공식 문서를 조회했고 로컬 `codex --help`로 실행 인터페이스를 확인했다. Codex·Claude Code에 업무를 실행시키거나 A2A·n8n 연결을 구현한 것은 아니다.
- 이전 문서 보관은 이미 완료되어 있다. 당시 검증 내역은 기존 문서와 보관 이력을 참고하며 이번에 실험을 재실행하지 않았다.
- 기존 코드·설정의 미커밋 변경이 많다. 이번 문서 작업과 무관한 변경은 유지한다. 커밋·푸시하지 않았다.
- 문서 변경의 공백 오류와 로컬 링크를 확인한다. 제품 코드 테스트는 이번 인계 작업 대상이 아니다.

## 권장 스킬

- `example-skills:doc-coauthoring`: 제품 개요와 후속 문서를 함께 다듬을 때. 사용자의 ‘미결 사항 하나씩’ 요청을 우선한다.
- `openai-docs`: Codex 실행 환경·설정·세션 연결을 구체적으로 확인할 때.
- `product-management:feature-spec`: 첫 업무 장면과 범위가 구체화되어 PRD를 작성할 때.
- `handoff`: 다음 세션 인계를 다시 정리할 때. 현재 사용자가 요청한 인계 문서는 이 파일이다.
