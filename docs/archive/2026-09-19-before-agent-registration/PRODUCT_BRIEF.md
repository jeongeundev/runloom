# 제품 개요 — 논의 초안

작성일: 2026-09-19
상태: 사용자와 논의 중. 핵심 문제에 대한 사용자 설명을 반영했으며, PRD·MVP 범위·기술 설계의 확정본이 아니다.
근거: [현재 논의](../CURRENT_HANDOFF.md)의 최근 사용자 의도와 이번 문서 작성 요청. 보관된 이전 기획은 현행 요구사항으로 사용하지 않았다.

## 한 문장으로 설명하면

사용자의 목표를 업무 흐름으로 구성하고, 팀의 각 담당자가 자기 키·도구·맥락으로 운영하는 에이전트들이 직접 소통하며 일을 이어받게 하여, 사람의 판단이 필요하지 않은 구간은 자동으로 이어가며 사람 사이의 대기와 연쇄 지연을 줄이려는 워크플로우 자동화 웹 서비스.

이 문장은 사용자 의도를 assistant가 정리한 초안이다. 사용자는 2026-09-19에 "내 에이전트가 실제 서비스들과 연결되어 작업하고, 다른 사람의 에이전트와 바로바로 소통하며 진행하는 자동화"가 보여주고 싶은 것이라고 확인했다. 워크플로우 자동화가 목적이므로 장기적으로는 다른 회사의 에이전트까지 염두에 두지만, 지금 그 범위로 가는 것은 너무 커진다고 판단해 데모와 첫 버전은 같은 팀 안으로 한정했다. 구체적인 제품 형태와 첫 지원 업무는 아직 합의하지 않았다.

## 해결하려는 문제

사용자는 혼자 일하며 작업 사이의 단절을 느꼈고, 친구의 팀 업무에서 담당 확인과 결정 대기가 발생하는 사례를 접했다. 긴급 오류에 태그되어 확인했지만 본인의 업무가 아니었던 일화가 있다.

**사용자가 직접 설명한 핵심 문제:** A → B → C 순서의 업무에서 A가 끝났는데 B가 바로 시작되지 않으면 C를 비롯한 뒷 작업도 계속 밀린다. 사용자는 이 작업 사이의 착수 대기를 처음 구상한 가장 큰 병목으로 보고 있다.

**최신 사용자 설명:** 업무 흐름에는 사람이 하는 일, 에이전트가 하는 일, 일정에 따라 진행되는 단계가 섞일 수 있다. 사람의 판단이 필요하지 않은 구간에서 에이전트 간 자동 실행을 가능하게 하면 업무 사이의 병목을 줄일 수 있지 않을까 하는 것이 제품 가설의 출발점이다. 모든 업무를 에이전트만 수행하는 흐름으로 한정하지 않는다. ‘일정’을 실행 주체가 아닌 시작·대기 조건으로 표현하는 것은 이 문서의 정리 방식이다.

사용자가 제시한 가능한 대기 원인은 다음과 같다. 실제 특정 팀에서 확인된 원인이나 빈도 순위는 아니다.

- 다음 담당자가 앞 작업의 완료나 결과를 전달받지 못한다.
- 다음 담당자가 다른 작업을 수행하고 있다.
- 다음 작업을 시작하려면 권한 요청 같은 선행 작업이 추가로 필요하다.

따라서 전달 누락만으로 문제를 한정하지 않는다. 사용자는 후속 작업까지 에이전트로 이어가는 방향을 원한다. 각 원인을 제품이 어디까지 해결할지, 사람이 개입할 지점은 아직 미결이다. 반복 빈도·손실 규모는 검증하지 않았으며, 긴급 오류 일화를 첫 MVP로 선택한 것도 아니다.

## 첫 사용자와 사용 장면

**추가 사용자 의도:** 개발자가 아니어도 에이전트의 모델·메모리·스킬·도구 구성을 직접 다루지 않고 업무 자동화를 사용할 수 있게 한다. 구체적인 직무와 첫 업무는 미정이다.

- **사용자 의도:** 다른 사람과 협업하는 팀을 중심으로 출발한다.
- **미결:** 어느 팀의 어떤 담당자들이 어떤 업무를 함께 수행하는가.
- **사용자 의도:** A 완료 후 B의 착수가 지연되어 C까지 밀리는 장면을 중심으로 문제를 구체화한다.
- **미결:** 실제 A·B·C 업무가 무엇이며, 어떤 결과에 도달하면 완료인가.

사용 장면을 구체화할 문장:

> [팀의 담당자 A]가 [시작 사건]을 처리한 뒤 [담당자 B]의 다음 작업으로 이어져야 한다. 지금은 [전달·대기의 문제]로 멈춘다. 제품은 [전달할 맥락·결과와 이어갈 작업]을 지원하고, [확인 가능한 결과]에 도달하도록 돕는다.

이 문장은 논의를 위한 틀이다. 순차 업무의 착수 대기가 문제의 중심이지만, 특정 역할이나 시스템의 실행 구조를 정한 것은 아니다.

## 사용자가 제시한 제품 구상

**사용자가 구체화한 연결 장면:** A → B → C → D → E → F 흐름에서 B는 본인의 Codex, C는 다른 담당자가 운영하는 에이전트에 맡길 수 있는지 질문했다. 각 에이전트에는 각자가 설정한 스킬·MCP 등이 이미 존재한다. 지금은 트리거·조건문 설계를 정하지 않고, 기존 설정을 가진 서로 다른 사람의 에이전트를 작업 단계에 연결하는 가능성을 확인하는 단계다. 한 업무 단계를 반드시 n8n 노드 하나로 구현한다는 결정은 아니다.

**기술적 설명, 구현 미확정:** 해당 설정을 읽을 수 있는 각자의 실행 환경에서 Codex·Claude Code 등을 호출하는 연결부를 두면 구현할 수 있다. 단순 모델 API 연결은 사용자의 기존 CLI 설정이나 대화 세션을 자동으로 가져오지 않는다. A2A를 사용할 경우 연결부가 업무 요청·상태·결과를 해당 실행 도구의 인터페이스로 변환하는 후보 구조다. 연결 대상은 접근 가능한 실행 환경이어야 하며 프로젝트·설정·인증을 올바르게 불러와야 한다. 스킬이 존재하는 것과 매 작업에 모든 스킬이 실행되는 것은 다르다. 실제 연결 및 설정 재사용 검증은 아직 하지 않았다.

**최신 사용자 제안 — n8n 안의 A2A 연결:** 사용자는 n8n 자동화와 A2A를 별도 제품처럼 나눌 필요 없이, n8n에 에이전트를 등록·연결하는 방법으로 A2A를 넣으면 된다고 제안했다. 이를 n8n 확장 방향의 구체적인 후보로 우선 검토한다. A2A 논의를 무조건 데모 뒤로 미루거나 데모에서는 내부 메시지만 사용한다고 확정하지 않는다.

**Assistant가 풀어 쓴 동작, 세부 설계 미합의:** A2A 지원 에이전트의 Agent Card 주소와 인증을 연결하면 노드가 능력 정보를 읽고, 업무 요청을 전달하며, 작업 상태·추가 질문·결과를 n8n 흐름에 전달한다. 외부 에이전트의 모델·메모리·도구는 해당 에이전트 쪽에서 유지할 수 있다. 연결 노드는 에이전트를 새로 만드는 기능과 구분한다. 에이전트 간 질문을 누구에게 보내고 답변 후 어떻게 이어갈지는 노드와 워크플로우의 구현 범위로 정해야 하며, 노드를 배치하는 것만으로 자동 협상이 완성된다고 가정하지 않는다. 등록 화면·자동 선택·질문 전달의 범위 및 기존 노드 재사용 여부는 아직 미정이다.

**최신 사용자 설명 — 업무를 맡기는 경험:** 사용자는 비개발자도 n8n을 사용할 수 있게 하는 방향을 설명하며, 대표적인 구성 부담으로 에이전트 등록과 메모리·스킬·수행 업무 설정을 들었다. Devin이 업무 티켓을 받아 실행하는 경험을 n8n에서도 제공할 수 있지 않느냐고 질문했다. 검토할 경험은 ‘업무를 맡기면 시스템이 필요한 에이전트 구성과 실행 연결을 준비’하는 것이다. 기존 에이전트 연결 구상을 폐기하거나 모든 요청마다 새 에이전트를 생성한다고 해석하지 않는다.

**구현 가능성과 제품 가설의 구분:** Jira 이벤트에서 AI Agent를 실행하는 흐름 자체는 기존 n8n 구성 요소로 만들 수 있다. 추가 가치는 비개발자가 업무를 설명하고 필요한 서비스 접근을 연결하는 과정만으로 사용하도록 구성 부담을 줄이는 데서 검증한다. 메모리·스킬·도구 설정은 내부적으로 필요에 맞게 처리하며, 모든 업무에 메모리가 필요하다고 가정하지 않는다. 티켓 감지 자체나 자연어 생성 자체를 새 기능으로 주장하지 않는다. 지원 업무, 자동 구성의 범위, 부족한 정보·권한을 질문하는 경험은 PRD에서 정한다.

**최신 구현 방향 후보:** 사용자는 독립 서비스의 운영 범위를 지금 선택하기보다, n8n의 개발자용 기능을 활용해 필요한 기능을 추가하고 그 동작을 웹 데모 시나리오로 보여주면 되지 않느냐고 제안했다. 현재 검토 대상은 ‘n8n 기반 기능 확장과 웹 시연’이다. 별도 SaaS 전체를 만드는 것을 전제로 하지 않는다. 추가할 핵심 기능과 시연 장면을 먼저 정하고, 커스텀 노드·n8n 화면 수정·별도 데모 화면 중 필요한 구현 방식은 기술 설계에서 결정한다. 이 발언은 코드 구현 착수 요청이 아니다.

**Assistant의 데모 제안, 미합의:** 목표 입력 → 필요한 에이전트와 연결 구성 제시 → 최초 확인 → A 작업 결과를 B에 전달해 자동 실행 → 사람이 필요한 지점에서 질문 → 답변 후 재개를 한 장면으로 보여준다. 모든 단계를 첫 데모에 넣는 범위나 특정 업무 사례는 아직 합의하지 않았다.

**이번 대화에서 추가로 짚은 구성 부담:** 사용자는 n8n에서 모델·도구·메모리 등을 직접 연결해 에이전트를 구성하는 일을 시스템이 대신하도록 하는 것이 자신의 생각에 가깝지 않느냐고 설명했다. ‘n8n을 더 쉽게 사용할 수 있도록 한다’는 표현으로 방향을 탐색 중이다. 병목 감소라는 목적에 더해, 이를 실현할 에이전트·워크플로우를 사람이 직접 조립해야 하는 부담을 줄이려는 의도로 기록한다. 독립 웹 서비스인지 n8n 내부 보조 도구인지, 구성 자동화만 제공할지 운영까지 맡을지는 아직 확정하지 않는다.

**확인한 기존 기능:** n8n의 [AI Workflow Builder](https://docs.n8n.io/build/ways-of-building-workflows/ai-workflow-builder)는 자연어로 워크플로우를 생성·수정·디버깅하고 노드 선택·배치·설정을 처리한다고 설명한다. 사용자는 생성 후 필요한 인증 정보와 매개변수를 검토한다. 따라서 ‘n8n에서는 반드시 사람이 모든 노드를 직접 구성한다’는 전제를 사용하지 않는다. 사용자가 원하는 구성 부담 감소와 기존 기능의 실제 차이는 미검증이다.

| 구상 | 현재 상태 |
|---|---|
| 웹 서비스에서 기존 에이전트를 연결하고 업무를 이어간다 | 사용자 구상. 연결 대상과 방식은 미정 |
| 사람이 목표를 전달하면 에이전트가 필요한 작업을 나누고 등록한다 | 사용자가 포함 의사를 확인. 처음 생성된 흐름은 확인하며, 작업 분해의 상세 방식은 미정 |
| 처음 생성된 워크플로우는 사람이 확인하고, 기존 흐름은 실행하되 필요한 순간에만 확인받는다 | 사용자가 제시한 운영 방향. 같은 흐름인지, 확인이 필요한 상황인지를 판단하는 기준은 미결 |
| 병목을 줄이기 위해 기존 워크플로우 도구를 활용한다 | 사용자가 설명한 접근. Git·Jira·n8n을 언급했으며 각 도구의 필수 채택과 역할 경계는 미정 |
| 시스템이 작업 내용을 보고 적합한 에이전트를 선택한다 | 사용자가 선호하는 방향으로 명시. 선택 기준과 적합한 에이전트가 없는 경우의 처리는 미정 |
| Jira 작업 등록도 에이전트가 수행하며 전체 업무 순환을 에이전트로 이어간다 | 사용자가 명시한 제품 방향. 목표 입력을 지원하며, 작업 분해 방식·사람 개입·MVP에서 지원할 업무 범위는 미정 |
| 에이전트 간 대화·맥락·결과 전달로 병목을 줄인다 | 사용자 의도. 필요한 상호작용과 효과는 구체화·검증 필요 |
| 에이전트가 없는 사용자는 DB·도구·역할 등을 설정해 필요한 에이전트를 생성한다 | 사용자 제안. 첫 버전 포함 여부와 지원 업무 유형은 미정 |
| 후속 에이전트 실행 등에 n8n을 활용한다 | 사용자가 강하게 검토 중인 기술 후보. 채택과 책임 분담은 미확정이며 다른 방식도 허용 |
| 일을 이어갈 때 일의 경중을 따지는 과정이 필요할 수 있다 | 사용자가 제기한 판단 필요성. 실행 우선순위 판단인지, 사람 개입이 필요한 중요도·위험도 판단인지, 둘 모두인지는 미결 |

사용자는 Jira의 담당자·우선순위·상태 관리와 담당자가 알림을 확인해 일을 이어가는 방식을 비교 대상으로 들었으며, 여러 에이전트를 작업에 맞게 실행해 업무를 이어가는 방식에 대한 이해를 설명했다. Jira 연동을 필수로 채택하거나, 모든 후속 작업의 자율 실행을 확정한 발언으로 해석하지 않는다.

## 제품 가설 — assistant의 정리, 검증 전

### 사용자가 제시한 구체적인 실행 흐름 — 검토 후보

`Jira에 작업 등록 → n8n이 해당 작업에 맞는 에이전트 실행 → 작업 완료 시 Jira에 반영`

사용자는 이 방식의 가능성을 질문했다. Jira를 업무 등록·결과 확인에, n8n을 실행 연결에 활용하는 구체적인 후보이며 최종 아키텍처 채택은 아니다.

**이후 사용자가 구체화한 방향:** 사람이 작업마다 에이전트를 미리 지정하기보다 시스템이 작업 내용을 보고 선택하는 것이 좋다고 말했다. Jira에 작업을 등록하는 과정도 에이전트가 수행해야 하며, 전체 업무 순환의 모든 단계를 에이전트를 통해 수행할 수 있기를 원한다.

이를 정리한 개념 흐름은 `사용자가 목표 전달 → 에이전트가 필요한 작업을 나누고 등록 → 시스템이 작업 내용에 맞는 에이전트 선택 → 작업 실행 → 결과 반영 → 후속 작업으로 연결`이다. 사용자는 목표를 받아 작업을 나누고 Jira에 등록하는 단계까지 포함한다고 확인했다. 제품 방향을 나타내며, 모든 단계를 무승인으로 실행하거나 모든 업무 유형을 MVP에서 지원하기로 합의한 것은 아니다. Jira·n8n의 최종 채택과 역할 분담도 별도 결정 대상이다.

사용자가 설명한 접근의 출발점은 병목 감소다. 업무 흐름을 잘 구성하면 병목을 줄일 수 있다고 보고, 기존 워크플로우 도구들을 활용해 이를 실현하려 한다. Git·Jira는 업무 상태를 보는 도구, n8n은 흐름을 구성하고 실행하는 도구로 이해하고 있었다. 이는 사용자의 구상 배경이며 도구 기능의 정확한 분류나 최종 설계는 아니다.

공식 문서상 n8n의 [Jira Trigger](https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.jiratrigger/), [AI Agent](https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.agent/), [Jira Software](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.jira/) 노드로 이벤트 수신·에이전트 작업·이슈 갱신을 연결할 수 있다. 기존 외부 에이전트의 연결 방법은 해당 에이전트의 실행 인터페이스에 따라 정해야 한다.

**Assistant의 보완 제안, 미합의:** 원래 문제인 A → B → C의 착수 대기를 해결하려면 등록된 개별 작업의 실행뿐 아니라, A 완료 후 B의 선행 조건을 확인하고 결과·맥락을 넘겨 B를 실행하는 흐름도 필요하다. 작업 등록과 실행 가능 시점은 구분하며, 에이전트 실행 종료를 업무 완료로 판단할 기준은 별도로 정한다.

미결: 목표 입력의 구체적인 경험과 작업 생성 범위, 시스템의 에이전트 선택 기준, 업무 간 의존 관계의 표현, 경중 판단 기준, 완료·리뷰의 구분, 별도 웹 서비스가 제공할 사용자 경험.

### 처음 확인한 흐름의 재사용 — 운영 방향과 판단 기준 제안

**사용자 의도:** 처음 생긴 워크플로우는 확인해야 하지만, 기존 워크플로우는 실행하고 필요한 순간에만 확인받는다. 사용자는 그 구분을 어떻게 판단할지가 핵심 문제라고 짚었다.

**Assistant 제안, 미합의:** 최초 확인 시 작업 순서뿐 아니라 사용할 도구·권한·작용 대상과 자동 실행을 허용할 조건을 함께 확인한다. 재실행 시에는 확인한 흐름과 이번 실행이 그 조건 안에 있는지 비교한다. 입력값이 바뀌는 것과 실행 방식·허용 범위가 바뀌는 것을 구분한다.

| 상황 예시 | 제안하는 처리 |
|---|---|
| 확인된 흐름에 새 작업 번호나 자료가 들어왔고, 허용한 대상·작업 범위 안이다 | 재확인 없이 실행 |
| 새로운 도구·권한·작업 단계나 허용하지 않은 대상이 필요하다 | 변경되는 부분과 이유를 보여주고 확인 |
| 같은 흐름이지만 사용자가 정한 확인 조건에 해당한다 | 해당 단계에서 확인 |
| 기존 흐름에 맞는지 판단할 정보가 부족하거나 실행 중 예상하지 못한 상황이 생긴다 | 불확실한 지점을 설명하고 질문. 기존 조건 안의 복구 방식은 별도 논의 |

예시는 판단 기준을 논의하기 위한 것으로 특정 작업을 항상 승인 대상으로 확정하지 않는다. 에이전트는 기존 흐름 후보와 차이를 제안하고, 실행 허용은 저장된 조건으로 확인하는 역할 구분을 제안한다. 에이전트의 유사성 판단만으로 과거 확인 범위를 확대하지 않는다. 조건으로 표현하기 어려운 업무 의미의 차이를 어떻게 다룰지는 미결이다.

### 효과에 대한 가설

사용자가 설명한 아이디어의 발전 순서는 `업무 간 병목을 줄이고 싶다 → 사람 판단이 필요 없는 구간을 에이전트가 자동으로 이어가면 어떨까 → 에이전트 사이를 어떻게 연결할까 → A2A를 연결 방법 후보로 발견`이다. A2A 채택 자체가 목적이거나 병목 감소의 검증 결과는 아니다.

앞 작업의 완료 이후 다음 작업의 착수를 막는 원인을 파악하고, 필요한 맥락·결과 전달이나 착수 준비, 에이전트 실행을 지원하면 작업 사이의 대기와 이후 일정의 지연을 줄일 수 있을 것이다. 이는 assistant의 해결 가설이며, 어떤 지원을 제공할지는 합의하지 않았다. 전달만으로 담당자의 업무 과부하나 권한 대기가 해소된다고 가정하지 않는다.

검증하려면 먼저 실제 사용 장면을 정하고 현재의 전달 방식·대기 원인을 확인해야 한다. 이후 PRD에서 비교할 지표와 수용 기준을 정한다. 연결된 에이전트 수나 실행 성공만으로 협업 병목이 줄었다고 판단하지 않는다.

## 기존 대안과 참고 대상

현재 팀이 쓰는 도구, 수동 전달 방식, 이미 적용한 자동화는 아직 확인하지 않았다. 따라서 기존 대안의 부족한 점이나 제품의 차별성을 확정할 근거가 없다.

- n8n: 연동·트리거·실행에 활용할 후보로 논의했다. 제품과의 경계는 미정이다.
- Devin·GitHub Copilot coding agent: 사용자가 대비 대상으로 언급했다. 사람이나 규칙이 등록한 티켓 하나를 에이전트가 받아 처리하는 방식으로, 이것도 병목을 줄이는 한 방법이지만 이미 존재한다. 이 제품은 여기서 더 나아가 에이전트 간 인계(A2A)를 가능하게 하려는 것이 사용자가 밝힌 차별점이다.
- Buzz: 기존 에이전트 연결·협업 경험의 참고 대상이다. 동일한 경험을 만들기로 합의한 것은 아니다.
- Baton: 기업 간 병목과 정보 공유 경계를 고민한 사용자의 이전 아이디어다. 저장소 구현을 분석한 상태는 아니다.

위 항목은 이전 논의에서 언급된 맥락을 기록한 것이며, 현재 기능이나 경쟁력을 조사한 결과가 아니다.

Jira에 대해서는 이번 논의에서 공식 문서를 확인했다. [자동화](https://support.atlassian.com/cloud-automation/docs/jira-automation-actions/)는 알림 외에도 할당·상태 변경 등을 지원하며, [워크플로 규칙](https://support.atlassian.com/jira-cloud-administration/docs/edit-an-issue-workflow/)에는 상태 전환 시 에이전트에 자동 할당해 작업을 시작하는 예도 있다. 따라서 ‘Jira는 알림만 보내고 반드시 사람이 다음 작업을 시작한다’를 제품 차별성의 전제로 삼지 않는다. 지원 환경·설정과 실제 팀의 사용 방식은 별도 확인이 필요하다.

도구 역할을 설명할 때 [Git](https://git-scm.com/)은 파일·코드의 변경 이력을 관리하는 버전 관리 도구, [Jira](https://support.atlassian.com/jira-software-cloud/docs/what-are-jira-workflows/)는 업무와 상태·전환을 관리하는 도구, [n8n](https://docs.n8n.io/)은 도구들을 연결하고 자동화 흐름을 구성·실행하는 도구로 구분한다. Git 자체를 업무 상태판으로 취급하지 않는다. 이 구분은 설명을 위한 것으로 기능이 완전히 분리되어 있거나 세 도구를 모두 채택해야 한다는 뜻은 아니다.

## 채택되지 않은 assistant 제안

### Devin과 비교하며 정리한 차별화 가설

사용자가 제공한 Devin 화면에는 하나의 요청에 따른 두 저장소의 PR과 테스트 보고서가 보인다. 화면만으로 Devin의 전체 지원 범위나 한계를 판단하지 않는다. [Devin의 Jira 연동 공식 설명](https://docs.devin.ai/integrations/jira.md)은 Jira 티켓에서 세션을 시작하고 PR 링크를 이슈에 반영하는 흐름을 안내한다. 티켓 실행·상태 반영은 이 제품 구상과 겹치는 부분이다.

추가 공식 문서 조사에서 겹치는 범위가 더 넓음을 확인했다. [Automations](https://docs.devin.ai/product-guides/automations.md)는 이벤트·조건·동작으로 실행을 연결하며 자연어로 설정 생성도 지원한다. [Managed Devins](https://docs.devin.ai/work-with-devin/advanced-capabilities.md)는 작업 분해·병렬 위임·진행 확인을, [Dynamic Workflows](https://docs.devin.ai/work-with-devin/dynamic-workflows.md)는 Devin이 작성하는 Python 스크립트로 단계 간 구조화된 결과 전달·실행 순서·중단 후 재개·재사용을 지원한다. Dynamic Workflows는 기본적으로 실행 전 승인을 받으며 자동 승인 설정도 있다. 이것이 이 제품에서 논의한 ‘동일 흐름의 허용 범위를 판단해 선택적으로 재확인’하는 정책과 동일하다는 근거는 없다.

[Auto-triage](https://docs.devin.ai/product-guides/auto-triage.md)는 Slack의 보고를 감시하는 부모 세션이 조사할 항목을 판단해 자식 세션에 맡기고, 중복·담당 정보를 누적하는 방식이다. 따라서 ‘여러 에이전트 조율’, ‘자동 후속 실행’, ‘워크플로우 생성·재사용’ 자체만으로 Devin과 차별화된다고 주장하지 않는다. 여기서 확인한 다중 에이전트 실행은 주로 Devin 세션의 조율이며, 이종 에이전트·사람·일정 전체를 다루는 실제 지원 범위와 차이는 추가 검증 대상이다. 문서 조사 결과이며 직접 실행 검증은 하지 않았다.

**사용자 의도에 대한 assistant의 해석:** 비교할 차이는 개별 작업의 수행뿐 아니라, 서로 다른 수행 주체와 일정 조건이 있는 업무 전체에서 다음 단계의 시작 조건을 충족시키고 결과를 전달해 대기를 줄이는 데 두는 제품의 초점이다. Devin이 이 영역을 전혀 지원하지 않는다고 확인한 것은 아니다. 등록된 티켓을 실행하고 결과만 기록하는 구현이라면 이 차이가 드러나지 않는다.

[A2A](https://a2a-protocol.org/latest/topics/what-is-a2a/)는 서로 다른 에이전트가 통신·협업하도록 하는 표준이다. 업무 순서, 우선순위, 사람 판단 필요 여부와 다음 단계의 착수 조건을 정하는 제품의 책임까지 자동으로 해결해 주는 것으로 취급하지 않는다. 실제 대상 에이전트의 지원 여부와 연결 방식은 기술 설계에서 확인한다.

차별성을 검증할 제안은 개별 작업의 성공뿐 아니라 앞 작업 완료부터 다음 작업 시작까지의 시간, 수동 인계 횟수, 전체 완료 시간을 함께 비교하는 것이다. 아직 채택한 성공 지표나 검증 결과는 아니다.

### 기타 미합의 제안

독립 웹 서비스의 뒤에서 n8n을 실행 엔진으로 사용하는 형태, 협업방, 요청·인계 서비스, 고정 업무 흐름 자동화는 모두 후보로만 논의됐다. 첫 사용자를 개발팀으로 정하거나, 긴급 버그 담당 확인 또는 `조사 → 사람 승인 → 수정`을 MVP로 삼기로 합의하지 않았다.

모든 중간 결과에 사람 승인을 요구하는 정책, 에이전트 생성의 후순위 배치, 특정 프로토콜·실행 환경·스택·자체 Work Engine도 확정 사항이 아니다.

2026-09-19에 assistant가 데모 장면으로 그린 "하나의 시스템이 자기 에이전트 A·B·C를 순서대로 실행하는" 틀은 사용자 의도가 아니었다. 사용자가 원하는 것은 서로 다른 소유자의 에이전트가 직접 소통하는 것이며, 아래 데모 섹션은 그 기준으로 다시 썼다.

## 공모전 데모 — 첫 구현 대상

**사용자 결정 (2026-09-19):** 완성된 서비스보다 심사위원용 핵심 기능 체험 데모를 먼저 만들고, 제대로 된 서비스는 그 뒤에 만든다.

### 제출 조건과 일정

- 웹 URL을 제출한다. 심사위원은 별도 설정·로그인 없이 핵심 기능을 체험할 수 있어야 한다. 로그인·결제 같은 기능이 있는 서비스라면 별도 데모 버전을 제출한다.
- 공식 일정([원티드 AI Championship 2026](https://event.wanted.co.kr/ai-championship/2026), 2026-09-19 확인): 과제 제출 9/20, 예선 심사·유저 투표 9/21~10/5, TOP20 발표 10/7, 데모데이 10/17. 심사는 유저 투표와 전문가 심사(크래프톤·라이너·퍼브·스파크랩)다.
- 데모는 서버에 미리 구성한 샘플 환경에서 돌아간다. 외부 도구의 자격증명은 서버가 보유하고 API로 호출하며, 심사위원은 우리 UI만 본다. 사용자가 이 구조를 확인했다.

### 데모가 보여줘야 하는 것 — 사용자가 밝힌 차별점

Devin·GitHub Copilot coding agent처럼 "등록된 티켓 하나를 에이전트가 처리한다"는 이미 있다. 이 제품은 **같은 팀의 서로 다른 담당자가 소유한 에이전트들이 각자의 키·도구·맥락을 갖고 직접 소통하며 일을 이어받는** 것을 보여준다. 회사 간 확장은 장기 방향으로만 두고 데모에서는 다루지 않는다. 하나의 시스템이 자기 에이전트 여러 개를 순서대로 돌리는 것과는 다르다.

같은 대회 출품작(2026-09-19 GitHub 검색 기준 22개)에는 에이전트 간 소통을 보여주는 것이 없었다. 대부분 단일 에이전트·단일 파이프라인에 사람 확인 지점 하나다. 데모 패턴은 무로그인 + 미리 채운 예시 + "3분 체험"으로 수렴하며, backstop처럼 실행 불가 시 예시 결과를 자동 표시하는 폴백도 쓰인다. 사람 확인 지점을 명시적으로 설계한 팀이 많으므로(AfA의 Human Approval, VoiceOps의 3레인, contextops의 팀장 승인), 우리의 "처음 흐름은 확인, 이후 자동"도 같은 언어로 설명한다.

### 데모 구성 — assistant 제안, 사용자 검토 중

심사위원이 여러 명일 필요가 없다. 심사위원은 한 자리에 앉고, 나머지 자리는 서버에 미리 만들어둔 상대방이다. **사람은 페르소나지만 에이전트는 각자 별도 인스턴스**다: 자기 이름, 자기 API 키, 자기 도구 권한, 자기 메모리. 서로는 메시지로만 소통한다.

| 자리 | 누구 | 에이전트의 도구·키 |
|---|---|---|
| 심사위원 | 팀의 담당자 A (예: 기획) | 팀 작업 보드(UI 안). 저장소 쓰기 권한 없음 |
| 서버 페르소나 | 같은 팀의 담당자 B (예: 개발) | 팀 GitHub 공개 저장소 쓰기 권한 |

흐름: 심사위원이 목표를 던진다 → A의 에이전트가 요청을 정리해 B의 에이전트에게 보낸다 → B의 에이전트가 모르는 것을 **되묻는다** → A의 에이전트가 A의 맥락에서 답한다 → B의 에이전트가 자기 키로 팀 저장소에 실제 PR을 만든다 → 결과 링크를 회신한다 → A의 에이전트가 보드를 갱신한다.

심사위원의 동작은 목표 선택 1번, 흐름 확인 1번이다. 그 뒤로는 보기만 한다.

### 심사위원이 "진짜"라고 확인하는 근거 — assistant 제안

1. **에이전트 간 대화 기록이 그대로 보인다.** 요청, 되묻기, 답변, 결과 회신이 타임스탬프와 함께 찍힌다. 되묻기(양방향)가 있어야 "정해진 순서를 돌린 것"과 구별된다.
2. **각 에이전트의 권한이 다르다는 것이 보인다.** 에이전트 카드에 소유자·도구·권한을 표시한다. B의 에이전트만 저장소에 쓸 수 있고, A의 에이전트는 못 한다. B의 카드에는 A에게서 받은 입력이 인용된다.
3. **외부에서 검증 가능한 흔적을 남긴다.** GitHub 공개 저장소는 로그인 없이 볼 수 있으므로, B의 에이전트가 만든 PR 링크를 심사위원이 직접 열어 확인할 수 있다. Jira는 프로젝트 공개 열람 설정이 가능하고, Slack은 불가능하므로 UI에 미러링만 한다.

### 데모에서 보여줄 수 없는 것

심사위원이 **자기** 에이전트·**자기** 키를 가져와 연결하는 것. 로그인이 없으므로 불가능하다. "에이전트 연결" 화면은 읽기 전용으로 보여주거나 데모에서 뺀다. 에이전트 생성 기능도 데모 체험 대상이 아니다. 둘 다 제품 범위에서 제외한다는 뜻이 아니다.

### 실행 방식 — 사용자 결정

작업·페르소나는 미리 구성해두고, 심사위원이 실행하면 에이전트가 그 자리에서 실제로 소통·실행한다. 결과를 미리 만들어 재생하는 방식은 택하지 않았다.

**Assistant 권장, 미확정:** 실행 실패 시 저장된 대화 기록으로 대체하는 폴백. 심사위원이 여럿이고 심사 기간 내내 돌아가므로 세션별 격리 또는 주기적 리셋. 실연동은 검증 가능한 GitHub 하나로 시작하고, 우리 쪽 보드는 UI 안에서만 그린 뒤 시간이 남으면 Jira에 미러링한다.

### 마감(9/20) 기준 최소 구성 — assistant 제안

자리 2개, 에이전트 2개, 되묻기 1회, GitHub 공개 저장소 PR 1개, 폴백 1개. 자리 3개 이상, Jira·Slack 실연동, 에이전트 연결·생성 화면은 마감 뒤로 미룬다.

프로토콜(A2A·ACP 등)은 외부 에이전트·회사 간 상호운용에서 실제 의미가 있지만, 데모에서는 내부 메시지 교환으로 충분하다. 선택은 데모 뒤에 한다.

## 미결 사항과 논의 순서

공모전 데모를 먼저 구현하므로 위 데모 구성(자리·흐름·되묻기·실연동)을 사용자가 확정하는 대로 기술 설계·구현 계획으로 넘어간다. 아래 순서는 데모 이후 제품 논의에 적용한다.

한 번에 하나씩 논의하고, 사용자 답변과 assistant의 제안을 구분해 반영한다.

1. 재사용과 확인의 판단 기준: 처음 만든 흐름은 확인하고 기존 흐름은 필요한 순간에만 묻는 방향을 기준으로, 최초 확인에 포함할 범위와 재확인 조건을 정한다. 위 assistant 제안은 아직 미합의다.
2. 일의 경중을 판단하는 목적: 먼저 실행할 일을 고르는 것인지, 에이전트가 진행해도 되는 일과 사람이 판단할 일을 나누는 것인지, 둘 모두인지 확인한다. 자율 실행 범위도 함께 구체화한다.
3. 첫 사용 장면: 어느 팀에서 누구의 어떤 일이 누구에게 넘어갈 때 생기는 문제를 먼저 해결할 것인가.
4. 현재 대안과 병목: 지금은 어떻게 처리하며, 실제로 무엇 때문에 멈추는가.
5. 기대 결과와 제품 역할: 어디까지 이어주면 유용하며, 사람이 판단해야 할 지점은 무엇인가.
6. 첫 버전 범위: 필요한 서비스·에이전트 연결과 생성 기능을 어디까지 제공할 것인가.

제품 개요가 구체화되면 PRD와 MVP 범위, 사용자 흐름, 기술 설계, 구현 계획 순으로 작성한다. 다음 문서를 만들기 전에 파일 구성을 논의하며, 기존 PRD·ARCHITECTURE 템플릿과 같은 역할의 기준 문서를 중복 생성하지 않는다. 구현은 아직 시작하지 않는다.
