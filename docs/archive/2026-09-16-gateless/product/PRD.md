## 1. 제품 정의와 문제 가설

Gateless는 서로 다른 owner의 context와 permission boundary 안에서 실행되는 Agent 및 기존 시스템 사이의 다음 실행과 handoff를 조율한다. 각 owner가 사전에 위임한 실행 범위와 순서 결정 범위 안에서, 기존 Work의 상태를 읽고 실행을 요청하며 결과에 따라 대기 중인 일을 재개한다.

핵심 원칙:

> **Move the work to the authority, not the authority to the work.**
>
> **Decentralized execution, delegated coordination.**

> **Owner defines the boundary → Agent proposes the work/result → Gateless enforces the contract → Agent performs the technical judgment.**

자동화의 핵심은 human authority를 유지하면서 사전 위임된 범위의 반복적인 cross-owner handoff에서 사람의 조율 개입을 줄이는 것이다. Owner가 자동 위임 가능한 요청 범위, 최소 결과·evidence 기준, 공유 가능한 context 범위를 정한다. Agent는 기술적 필요성과 기대 결과를 제안하고 수행 중 기술적 판단을 맡는다. Gateless는 요청과 반환 결과가 사전 위임된 contract를 충족하는지 확인하고 원래 Work의 재개를 연결한다. 기술적 정답 전체를 다시 판단하는 super-agent나 매 결과마다 사람의 재개 승인을 요구하는 제품으로 만들지 않는다.

현재 문제 가설은 다음과 같다.

> 서로 다른 owner와 authority/context boundary를 가진 환경에서, 작은 사전 합의만으로 담당자 탐색 → context 전달 → 실행 시작 → 결과 관찰 → 후속 Work 재개를 이어 주면, 사람이 반복하는 coordination intervention과 coordination time을 줄일 수 있다.

예상되는 현재의 수동 과정은 `누구 담당인지 결정 → 지금 요청할지 판단 → 필요한 맥락 전달 → 상대가 자기 Agent 실행 → 결과 확인 → 원래 작업 재개`다. 이 과정이 얼마나 자주 발생하고 얼마만큼의 손실을 만드는지는 아직 실제 사용자 증거로 확인하지 않았다. 본 PRD의 사례는 이를 검증하기 위해 준비하는 실험 시나리오이며, 관찰된 고객 사례가 아니다.

## 2. 첫 사용자와 제품 경계

### 2.1 첫 persona

백엔드·프론트엔드처럼 책임 영역이 나뉘고, 각 담당자가 자신의 코딩 Agent를 운영하며, 공동 프로젝트에서 영역 간 요청과 대기가 발생하는 소규모 개발팀.

- **요청하는 owner:** 자신의 Work를 진행하는 데 필요한 다른 영역의 결과를 반복 설명·수동 실행 요청 없이 받으려 한다.
- **요청받는 owner:** 기존 권한을 유지하면서, 자신이 허용한 업무와 실행 슬롯만 공동 작업에 제공하려 한다.
- **공모전 체험자:** 준비된 실제 환경을 웹에서 실행하고, 어느 경계에서 무엇이 자동으로 이어지는지 확인한다.

공모전 실험은 1인이 두 owner 역할을 준비할 수 있다. 실제 실행 환경과 접근 경계는 분리하되, 이 구성만으로 서로 다른 실제 사용자의 정책 합의나 신뢰 형성을 검증했다고 주장하지 않는다.

### 2.2 개인·비개발자로의 확장

개인이 여러 Agent를 운영할 때도 조율 문제는 존재할 수 있다. 그러나 한 사람이 전체 맥락과 결정권을 가진 상황은 multi-owner 환경과 위임·설정·도입 이유가 다르다. 비개발자 지원 역시 별도의 업무 해석과 온보딩 검증이 필요하다. 공통 모델의 가능성을 유지하되, 동일한 첫 persona나 보편적 수요를 가정하지 않는다.

### 2.3 기존 제품과의 관계

Gateless의 가설은 Agent의 지능이 더 높다거나, 연결·메시징·FIFO 자체가 새로운 기능이라는 주장이 아니다. 기존 업무·자동화·Agent 사이에서 사람이 하던 조율을 줄이는 사용 경험을 검증한다.

- 첫 MVP에서는 사람이 준비한 GitHub Issue가 원본 업무의 목표·취소·최종 완료를 관리한다.
- GitHub와 같은 저장소 서비스에서는 코드·PR·검증 결과를 읽거나 필요한 동작을 요청할 수 있다.
- 기존 자동화는 필요할 때 지정 절차를 수행한다. Jira와 n8n은 이번 MVP에서 제외한다.
- Agent는 위임받은 작업 안에서 판단·생성·수정을 수행한다.
- Gateless는 이들 사이의 실행 조건, 요청, 대기, 결과 연결, 재개를 조율한다.

이 목록은 제품마다 하나의 고정 역할을 부여하지 않는다. 각 integration이 읽고 쓰는 state와 실행 가능한 action을 별도로 정의한다. 예를 들어 하나의 서비스가 업무 입력과 실행 결과 출처를 동시에 맡을 수 있다.

A2A는 선택된 Agent에게 request/context를 전달하고 status/result를 받는 연결 방식이다. 책임자 결정, 우선순위, 위임 범위, 업무 결과의 적합성을 프로토콜이 대신 결정한다고 가정하지 않는다.

## 3. 목표와 검증할 가설

| 구분 | 목표 또는 가설 | 확인 방법 |
|---|---|---|
| 주요 제품 목표 | 동일 시나리오의 결과 적합성을 유지하면서 수동 조율 대비 사람의 개입 횟수와 조율 시간을 줄인다. | 9절의 비교 실험 |
| 위임 가설 | 작은 사전 합의만으로 owner 사이의 반복적인 실행 승인을 줄일 수 있다. | 자동 진행과 escalation·정책 수정의 기록 |
| 실행 목표 | 실제 서비스와 분리된 Agent 환경에서 요청 → 결과 반환 → 원래 작업 재실행을 완주한다. | 실제 실행·산출물·연결 이력 확인 |
| 경계 보존 목표 | 상대 저장소 권한을 요청자에게 전달하지 않고 상대 영역 작업을 수행한다. | 환경별 접근 범위와 실행 증거 확인 |
| 비용 검증 | 초기 설정·정책 유지·잘못된 위임의 재작업이 절감 효과를 상쇄하는지 공개한다. | 조율 지표와 함께 별도 비용 보고 |

업무 처리량 극대화, 조직 전체의 최적 순서 결정, downstream 개수 기반 최적화는 첫 MVP의 성공 목표가 아니다. 순서 결정은 조율 부담 감소를 위한 baseline이다.

## 4. 위임과 상태에 관한 제품 원칙

### 4.1 권한과 위임의 구분

| 개념 | 제품상 의미 |
|---|---|
| Provider permission | Agent가 자신의 외부 시스템·실행 환경에서 실제로 할 수 있는 일 |
| Execution delegation | owner가 Gateless를 통한 요청에 사전 허용한 행동과 요청 범위 |
| Scheduling delegation | owner가 제공한 실행 슬롯과 규칙 안에서 Gateless가 시작 순서를 결정할 수 있는 범위 |
| Coordination decision | 현재 업무·의존성·가용 슬롯·허용 규칙에 근거해 누구에게 무엇을 언제 요청할지 내리는 결정 |

이 구분은 제품 의미이며, 특정 도메인 객체나 데이터베이스 구조를 확정하지 않는다.

Frontend owner의 대표 허용 범위는 지정 공동 프로젝트의 진단, 코드 수정, 테스트, draft PR 생성이다. PR merge, production deploy, 별도로 승인해야 하는 비용 발생, 권한 변경은 자동 허용 범위에 포함하지 않는다. 요청을 생성하는 측과 수행하는 측 양쪽의 사전 위임 범위를 충족해야 한다.

Gateless는 연결 동작에 필요한 연동 권한을 사용할 수 있지만, 상대 owner의 코드 수정 권한을 요청 Agent에게 전달하거나 모든 owner의 실행 권한을 한곳에 모으는 것을 전제로 하지 않는다. 전달 context도 해당 요청을 위해 공유가 허용된 범위여야 한다.

### 4.2 첫 순서 결정 정책

- 각 owner는 지정 공동 프로젝트에 execution slot 하나를 명시적으로 제공한다.
- Gateless는 제공된 슬롯의 큐만 관리한다. owner의 모든 로컬 작업이나 전체 자원 사용을 안다고 가정하지 않는다.
- 신뢰할 수 있는 출처에서 확인된 긴급 요청을 우선한다. requester가 Critical이라고 주장했다는 이유만으로 우선하지 않는다.
- 그 외 실행 가능한 READY 요청은 기본적으로 접수순으로 처리한다.
- dependency는 실행 가능 여부를 판정하는 조건이다. downstream 수를 초기 순위 점수로 사용하지 않는다.
- RUNNING Work는 순위 변경 때문에 자동 preempt하지 않는다.
- 판단 근거 부족, 책임 불명확, 위임 범위 밖의 요청, 정책 충돌은 owner에게 escalation한다.

서로 다른 슬롯에서 독립적인 Work는 동시에 실행할 수 있다. Gateless가 조직 전체에서 단 하나의 다음 Work를 선택하는 모델로 만들지 않는다.

### 4.3 업무와 조율 상태의 소유권

첫 prepared environment에서는 업무의 목표·취소·최종 완료를 GitHub Issue 기준으로 삼는다. Gateless는 실행 시도, 큐, 대기·재개, cross-owner 요청과 결과 연결 등 coordination state를 관리한다.

- Issue의 취소·종료를 인지하면 해당 업무의 후속 자동 실행을 중단한다. 늦은 결과로 다시 실행하지 않는다.
- Agent execution이나 PR/check 성공만으로 Issue를 완료 처리하지 않는다.
- Issue가 열려 있는 동안 Gateless의 실행·대기·재개는 여러 번 발생할 수 있다.
- 완료와 취소에 해당하는 Issue 상태·종료 사유 및 불명확한 사유의 처리 규칙은 MVP Spec에 명시한다.

외부 변경의 관찰 지연과 이미 RUNNING인 실행의 처리는 Work Engine을 따른다. 즉시 중단이나 이미 발생한 효과의 되돌림을 보장하지 않는다. GitHub가 원본 업무와 산출물 출처를 함께 맡아도 Issue/PR/check의 의미를 합치지 않는다. Source of truth는 integration별로 정하며 특정 제품에 고정하지 않는다.

### 4.4 사전 위임된 contract와 제품 책임

| 주체 | 책임 |
|---|---|
| Owner | 자신의 책임·권한 안에서 자동 위임 가능한 요청·행동, 제공 슬롯과 순서 결정 범위, 최소 결과·evidence 기준, 공유 가능한 context 범위를 정한다. 범위 밖 판단과 위임 변경은 사람에게 남는다. |
| 요청 Agent | 기존 Work에 필요한 기술적 요청과 기대 결과를 제안한다. 사전 기준을 약화하거나 공유·실행 범위를 스스로 확대하지 않는다. |
| Gateless | 양측 사전 위임에 대한 요청 적합성, 반환 결과·증거의 조건 충족, 허용된 재개 입력의 준비 여부를 확인한다. 큐·실행·대기·재개를 연결하고, 판단할 수 없는 항목은 근거와 함께 escalation한다. |
| 수행·후속 Agent | 허용된 context와 도구로 진단·수정·테스트 및 후속 기술적 판단을 수행한다. 요청 부적합이나 결과의 기술적 문제를 드러낸다. |
| 외부 시스템·owner 실행 환경 | 실제 접근·실행 권한과 외부 상태를 집행·소유한다. Gateless의 요청 확인만으로 실행 내부의 모든 행동이 제한됐다고 간주하지 않는다. |

Execution Delegation, Scheduling Delegation, Result Condition, Context Sharing을 “사람이 반복적인 handoff에서 빠져도 되는 사전 경계”의 의미적 집합인 **Coordination Contract**로 묶는다. 하나의 permission boolean으로 축약하지 않고 각 조건의 소유자와 적용 시점, Provider permission과의 차이를 유지한다. Request는 handoff 관계·조건을 표현하며 독립 실행 상태 머신을 갖지 않는다. Work는 실행 lifecycle, Execution은 실제 시도를 소유하고 결과 판정은 Request 조건과 Result/Evidence의 관계에서 관리한다. Contract 변경·철회는 과거 사실을 다시 쓰지 않으며 향후 행동에 관련된 현재 위임을 적용한다. Accepted는 영구 실행권이 아니다. 상세 도메인 기준선은 [Domain Model](../domain/DOMAIN_MODEL.md)을 따른다. 범용 정책 언어나 편집기를 만들기로 한 결정은 아니다.

## 5. Work 생성과 cross-owner 요청의 범위

### 5.1 허용하는 입력

1. 기존 시스템에 명시적으로 등록된 업무와 요청을 가져온다.
2. 실행 Agent가 기존 Work의 목표 달성에 필요한 cross-owner 요청을 구조화해 제출한다.

Gateless는 원시 로그·이메일·문서에서 새로운 업무 필요성을 스스로 발굴하지 않는다. 실행 Agent가 만든 요청은 새로운 조율 대상이지만, 그 필요성을 Gateless가 발명한 것은 아니다.

### 5.2 한 단계 위임

원래 Work에서 직접 파생된 cross-owner 요청 한 단계까지만 자동 허용한다. 양측의 사전 위임과 공동 프로젝트 범위에 맞으면 수신 owner의 큐에 사람 확인 없이 넣을 수 있다. 수신 Agent가 다시 제3의 owner에게 요청해야 하면 자동 연쇄 위임 대신 human escalation으로 처리한다. MVP에서는 이 1-hop 깊이 제한과 별개로 original Work당 active cross-owner Request 하나로 fan-out을 제한한다. 서로 다른 original Work의 handoff는 owner 슬롯이 허용하는 범위에서 독립적으로 진행한다. Active 관계의 해소 기준은 Work Engine을 따른다.

요청에는 원래 Work와의 연결, 필요한 결과, 현재 목표와의 관련성, 대상 프로젝트·책임 영역, 공유 가능한 context, 결과 충족을 확인할 조건이 있어야 한다. Gateless가 기술적 진단의 정확성을 보증하는 것은 아니다. 잘못된 요청이나 부족한 입력을 성공으로 취급하지 않고 확인이 필요한 상태로 드러내야 한다.

Agent가 제안한 기대 결과만으로 자동 재개 기준을 자유롭게 정하지 않는다. 요청별 결과 조건은 owner의 사전 최소 결과·evidence 기준을 충족해야 하며, 기준과 충돌하거나 판정할 수 없는 요청은 자동 진행하지 않는다.

이 시나리오에서 cross-owner 요청은 원래 Work 전체의 소유권 이전이 아니다. 원래 Work는 유지되며 요청 결과가 후속 진행의 조건이 된다. Capability 일치만으로 다른 책임 영역의 Agent를 대체 실행자로 선택해서는 안 된다.

## 6. 결과 확인과 자동 재개

다음 세 가지를 구분한다.

1. Provider의 execution이 성공했는가.
2. 요청 시 명시한 검증 가능한 결과가 충족됐는가.
3. 원래 Work를 재개할 조건이 충족됐는가.

대표 시나리오는 수정안·테스트 결과·draft PR처럼 검토 가능한 결과를 전달받으면 원래 Agent가 다음 작업을 진행할 수 있는 경우로 제한한다. 실제 merge나 production 반영이 선행돼야 하는 dependency는 대표 시나리오에서 제외한다.

Provider의 성공 문자열만으로 요청 충족이나 dependency 해제를 판단하지 않는다. 시나리오에서 합의한 산출물과 검증 증거를 확인해야 한다. 구체적인 검증 방식은 Work Engine 및 MVP Spec에서 정한다.

이 확인은 사전 위임된 contract와 요청별 결과 조건의 충족 판정이다. 기술적 정답 전체나 원본 업무의 최종 완료를 보증하지 않는다. 결과와 증거가 조건을 충족하고, 공유가 허용된 재개 입력을 후속 Agent가 사용할 수 있으며, 현재 업무 상태가 재개를 허용하면 매번 사람의 승인 없이 READY로 복귀한다. 접근할 수 없는 상대 저장소의 URL만 받은 것을 충분한 재개 입력으로 간주하지 않는다.

외부 결과를 기다리는 Work는 실행 슬롯을 반환한다. Gateless는 재개에 필요한 context와 요청·결과 연결을 보존한다. 동일한 Agent 프로세스나 세션을 계속 유지할 필요는 없다.

```text
RUNNING
  → 외부 결과 대기, 슬롯 반환
WAITING
  → 필요한 결과 조건 충족
READY
  → 기존 순서 규칙에 따라 슬롯 배정
RUNNING
```

자동 재개는 즉시 실행이 아니라 실행 대기열에 자동 복귀하고 슬롯을 받으면 사람의 수동 시작 없이 이어가는 것이다. 재개를 위해 다른 RUNNING Work를 중단하지 않는다. BLOCKED는 아직 실제 실행 전 조건 부족, WAITING은 적어도 한 번 실행된 Work의 continuation 조건 대기다. 원인 종류는 별도 사유이며 상세 전이는 Work Engine을 따른다.

## 7. 첫 체험 범위와 사용자 이야기

### 7.1 실제 연동 체험

공모전 체험자는 새로 준비한 demo app, 실제 GitHub Issue·저장소, 분리된 두 owner의 Agent 환경과 A2A endpoint를 웹에서 실제 실행한다. 대표 업무는 synthetic이며 실제 기존 고객 프로젝트라고 주장하지 않는다. 서비스 API와 Agent 연결 인터페이스를 사용하며, 모의 결과 재생만으로 실제 loop를 대체하지 않는다.

사용자가 자기 계정·저장소·PC를 연결하는 범용 온보딩은 이번 범위에 포함하지 않는다. 두 owner가 서로 다른 Agent 제품을 사용할 필요는 없다. 현재 개발자는 Codex와 Claude Code를 사용 중이지만, 첫 지원 런타임과 호스팅 방식은 Architecture에서 결정한다.

Jira와 n8n은 이번 MVP에서 제외한다. 기존 환경을 억지로 전제하지 않고 GitHub Issue를 external Source Work로 사용한다. A2A는 실제 왕복을 검증할 핵심 integration이다. 현재 임시 owner endpoint 두 경로와 격리된 실제 Agent 실행·shared context 재개를 검증했으며, 상시 endpoint·GitHub 발행·제품 통합이 완료됐다는 뜻은 아니다. 최소 구성은 private repo 하나의 owner별 Work snapshot과 단일 호스트의 분리 컨테이너이며, 전체 repo/자격 증명을 Agent에 공유하지 않는다. 상세 구성과 검증 한계는 MVP Spec을 따른다.

### 7.2 대표 경험의 골격

1. 공동 프로젝트의 명시적인 업무 여러 개가 기존 시스템에 존재한다.
2. Gateless는 책임 영역, 위임 범위, 실행 가능 여부와 제공 슬롯을 확인한다.
3. 같은 슬롯의 READY 업무는 경쟁하고, 별도 슬롯의 독립 업무는 병렬 진행한다.
4. Backend Agent가 수행 중 Frontend 결과가 필요함을 명시적으로 요청하고 슬롯을 반환한다.
5. Frontend 요청이 허용 범위 안에서 큐에 들어가고, 기존 규칙에 따라 실행된다. Backend 슬롯은 다른 준비된 일을 처리할 수 있다.
6. Frontend가 요청에 명시된 결과를 반환한다. 필요한 기존 자동화가 확인되어 MVP에 포함한 경우에만 그 상호작용도 실제로 수행한다.
7. 결과 조건 충족 후 Backend Work가 READY로 복귀하고, 슬롯을 받아 보존 context와 결과로 이어간다.
8. 웹에서 실행 근거, 외부 산출물, 요청·결과 연결, 대기와 재개를 확인한다. 원본 Issue 최종 완료는 Agent 성공과 분리된다.

이는 고정된 `수정 → 테스트 → 배포` 재생이 아니다. 작업·이벤트의 발생 시점에 따라 큐와 실행 가능 집합이 달라져야 한다. 구체적 업무 내용과 검증용 이벤트 순서는 MVP Spec에서 작성한다.

### 7.3 우선 사용자 이야기

- owner로서, 공동 프로젝트에 제공한 슬롯과 허용 행동 안에서는 매 요청마다 Agent를 켜거나 승인하지 않고도 작업이 진행되기를 원한다.
- 요청하는 owner로서, 다른 책임 영역의 결과를 받으면 원래 작업이 맥락을 잃지 않고 이어지기를 원한다.
- 요청받는 owner로서, 상대의 긴급 주장만으로 내 큐가 바뀌거나 허용하지 않은 작업이 수행되지 않기를 원한다.
- owner로서, 요청이 막히면 부족한 정보와 필요한 판단을 보고 개입할 수 있기를 원한다.
- 체험자로서, 무엇이 실행·대기 중인지와 왜 다음 실행이 선택됐는지, 실제 결과가 어디에 있는지를 웹에서 확인하기를 원한다.

## 8. 필수 요구사항과 제품 수용 기준

아래는 첫 제품 가설을 검증하기 위한 요구사항이다. 상세 인터페이스·구현·테스트 사례는 후속 문서에서 구체화한다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| P-01 | 실제 기존 업무에서 시작 | 준비 단계에서 실제 GitHub Issue로 등록한 synthetic 업무를 Gateless에 다시 수동 작성하지 않고 조율 대상으로 연결하고, 원본과의 연결을 확인할 수 있다. |
| P-02 | 책임과 양측 위임 확인 | 지정 프로젝트·책임·요청 및 실행 허용 범위에 맞는 요청만 자동 배정한다. 불명확하거나 허용 밖이면 이유와 필요한 사람 판단을 표시한다. |
| P-03 | 슬롯과 기본 큐 관리 | owner당 제공 슬롯 하나를 초과해 실행하지 않는다. 일반 READY는 FIFO, 확인된 긴급은 우선, 실행 중 작업은 자동 preempt하지 않는다. 별도 슬롯은 병렬 실행 가능하다. |
| P-04 | 제한된 cross-owner 생성 | 원래 Work의 Agent가 직접 요청한 한 단계는 자동 접수한다. 수신 측의 추가 owner 요청은 자동 실행되지 않고 escalation된다. |
| P-05 | 분리된 실제 수행 | 수신 Agent가 자신의 환경과 권한으로 작업한다. 요청 Agent에 상대 저장소 수정 자격 증명을 전달하지 않는다. |
| P-06 | 결과 충족 판정 | Owner가 정한 최소 결과·evidence 기준과 이를 충족하는 요청별 조건으로 판정한다. Agent가 기준을 임의로 약화할 수 없다. 실행 성공 보고와 요청 결과 충족을 구분하며 누락·부적합한 증거로 자동 재개하지 않는다. |
| P-07 | 슬롯 반환과 재실행 | 외부 결과 대기 중 슬롯을 다른 Work가 사용할 수 있다. 결과 조건, 허용된 재개 입력, 현재 업무 상태가 재개를 허용하면 매번 사람 승인 없이 READY로 복귀한다. 후속 실행은 원래 맥락과 결과를 사용할 수 있다. |
| P-08 | 업무 상태 존중 | 원본 Issue 취소 인지 후 새 후속 실행을 시작하지 않으며, 늦은 결과로 취소 작업을 재개하지 않는다. 단일 실행 성공을 원본 Issue 최종 완료와 동일시하지 않는다. |
| P-09 | 실제 연동 왕복 | GitHub·분리된 owner Agent 및 A2A 연결의 선택한 동작이 실제 수행되고, 입력·실행·결과를 연결해 확인할 수 있다. 외부 실패를 성공이나 모의 결과로 숨기지 않는다. Jira와 n8n은 이번 검증 범위에서 제외한다. |
| P-10 | 조율 가시성 | 웹에서 담당 owner, 큐·대기 상태, 선택 또는 보류 근거, 요청·결과·재개 연결과 외부 산출물을 확인할 수 있다. 설명은 실제 입력과 정책에 근거한다. |
| P-11 | 실패와 사람 개입 | 실행 실패, 요청 부적합, 권한·정책 문제를 구분해 현재 진행이 멈춘 이유를 보여준다. 완료 여부가 불명확한 외부 동작을 무조건 다시 실행하지 않는다. 복구 절차는 후속 명세에서 정한다. |
| P-12 | 비교 가능한 측정 | 9절의 수동·자동 조율 개입과 시간, 설정·정책 수정·재작업을 기록하고 결과 적합성 증거와 함께 보고할 수 있다. |
| P-13 | 구조화된 coordination history 보존 | Gateless가 관찰·수행한 Work, Execution, Request, Result 관련 변화와 Waiting, Resume, Escalation 및 관찰 가능한 human intervention을 구조화해 보존한다. 이벤트 종류·시각·관련 업무/요청/실행 식별자와 해당하는 주체·사유·결과 참조를 통해 handoff와 대기·재개의 흐름을 연결해 확인할 수 있다. 자유 서술 로그나 현재 상태만으로 이력을 대체하지 않는다. |

이력 보존은 MVP의 조율 가시성과 측정을 지원하며, 이후 분석에 활용할 기반을 남기는 요구사항이다. Agent 내부 trace나 외부 시스템의 모든 원시 로그를 수집하는 것은 요구하지 않는다. 상세 이벤트 정의와 보존 범위는 후속 문서에서 정하며, 특정 저장 기술이나 event sourcing 아키텍처를 전제하지 않는다.

## 9. 실험과 성공 기준

### 9.1 비교 설계

준비된 동일 cross-owner 시나리오를 수동 조율과 Gateless 조율로 수행한다. 수동 조건에서도 같은 Agent·기존 자동화·권한·결과 조건을 사용할 수 있어야 한다. 수동 조건만 사람이 코드를 작성하도록 만들어 Agent의 생산성 효과를 Gateless의 조율 효과로 계산하지 않는다.

가능한 한 같은 시작 자료, 작업 내용, 허용 범위와 자원을 사용하고, 실행마다 달라진 Agent 결과·외부 지연·실험 순서·반복 학습 영향을 기록한다. 실행 횟수와 시나리오 초기화 방법은 MVP Spec에서 정한다. 한 명이 두 owner 역할을 수행한 결과라는 한계도 공개한다.

### 9.2 측정 대상

| 측정값 | 기록 원칙 |
|---|---|
| Coordination intervention | 담당자/실행 주체 결정, context 전달, 실행 시작, 결과 확인, 후속 Work 재개를 위해 사람이 수행한 조율 행동을 종류별로 기록한다. 한 조율 행동을 화면 클릭 여러 번으로 임의 분할하지 않는다. |
| Coordination time | 위 조율 행동에 사람이 능동적으로 사용한 시간을 기록한다. Agent 실행이나 외부 결과를 기다린 전체 경과 시간과 구분한다. |
| Setup 비용 | 계정·실행 환경 연결, 책임 및 위임 범위 설정, 최초 정책 합의에 든 시간을 기록한다. 공모전 준비 환경에서 대신 수행한 작업도 숨기지 않는다. |
| Policy 유지 비용 | 실험 중 규칙 변경·예외 판단·escalation 처리의 횟수와 시간을 기록한다. |
| Rework | 잘못된 handoff·request·결과 수용으로 생긴 사람 수정과 추가 실행을 원인별로 기록한다. |
| 결과 적합성 | 양 조건에 같은 산출물·검증 기준을 적용하고 증거를 남긴다. Agent가 성공했다고 말한 것만으로 적합 판정을 내리지 않는다. |

개입 기록에는 관련 Work/요청, 행동 유형, 시작·종료 또는 소요 시간, 원인이 필요하다. 수동 관찰 기록을 사용할 수 있으며 별도의 범용 분석 제품은 요구하지 않는다. 설정·유지·재작업을 조율 시간에도 포함할 경우 중복 합산하지 않도록 보고 기준을 명시한다.

### 9.3 성공의 해석

첫 성공 기준은 **준비된 동일 시나리오에서 결과의 적합성을 유지하면서, 수동 조율 대비 사람의 coordination intervention과 coordination time이 줄어드는가**다. 임의의 사전 감소율 목표를 설정하지 않고 실제 값과 차이를 공개한다.

개입 횟수만 줄고 시간·재작업이 늘었다면 성공으로 단정하지 않는다. 설정·정책 유지 비용도 별도로 공개하고, 반복 사용에 따른 상쇄 효과를 실제 측정 없이 주장하지 않는다.

| 관찰 | 해석 |
|---|---|
| 작은 정책으로도 개입과 시간이 줄고 결과가 적합함 | sophisticated priority engine 없이도 조율 계층의 가치가 있을 수 있다. |
| 일반 요청 순서 때문에 반복 개입함 | 추가 scheduling 정보가 필요한 근거를 수집한다. |
| 정책 예외와 escalation이 빈번함 | delegation model 자체의 적합성을 재검토한다. |
| 설정·유지·재작업 부담이 절감 효과를 상쇄함 | 제품 가설이나 적용 범위를 재검토한다. |
| 결과 적합성이 떨어짐 | 개입 감소만으로 가설을 지지하지 않는다. |

결과는 준비된 cross-owner coordination loop의 가능성 검증으로 한정한다. 실제 조직 전체의 수요·장기 효과·시장 차별성·범용 온보딩의 용이성을 입증한 것으로 주장하지 않는다.

## 10. 첫 MVP의 제외 범위

- 원시 정보에서 새로운 Work 필요성을 Gateless가 발견하는 기능 및 process mining.
- 원래 Work에서 두 단계 이상 이어지는 자동 cross-owner 위임.
- 조직 전체 우선순위 최적화, dependency 영향 점수, owner 전체 자원의 추론, 자동 preemption.
- 자유로운 업무 유형과 임의의 도구를 이해하는 범용 연결·정책 편집 플랫폼.
- 사용자 자신의 계정·로컬 Agent를 연결하는 범용 온보딩.
- 중앙 IAM, 상대 권한의 요청자 전달, 모든 조직 context의 중앙 수집.
- PR merge·production deploy 또는 그 완료를 기다리는 대표 dependency 및 복잡한 승인 workflow.
- Agent 프레임워크, Jira 대체재, n8n 대체 워크플로 빌더의 구현.
- 개인·비개발자·기업 전체를 동시에 대상으로 하는 제품 경험.

이는 해당 방향을 영구 폐기한다는 뜻이 아니다. 첫 가설의 검증 비용을 제한하기 위한 범위다.

### 10.1 Post-MVP / Future Direction

Gateless가 수행한 coordination/execution history를 기반으로 반복되는 handoff, 대기, escalation, human intervention pattern을 분석하고 automation opportunity를 발견·제안하는 방향을 유지한다. 예를 들어 같은 영역 간 요청에서 사람이 반복해서 context를 보충하거나 실행을 재개하는 패턴을 찾아, 기존 Agent·자동화를 재사용하거나 위임 범위를 조정할 기회를 제안할 수 있다.

이는 Discovery에서 폐기한 방향이 아니라 post-MVP로 미룬 가설이다. 패턴의 반복만으로 자동화가 적절하다고 단정하지 않으며, 실제 조율 비용과 적용 가능성을 후속 검증한다. 기회 제안이 기존 위임 범위를 자동으로 확대하거나 새로운 실행을 허가하는 것은 아니다.

첫 MVP에는 P-13의 구조화된 이력 보존만 포함한다. 반복 패턴 분석, automation opportunity 발견·추천, process mining과 그 분석 UI는 구현 범위에 포함하지 않는다. raw log/email/docs에서 새로운 Work를 스스로 발견하는 기능도 계속 제외한다.

## 11. Discovery에서 변경된 판단과 이유

| 이전 방향 | 현재 제품 기준 | 변경 이유 |
|---|---|---|
| What next의 sophisticated scheduling을 핵심으로 강조 | 작은 정책 안에서 조율 개입 감소를 우선 검증 | 최적 순위 판단의 가치와 입력 근거가 입증되지 않았고, handoff 자동화만으로도 가치가 있을 수 있다. |
| Dependency 영향도를 priority에 반영 | 실행 가능 조건으로만 사용 | 가중치·업무 분할·가치 비교의 가정을 MVP에 넣지 않는다. |
| 개인부터 조직까지 동일한 첫 제품 | multi-owner 개발팀으로 좁힘 | 책임·context·권한 경계가 독립된 환경에서 위임의 필요성이 더 명확하다. |
| 기존 Work만 취급 | 기존 Work에서 시작하는 명시적 후속 요청 한 단계 포함 | cross-owner 요청 발생을 검증하되 Gateless의 범용 discovery는 제외한다. |
| A2A는 메커니즘 | 유지 | Agent 연결만으로 제품 가치는 입증되지 않는다. |
| History 기반 반복 패턴·자동화 기회 발견 | post-MVP 방향으로 유지하고 MVP에는 구조화된 이력 보존만 포함 | 분석·추천은 첫 loop 검증 이후로 미루되, 해당 방향을 폐기하거나 원시 정보 기반 Work discovery와 동일시하지 않는다. |
| Authority를 중앙에서 관리하지 않음 | 유지하되 제한된 coordination authority는 명시적으로 위임 | Provider permission과 요청·실행·순서 위임은 다른 문제다. |
| Jira·n8n을 포함한 기존 업무 환경 전제 | GitHub Issue와 새 prepared demo/owner/A2A 환경으로 좁힘. Jira·n8n 제외 | 실제 기존 프로젝트가 없음을 확인했다. Synthetic 업무의 실제 실행으로 핵심 조율 가설을 검증하며 연동 시연을 위한 역할을 만들지 않는다. |
| Mock부터 만들고 실제 연결로 대체 가능 | 최종 MVP는 준비된 실제 연동 왕복 필수 | 시뮬레이션만으로 기존 서비스 사이의 조율 감소를 입증하지 않는다. |

기존에 약화한 범용 메시징·오케스트레이션·워크플로 빌더·process mining을 단순한 신규성 주장으로 되살리지 않는다. 초기 handoff 문서는 탐색 이력으로 보존한다.

문서는 다음 순서로 작성한다.

1. `docs/product/PRD.md` — 본 문서: 문제 가설, 제품 경계, 요구사항, 성공 기준.
2. `docs/domain/DOMAIN_MODEL.md` — 용어, 책임, 관계와 생명주기.
3. `docs/domain/WORK_ENGINE.md` — 실행 가능성, 큐, 위임, 대기·재개, 예외의 규칙.
4. `docs/product/MVP_SPEC.md` — 실제 시나리오, 지원 연동 동작, 검증 범위.
5. `docs/architecture/ARCHITECTURE.md` — 위 결정을 실현할 구성과 기술 선택.
6. 필요한 `docs/adr/*.md` — 실제로 결정한 중요한 trade-off만 기록.
7. `docs/implementation/PLAN.md` — 구현 순서와 검증 계획.

후속 문서는 이 PRD를 제품 source of truth로 사용한다. 상세 설계가 제품 합의를 바꾸면 이 PRD와 영향받는 문서를 함께 갱신한다. 기존 `docs/PRD.md`는 저장소의 빈 템플릿이며 Gateless 제품 기준 문서는 이 파일이다. 구현은 위 문서 논의가 충분히 안정된 뒤에 시작한다.
