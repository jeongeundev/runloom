# Gateless Work Engine

> 상태: 확정된 Work Engine baseline. 2026-09-16 사용자 합의 반영. 확정된 [Domain Model](DOMAIN_MODEL.md)과 [PRD](../product/PRD.md)를 구체화한다.
> Handoff lifecycle과 MVP runtime 정책의 기준선이다. 실제 환경별 값·집행 방법은 MVP Spec/Architecture에서 정하며, 실제 연동·실행 검증이나 구현을 완료한 문서는 아니다.

## 1. 범위와 불변식

Coordination Contract 아래에서 cross-owner handoff의 accept / dispatch / wait / result satisfaction / resume / escalation을 이어 준다. 임의 workflow graph, 분기 언어, 범용 정책 편집기, 조직 최적화 또는 자동 연쇄 위임을 추가하지 않는다. 외부 자동화 내부 절차는 해당 제공자가 소유한다. 현재 MVP는 Jira·n8n을 제외하고 GitHub Issue를 원본 업무로 사용한다. 이 매핑은 아래 lifecycle을 변경하지 않는다.

- Request는 관계·조건이며 독립 실행 상태 머신이 없다. Work가 조율 생명주기를, Execution이 실제 시도를 소유한다.
- 결과 충족 판정은 요청 조건과 Result/Evidence의 관계에서 한 번 기록한다. Dependency와 화면 표시가 이 판정을 참조한다.
- Accepted는 영구 실행권이 아니다. 향후 행동에는 그 행동과 관련된 현재 양측 위임을 적용한다.
- Owner별 제공 슬롯 하나를 초과하지 않는다. 별도 owner의 슬롯은 독립적이며 실행 중 순위 변경으로 preempt하지 않는다.
- 실행 성공, 결과 충족, 재개 허용, 원본 업무 최종 완료를 구분한다.
- 실행 여부·종료 여부가 불명확하면 성공·실패·슬롯 해제를 추측하지 않는다.
- 취소 인지 뒤 후속 자동 실행을 시작하지 않는다. 과거 사실이나 이미 발생한 외부 효과를 지우지 않는다.

## 2. 판정 단위와 상태

각 판정은 대상 Work/Request/Execution, 요청 조건의 판본, 행동에 적용한 현재 contract 근거, 관찰 입력, 시각, 허용·보류 이유를 연결한다. 전역 permission boolean을 저장해 이후 행동의 인가를 대체하지 않는다.

### 2.1 Work 상태

| 상태 | 의미 |
|---|---|
| BLOCKED | 첫 실행 전 조건이 부족하거나 사람 판단이 필요함 |
| READY | 알려진 조건이 충족되어 다음 실행 배정을 기다림. Dispatch 시 재확인 필요 |
| RUNNING | 실행 시작이 확인된 시도가 진행 중 |
| WAITING | 적어도 한 번 수행한 뒤, 활성 실행 없이 외부 결과·재개 입력·결과 확인·사람 판단을 기다림 |
| CLOSED | 이 Work의 조율을 종료함. 이유는 산출물 전달 완료, 원본 취소/완료, 사람이 종료한 실패 등으로 구분 |

BLOCKED/WAITING은 원인 종류가 아니라 해당 Work의 실제 execution history로 구분한다. BLOCKED는 아직 실제 실행 전 조건 부족, WAITING은 적어도 한 번 실행된 Work의 continuation 조건 대기다. Execution 레코드 생성·예약·HTTP 접수만으로 실행 이력이 생기지 않는다. 시작 여부가 불명확하면 아래의 마지막 확인 상태 규칙을 적용한다. 같은 context 부족이나 사람 판단 대기도 실행 전에는 BLOCKED, 실행 후에는 WAITING이다. 부족한 조건은 별도 사유로 붙인다. Escalation을 별도 실행 상태로 만들지 않는다. CLOSED는 원본 Issue 완료가 아니며, 수신 Work의 결과 충족 여부도 CLOSED라는 이름으로 대신 판단하지 않는다.

Dispatch 중 시작 여부가 불명확하면 Work는 마지막 확인 상태를 유지하고 Execution의 시작 확인 대기·불명 사실과 슬롯 예약을 함께 표시한다. READY 표시만으로 실행 후보가 되지 않으며 활성 예약이나 미확정 시도가 있으면 제외한다. RUNNING 종료가 불명확하면 RUNNING을 유지하고 확인 불가 사유를 표시한다. 실행 사실을 Work 상태만으로 추정하지 않는다.

### 2.2 실행과 슬롯

Execution은 최소한 실행 요청 준비, 외부 접수/시작 관찰, 실제 종료와 종료 이유, 확인 불가 사실을 구분한다. HTTP 접수와 실제 시작은 같지 않다. 상태 문자열을 A2A나 CLI 상태에 그대로 맞추지 않는다.

슬롯은 dispatch 전에 특정 Execution을 위해 예약하고, 시작 확인 후에도 그 시도에 귀속한다. 다음이 확인될 때만 반환한다.

- 요청이 외부로 나가지 않았고 앞으로도 그 시도가 실행되지 않음.
- 수신 측이 해당 시도를 실행하지 않았고 이후에도 실행하지 않을 것으로 확정함.
- 해당 시도의 실행 종료·정지를 확인함.

시간 경과, 연결 단절, 취소 요청 접수, Agent의 “대기” 텍스트는 해제 근거가 아니다. 프로세스 외에 계속 실행되는 부수 작업이 있다면 실제 실행 계약에서 종료의 범위를 확인해야 한다.

## 3. Accept: 제안을 수락된 handoff로 연결

1. 요청 출처와 제출한 Execution, 원래 Work 및 최초 원본 업무를 확인한다. 이미 처리한 동일 요청의 재전달은 기존 판단과 연결한다.
2. 최초 Work에서 직접 파생된 한 단계인지 확인한다. 수신 Work에서 다른 owner로 나가는 추가 요청은 자동 수락하지 않는다.
3. 프로젝트·책임 owner를 식별하고 요청·수행 양측의 현재 위임을 확인한다. Capability만으로 책임을 대체하지 않는다.
4. 필요한 결과와 검증 조건이 owner의 최소 기준을 충족하는지, 요청 context를 해당 수신자에게 공유할 수 있는지 확인한다. 기술적 진단 전체를 다시 판단하지 않는다.
5. 수락 시 요청별 조건과 근거를 보존하고, 논리적 Request 하나에 수신 Work 하나를 연결한다. 원래 Work에 이 결과를 기다리는 관계를 연결한다.
6. 수신 Work의 알려진 실행 조건이 충족되면 READY, 부족하면 BLOCKED로 둔다. 수락 자체가 dispatch는 아니다.

거절·보류된 제안도 근거를 남기지만 실행 가능한 수신 Work를 만들지 않는다. 누락·범위 위반·책임 충돌을 구분해 관련 owner에게 escalation한다. 요청 Agent는 조건을 임의로 낮추거나 다른 owner로 우회할 수 없다.

MVP fan-out 제한은 **하나의 original Work당 active cross-owner Request 하나**다. 시스템 전체 제한이 아니다. 서로 다른 original Work의 handoff는 owner 슬롯이 허용하는 범위에서 독립적으로 진행한다. 동일 owner를 향한 요청은 그 owner 큐에서 경쟁한다. 이 제한은 위임 깊이를 제한하는 1-hop 규칙과 별개다.

여기서 active는 별도 Request 상태가 아니라, 수락된 handoff 중 원래 Work의 continuation에서 아직 해소하지 않은 관계를 뜻한다. 결과가 충족돼도 원래 Work가 아직 해당 결과로 재개하지 못했다면 관계는 유지한다. 결과를 사용한 후속 실행 시작이 확인되거나 해당 handoff의 포기·조율 종료가 기록되면 해소한다. 취소·종료 처리 중 수신 실행이 미확정이면 해소된 것으로 보아 새 요청을 자동 수락하지 않는다. 단순 timeout·실패·escalation으로 제한을 풀지 않는다.

같은 original Work에서 두 번째 요청이 오면 기존 관계를 덮어쓰거나 자동 병렬 수락하지 않고 제한 사유를 드러낸다. 동일 요청의 재전달과 수정 제출은 식별해 기존 관계에 연결하며 자유 서술 유사성으로 중복을 추측하지 않는다. 이후 다른 요청도 같은 최초 Work 계보와 양측 위임을 유지하며 반복 한도는 9절을 따른다. 이 제한의 확인과 수락은 하나의 논리적 결정으로 묶어 동시 제출로 우회되지 않게 한다.

## 4. Dispatch: 실행 선택과 실제 시작

### 4.1 READY 순서

- owner별로 현재 실행 가능한 READY 집합만 정렬한다.
- 확인된 긴급을 먼저, 같은 긴급도는 **이번 READY 진입 순서**로 처리한다. 안정적인 진입 순번으로 동시 시각의 동률을 해소한다.
- Accept 시각은 이력이며 READY 진입 순번과 구분한다. BLOCKED에서 풀리거나 WAITING 후 재개·retry하는 Work는 새 순번을 받는다.
- 같은 READY 기간 중 긴급도 변경은 진입 순번을 초기화하지 않는다. 중복 이벤트 역시 큐 위치를 바꾸지 않는다.
- 긴급성은 사전에 정한 신뢰 출처와 조건으로 확인한다. 출처가 없거나 충돌하면 우선권을 추측하지 않고 escalation한다. 실제 필드·확인 유효기간은 MVP Spec에서 정한다.

### 4.2 Dispatch 판단 경계

선택한 Work에 대해 원본 업무가 활성인지, 필요한 결과와 재개 입력이 여전히 유효한지, 실행·순서·공유에 관련된 현재 contract가 허용하는지 확인한다. 진행을 막는 escalation, 같은 Work의 미확정 시도, 점유·예약된 슬롯이 있으면 dispatch하지 않는다.

확인한 입력의 변경 여부와 슬롯 예약을 하나의 논리적 dispatch 결정으로 묶는다. 판단과 예약 사이에 취소·관련 위임 변경·다른 예약을 인지했다면 다시 평가한다. 구현 방식은 Architecture에서 정한다.

예약 후 외부 전송 전 관련 변경을 인지하면 전송하지 않는다. Owner 측 실행 연결부도 실제 시작 전에 현재 유효한 실행 허가와 범위를 확인해야 한다. 유효 여부를 확인할 수 없으면 시작을 보류한다. 이미 보낸 요청은 취소 메시지만으로 미실행을 확정할 수 없으므로 확인 전 슬롯을 재사용하지 않는다.

외부 취소 관찰과 실제 시작 사이를 전역적으로 원자화했다고 주장하지 않는다. 취소/철회 인지 시각, dispatch 판단, 외부 접수·시작 관찰을 각각 기록한다. 실제 권한 집행 방법과 지연은 연동 계약에서 검증해야 한다.

## 5. Wait: 원래 실행 종료와 결과 대기

Agent는 handoff 요청과 재개에 필요한 작업 상태를 반환한다. Gateless는 요청 수락/보류 결과, 원래 Work와 요청의 연결, 재개 입력 참조를 보존한다. 공유용 context와 owner 환경에 남는 상태를 구분한다.

실행 종료를 확인한 뒤 원래 Work를 WAITING으로 옮기고 슬롯을 반환한다. 종료 전에 수신 owner가 독립 슬롯에서 작업할 수 있지만, 원래 Work의 재실행이나 같은 슬롯의 다른 실행은 허용하지 않는다.

수락이 보류돼도 원래 Agent가 종료했다면 WAITING에 필요한 사람 판단을 사유로 남긴다. 외부 결과가 먼저 도착했어도 원래 실행 종료와 context 준비가 확인될 때까지 재개하지 않는다. 정상적인 결과 대기 자체는 escalation 사유가 아니다.

## 6. Result satisfaction: 증거와 요청 조건의 판정

결과를 받으면 출처·요청·실행 시도·산출물 버전을 확인한다. 요청별 보존 조건의 충족과 현재 자동 수용에 관련된 최소 기준을 구분해 판단한다. 검사 완료와 검사 성공, PR 존재와 해당 변경의 검증을 구분한다.

| 관찰 | 처리 |
|---|---|
| 필요한 검사가 아직 실행 중 | 결과 대기 사유를 유지하고 관찰을 계속함 |
| 해당 버전의 필요한 증거가 조건을 충족 | 조건과 Result/Evidence 사이에 충족 판정을 기록 |
| 증거가 명시적으로 부적합하거나 필수 결과 누락 | 미충족 이유를 기록하고 보정에 필요한 판단을 escalation |
| 조회 권한·출처·결과 연결을 확인할 수 없음 | 판정 불가로 보류. 성공이나 기술적 실패로 추정하지 않음 |

Execution이 종료되고 수신 Work의 요청 결과가 충족되면, 수신 Work는 산출물 전달 완료 사유로 CLOSED가 될 수 있다. 원래 Work 재개까지 수신 Work를 열어둘 필요는 없다. 충족 여부의 근거는 CLOSED가 아니라 결과 판정 기록이다. 실행은 종료됐지만 결과 확인이 남으면 수신 Work는 WAITING이다.

과거 판정은 바꾸지 않는다. 다른 산출물 버전의 결과, 요청 조건의 명시적 변경, 현재 기준 변경은 새 판정의 근거가 된다. 기존 결과가 어떤 고정 버전으로 재개에 사용되는지 식별한다. 단순 PR URL의 최신 내용과 이전 commit의 검사를 혼합하지 않는다.

## 7. Resume: 자동 READY 복귀와 새 실행

다음 조건이 모두 충족되면 원래 Work를 사람 승인 없이 READY로 복귀시킨다.

1. 필요한 Request 결과의 충족 판정이 있고 지금 사용할 결과·증거와 일치한다.
2. 이전 실행이 종료됐으며 동일 Work의 활성·미확정 실행이 없다.
3. 원래 context와 받은 결과가 연결되고, 후속 Agent가 허용된 경로로 사용할 수 있다.
4. 원본 업무가 취소·완료되지 않았고, 현재의 재개·실행·순서·결과 공유/사용 경계가 허용한다.
5. 이 재개를 막는 미해결 사람 판단이 없다.

결과가 충족돼도 context가 부족하면 WAITING을 유지하고 부족한 항목을 명시한다. 결과를 보기 위한 상대 저장소 권한을 임의로 전달하지 않는다. 준비된 결과를 사용할 뿐인 Backend 재개에 Frontend의 추가 코드 수정 위임까지 요구하지 않는다.

동일 대기 회차와 결과 판정에 대한 READY 복귀는 한 번만 반영한다. 중복 통지는 새 실행이나 새 READY 순번을 만들지 않는다. Slot 배정 시 4절의 현재 조건을 다시 확인하고 새 Execution을 시작한다. 같은 CLI 세션의 유지·복구는 필수가 아니다.

## 8. Escalation과 contract 변경·취소

Escalation에는 관련 대상, 막힌 행동, 이유와 근거, 필요한 결정, 해당 경계를 결정할 owner를 포함한다. 여러 owner의 경계가 충돌하면 한쪽 승인으로 다른 쪽을 우회하지 않는다. 동일한 미해결 사유를 이벤트마다 새 개입으로 중복 계산하지 않는다.

사람은 정보 보충, 요청별 조건 조정, 자신이 소유한 경계의 한정 예외/개정, 안전성이 확인된 재실행, 조율 종료 등을 결정할 수 있다. 답변은 무조건 실행시키는 명령이 아니라 관련 판단을 다시 평가하는 입력이다. 모든 조건이 충족되면 추가 재개 승인 없이 진행한다. 요청별 예외는 미래 요청 전체의 정책 변경이 아니다.

| 변경 시점·종류 | 처리 |
|---|---|
| READY 중 관련 위임 철회 | dispatch 후보에서 제외. 미실행이면 BLOCKED, 이전 실행 후라면 WAITING으로 두고 이유 기록 |
| WAITING 중 무관한 위임 변경 | 해당 재개를 일괄 차단하지 않음 |
| 결과 기준 강화 | 보존 조건을 지우지 않고 현재 행동에 강화 기준 적용. 추가 작업을 자동 생성하지 않음 |
| Dispatch 이후 취소·철회 인지 | 후속 시작을 차단하고 가능한 취소/정지를 요청. 실제 미실행·종료 확인 전 슬롯 유지 |
| 원본 업무 취소·최종 완료 관찰 | 원래 Work와 그 목적에만 연결된 수신 Work의 새 실행을 중단. 활성 실행을 정리한 뒤 CLOSED. 늦은 결과로 다시 열지 않음 |
| RUNNING 중 범위 축소 | 관련 실행 연결부에 반영하고 집행 결과 확인. 이미 발생한 효과는 보존하며 중단 가능성을 과장하지 않음 |

위임 철회만으로 Work를 자동 CLOSED로 만들지 않는다. 목표가 남아 있으면 사람 판단을 기다릴 수 있다. 원본 업무 취소와 위임 철회는 서로 다른 사유다.

## 9. 실패·retry·응답 유실의 최소 정책

범용 자동 복구 플로우는 만들지 않는다. MVP의 보수적인 기본값은 다음과 같다.

- 읽기·상태 확인은 연동 계약이 허용하는 한도에서 다시 시도할 수 있다. 조회 실패가 원본 취소나 실행 실패를 의미하지 않는다.
- 외부 효과를 일으키는 호출의 응답 유실은 결과 불명으로 둔다. 상관 식별자로 접수·시작·종료를 확인하기 전 동일 효과를 다시 요청하지 않는다.
- 같은 전송을 재전달하는 경우와 새 실행 시도를 구분한다. 수신 측 중복 방지가 실제 보장되는 동작만 동일 시도 식별자로 재전달할 수 있다. 지원을 추정하지 않는다.
- 실행의 확정 실패·잘못된 산출물은 자동으로 Agent를 다시 돌리지 않고 escalation한다. 안전한 재실행 결정 후 같은 Work의 새 Execution을 만들며 현재 조건과 순서를 다시 적용한다.
- 결과 수용 후 후속 Agent가 재작업을 요구하면 이전 판정을 지우지 않는다. 자동 재작업이나 같은 목적의 반복 handoff는 첫 MVP에서 escalation 대상으로 처리한다. 사전 한도가 없는 무한 loop를 허용하지 않는다.
- 동일 원본 Work의 추가 독립 handoff를 지원할지와 허용 횟수는 준비된 시나리오에서 정한다. 정의되지 않은 추가 요청은 자동 실행하지 않는다.
- 외부 실행을 확인할 수 없으면 해당 슬롯을 격리한 채 escalation한다. 사람의 단순 “재개” 클릭만으로 실제 종료 확인을 대체하지 않는다.

관찰 시간 제한·재조회 간격·읽기 retry 횟수는 실제 서비스 특성에 맞춰 MVP Spec에서 정한다. Timeout 자체를 외부 실행 종료로 취급하지 않는 원칙은 고정한다.

## 10. History와 검증 시나리오

Accept 판단, READY 진입, dispatch 근거와 슬롯 예약, 외부 접수·시작·종료 관찰, wait와 슬롯 반환, 결과 판정, resume, escalation 및 사람의 결정을 연결한다. 이름은 예시이며 저장 기술을 정하지 않는다. 상태 변경 이유와 적용 조건을 남기고 원시 secret·전체 context 수집을 요구하지 않는다.

아래는 후속 구현의 수용 사례이며 현재 실행한 테스트가 아니다.

| 입력·사건 | 기대 관찰 |
|---|---|
| 범위 내 한 단계 요청 | 수락 기록, 수신 Work 하나, 조건 충족 시 READY |
| 동일 요청·결과의 재전달 | 수신 Work·READY 진입·Execution 중복 생성 없음 |
| Backend가 대기하고 실제 종료 | 슬롯 반환 후 다른 Backend READY 실행 가능 |
| Frontend 결과가 Backend 종료보다 먼저 도착 | 결과 기록은 가능하지만 Backend 중복 실행 없음 |
| 검사 성공이 다른 commit의 증거 | 자동 결과 충족·재개 없음 |
| 조건 충족 결과와 허용된 context 준비 | 사람 승인 없이 READY 복귀, 기존 대기열 순서 적용 |
| READY 대기 중 관련 위임 철회 | 새 실행 시작 없음, 과거 accepted 유지 |
| Frontend 수정 위임만 철회, 이미 받은 결과의 사용은 허용 | Backend 재개를 불필요하게 차단하지 않음 |
| 실행 요청 응답 유실 | 새 시도로 무조건 retry하지 않음, 슬롯 유지와 확인 경로 표시 |
| 원본 취소 후 늦은 결과 | 결과 기록은 남고 재개하지 않음 |
| 수신 Work의 제3 owner 요청 | 자동 연쇄 위임 없이 escalation |
| 서로 다른 original Work가 각각 handoff 제출 | 시스템 전체 한 개 제한 없이 각각 수락 가능. owner 슬롯에 따라 병렬 실행 또는 큐 경쟁 |
| 같은 original Work가 두 번째 active handoff 제출 | 자동 fan-out 없이 기존 관계 유지와 제한 사유 표시 |
| 동일한 context 부족이 첫 실행 전/실행 후 발생 | 각각 BLOCKED/WAITING. 원인 종류로 상태를 바꾸지 않음 |
| 관련 없는 두 owner의 READY | 각 제공 슬롯에서 독립 실행 가능 |

## 11. Baseline 최종 점검과 다음 단계

2026-09-16 사용자 합의와 최종 점검을 반영했다.

- FIFO는 이번 READY 진입 순번이며 resume는 새 순번을 받는다.
- 시작·종료 불명 시 슬롯을 유지하고 실행 사실을 추정하지 않는다.
- Active handoff 제한은 original Work별 하나이며 1-hop과 독립적이다. 서로 다른 original Work를 전역 직렬화하지 않는다.
- BLOCKED/WAITING은 execution history 기준이며 원인과 escalation은 별도 사유다.
- 실행 실패·재작업의 자동 retry는 MVP에서 제외한다.
- 실제 시작 전 owner 연결부도 유효한 실행 허가를 확인한다.

Request/Work/Execution/결과 판정의 중복 상태, 다른 original Work의 병렬성, 취소·철회와 과거 사실 보존, early/duplicate result와 재개 조건을 대조했다. 새 제품 책임 충돌은 발견하지 않았다. 이 문서를 runtime 기준선으로 확정하고 [MVP Spec](../product/MVP_SPEC.md)으로 진행한다.

구체적인 업무·증거·공유 context·prepared demo 환경, 긴급성 출처, 반복 한도·예산·관찰 시간 값, 실제 집행 경로는 후속 명세 대상이다. 이들이 미정이라는 이유로 baseline을 미확정으로 되돌리지 않으며, 실제 확인 없이 구현 기본값으로 숨기지도 않는다.
