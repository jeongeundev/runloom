# Gateless Domain Model

> 상태: 확정된 domain baseline. 2026-09-16 사용자 합의 반영. Runtime 상태·전이의 상세화는 Work Engine의 책임이다.
> 기준: [PRD](../product/PRD.md), [연동 조사](../research/INTEGRATION_FEASIBILITY.md), [외부 업무·자동화 조사](../research/EXTERNAL_WORK_API_RESEARCH.md).
> 범위: 용어·책임·관계·생명주기. DB schema, API payload, 런타임, 배포 또는 범용 정책 엔진을 정하지 않는다. 실제 계정의 API 왕복은 미검증이다.

## 1. 확정된 제품 책임

**Owner defines the boundary → Agent proposes the work/result → Gateless enforces the contract → Agent performs the technical judgment.**

- Owner는 자신의 책임 범위에서 자동 위임 가능한 요청·행동, 순서 결정 범위, 최소 결과·evidence 기준과 공유 가능한 context를 정한다. 요청·수행 양측의 위임이 필요하다.
- Agent는 기존 Work의 기술적 필요성과 기대 결과를 제안하고 기술적 작업을 수행한다. 재개 기준을 임의로 약화하거나 권한·공유 범위를 확대할 수 없다.
- Gateless는 사전 위임된 조건과 요청·반환 결과의 적합성을 확인하고 실행·대기·재개를 조율한다. 기술적 정답을 다시 판단하는 super-agent가 아니다.
- 조건이 충족되면 매 결과마다 사람에게 재개 승인을 받지 않는다. 판단 근거 부족·범위 밖 요청·정책 충돌은 escalation한다.
- 외부 업무의 목표·취소·최종 완료와 Gateless coordination state는 분리한다. 현재 prepared MVP에서는 전자를 GitHub Issue가 소유한다. 이는 integration 매핑이며 도메인 책임 변경이 아니다.

Coordination Contract의 의미적 집합, Request/Work의 책임 분리와 변경·철회 원칙은 사용자 합의로 확정됐다. Runtime 세부 규칙은 [Work Engine](WORK_ENGINE.md)에서 정한다.

## 2. Coordination Contract

### 2.1 채택: 하나의 개념으로 묶고, 판단은 구분한다

**Coordination Contract는 owner들이 반복적인 handoff에 매번 개입하지 않아도 되는 조건의 집합**으로 둔다. Execution Delegation, Scheduling Delegation, 최소 Result/Evidence 기준, Context Sharing을 그 구성 요소로 표현한다.

이 개념은 “왜 이 요청을 자동으로 진행할 수 있는가”를 설명하는 단위다. 하나의 전역 정책, 하나의 DB 객체 또는 하나의 승인 boolean으로 합치자는 뜻은 아니다. 실행을 허용해도 슬롯이 없을 수 있고, 결과 증거가 유효해도 재개 context가 없거나 원본 업무가 취소됐을 수 있다.

| 구성 요소 | 표현하는 경계 | 주로 확인하는 시점 |
|---|---|---|
| 적용 범위와 책임 | 공동 프로젝트, 요청·수행 owner, 책임 영역, 허용 요청 종류와 한 단계 위임 | 요청 수락 |
| Execution Delegation | 허용 행동과 금지 행동, 자동 실행 가능한 범위 | 수락·실행 및 실행 환경의 행동 집행 |
| Scheduling Delegation | 제공 슬롯과 그 안의 순서 결정 범위 | 큐 진입·실행·재개 |
| 최소 Result/Evidence 기준 | 자동 수용에 필요한 산출물과 검증 근거의 하한 | 요청 조건 구체화·결과 확인 |
| Context Sharing | 요청·결과 각각의 공유 대상과 허용 정보 범위 | 요청 전달·결과 전달·재개 입력 준비 |

Provider permission은 contract가 만들어 주는 권한이 아니다. 실제 권한이 넓어도 contract 밖 행동은 허용되지 않고, contract 안 행동이어도 실제 권한이 없으면 수행할 수 없다. Gateless의 조율 판정과 owner 측 실행 환경의 행동 제한이 함께 필요하다. 집행 지점과 한계는 Architecture에서 검증한다.

### 2.2 양측 경계와 요청별 구체화

요청 owner가 허용한 요청 범위와 수행 owner가 허용한 수락·실행 범위를 모두 만족해야 한다. 각 owner는 자신이 통제하는 정보의 공유 범위를 정한다. 한쪽 조건이 다른 쪽의 허용 범위를 덮어쓰지 않는다. 책임 매핑이 없거나 모호하면 capability만으로 다른 owner를 선택하지 않는다.

다음 세 가지를 구분한다.

1. **사전 경계:** owner들이 정한 재사용 가능한 허용 범위와 최소 기준.
2. **요청별 조건:** Agent 제안을 사전 경계 안에서 구체화한 대상·산출물·증거·전달 context. 구체화로 기준을 약화할 수 없다.
3. **판정 기록:** 특정 시점에 어떤 조건과 관찰 근거로 수락·보류·결과 수용·재개를 결정했는지.

별도 엔티티 세 개를 요구하는 것은 아니다. 특히 Agent가 “테스트 불필요”라고 제안해도 사전 기준이 테스트 증거를 요구하면 자동 수락할 수 없다. 조건의 의미를 확인할 수 없는 경우도 자동 통과시키지 않는다. MVP에서 지원할 요청 종류와 판정 가능한 조건을 제한하는 방법은 MVP Spec에서 정한다.

과거 판단에 적용한 경계와 요청 조건을 추적할 수 있어야 한다. 과거 조건 기록을 현재 실행의 영구 허가로 해석해서는 안 된다. 변경·철회의 원칙은 2.4절에 정리한다.

### 2.3 별도로 유지할 네 가지 판단

| 판단 | 확인할 내용 | 의미하지 않는 것 |
|---|---|---|
| 요청 수락 | 원래 Work와의 관계, 한 단계 범위, 책임, 양측 위임, 결과·공유 조건 | 즉시 실행 또는 기술적 진단의 정답 보증 |
| 실행 허용 | 현재 업무 상태, 실행 조건, 실제 수행 가능성, 제공 슬롯과 순서 | 외부 실행 성공 |
| 결과 수용 | 요청에 대응하는 산출물과 버전에 대한 최소 기준·요청별 조건·증거 충족 | 원본 업무 최종 완료 또는 자동으로 즉시 재실행 |
| 재개 허용 | 필요한 결과 충족, 사용 가능한 허용 context, 현재 업무와 위임 상태 | 슬롯 독점 또는 기존 RUNNING 작업 중단 |

Gateless가 검사 결과를 확인하기 위해 기존 자동화를 호출할 수 있지만, 테스트·진단을 전부 다시 수행하는 기술적 심판이 되지는 않는다. 결과 수용 이후 후속 Agent가 기술적 문제를 발견할 수 있으며, 이때 재작업과 원인을 기록한다. 이전 수용 기록을 지우거나 곧바로 원본 업무 완료로 처리하지 않는다.

### 2.4 변경·철회의 도메인 원칙

**과거 수락과 수행 사실은 보존하고, 앞으로의 자동 행동은 그 행동에 현재 유효한 위임을 필요로 한다.** Accepted는 영구 실행 허가나 owner의 철회권 포기가 아니다. 위임 철회 자체도 원본 업무 취소나 과거 결과의 기술적 무효를 뜻하지 않는다.

요청 수락 시 구체화한 목표·범위·결과 조건과 적용 contract 근거를 보존한다. Contract 변경이 기존 요청의 약속을 암묵적으로 다시 쓰지 않는다. 앞으로 수행하려는 행동에는 양측의 관련된 현재 경계도 적용한다. 버전이 바뀌었다는 사실만으로 무조건 멈추거나 모든 과거 결과를 다시 판정하지 않는다.

| 대상 | 변경·철회의 의미 |
|---|---|
| Accepted Request | 수락 사실과 당시 조건은 유지한다. 남은 행동이 현재 경계 안에 있으면 진행 가능하며, 벗어나면 자동 진행 권한이 없음을 드러낸다. 요청 자체를 자동 취소하거나 완료 처리하지 않는다. |
| 아직 시작하지 않은 Execution | 생성·예약·큐 진입만으로 실행권을 획득하지 않는다. 해당 행동의 현재 실행·순서·공유 위임이 없으면 시작하지 않는다. 실제 시작·인가의 경계와 경쟁 조건은 Work Engine에서 정한다. |
| WAITING 후 Resume | 이전 실행의 허가를 상속하는 것이 아니라 새로운 실행 행동이다. 요청 결과 충족과 별도로 원래 owner의 현재 실행·순서 위임, 결과 전달·사용의 공유 범위를 만족해야 한다. |
| 이미 RUNNING인 Execution | 철회가 과거 실행을 없애거나 즉시 중단·rollback을 보장하지 않는다. 철회 범위에 해당하는 새 자동 행동은 허용하지 않는다. 진행 중 행동의 중단 가능성·인지 지연·집행 경계는 Work Engine/Architecture에서 정한다. |
| 이미 반환·수용한 Result | 산출물과 과거 판정은 보존한다. 새 공유·재개가 허용되는지는 별도다. 철회가 이미 전달된 정보를 회수했다는 뜻은 아니며, 보존·삭제 규칙도 별도로 정한다. |

변경 종류에 따라 다음과 같이 해석한다.

- **범위 확대·기준 완화:** 기존 요청의 목표를 확대하거나 이미 약속한 결과 조건을 낮추지 않는다. 기존 조건은 명시적으로 변경하지 않는 한 유지한다.
- **범위 축소·기준 강화:** 앞으로의 관련 행동은 강화된 현재 경계도 충족해야 한다. 필요한 증거가 이미 있다면 자동 진행할 수 있지만, 추가 작업이 필요하면 이를 원래 수행 범위에 몰래 더하지 않는다. 조건 조정이나 추가 업무는 별도로 적합성을 확인하고, 불확실하면 escalation한다.
- **철회:** 해당 위임에 의존하는 향후 행동만 막는다. Frontend의 추가 코드 수정 위임을 철회했어도 이미 반환된 결과의 공유·사용 및 Backend 재개 위임이 유효하면 Backend 재개까지 일괄 금지하지 않는다. 결과 공유나 요청 owner의 재개 위임을 철회했다면 해당 전달·재개는 불가하다.
- **요청별 예외:** 권한을 가진 owner가 해당 요청·행동에 부여한 한정된 위임으로 명시한다. 향후 모든 요청의 contract 변경이나 다른 owner의 경계 우회로 해석하지 않는다.

결과 조건 역시 두 층을 구분한다. 수락 당시 요청 조건의 충족 여부는 보존된 조건으로 설명하고, 지금 결과를 자동 수용하거나 재개에 사용할 수 있는지는 그 행동에 현재 적용되는 최소 기준도 확인한다. 과거 판정을 덮어쓰는 대신 현재 진행 가능 여부와 근거를 남긴다. 이는 각 객체에 새로운 상태 머신을 추가하라는 요구가 아니다.

## 3. 핵심 용어와 관계

| 용어 | 도메인 의미 |
|---|---|
| Owner | 특정 책임 영역의 위임·공유 경계와 제공 슬롯을 결정하는 주체. Agent나 API 계정 자체와 동일하지 않다. |
| Responsibility | 프로젝트 안에서 요청을 맡을 책임 영역. 수행 능력인 capability만으로 책임을 얻지 않는다. |
| Provider | 허용된 실행을 수행하거나 결과를 제공하는 Agent·기존 자동화 등. 서비스 제품명과 역할을 1:1로 고정하지 않는다. |
| Coordination Contract | 자동 조율이 허용되는 사전 경계들의 집합. 요청별 조건과 현재 판정 결과를 구분한다. |
| Source Work Reference | 외부에서 관리되는 원본 업무의 식별과 참조. 원본의 목표·취소·완료를 Gateless 상태로 덮어쓰지 않는다. |
| Work | Gateless가 실행 가능성·대기·재개를 조율하는 논리적 업무 단위. 여러 실행 시도에 걸쳐 정체성을 유지한다. |
| Request | 원래 Work가 다른 owner에게 필요한 결과를 요구하는 명시적인 handoff. 원래 Work와 결과 조건을 연결한다. |
| Execution | Work를 수행하려는 한 번의 실행 시도. 접수·시작·종료·결과 충족은 서로 다르다. |
| Result | 수행 측이 요청 또는 Work에 대해 반환한 산출물과 결과 보고. 성공 주장만으로 수용되지 않는다. |
| Evidence | 결과 조건을 확인하는 근거. 해당 요청·산출물·버전·검사와 연결돼야 한다. |
| Dependency | Work의 실행·재개에 필요한 결과 조건. 우선순위 점수가 아니다. |
| Resume Context | 후속 실행이 원래 작업과 외부 결과를 이어 사용할 수 있는 입력. 동일 세션 유지와 별개다. |
| Slot | Owner가 Gateless에 제공한 실행 용량. MVP에서는 owner당 하나이며 owner 전체 자원을 뜻하지 않는다. |
| Escalation | 자동 판단을 계속할 수 없어 필요한 사람 판단과 이유를 드러내는 것. 단순 Provider 실행 실패와 구분한다. |
| Coordination Event | 관찰·결정·실행·사람 개입의 연결 가능한 기록. 외부의 모든 사실이나 Agent 내부 trace를 뜻하지 않는다. |

**Work와 Request의 관계:** 원본 업무에 대응하는 Work를 유지하고, 수락된 cross-owner Request의 수행도 별도 Work로 조율한다. Request는 왜 무엇을 누구에게 요구했는지를, 수신 Work는 해당 수행의 큐·실행·대기를 나타낸다. 재시도는 같은 논리적 요청의 새 Execution이며 자동으로 새 Request나 새 원본 업무를 만들지 않는다. 이 관계는 DB 테이블 분리를 요구하지 않는다.

### 3.1 더 단순한 모델과 비교

| 대안 | 장점 | 비용·판단 |
|---|---|---|
| Request가 수신 실행 생명주기도 소유, 수신 Work 제거 | 객체 하나 감소 | 원래 업무는 Work, 위임 업무는 Request가 큐·대기·실행을 소유하게 된다. 같은 실행 규칙이 두 종류의 대상에 걸쳐 존재한다. 요청을 사실상 Work의 다른 이름으로 만드는 경우에만 단순하다. |
| Work 하나에 handoff 정보 포함 | 실행 생명주기를 Work로 통일하고 별도 Request 저장 없이 표현 가능 | 수락 전 제안·거절 근거, 원래 Work와의 관계·합의 조건은 여전히 구분해야 한다. 저장 형태로는 적절하며 아래 채택 모델과 양립한다. |
| Request는 관계·요청별 조건, Work는 실행 생명주기 | 요청 의미와 실제 수행을 구분하면서 실행 대상은 Work로 통일 | Request에 큐·실행·완료 상태를 복제하면 오히려 복잡해진다. 독립적인 Request 실행 상태 머신을 두지 않는 조건으로 채택한다. |

**채택:** Request를 coordination relationship이자 요청별 contract 구체화로 유지하고, 수락된 요청 하나에 수신 Work 하나를 연결한다. 단, 별도 저장 객체를 필수로 하지 않는다. 수신 Work에 handoff 정보를 포함해도 의미상 같은 모델이다. MVP에서 여러 Request가 하나의 Work를 공유하거나 하나의 Request가 여러 수신 Work로 분해되는 모델은 도입하지 않는다.

### 3.2 상태의 소유권

| 개념 | 소유하는 사실·판단 | 복제하지 않는 상태 |
|---|---|---|
| Request | 요청·수행 owner와 원래/수신 Work의 관계, 요청별 조건, 수락·거절 및 조건 변경의 판정 기록 | QUEUED/RUNNING/WAITING/COMPLETED 같은 실행 진행 상태 |
| Work | 실행 가능성·대기·재개와 조율 종료 등 논리적 수행 생명주기 | Provider 실행의 성공·실패 사실, Result 자체의 별도 생명주기 |
| Execution | 한 번의 실제 실행 시도의 접수·시작·종료·실패 등 관찰 사실 | 논리적 요청 전체의 충족이나 원본 업무 완료 |
| Result/Evidence | 무엇을 어느 요청·산출물 버전에 대해 반환·검증했는지와 그 근거 | Work와 같은 READY/RUNNING/COMPLETED 상태 |

결과 충족 판정은 **특정 Request 조건과 Result/Evidence 사이의 판정 기록**으로 한 곳에 둔다. Result.success, Request.completed, 수신 Work.completed를 서로 독립적으로 갱신해 같은 의미를 표현하지 않는다. 화면의 “요청 진행 중/충족”은 수신 Work의 진행 또는 해당 판정으로부터 설명한다. Dependency 충족도 같은 판정을 참조한다.

Work는 조율을, Execution은 실제 시도를 설명하므로 둘의 상태는 구분할 이유가 있다. 실행 종료를 관찰했다고 곧바로 Work 완료가 되지 않는다. 결과 확인이 남았거나 원래 Work가 후속 실행을 기다릴 수 있다. 파생 표시와 전이 규칙은 Work Engine에서 정하되 같은 사실의 독립적인 원장을 여러 개 두지 않는다.

다음 반례로 중복 여부를 검토했다.

- 요청이 거절되면 수락 판정 기록만 필요하며 실행 가능한 수신 Work는 필요 없다.
- Execution이 성공해도 evidence가 부족하면 결과 충족 판정은 성립하지 않는다. Request에 별도 실행 실패 상태를 덧붙일 필요가 없다.
- 결과 조건을 충족해도 원래 Work가 취소됐다면 결과 충족 사실과 재개 금지를 함께 설명할 수 있다.
- Contract가 철회돼도 accepted를 rejected로 되돌리지 않는다. 향후 실행을 허용하지 않는 현재 판단과 과거 수락을 구분한다.

```text
Source Work Reference → 원래 Work → Execution(s)
                           │
                           └─ Request → 수신 Work → Execution(s) → Result + Evidence
                                │                                  │
                                └─ 결과 조건 / Dependency ←─────────┘
                                           │
                      원래 Work + Resume Context → READY → 새 Execution
```

수신 Work는 원래 Work의 소유권을 인수하지 않는다. 수신 Work가 제3 owner에게 요청하면 두 번째 자동 위임 단계이므로 escalation한다. 수신 Work를 별도 원본 업무처럼 취급해 depth를 초기화하지 않는다. MVP에서는 original Work당 active cross-owner Request 하나로 fan-out을 제한한다. 이는 1-hop 깊이 제한과 별개이며 서로 다른 original Work의 handoff는 owner 슬롯에 따라 독립 진행한다. Active의 해소 기준과 반복 요청·재작업 규칙은 Work Engine을 따른다.

외부 Issue ID, PR/commit, 자동화 execution ID, A2A task, CLI 실행 식별자는 연결하되 동일시하지 않는다. A2A task의 종료나 CLI 성공은 Gateless Work의 종료와 같지 않다.

## 4. 생명주기의 도메인 경계

아래는 정상 대기·재개 흐름의 의미다. 실패·취소·판정 대기까지 포함하는 최종 상태 열거형은 아니다.

| 상태 | 기본 의미 | 슬롯 |
|---|---|---|
| BLOCKED | 첫 실행 전에 필요한 조건이 미충족 | 점유하지 않음 |
| READY | 다음 실행 조건을 충족하여 순서·슬롯 배정을 기다림 | 점유하지 않음 |
| RUNNING | 실행 시도가 진행 중 | 점유 |
| WAITING | 수행 도중 외부 결과가 필요해 실행을 끝내고 재개를 기다림 | 종료 확인 후 반환 |

대표 경로는 `READY → RUNNING → WAITING → READY → RUNNING`이다. BLOCKED와 WAITING은 원인 종류가 아니라 실제 execution history로 구분한다. BLOCKED는 아직 실행 전 조건 부족, WAITING은 적어도 한 번 실행된 Work가 continuation 조건을 기다리는 상태다. 결과·context·사람 판단 등 부족한 조건은 별도 사유다. 실행이 끝났는데 재개 입력이 부족한 경우, 사람 판단을 기다리는 경우, 실행 상태가 불명확한 경우를 어느 상태·사유로 표현할지는 Work Engine에서 정한다.

Agent가 “대기”라고 보고한 것만으로 슬롯을 반환하지 않는다. 실제 실행 종료·정지를 확인해야 하며, 확인되지 않은 실행 때문에 같은 슬롯에 중복 dispatch해서는 안 된다. RUNNING에서 대기로 넘어가는 중간 과정과 슬롯 예약 시점은 Work Engine이 정한다.

Execution 종료, 요청 결과 수용, Work의 다음 실행 조건 충족, 외부 업무의 최종 완료는 독립적으로 기록한다. 논리적 Work의 종료 상태와 외부 취소 후 RUNNING 처리의 세부 규칙은 확정된 Work Engine을 따른다.

## 5. Context와 evidence의 경계

요청 전달 context, 결과 전달 context, 원래 owner 환경에 남는 재개용 작업 상태를 구분한다. 모든 원시 코드·대화·로그를 Gateless로 모을 필요는 없다.

- 요청 시에는 수행에 필요한 목표·입력 중 공유가 허용된 부분을 전달한다.
- 결과는 증거 참조와 후속 Agent가 실제 사용할 수 있는 허용된 내용을 포함해야 한다. 상대 저장소 URL을 전달해도 읽기 권한은 생기지 않는다.
- 원래 owner 환경의 branch·작업 변경·남은 행동 같은 상태와 외부에서 받은 결과를 연결해 재개한다. 필요한 항목은 시나리오별로 정한다.
- Gateless가 evidence를 읽을 권한과 요청 Agent가 결과 내용을 읽을 권한도 별개다. 양 경로의 권한·충분성을 확인해야 한다.
- 보존 데이터 역시 공유 경계를 따른다. 자유 서술 요약이라는 이유만으로 공유가 허용됐다고 간주하지 않는다.

GitHub 시나리오의 evidence 후보는 repository, PR, 대상 commit, 필요한 검사와 판정의 연결이다. 정확한 필드와 검사는 확정하지 않는다. 현재 MVP는 Jira·n8n을 제외한다. GitHub Issue/PR/check별 역할은 MVP Spec에서 구체화한다.

## 6. 경계 사례로 확인한 책임

아래는 모델 검토 사례이며 실제 API 테스트 결과가 아니다.

| 상황 | 이 모델에서 필요한 처리 |
|---|---|
| Agent가 최소 테스트 기준을 생략한 요청을 제출 | 기준을 낮춰 수락하지 않는다. 조건 보충 또는 사람 판단이 필요함을 드러낸다. |
| 필요한 검사가 이전 commit에서만 성공 | 현재 요청 결과의 증거로 자동 수용하지 않는다. |
| 결과는 유효하지만 요청 Agent가 링크를 읽지 못함 | 허용된 재개 입력이 마련되기 전 자동 재개하지 않는다. 읽기 권한을 임의로 확대하지 않는다. |
| 결과·context가 유효하고 업무가 활성 상태지만 슬롯이 바쁨 | READY로 복귀해 기존 순서 규칙을 따른다. 사람 승인이나 preemption이 필요하지 않다. |
| 원본 업무 취소 인지 뒤 성공 결과 도착 | 결과를 기록하되 원래 Work를 다시 실행시키지 않는다. 진행 중 외부 효과의 되돌림은 보장하지 않는다. |
| CLI 종료 확인 없이 대기 보고만 도착 | 슬롯이 비었다고 간주하지 않는다. |
| 외부 요청 응답 유실 또는 동일 결과 중복 도착 | 실행 실패로 단정해 재전송하거나 원래 Work를 중복 재개하지 않는다. 불명확한 상태의 확인 경로가 필요하다. |
| 수신 Agent가 제3 owner에게 요청 | 최초 원본 Work와의 관계를 유지하여 자동 연쇄 위임을 막고 escalation한다. |
| Evidence는 충족했지만 후속 Agent가 기술적 문제 발견 | 기술적 판단과 재작업을 기록한다. Gateless 수용을 기술적 정답 보증으로 해석하지 않는다. |
| 대기 중 owner가 위임을 변경·철회 | 2.4절 원칙에 따라 과거 수락은 보존하고 다음 행동의 관련 현재 위임을 확인한다. 철회를 원본 업무 취소와 동일시하지 않는다. |

## 7. History와 설명 책임

요청 수락·보류, 실행 요청·관찰, 대기·슬롯 반환, 결과 확인, 재개, escalation과 관찰 가능한 사람 개입을 연결 가능하게 남긴다. 관련 Work/Request/Execution, 주체, 사유, 시각, 적용 조건과 근거 참조를 구분한다. 외부 발생 시각이 제공되면 관찰 시각과 구분한다.

무엇을 보았는지와 무엇을 결정했는지를 구분해야 지연·중복 이벤트에 대해 설명할 수 있다. 현재 상태만 저장하거나 자유 서술 로그로 대체하지 않는다. 보존 기간과 payload 범위는 후속 설계에서 정하며 event sourcing을 요구하지 않는다. 패턴 분석·automation opportunity 제안은 post-MVP다.

## 8. 확정 범위 및 후속 문서 경계

Coordination Contract의 의미적 집합과 다음 두 원칙을 확정된 도메인 기준선으로 사용한다.

1. Request는 관계·요청별 조건과 판정 근거를 보존하고, 수신 Work만 실행 조율 생명주기를 갖는다. Request의 독립적인 실행 상태 머신과 별도 저장 객체를 요구하지 않는다. Result 충족은 조건과 증거 사이의 판정으로 한 곳에서 설명한다.
2. 과거 수락·조건·수행·판정은 보존하되, 새로운 행동에는 현재의 관련 위임이 필요하다. 조건 변경은 기존 요청을 암묵적으로 다시 쓰지 않고, 철회는 해당 향후 행동을 제한한다.

아래 항목은 후속 명세에서 결정한다. 이들의 미결은 domain baseline의 미확정을 의미하지 않는다. 도메인 책임을 바꾸는 후속 결정은 이 문서와 PRD에 함께 반영한다.

| 후속 결정 | 결정 문서 |
|---|---|
| READY 순서, retry, 슬롯 반환, dispatch/철회의 경쟁, 응답 유실·중복·취소 처리 | WORK_ENGINE |
| BLOCKED/WAITING 및 사람 판단 대기·실행 불명·실패·종료 상태의 정확한 전이와 파생 표시, 재작업 한도 | WORK_ENGINE |
| 요청 종류별 최소 evidence와 구체화 가능한 결과 조건, 실제 공유·재개 입력과 demo 환경 | WORK_ENGINE / MVP_SPEC |
| 실제 계정·배포·연동 계약, 현재 위임의 확인·집행 지점과 한계 | MVP_SPEC / ARCHITECTURE |

다음 단계는 Work Engine의 handoff lifecycle 검토다. 이 문서의 확정은 구현 착수를 의미하지 않는다.
