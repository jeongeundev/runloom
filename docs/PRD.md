## 실서비스 업무 순환 — 2026-09-22 확정

출시 범위 갱신(2026-09-23): [ROADMAP](product/ROADMAP.md)과 [ADR-0013](adr/0013-existing-tasks-first-staged-rollout.md)을 따른다. 아래 업무 순환은 지원 업무 한 유형에 제한해 MVP에서 검증하고, 기록 기반 설정 추천·패턴 개선 절은 후속 버전 요구다. 장기 요구 전체를 첫 출시 조건으로 읽지 않는다.

### MVP의 시작 경험과 범위

외부 업무 도구 1종에서 범위를 선택해 가져오기 → 기존 담당자·Agent·위임 연결 → 준비된 업무 실행 → 원본에 결과 요약·링크 반영 → 기존 후속 연결 또는 제한된 후속 Task 생성·착수를 지원한다. 직접 등록도 같은 판정을 사용한다. GitHub Issues 버그 수정 → 검토를 첫 사례로 제안하며 파일럿 도구와 업무는 아직 미확정이다.

자연어 워크플로우 생성·로그 분석을 가입 후 필수 단계로 두지 않는다. 원본 업무 정보는 재사용하고 누락된 필수 입력만 보충한다. 업무 목록·실행·결과·대기 이유를 중심으로 제공한다. 원본 업무 수정 충돌·중복 수신·결과 반영 실패와 재전송은 구현 전에 계약으로 구체화한다.

| MVP 추가 수용 항목 | 기대 결과 |
|---|---|
| 기록 없는 첫 사용자 | 과거 로그·메모리 없이 지원 업무의 입력과 Agent·위임 설정만으로 시작 |
| 실제 외부 업무 접수 | 선택한 범위만 가져오고 원본 ID·링크·담당 정보를 보존. 같은 이벤트는 중복 Task를 만들지 않음 |
| 기존 서비스에서 다음 업무 등록 | 연결된 범위 안의 준비된 업무는 별도 프롬프트 재작성·실행 조작 없이 착수 |
| 원본 결과 반영 | 요약·결과 링크를 원본에서 확인. 전송 실패와 작업 실패를 구분하고 재전송 시 중복 반영 방지 |
| 후속 업무 | 아래 A → C 및 B → F를 검증. F를 원본 도구에도 생성할지는 별도 정책이며 무조건 복제하지 않음 |
| 기록과 집계 | 입력·판정·결과·대기·사람 개입·시각·설정 버전을 보존. 초기 효과 검증은 수동 집계 가능 |

2026-09-23 확장: [ADR-0012](adr/0012-delegated-decisions-and-pattern-feedback.md)에 따라 위임된 판단은 AI가 수행한다. 부족한 정보는 허용된 조회·전문 에이전트 검토로 먼저 해결할 수 있고, 위임 범위 밖이거나 해결하지 못한 경우 사람에게 요청한다. 아래 D·E는 위임 범위 밖 권한·의견 조율을 기다리는 사례다.

업무 등록·가져오기 → 필요한 입력과 담당 관계 파악 → 업무별 실행 가능 판단 → 담당자의 기존 에이전트 실행 → 결과로 기존 업무 연결 또는 후속 업무 생성 → 배정·실행 판단을 반복한다. 사람의 결정·승인·권한·의견 조율이 필요하면 해당 업무가 기다리고, 응답 후 재평가한다. 독립 업무는 계속 진행한다.

### 요구사항

- 목록은 직접 등록·외부 도구에서 가져온 업무와 결과에서 생성한 업무를 함께 보여준다. 출처와 원인이 된 업무·결과를 추적할 수 있어야 한다.
- 목표·역할·담당자·작업 대상·필요 자료·완료 기준을 파악한다. 알려진 정보는 재사용하고 자동 추정으로 확정할 수 없는 필수 정보만 요청한다.
- 담당자와 실행 Agent를 구분한다. 조직의 담당 관계와 사용 가능한 Agent·위임 범위를 대조해 배정하며, 모호하면 이유와 필요한 선택을 표시한다.
- 자동 실행 조건은 필요한 입력·의존 관계·권한·위임·실행 환경의 충족이다. 선행 업무가 없다는 이유만으로 수동 실행을 강제하지 않는다. 사용자가 직접 실행으로 설정한 업무는 자동 착수하지 않는다.
- 사람 대기는 필요한 결정·정보·권한, 응답할 사람, 해결 후 재개할 업무를 보여준다. 입력 변경이나 응답 후 현재 조건을 재평가하고, 무관한 업무를 멈추지 않는다.
- 결과는 산출물·검증 근거·남은 문제·필요한 후속 작업 정보를 포함한다. 적합한 기존 업무에는 입력을 연결하고, 없으면 허용된 범위에서 새 업무를 생성한다. 근거 없는 담당자 지정이나 범위 확장은 보류한다.
- 결과 제출, 형식 검증, 품질 검증, 사람 승인을 구분한다. 승인 전 가능한 후속 검토와 승인 후 가능한 외부 반영을 구분한다. 필요한 승인이 해결되기 전에는 해당 작업을 실행하지 않는다.
- 동일 입력 이벤트·결과 재처리·응답 재전송으로 업무나 실행을 중복 생성하지 않는다. 반복적인 후속 업무 생성에는 중단·확인 기준을 둔다. 구체적 정책은 기술 설계에서 정한다.

### 첫 수용 시나리오와 기대 결과

아래는 테스트 설계를 위한 구체적인 검증 사례이며 특정 기업의 실제 업무 기록이 아니다. 실행 가능한 Agent와 필요한 자원을 준비하고, 독립적인 자동 실행 업무 A·B 및 정보 대기 C·권한 대기 D·의견 조율 대기 E를 등록한다.

| 단계 | 수용 기준 |
|---|---|
| 5개 업무 접수 | 목록에 5개가 보이고 입력·담당자·실행 여부와 이유를 확인할 수 있음 |
| 최초 실행 판단 | A·B만 추가 실행 조작 없이 착수. C·D·E는 각 대기 이유와 응답할 사람을 표시. 자원 충돌이 없는 A·B를 서로의 완료 대기로 묶지 않음 |
| A 결과로 기존 업무 진행 | A의 결과가 C의 부족한 입력을 충족하면 기존 C에 결과 버전을 연결하고 다른 조건을 평가해 착수. C를 복제하지 않음 |
| B 결과로 새 업무 생성 | 기존 대응 업무가 없는 후속 F를 생성하고 생성 근거·담당자·입력을 표시. 위임 범위와 조건이 충족되면 담당 Agent가 착수 |
| 권한·조율 해결 | D·E는 필요한 권한 확인·사람 응답이 있기 전 착수하지 않음. 해결 후 조건을 재평가해 자동 착수하며 원래 업무를 다시 등록할 필요가 없음 |
| 모호한 후속 제안 | 담당자·대상·필수 자료가 불명확하거나 위임 밖인 제안은 임의 실행하지 않고 필요한 확인을 표시 |
| 재전송·재시작 | 같은 원인 이벤트·결과를 다시 처리해도 F와 각 Execution은 중복 생성되지 않음. 대기와 처리 근거가 보존됨 |
| 결과 확인 | 모델의 성공 문장과 실제 검증 근거를 구분하고, 승인 없는 외부 반영을 완료로 표시하지 않음 |

단위·통합 테스트에서는 대역으로 위 조건을 검증한다. 제품 효과는 실제 외부 업무 입력과 실제 Agent를 이용한 전체 순환에서 별도로 확인한다. 유료 호출은 기존 키·예산 확인 규칙을 따른다. 인계 대기 시간, 사람 중계 횟수, 재작업률, 전체 처리 시간을 수동 처리와 비교하며 초기 설정 비용은 분리한다. 절감 목표 수치는 기준 측정 후 정한다.

### 현재 구현과의 차이

`service`는 사전 등록한 체인과 단일 선행 관계, 능력·범위 기반 Agent 선택, 등록 규칙에 따른 인계, n8n 입구·사람 차례 callback을 지원한다. GitHub·Jira 가져오기는 fixture다. phase 8 브랜치(미병합)가 아래 GitHub 한 유형에 한해 실제 수집·새 검토 Task 생성·사람 요청·응답을 구현했고 대역으로만 검증했다. 새 업무 생성, 일반적인 조직 담당 관계, 사람 요청·응답, 위 수용 시나리오 전체는 미구현이다. 이 차이를 단순 문서 갱신으로 구현 완료 처리하지 않는다.

| 업무 | GitHub 사례 | 기대 결과 |

| A | 담당자 1명(연결됨), 재현 정보 있는 버그 | 추가 조작 없이 `bug_fix` 착수. 결과가 기존 C 의 입력을 채움 |

| D | 위임 밖 — 허용 저장소·능력 범위 밖 | `delegation_denied` 대기. 운영자가 설정을 바꾸기 전 착수하지 않음 |
| E | 담당자 2명 — 누구 Agent 로 할지 결정 필요 | `assignee_multiple` + 사람 요청. 응답 후 재평가해 착수, 이슈 재등록 없음 |

반드시 대역 테스트로 확인할 경계 사례:

| 사례 | 기대 결과 |
|---|---|
| 담당자 없음 / 연결 없는 담당자 | `assignee_missing` / `assignee_unbound` 대기, 자동 추정 없음 |
| 검토 `approved` | 검토 Task 완료, 수정 Task 는 `확인 필요`(병합·이슈 종료는 사람). close·merge·push 없음 |
| 검토 `changes_requested` | 같은 수정 Task 의 다음 Execution, 새 결과 커밋을 다시 검토 |
| 검토 `needs_information` | 사람 요청, 응답 후 재평가 |
| 재작업 상한(기본 1회) 도달 | 더 돌리지 않고 `rework_limit_reached` 사람 요청 |
| 사람 응답 재전송·오래된 revision 응답 | 같은 `response_id` 는 한 번만 반영, revision 불일치 409 |
| 운영자 종료 / 원본 이슈 닫힘 | 종료는 `실패` 마감·새 후속 없음 / 닫힘은 새 착수 중지·재오픈 시 재평가, 진행 중 실행은 계속 |
| 실행 중 이슈 편집 | 실행 입력 불변, 새 스냅샷은 다음 revision |
| 같은 이슈·결과·응답 재수신, 워커 재시작 | Task·Execution·후속·댓글 중복 없음(중복 키 표) |
| 댓글 POST 응답 유실 | `반영 불확실` 표시, marker 조회로 조정, 확인 전 재POST 없음. 작업 실패와 별도 표시 |
| 구버전 연결 프로그램 | 새 종류 실행을 받지 않고 `executor_outdated` 대기 |
| 진단 데모·n8n | 기존 `code_change` 판정(`report_matches` 포함)·입구·callback 회귀 없음 |

## 위임 판단과 패턴 개선 — 2026-09-23 확정

연결이 허용된 서비스의 티켓·상태 변경·실행·결과 기록, 개인 작업 이력, 접근 가능한 LLM 메모리를 분석해 자동화 후보를 찾는다. 업무 식별자·시각·행동·담당 역할·입출력·결과를 가능한 범위에서 연결하고, 사실 기록과 메모리의 요약·선호·추정을 구분한다. 시각이나 결과가 없으면 작업 시간·성공 여부를 추정값으로 숨겨 채우지 않는다.

후보에는 시작 조건·입력·담당 역할·자동 행동·후속 조건·예외·완료 기준·근거 사례·관측 기간과 누락을 표시한다. 사용자는 왜 제안됐는지 확인하고 적용 범위를 정할 수 있다. 기존 위임 정책 안에서 자동 적용을 허용할 수 있으며 권한 확대는 별도 결정이다. 모델 가중치 학습이나 모든 개인 기록의 자동 수집은 요구하지 않는다.

| 검증 사례 | 수용 기준 |
|---|---|
| 반복과 예외를 포함한 이력 | 후보 패턴과 근거 사례를 연결하고 실패·재작업·예외를 숨기지 않음 |
| 중복·누락·상충 기록 | 중복 이벤트로 빈도를 부풀리지 않음. 근거가 부족하면 패턴·효과 판단의 한계를 표시 |
