# PRD 초안 — 기존 에이전트 등록과 업무 자동 실행

갱신일: 2026-09-20
상태: 검토용 v0.1. 제품 방향은 [제품 개요](product/PRODUCT_BRIEF.md)를 따른다. 사용자 합의와 assistant 제안을 항목별로 구분한다. 시연 업무는 합의했으며 세부 데이터·검증 설계는 제안이다. 아직 구현 지시가 아니다.

## 목표

기존 개인·팀·사내 에이전트를 업무에 연결해, 실행 가능한 작업이 사람의 전달·실행 조작을 기다리는 시간을 줄인다.

첫 검증 질문:

1. 사용자가 연결 코드를 작성하거나 기존 에이전트 설정을 다시 구성하지 않고 등록할 수 있는가?
2. 업무가 실행 가능해지면 연결된 에이전트가 사람의 추가 조작 없이 실제 작업을 시작하는가?
3. 선행 결과를 이용해 다음 에이전트가 업무를 이어받는가?

## 첫 사용자와 지원 범위 제안

기존 에이전트를 이미 사용하고 있으며 반복적인 업무 전달·착수가 있는 개인 또는 소규모 협업 팀을 검증 대상으로 제안한다. 특정 직무는 아직 확정하지 않았다.

| 구분 | 초안 범위 | 상태 |
|---|---|---|
| 실행 대상 | 로컬 Codex CLI + 사내 운영 진단 API 에이전트 | 사용자 합의. 사내 역할은 별도 데모 서비스로 재현. 로컬 도구는 Codex로 확정([ADR-0001](adr/0001-first-local-agent-codex.md)), Claude Code는 후속 |
| 업무 입력 | 서비스 내 간단한 업무 등록 | 사용자 선택. Jira 등 외부 업무 입력 연동은 첫 MVP 필수에서 제외 |
| 에이전트 연결 | 사용자 직접 선택 + 업무 내용에 따른 시스템 자동 선택 | 두 방식 모두 필요하다는 사용자 결정. 기본값은 자동 선택, 판단 규칙은 능력 코드·범위 일치(2절, 2026-09-20 확정) |
| 실행 방식 | 직접 실행 및 설정된 조건 충족 시 자동 실행 | 두 방식 모두 지원한다는 사용자 결정. 기본값은 선행 업무가 있으면 자동, 없으면 직접(2절, 2026-09-20 확정) |
| 완료 방식 | 업무별 자동 완료 또는 검토 후 완료 | 사용자 결정. 기본값은 검토 후 완료. 완료 기준은 종류별 템플릿 제안·사용자 수정(4절, 2026-09-20 확정) |
| 업무 순서 | 선행 작업 1개를 가진 A → B 흐름 | 복잡한 분기·병렬은 첫 검증 밖으로 제안 |
| 실행 맥락 | 현재 컴퓨터의 연결 프로그램이 지정한 폴더에서 기존 설정을 읽는 새 작업 실행 | 사용자 선택. 열린 대화 자동 승계는 포함하지 않음 |

개인·팀·사내는 소유 구분이고 CLI·API는 연결 방식이다. 소유 유형마다 별도 실행 엔진을 만들지 않는다.

사용자에게 실제 연결할 사내 에이전트는 없다. 이후 이종 에이전트 연결을 보여주기 위해 로컬 에이전트 1종과 사내 역할의 API 에이전트를 함께 구성하기로 합의했다. API 대상은 데모용 별도 서비스이며 실제 기업 시스템 연동으로 소개하지 않는다. 개인 환경만으로 시작한다는 이전 범위는 이 합의로 대체한다.

## 사용자 흐름과 기능

### 1. 기존 에이전트 등록

사용자는 다음 등록 흐름에 동의했다.

1. 사용 중인 Codex 또는 Claude Code의 실행 환경과 작업 폴더를 연결한다. 로컬 에이전트는 실행 도구 + 작업 폴더 하나를 에이전트 하나의 등록 단위로 삼는다. 같은 도구라도 작업 폴더가 다르면 별도로 등록할 수 있다. 이 등록 단위는 사용자 합의다.
2. 시스템이 사용자가 연결한 범위에서 설정·스킬·도구 정보를 확인하고 수행 가능한 업무 설명을 제안한다.
3. 사용자가 이름·개인/팀/사내 소유 구분·업무 설명을 확인하고 수정해 등록한다. 읽어오지 못한 정보는 직접 보충할 수 있다.

자동 파악한 정보는 능력에 대한 제안이며 모든 업무 수행을 보장하는 인증이 아니다. 실제로 읽을 수 있는 정보와 기존 설정의 활용 범위는 대상별 기술 검증이 필요하다. 첫 MVP는 현재 사용 중인 컴퓨터에 연결 프로그램을 두는 방식으로 사용자와 합의했다. 웹 서비스의 업무를 연결 프로그램이 받아 지정한 작업 폴더에서 기존 설정을 활용한 새 CLI 작업을 실행하고 상태·결과를 전달한다. 현재 열린 대화창에 메시지를 넣거나 대화를 그대로 이어가는 방식은 첫 연결 범위가 아니다. 컴퓨터가 꺼져 있거나 연결이 끊기면 새 업무는 대기하며 이유를 표시한다. 연결 통신·설치·인증 방식은 기술 설계에서 정한다. 사내 역할의 API 에이전트는 별도 데모 서비스로 구성한다. API 대상은 주소·인증·능력 정보로 등록하는 방안을 제안하며 로컬 작업 폴더를 필수로 요구하지 않는다. 정확한 인터페이스와 프로토콜은 기술 설계에서 정한다.

- 연결 확인 후 사용 가능 여부를 표시한다.
- 기존 도구·프로젝트 설정의 재사용 범위를 명시한다.
- 소유자의 연결 허용 범위 안에서 업무를 실행한다.
- 외부 주소만 입력하면 모든 에이전트가 동작한다고 약속하지 않는다.

작업 폴더가 Git 저장소이면 이후 업무와 변경 내역·브랜치·커밋을 연결할 기준으로 활용할 수 있다. 사용자는 이 후속 연동 가능성을 언급했다. Git 저장소를 등록 필수 조건으로 삼거나 GitHub·GitLab 인증, 커밋·푸시·PR 생성을 첫 MVP에 포함하기로 결정한 것은 아니다. 같은 폴더에 여러 작업이 실행될 때의 충돌 처리는 기술 설계에서 정한다.

### Git 작업의 실행 환경 — 논의 방향과 제안

사용자는 같은 저장소의 업무를 일괄 순차 실행하는 제안에 대해 worktree 활용을 제안했다. Git 코드 작업은 worktree로 작업 환경을 분리하는 방향을 검토한다. 구체적인 생명주기는 아래 assistant 제안이며 일괄 확정하지 않는다.

- 등록한 폴더는 기준 저장소로 두고 독립적인 코드 업무별로 작업 브랜치와 worktree를 만든다. 에이전트 하나당 worktree 하나로 고정하지 않는다.
- 같은 업무의 수정·재실행은 해당 worktree를 유지하는 방향이다. 독립 업무는 병렬 실행할 수 있고, 선행 업무가 필요한 작업은 조건 충족을 기다린다.
- 읽기 전용 작업이나 Git이 아닌 폴더에 worktree를 필수로 요구하지 않는다. 그 밖의 동시 수정 정책은 미결이다.
- 기존 환경의 미추적 설정·환경 파일·상대 경로 도구가 새 worktree에서 어떻게 동작할지 기술 검증한다. 설정 전체를 무조건 복사하지 않는다.
- 업무 완료, 변경 결과의 보존, 기준 브랜치 병합, worktree 제거는 구분한다. 기준 브랜치 병합은 사용자 확인 후 진행한다는 데 합의했다. 결과 버전의 보존 방법과 커밋·푸시·worktree 정리 정책은 기술 설계에서 구체화한다.

사용자는 다음 인계 순서에 동의했다.

1. A가 선택한 완료 방식의 기준을 충족하면 결과 버전을 보존한다.
2. A의 코드 결과가 필요한 B는 보존된 A의 결과 버전에서 별도 worktree로 시작한다. B의 실행 방식이 직접 실행이면 사용자 조작을 기다린다.
3. 작업 요약·검증 결과·남은 사항도 함께 전달한다.
4. 후속 작업 결과를 확인한 뒤 기준 브랜치 병합은 사용자 확인 후 진행한다. 중간 단계마다 기준 브랜치에 병합할 필요는 없다.

자동 완료·자동 실행은 기준 브랜치의 무승인 병합을 뜻하지 않는다. worktree 분리를 병합 충돌 해결로 설명하지 않는다. 결과 버전을 어떻게 고정하고 서로 다른 실행 환경으로 전달할지는 기술 설계에서 검증한다.

### 2. 업무 등록과 연결

첫 업무 입력은 서비스 안의 간단한 등록 화면으로 제공한다. Jira 등 외부 업무 도구 연동은 첫 MVP 필수 범위에 넣지 않는다. 전체 업무 관리 도구를 재구현하는 범위는 아니다.

최소 입력 항목 제안:

- 제목과 요청 내용: 무엇을 수행할지 작성한다. 결과물·완료 기준은 요청 내용에 함께 적을 수 있게 한다.
- 에이전트 선택 방식: 직접 선택 또는 자동 선택. 직접 선택에서는 등록된 에이전트를 지정하고, 자동 선택에서는 시스템이 업무 내용을 바탕으로 실행 대상을 정한다.
- 실행 방식: 직접 실행 또는 자동 실행. 선행 작업이 있으면 완료 전에는 자동 실행하지 않는다.
- 완료 기준: 시스템이 업무 내용에서 제안하고 사용자가 등록할 때 수정할 수 있다.
- 완료 방식: 자동 완료 또는 검토 후 완료를 업무별로 선택한다.
- 선행 업무: 선택 항목. A → B 인계를 검증할 때 사용한다.

사용자는 직접 선택과 업무 내용에 따른 자동 선택이 모두 필요하다고 확인했다. 담당자·우선순위·마감일 등의 추가 필드를 필수로 만들지 않는 것은 assistant 제안이다.

사용자는 직접 실행과 자동 실행을 모두 지원해야 한다고 확인했다. 둘 중 하나만 제품에 채택하는 선택지가 아니다. 업무별 실행 방식 선택 UI는 제안이다.

에이전트 선택 방식과 실행 시점은 별개다. 직접 고른 에이전트도 조건 충족 시 자동 실행할 수 있고, 시스템이 고른 에이전트도 사용자가 실행 버튼을 누를 때까지 기다릴 수 있다.

기본값 — 2026-09-20 사용자 확정. 업무별로 바꿀 수 있다.

- 선택 방식: 자동 선택. 등록 화면에서 직접 선택으로 전환한다.
- 실행 방식: 선행 업무가 있으면 자동 실행, 없으면 직접 실행. 착수 대기는 선행 완료 뒤 후속 착수에서 생기므로 후속 업무는 자동이 기본이고, 흐름의 첫 업무는 사람이 시작한다.
- 완료 방식: 검토 후 완료. 자동 완료는 자동 판정기가 있는 업무 종류에서만 선택할 수 있다. 첫 구현에서는 진단 업무의 `response_path_changed` 판정만 해당한다.

자동 선택의 동작 — 확인 절차는 합의, 비교 기준은 제안:

- 사용자가 연결해 사용을 허용한 에이전트 중에서 선택한다.
- 업무 요청 내용과 각 에이전트의 수행 가능 업무·사용 가능한 도구·작업 환경을 비교한다. Codex·Claude Code라는 제품명만으로 역할을 단정하지 않는다.
- 선택한 대상과 이유를 표시·기록한다. 직접 실행 업무는 사용자가 대상을 변경하거나 실행할 때까지 기다린다. 자동 실행 업무는 실행 조건이 충족되면 별도 승인 없이 시작한다. 이 확인 절차는 사용자 합의다.
- 적합한 대상이 없거나 결정에 필요한 정보가 부족하면 이유를 표시하고 선택 또는 정보 보완을 요청한다. 임의 대상에 실행하지 않는다.

적합한 대상을 정할 수 없을 때는 실행을 보류하고 필요한 정보 또는 사용자 선택을 요청한다. 이 예외 처리도 사용자 합의다. 에이전트 자동 선택이 새 에이전트 생성이나 기존 설정 변경을 뜻하지는 않는다.

첫 구현의 판단 규칙 — 2026-09-20 사용자 확정:

- 업무는 요구 능력 하나(`required_capability`: 능력 코드 + 범위)를 가진다. 에이전트는 등록 능력 목록(`capabilities`)을 가진다. 필드 구조는 [ARCHITECTURE](ARCHITECTURE.md)의 등록·선택·권한 절을 따른다.
- 사용을 허용한 에이전트 중 능력 코드와 범위가 모두 일치하는 후보를 센다. 정확히 1개면 그 대상을 선택하고 일치한 항목을 이유로 표시한다. 0개면 "적합한 에이전트 없음", 2개 이상이면 "후보 N개 — 선택 필요"로 확인 필요에 둔다. 우선순위·최근 사용·모델 판단으로 후보를 줄이지 않는다.
- 첫 구현의 능력 코드는 `operations.diagnose`(범위: `workflow_id`)와 `code.modify`(범위: `repository_id`) 둘이다. 범용 선택 알고리즘은 만들지 않으며, 중앙 서비스는 이 비교에 LLM을 쓰지 않는다([ADR-0004](adr/0004-central-service-rule-based-no-llm.md)).

### 3. 실행과 관찰

선행 조건을 충족한 업무에 실행 요청을 전달한다. 접수와 실제 시작을 구분해 기록한다. 실행 결과와 산출물을 업무에 연결한다.

| 사용자에게 보일 상태 | 의미 |
|---|---|
| 대기 | 선행 작업·연결·실행 환경 등 필요한 조건을 기다림. 이유 표시 |
| 실행 요청됨 | 요청을 전달했으나 실제 시작은 아직 확인하지 못함 |
| 실행 중 | 실행 환경에서 시작을 확인함 |
| 확인 필요 | 추가 입력·판단이 필요하거나 완료 기준 충족을 확인할 수 없음 |
| 완료 | 정해진 완료 기준을 만족한 결과를 확인함 |
| 실패 | 실행 실패와 이유를 확인함 |

프로세스 종료만으로 업무 완료를 판정하지 않는다. 내부 실행 상태(`Execution`, [ARCHITECTURE](ARCHITECTURE.md) 참고)와 완료 방식에 따른 사용자 상태 대응은 다음과 같다 — 2026-09-20 사용자 확정. `대기`는 시스템이 조건을 기다리는 상태, `확인 필요`는 사람의 행동이 필요한 상태다.

| 상황 | 사용자 상태 | 표시할 이유·동작 |
|---|---|---|
| 활성 실행 없음. 선행 업무 미완료 또는 연결 프로그램 오프라인 | 대기 | 선행 대기 / 연결 끊김과 마지막 확인 시각 |
| 활성 실행 없음. 자동 선택 후보 0개 또는 2개 이상 | 확인 필요 | 후보 없음 / 후보 N개 — 에이전트 선택 요청 |
| 활성 실행 없음. 직접 실행 조건 충족, 사용자 조작 전 | 실행 가능 | 선택된 대상·이유와 실행 버튼 |
| Execution `queued`, `accepted` | 실행 요청됨 | 접수 여부 |
| Execution `running` | 실행 중 | 마지막 진행 메시지 |
| `result_ready`, 자동 완료, 판정 통과 | 완료 | 판정 근거 |
| `result_ready`, 자동 완료, 판정 불가 또는 미충족 | 확인 필요 | 미충족 항목 — 승인·수정 요청·종료 |
| `result_ready`, 검토 후 완료 | 확인 필요 | 검토 대기 — 승인·수정 요청·종료 |
| `failed`, 프로세스 종료 확인 | 실패 | 실패 코드·메시지 |
| `failed` 종료 미확인 또는 `unknown` | 확인 필요 | 시작 여부 불명 — 재실행하지 않음 |

`실행 가능`은 직접 실행 업무가 사용자 조작을 기다리는 상태로, 위 6개 상태에 추가한다.

### 4. 완료 처리와 후속 업무 시작

사용자는 업무별로 다음 두 완료 방식을 선택하는 안에 동의했다.

- 자동 완료: 정해둔 완료 기준을 충족한 결과를 확인하면 완료 처리한다.
- 검토 후 완료: 에이전트 결과가 나와도 검토를 기다리며, 사람이 확인하고 완료 처리해야 완료된다.

사용자는 업무 내용을 바탕으로 시스템이 완료 기준을 먼저 제안하고, 등록 시 사용자가 수정할 수 있는 방식에 동의했다. 실행 후 결과를 기준과 비교하며 충족 여부를 판단할 수 없으면 ‘확인 필요’로 둔다. 에이전트의 종료 또는 ‘완료했다’는 응답만으로 기준 충족을 보장하지 않는다.

완료 기준의 제안과 수정 — 2026-09-20 사용자 확정:

- 시스템은 업무 종류별 템플릿에서 완료 기준을 제안한다. 진단 업무는 "결과가 `ready_for_handoff`이고 근거 검증을 통과함", 코드 수정 업무는 "등록된 검증 프로필이 결과 커밋에서 통과하고 결과가 보존됨"이다.
- 사용자는 등록 화면에서 문구를 수정하고 항목을 추가할 수 있다. 자동 판정에는 구조화된 항목만 사용하고, 사용자가 추가한 자유 텍스트는 검토자에게 표시한다.
- 중앙 서비스는 제안에 LLM을 쓰지 않는다([ADR-0004](adr/0004-central-service-rule-based-no-llm.md)).

검토 동작 — 2026-09-20 사용자 확정. 검토 후 완료 업무의 결과가 나오거나 자동 완료 업무가 판정 불가로 확인 필요가 되면 검토자는 다음 중 하나를 고른다.

- 완료 승인: 업무를 완료 처리한다. 후속 업무의 선행 조건이 충족된다.
- 수정 요청: 검토 의견을 적고 같은 업무의 새 시도를 만든다. 이전 결과 산출물과 검토 의견을 새 시도의 입력에 포함하고, 코드 업무는 같은 worktree·같은 작업 브랜치를 이어서 사용한다. 이전 시도는 종결 처리한다. 새 업무를 만들지 않는다.
- 종료: 업무를 실패(검토 거절)로 마감한다. 후속 업무는 시작하지 않는다.


A가 선택한 완료 방식에 따라 완료되고 B의 입력·연결·실행 조건이 충족되면 A의 필요한 결과를 B에 전달한다. B가 자동 실행이면 추가 실행 조작 없이 시작하고, 직접 실행이면 실행 가능한 상태로 사용자 조작을 기다린다.

실패·접수만으로 후속 작업을 실행하지 않는다. 실행 환경이 오프라인이면 시작했다고 표시하지 않는다. 중복 완료 이벤트가 같은 업무를 중복 실행시키지 않아야 한다. 복구·재시도 정책의 구체적인 설계는 후속 문서에서 정한다.

| 에이전트 | 정보·도구 | 역할과 결과 |
|---|---|---|
| 사내 운영 진단 API 에이전트 | 가상의 내부 실행 이력·오류 로그·운영 문서를 조회하는 도구 | 실패 원인·근거·수정할 대상을 정리 |

시연은 서비스 내 업무 등록에서 시작한다. n8n의 실패 이벤트 실연동까지 필수로 추가한 것은 아니다. 실제 n8n 워크플로우를 준비할지는 별도 결정하며, 재현 데이터는 실제 운영 데이터로 표시하지 않는다.

### 시연 흐름

1. API 에이전트와 로컬 에이전트의 등록을 보여준다. 서로 다른 기능·정보 접근 범위와 연결 상태를 확인한다. (카탈로그 등록 — `/agents/register`)
2. 실패 진단 업무 A와 그 결과를 사용하는 수정 업무 B를 등록한다. 두 업무는 미리 채운 예시로 제안하며 목표 자동 분해를 구현한 것으로 표시하지 않는다. (GitHub·Jira fixture 가져오기 — `/tasks/import`. 직접 등록 `/tasks/new?example=…` 도 남아 있다)
3. 자동 선택으로 A에 운영 진단 에이전트, B에 개발 에이전트를 연결하고 이유를 표시한다. 직접 선택도 제품에서 지원한다.
4. A가 자기 조회 도구로 실패 기록·과거 정상 기록·운영 문서를 확인해 근거가 있는 진단을 작성한다.
5. A의 완료 기준을 충족하면 B가 진단 결과를 받아 로컬 worktree에서 자동 착수한다. 결과 복사와 별도 실행 지시를 요구하지 않는다.
6. B가 오류 재현 테스트를 먼저 작성하고 실패를 확인한 뒤 수정한다. 테스트 결과·변경 내역을 제출하고 사람이 검토한다.
7. 기준 브랜치 병합은 사용자 확인 후 진행한다. 데모에서 이 확인은 운영자 전용이며 심사자 세션에는 "운영자 확인 대기"로 표시한다(ADR-0005). 실제 운영 환경 배포는 이 시연 범위로 합의하지 않았다.

A는 코드 변경을 하지 않으므로 A에서 코드 worktree를 만들거나 A의 코드 커밋을 B에 넘길 필요가 없다. A → B는 진단 근거의 인계다. 코드 업무끼리 연결할 때는 앞서 합의한 결과 버전·worktree 인계 규칙을 적용한다.

### 데모 데이터와 검증 상세 — assistant 제안

아래 필드·수치·시각·식별자는 검토용 가상 데이터다. 실제 실행 로그나 사용자 확정 스키마가 아니다. 저장소 언어는 미결이며, 이번에는 데이터와 기대 동작만 제안한다.

#### 사건과 입력 계약

가상의 외부 업무 집계 API에서 전날의 팀별 완료·미완료 건수를 받아 일일 보고서를 만든다. 매일 09:00(Asia/Seoul)에 실행하며, `report_date`는 집계 대상 날짜다. 각 행의 `completed`와 `pending`은 해당 날짜의 0 이상 정수 건수다. 데모 응답은 전체 팀을 한 번에 반환하고 페이지 나눔은 없다.

변경은 목록 위치가 최상위 `items`에서 `data.records`로 이동하는 한 가지다. 날짜·팀·건수의 의미와 자료형은 같다. 기존 변환기는 `items`만 읽으므로 HTTP 요청은 성공해도 보고서 생성은 실패한다. 두 형식을 함께 지원하는 작은 수정으로 원인과 해결을 명확히 보여준다.

과거 정상 응답 `response-before` — 2026-09-19 09:00에 수집, HTTP 200:

```json
{
  "report_date": "2026-09-18",
  "items": [
    { "team": "운영", "completed": 12, "pending": 3 },
    { "team": "개발", "completed": 8, "pending": 2 }
  ]
}
```

변경 응답 `response-after` — 2026-09-20 09:00에 수집, HTTP 200:

```json
{
  "report_date": "2026-09-19",
  "data": {
    "records": [
      { "team": "운영", "completed": 12, "pending": 3 },
      { "team": "개발", "completed": 8, "pending": 2 }
    ]
  }
}
```

두 날짜의 건수는 비교 편의를 위해 같게 잡았다. 형식 간 동등성 테스트에서는 같은 날짜와 같은 행을 두 형식으로 감싸 결과를 비교한다. 과거 실행 결과와 실패일 복구 결과의 날짜까지 같아야 한다는 뜻은 아니다.

#### 실행 이력과 실패 로그

아래는 일일 보고서 자동화의 실행 이력이다. 이를 조사하는 A·B 업무의 실행 이력과 구분한다. `report-base`는 수정 전 코드 버전의 가상 식별자이며, 구현 시 실제 버전 식별자로 대체한다.

| 실행 ID | 실행 시각(Asia/Seoul) | 코드 버전 | 응답 참조 | 단계별 결과 | 보고서 |
|---|---|---|---|---|---|
| `daily-0919-0900` | 2026-09-19 09:00 | `report-base` | `response-before` | 조회 성공 → 변환 성공 → 생성 성공 | 2026-09-18 보고서, 완료 20·미완료 5 |
| `daily-0920-0900` | 2026-09-20 09:00 | `report-base` | `response-after` | 조회 성공 → 변환 실패 → 생성 미실행 | 없음 |

`log-daily-0920`의 예상 내용은 다음과 같다. `MISSING_RECORDS_FIELD`는 언어에 종속되지 않는 제안 오류 코드다. 실제 런타임 예외·스택은 구현 후 재현 실행에서 수집하며, 아래 예시를 실제 실행 증거로 사용하지 않는다.

```text
2026-09-20T09:00:00+09:00 INFO  run_id=daily-0920-0900 stage=fetch event=response_received http_status=200 response_ref=response-after
2026-09-20T09:00:01+09:00 ERROR run_id=daily-0920-0900 stage=transform component=report_transformer code=MISSING_RECORDS_FIELD expected_path=$.items observed_root_keys=[report_date,data] response_ref=response-after
2026-09-20T09:00:01+09:00 INFO  run_id=daily-0920-0900 stage=render status=skipped reason=transform_failed
2026-09-20T09:00:01+09:00 ERROR run_id=daily-0920-0900 event=run_finished status=failed report_created=false
```

로그만으로 `data.records`가 정답이라고 단정하지 않는다. 응답 본문과 아래 변경 안내를 함께 확인해야 한다. 동일 코드 버전에서 정상·실패가 갈리고, 실패 실행의 HTTP 200과 변환 오류가 구분되는 것이 핵심 증거다.

| `daily-report-runbook@1` | 09:00 실행, 전날 집계, 조회 → `report_transformer` → 보고서 생성 순서. 변환기는 `items`를 읽음. 실패 시 해당 날짜 보고서를 생성하지 않음. 수정 대상은 등록된 데모 저장소의 응답 변환부 | 실패 단계와 코드 조사 위치. 실제 파일 경로는 저장소 설계 후 기입 |
| `upstream-response-change@1` | 가상 API 제공자의 안내. 2026-09-20 00:00+09:00부터 목록 위치를 `items` → `data.records`로 변경. 행 필드·의미·자료형과 `report_date`는 유지 | 실행 시각에 적용되는 형식과 새 경로의 의미 |
| `daily-report-contract@1` | 날짜, 팀별 완료·미완료, 합계가 필수. 입력 행 순서 유지. 과거 저장 응답 재처리를 위해 두 형식을 지원. 명시적 빈 배열은 0건, 누락된 목록은 오류 | 하위 호환이 필요한 이유와 수정 후 결과 판정 기준 |

#### 기대 수정 결과와 보고서

B는 실제 데모 저장소에서 응답 변환부를 확인하고, 실패 응답을 넣는 재현 테스트를 먼저 작성한다. 수정 전 실패를 확인한 뒤 두 경로를 지원하도록 최소 수정한다. 보고서 계산·표시 규칙은 유지한다.

변경 응답을 수정된 코드로 재처리하면 다음 보고서가 생성되어야 한다.

```text
일일 업무 보고서 — 2026-09-19

팀      완료  미완료
운영    12    3
개발    8     2
합계    20    5
```

완료 판정은 공백 정렬보다 날짜·행·건수·합계의 정확성을 기준으로 한다. 기존 정상 응답도 2026-09-18 날짜와 같은 집계값으로 처리되어야 한다. 지원하는 두 경로 중 정확히 하나에 배열이 있어야 하며, 목록 누락·배열이 아닌 값·두 경로가 동시에 있는 모호한 응답은 오류로 처리하는 계약을 제안한다. 명시적 빈 배열만 정상 0건으로 처리하며, 오류를 빈 목록으로 바꿔 성공시키지 않는다.

| 검증 입력·상황 | 기대 결과 |
|---|---|
| 수정 전 코드 + `response-after` | 변환 실패 재현, 해당 날짜 보고서 없음 |
| 수정 후 코드 + `response-after` | 2026-09-19 보고서 생성, 팀별 값과 합계 20·5 일치 |
| 수정 후 코드 + `response-before` | 2026-09-18 보고서 정상 생성, 기존 동작 유지 |
| 같은 날짜·행을 구형/신형으로 각각 표현 | 동일한 보고서 내용 |
| 각 형식의 명시적 빈 배열 | 해당 날짜의 팀 행 없는 보고서, 합계 0·0 |
| 목록 누락, 목록이 배열이 아님, 두 경로 동시 존재 | 변환 실패, 해당 실행에서 보고서 생성 안 됨 |
| 행의 완료 건수를 12 → 13으로 바꾼 유효 응답 | 해당 팀 완료 13·합계 완료 21로 변경되어 고정 보고서 출력이 아님을 확인 |

B의 제출물은 수정 diff, 수정 전 실패·수정 후 통과한 테스트 실행 기록, 변경 응답으로 실제 생성한 보고서, 작업한 코드 버전이다. 재처리는 로컬 검증이며 운영 복구·배포 완료로 표시하지 않는다. 사람이 검토하기 전 B를 완료 처리하지 않는 시연 설정을 제안한다.

#### A의 진단 결과와 B 착수 조건

A는 `daily-0920-0900`을 조사 대상으로 받아 자기 조회 도구로 기록을 읽고 아래 내용을 도출한다. 다음은 기대 진단 내용이며 반환할 고정 답변이 아니다. 논리적 입출력은 다음 절에 제안하며, 전송 프로토콜은 후속 기술 설계에서 정한다.

- 원인: 외부 응답의 목록 위치 변경을 기존 변환기가 지원하지 않아 보고서 변환 실패.
- 근거: `daily-0919-0900`·`daily-0920-0900`의 같은 코드 버전, `response-before`·`response-after`의 경로 차이, `log-daily-0920`의 HTTP 200 이후 변환 실패, `upstream-response-change@1`의 적용 시각과 새 경로.
- 수정 대상: 등록된 데모 저장소의 `report_transformer` 역할을 하는 응답 변환부. A의 경로 제안은 B가 실제 코드에서 확인한다.
- 기대 동작: `daily-report-contract@1`에 따라 두 형식을 처리하고 변경일 보고서의 합계가 완료 20·미완료 5가 됨.
- 인계 자료: 실행 ID, 근거 ID·버전과 관련 발췌, 두 응답 예시, 오류 로그, 기대 보고서·검증 항목. 개인 에이전트에 운영 시스템 전체 접근 권한을 자동 부여하지 않는다.

A의 자동 완료는 위 근거를 실제로 조회했고, 적용 대상과 원인·수정 요구 사이에 모순이 없으며 B가 재현할 입력을 받는 경우로 제안한다. 에이전트가 스스로 완료라고 말한 것만으로 통과시키지 않는다. 아래에 데모에 한정한 확인 규칙을 제안하며, 범용 완료 검증기는 후속 설계 대상이다.

실패 응답 본문이나 변경 안내를 제공하지 않는 비교 사례에서는 “형식 변경 가능성이 있으나 새 입력 계약 확인 필요”로 표시하고 부족한 자료를 명시한다. A는 확인 필요 상태로 남고 B는 시작하지 않는다. 입력 기록이 달라졌는데도 같은 확정 진단을 내놓으면 수용 기준 실패다.

별도 API 에이전트는 등록 대상의 예시다. 플랫폼이 모든 사내 에이전트를 대신 생성해야 한다는 요구가 아니다. 등록 이후 자동화 기능과 데모 대상 제작의 범위를 구분한다.

심사자는 로그인 없이 접속하며 자기 기기에 연결 프로그램을 설치하지 않는다([ADR-0000](adr/0000-principles.md) 공모전 제약). 운영자가 준비한 컴퓨터의 연결 프로그램과 진단 API를 미리 등록해 두고, 심사자는 익명 세션에서 등록 목록을 읽기 전용으로 보며 업무 등록·실행·검토를 체험한다([ADR-0005](adr/0005-access-model-anonymous-session-operator-token.md)). 등록 절차 자체는 실연 또는 기록 영상으로 증명한다.

### 진단 조회 도구와 A → B 인계 — assistant 제안

이 절은 위 데모 데이터에 대한 논리적 계약이다. HTTP 경로·MCP·A2A·구현 언어를 확정하지 않는다. 도구는 사실 자료를 반환하고, A는 조회 결과를 비교해 진단을 작성한다. 업무 상태 전환과 B 실행은 웹 서비스가 담당한다.

#### A에 전달할 조사 요청

```json
{
  "task_id": "diagnose-daily-0920",
  "run_id": "daily-0920-0900",
  "request": "일일 보고서 생성 실패를 조사하고, 로컬 개발 에이전트가 재현·수정할 수 있도록 근거와 기대 동작을 정리해 주세요."
}
```

`task_id`는 제품의 진단 업무 ID이고 `run_id`는 조사할 보고서 실행 ID다. 실패 원인이나 새 응답 경로는 요청에 미리 넣지 않는다. 허용된 조회 범위는 등록된 API 연결의 권한에서 정하며, 요청 본문의 ID만으로 다른 범위의 자료 접근을 허용하지 않는다.

#### 읽기 전용 조회 도구 4개

| 도구 | 입력 | 반환할 사실 자료 |
|---|---|---|
| `get_run` | `run_id` | 실행 ID, `workflow_id`, 시작·종료 시각, 상태, 코드 버전, HTTP 상태, 응답·로그·보고서 자료 참조 |
| `list_runs` | `workflow_id`, `before`, `status`, `limit` | 지정 시각 이전의 해당 자동화 실행 목록. 최신순이며 실행 ID·시각·상태·코드 버전 반환. 상세는 `get_run`으로 조회 |
| `list_documents` | `workflow_id` | 관련 문서 ID·버전·제목·적용 시각. 데모의 소수 문서를 열거하며 검색 인프라는 필수로 두지 않음 |
| `read_evidence` | `evidence_id`, `version` | 해당 버전의 실행 기록·응답 JSON·로그·문서·보고서 본문과 출처 메타데이터 |

`get_run`이 반환한 실행 기록에도 근거 ID·버전을 붙인다. 예를 들어 실행 `daily-0920-0900`의 `workflow_id`는 `daily-report`이고 응답 참조는 `response-after@1`, 로그 참조는 `log-daily-0920@1`이다. 이전 절의 실행 이력·응답·로그는 모두 최초 데모 자료 버전 `1`로 제안한다. 자료 버전은 실행 코드 버전 `report-base`와 별개다.

조회 성공 결과에는 `evidence_id`, `version`, `content_type`, `content`를 포함한다. 응답 JSON은 구조를 유지하고, 로그·문서는 줄 번호로 발췌 위치를 지정할 수 있게 한다. 시각은 실행 기록의 실행 시각과 문서의 적용 시각을 구분한다. 원본 전체를 모델의 진단 문장으로 대체하지 않는다.

조회 계층은 호출 ID·입력·성공 여부·실제로 반환한 근거 ID와 버전을 기록한다. 이 기록은 A가 작성한 인용 목록과 별도로 보존해, 읽지 않은 자료를 인용했는지 확인하는 데 사용한다.

목록 결과가 없으면 빈 목록을 반환한다. 개별 자료 조회의 실패는 `not_found`, `access_denied`, `unavailable`로 구분한다. 접근 불가나 조회 오류를 빈 본문으로 바꾸지 않는다. 필요한 자료가 없으면 A는 확인 필요 결과를 작성하고, API 자체가 결과를 반환하지 못한 실행 오류는 제품에서 실패로 표시한다.

예상 조사 순서는 실패 실행 조회 → 동일 자동화의 직전 정상 실행 조회 → 두 응답과 실패 로그 확인 → 관련 문서 목록·본문 확인이다. 도구 호출 순서를 하드코딩한 진단 답변으로 대체하지 않는다.

#### 진단 결과 형식

| 필드 | 의미·제약 |
|---|---|
| `task_id`, `run_id` | 입력 요청과 일치해야 함 |
| `outcome` | `ready_for_handoff` 또는 `needs_information`. 제품의 완료 상태와 구분 |
| `summary` | 사람이 읽을 진단 요약. 불확실하면 가설로 표현 |
| `findings` | `claim`과 이를 뒷받침하는 `evidence_refs` 목록. 참조마다 근거 ID·버전·위치 포함 |
| `diagnosis` | 자동 검증할 구조화 원인. 데모는 `response_path_changed`와 이전/이후 경로·정상/실패 실행·문서 참조를 사용. 확인 필요이면 null |
| `repair_request` | 수정 대상 역할, 변경 요구, 기존 동작 유지 조건, 검증 항목. 자료 부족 시 `null` 가능 |
| `missing_information` | 부족한 자료와 필요한 이유. 인계 가능 결과에서는 빈 배열 |
| `attachments` | 근거 ID·버전·산출물 참조·해시 목록과 실제 원문 파일을 같은 인계 묶음으로 전달. 서비스가 조회 기록에서 조립하며 인용 위치를 원문에서 확인할 수 있어야 함 |
| `provenance` | 진단 서비스가 기록한 모델·프롬프트·도구 계약 버전과 조회 이력 산출물 참조 |

전송 봉투의 `contract_version`, `execution_id`와 필드 타입·조건·DB 제약은 [아키텍처 계약 v1](ARCHITECTURE.md)에 있고, 요청·이벤트·결과·오류의 완전한 예시는 [CONTRACT.md](CONTRACT.md)에 있다. 아래 JSON은 핵심 내용 발췌이며 완전한 전송 예시가 아니다. 구조화 출력만으로 완료하지 않고 실제 근거 관계를 검사한다. 확인 필요 결과는 diagnosis·repair_request를 null로 두고 부족한 정보·충돌 사유를 하나 이상 기록한다.

인계 가능 결과의 핵심 필드 예시는 다음과 같다. 아래는 설명용 발췌이며, 실제 결과에는 정상 실행과 응답 비교·문서 적용 시각·보고서 계약에 관한 근거와 `attachments` 본문을 모두 포함해야 한다.

```json
{
  "task_id": "diagnose-daily-0920",
  "run_id": "daily-0920-0900",
  "outcome": "ready_for_handoff",
  "summary": "조회는 성공했으나, 목록 경로 변경을 지원하지 않는 변환부에서 보고서 생성이 중단되었습니다.",
  "findings": [
    {
      "claim": "실패 응답의 목록은 data.records에 있고 기존 변환기는 items를 요구합니다.",
      "evidence_refs": [
        { "evidence_id": "response-after", "version": "1", "location": "$.data.records" },
        { "evidence_id": "log-daily-0920", "version": "1", "location": "lines:2-3" }
      ]
    }
  ],
  "repair_request": {
    "target_component": "report_transformer",
    "change": "items와 data.records 중 하나에 있는 목록을 처리합니다.",
    "preserve": "날짜·행 순서·건수·합계와 과거 응답 재처리를 유지합니다.",
    "checks": ["변경 응답의 수정 전 실패 재현", "수정 후 완료 20·미완료 5", "구형 응답 회귀 및 입력 계약 경계 사례 통과"]
  },
  "missing_information": []
}
```

변경 안내를 읽을 수 없는 경우의 결과는 `outcome=needs_information`, `repair_request=null`로 둔다. 요약은 “응답 경로 차이는 확인했으나 새 경로의 의미와 적용 계약을 확인하지 못했습니다”로 작성하고, `missing_information`에 `upstream-response-change` 문서와 필요한 이유를 기록한다. 조회된 근거만 첨부하며 누락 문서를 읽었다고 인용하지 않는다. 이 시연에서는 변경 안내까지 있어야 인계하는 보수적인 완료 기준을 사용한다.

#### 완료 판정과 실제 인계

1. API 실행 결과를 받은 웹 서비스는 요청 ID 일치, 필수 필드, 근거 참조와 첨부의 일치, 실제 조회 기록에 해당 근거가 있는지 확인한다. 계약이 깨진 결과는 확인 필요로 표시하고 B를 시작하지 않는다.
2. 데모용 완료 검증은 같은 자동화·같은 코드 버전의 정상/실패 기록, HTTP 200 이후 변환 실패, 두 응답 경로 차이, 변경 안내의 적용 시각·필드 의미, 보고서 계약의 구형 지원 요구를 확인한다. 자료 간 모순이나 판단 불가는 확인 필요다. 자연어 인용이 존재한다는 것만으로 의미가 맞다고 판정하지 않는다. 이 확인을 자동화할 구체적 판정기는 기술 설계에서 검증해야 한다.
3. `ready_for_handoff`이고 위 기준을 통과한 경우에만 A를 자동 완료한다. A가 검토 후 완료로 설정됐다면 사람의 완료 처리를 기다린다. 결과의 `outcome` 자체가 B 실행 명령은 아니다.
4. 서비스는 진단 결과와 필요한 근거 본문을 하나의 보존된 인계 자료로 B 업무에 연결한다. B가 사내 자료 ID만 받고 접근할 수 없는 상황이 없도록 두 응답·관련 로그·운영 문서 발췌·기대 보고서와 검증 항목을 포함한다. 전송 가능한 범위를 넘는 자료가 필요하면 확인 필요로 남긴다.
5. B는 등록된 저장소와 서비스가 지정한 기준 코드 버전에서 worktree를 시작한다. A의 `target_component`는 조사 단서이며 실행 경로나 셸 명령으로 그대로 사용하지 않는다. B는 실제 코드와 재현 입력을 확인하고 TDD로 수정한다. 기준 코드 버전이 조사 기록과 달라 재현되지 않으면 차이를 보고하고 확인을 요청한다.

B의 대상 등록 정보·기준 코드 버전·실행 및 완료 방식은 업무 설정에서 가져온다. A가 다른 저장소를 선택하거나 권한을 확대하지 않는다. 자동 실행으로 설정된 B는 A 완료와 입력·연결 조건 충족 후 시작한다. 오프라인이면 대기하며, 같은 A 완료 이벤트가 중복되어도 B 실행은 하나만 생성한다. 인계 자료의 저장 방식과 버전 고정 방식은 기술 설계에서 정한다.

#### 도구·인계 수용 기준

| 사례 | 확인할 결과 |
|---|---|
| 모든 데모 근거 조회 가능 | 실제 조회 기록과 근거 인용이 일치하고, 완료 검증 후 B가 첨부만으로 실패를 재현할 수 있음 |
| 실패 응답 본문 또는 변경 안내 누락 | 부족한 자료·이유 표시, A 확인 필요, B 미실행 |
| 문서 조회 접근 거절 또는 일시 오류 | 실패 이유 구분, 읽지 않은 근거 인용 없음, B 미실행 |
| 변경 안내의 적용 시각이 실패 실행보다 뒤 | 근거 충돌을 표시하고 확정 진단·자동 인계 보류 |
| 읽지 않은 근거 ID·버전 인용 또는 첨부 누락 | 완료 검증에서 차단, B 미실행 |
| 입력에서 목록 위치는 그대로인데 HTTP 오류로 바꿈 | 기존 형식 변경 진단을 재생하지 않고 조회 실패를 조사·보고. 이 데모의 수정 인계 기준은 미충족 |
| B에 사내 조회 권한 없음 | 전달받은 근거 본문으로 조사·재현 가능. 추가 내부 접근이 필요하면 확인 요청 |
| B 결과 제출 | diff·실제 테스트 기록·생성 보고서 확인 가능, 사람 검토 전 완료·병합으로 표시하지 않음 |

### 문서 검색 기반과 OpenArchive — 최신 범위 정리

사용자는 자신이 개발 중인 [OpenArchive](https://github.com/jeongeundev/OpenArchive)를 공유했으나, 필수가 아니면 사용하지 않거나 후속 기능으로 두어도 된다고 밝혔다. Assistant는 첫 MVP 연동을 보류하고 작은 JSON 실행 기록·로그와 Markdown 운영 문서, 조회 도구로 진단 에이전트를 시작하는 안을 제안했다. 최소 데이터와 논리적 조회·인계 계약은 위에 작성했으며, 전송·인증 인터페이스는 후속 기술 설계에서 구체화한다.

OpenArchive 재사용이나 범용 사내 에이전트 생성 기능은 첫 MVP의 필수 조건이 아니다. 후속에 문서 수집·갱신·검색·출처·권한 관리가 필요하면 재검토한다. 소수의 자료로 실제 조회·진단을 수행하며 고정된 답변 재생으로 대체하지 않는다.

사내 에이전트는 내부 문서가 있다는 이유만으로 필수인 것은 아니다. 개인 에이전트에 필요한 MCP 도구와 권한을 제공하는 구성도 가능하다. 이번 사례에서는 조직의 실행 이력·로그·운영 절차를 종합해 진단하는 업무를 별도 에이전트로 재현한다. MCP는 도구 연결 규격, RAG는 검색 근거를 이용한 생성 방식이며 서로 대체 관계가 아니다. 사내 배포나 RAG 자체가 외부 데이터 전송을 막는다고 주장하지 않는다.

## 수용 기준 제안

| 대상 | 검증 가능한 기준 |
|---|---|
| 등록 | 선정한 로컬 환경과 API 에이전트 각각의 연결 확인 후 등록 목록에 상태가 표시됨. 사용자에게 맞춤 연결 코드 작성을 요구하지 않음 |
| 등록 정보 제안 | 연결을 허용한 범위에서 파악한 정보로 업무 설명을 제안하고, 사용자가 수정·보충한 정보를 저장함. 읽지 못한 설정을 확인한 것으로 표시하지 않음 |
| 기존 환경 활용 | 서비스에서 실행한 작업이 해당 환경에 이미 있는 설정·자료 또는 도구를 사용했다는 증거가 남음 |
| 직접 선택 | 사용자가 지정한 에이전트로 연결되고 시스템이 임의로 다른 대상으로 바꾸지 않음 |
| 자동 선택 | 능력·접근 가능한 자료가 서로 다른 등록 환경과 업무 사례를 준비해, 업무에 필요한 조건을 충족하는 대상을 선택하고 이유를 표시함. 적합한 대상이 없는 사례에서는 실행하지 않음 |
| 직접·자동 실행 | 자동 선택한 대상과 이유를 표시·기록함. 직접 실행은 사용자 조작 후 시작하며, 자동 실행은 대상이 정해지고 조건 충족 후 별도 승인 없이 시작. 대상 미결정이면 실행을 보류하고 정보 또는 선택을 요청함 |
| 순차 실행 | A 완료 기준을 만족하기 전에는 B가 시작되지 않으며, 만족한 뒤 B가 A의 결과를 사용해 실행됨 |
| 완료 기준 | 업무 내용에 따른 기준 제안을 표시하고 사용자가 수정할 수 있음. 수정한 기준을 저장하고 실행 후 검증에 사용함. 충족 여부를 판단하지 못하면 확인 필요로 표시함 |
| 완료 방식 | 자동 완료는 완료 기준 충족 확인 후, 검토 후 완료는 사람의 완료 처리 후에만 후속 업무의 선행 조건을 충족시킴 |
| 코드 결과 인계 — 코드 업무 간 연결 시 | B가 기준 브랜치의 이전 코드가 아닌 A의 보존된 결과 버전에서 시작하며, 작업 요약·검증 결과·남은 사항을 받음 |
| 기준 브랜치 병합 | 업무가 자동 완료돼도 사용자 확인 전에는 기준 브랜치에 병합하지 않음 |
| 상태 정확성 | 접수와 시작을 구분. 오프라인·실패·확인 필요를 성공이나 완료로 표시하지 않음 |
| 중복 방지 | 같은 시작 또는 완료 이벤트를 두 번 전달해도 해당 업무의 실행은 한 번만 시작됨 |
| 연결 권한 | 연결이 허용되지 않은 다른 소유자의 실행 환경으로 업무를 보낼 수 없음 |
| 결과 확인 | 실행한 대상, 결과·산출물, 시작·종료 시각을 업무에서 확인할 수 있음 |
| 실행 예산 | 진단 1회·하루·세션·총액 상한을 넘으면 새 진단을 접수하지 않고 이유를 표시함. 상한 값은 [ARCHITECTURE](ARCHITECTURE.md) 배포·예산 절 |
| 연결 끊김 | 연결 프로그램이 오프라인이면 B는 대기와 마지막 확인 시각을 표시하고, 재접속 후 이어서 실행됨 |

성능 목표 수치는 연결 방식 검증 후 정한다. 측정 전 지연 시간이나 성공률을 약속하지 않는다.

## 효과 측정

- 등록 편의성: 준비된 실행 환경에서 연결 시작부터 첫 실제 업무 성공까지 걸린 시간, 수동 입력과 설정 변경 수, 맞춤 코드 작성 여부.
- 착수 대기: 업무 실행 조건이 모두 충족된 시각부터 실제 에이전트 시작까지의 시간.
- 수동 중계: 한 흐름에서 사람이 복사·전달·실행한 횟수.
- 신뢰성: 시도 대비 올바른 대상의 실제 시작·완료 수, 중복 실행 수와 실패 이유.

같은 입력·환경·업무를 사람이 수동으로 전달하는 방식과 비교한다. 연결 설치 비용은 반복 실행의 시간 절감과 구분한다. 데모의 단일 성공은 실제 팀의 지속적인 병목 감소를 증명하지 않는다.

## 첫 검증에서 보류할 범위 제안

모든 에이전트 범용 지원, 기존 대화 자동 승계, Jira 전체를 대체하는 업무 관리, 복잡한 워크플로우 편집기는 첫 검증에서 보류한다.

목표에서 작업 분해, 에이전트 생성, 에이전트 간 자율 질의·응답은 제품 방향에서 삭제하지 않는다. 이번 좁은 검증 이후의 범위로 두자는 제안이며 사용자 확정은 아니다.

## 다음 결정과 구현 진입 조건

실행 위치는 현재 사용 중인 컴퓨터의 연결 프로그램으로 정했다. 첫 로컬 도구는 Codex CLI다(ADR-0001). 업무 입력은 서비스 내 등록으로 정했으며, 에이전트 연결은 직접 선택과 업무 내용 기반 자동 선택을 모두 지원한다. 직접 실행과 자동 실행도 모두 지원한다. 업무별 자동 완료·검토 후 완료를 지원한다. 완료 기준은 시스템이 제안하고 사용자가 수정할 수 있다. 에이전트 등록은 실행 환경 연결 → 정보 자동 파악·제안 → 사용자 확인·수정으로 정했다. 자동 선택 후 직접 실행은 사용자 조작을 기다리고 자동 실행은 별도 승인 없이 진행하며, 대상 미결정 시 보류한다. 등록 단위는 실행 도구 + 작업 폴더 하나로 정했다. Git 코드 작업은 업무별 worktree 활용을 검토한다. 선행 결과 버전을 보존해 후속 업무의 별도 worktree로 넘기고, 기준 브랜치 병합은 사용자 확인 후 진행하는 순서에 합의했다. 첫 시연은 일일 보고서 자동화의 응답 형식 변경으로 인한 실패 진단 → 로컬 코드 수정으로 합의했다. 다음은 API 에이전트의 입력·조회 도구·진단 결과와 연결 인터페이스를 설계한다. 선택·실행·완료 방식의 기본값, 자동 선택 판단 규칙, 완료 기준 템플릿, 검토 동작(승인·수정 요청·종료)은 2026-09-20 확정했다. n8n·A2A 채택은 이 요구를 충족하는 비용과 재사용 가능성을 보고 정한다.

기술 설계는 연결 인증·실행 인터페이스·기존 설정 로드·상태 수집 가능성을 확인한 후 [ARCHITECTURE.md](ARCHITECTURE.md)에 작성한다. 이후 작은 단계의 구현 계획과 테스트 기준을 만든다. 별도 구현 요청 전에는 제품 코드·실연동·배포를 시작하지 않는다.
