# 사내 요청 파일럿 실행과 측정 기록

작성일: 2026-10-04
상태: 합성 통합 사례 통과. 실제 사례 기록·효과 비교는 미실행.

## 1. 지금 재현할 수 있는 검증

```bash
python3 -m pytest -q tests/workflow/server/test_internal_investigation.py -k synthetic_pilot
```

실제 FastAPI 앱·임시 SQLite DB·산출물 저장소를 사용하는 통합 테스트다. 요청자, 처리 담당자, 판단 담당자를 서로 다른 멤버로 등록한다. 담당 범위 등록·요청 생성·수락은 공용 준비 함수에서 실제 API로 수행한다.

| 단계 | 실행·통과 조건 |
|---|---|
| 접수 | 원래 업무와 요청자·수신자·판단 담당자를 연결하고 수락 |
| 정보 확인 | 오류 시각·공유 가능한 식별자를 질문; 미답변 중 조사 시작 차단 |
| 조사 예약 | 답변을 실행 입력에 포함; 재시도에도 조사 작업·실행 한 개 유지 |
| 결과 검증 | 합성 산출물을 저장하고 실제 워커가 계약 판정; 사람 검토 전 반환 차단 |
| 판단 | 처리 담당자가 반환 쟁점 요청; 요청자가 대신 응답하면 거부; 판단 대기 중 반환 차단 |
| 반환 | 지정 담당자 승인 후 결과 요약·산출물을 원래 요청에 연결 |
| 재개 기록 | 실제 요청자만 기록; 반환 실행·산출물과 연결; 재시도에도 같은 기록 유지 |
| 보존 | 원래 업무 담당·완료 여부 보존, 질문·판단·반환·재개 이력과 시각 보존 |

합성 결과는 “결제 API 타임아웃 확인, 운영 원인은 미확인, 다음 행동은 설정 검토”다. 테스트가 결과를 직접 저장하므로 실제 모델 조사·CLI 실행·러너 프로세스·회사 협업을 검증한 것은 아니다. 서로 다른 계정도 부서별 자료 격리를 증명하지 않는다. 서버 워커의 일반 상태 집계가 적용된 원래 업무 상태를 기준으로 이후 상태 보존을 비교한다.

잘못된 담당 재전달, 정보 변경 후 판단 재요청, 거절, 오프라인·소유자 승인은 개별 회귀 테스트에서 검증한다. 이번 정상 통합 사례에 모두 발생했다고 기록하지 않는다.

## 2. 실제 파일럿 진행 순서

1. 익명화된 오류 요청 하나로 최초 연락·담당 탐색·추가 질문·판단·반환·재개를 복원한다. 시각·횟수를 모르면 미확인으로 둔다.
2. 읽기 전용으로 공유할 자료와 처리·판단 담당자를 정한다. 현재 제품이 제공하지 않는 실제 자료 접근 권한은 상대 시스템에서 확인한다.
3. 같은 유형의 기존 사례와 서비스 사용 사례를 각 5건부터 모은다. 회사·팀·오류 난이도·근무 시간·모델·자료 조건 차이를 기록한다.
4. 아래 양식으로 사건과 수동 작업을 기록한다. 서비스에 없는 시각·실제 작업 시간은 수동 기록한다.
5. 완료·미완료·거절을 모두 보고한다. 왕복 감소와 결과 재사용을 함께 확인한 뒤 다음 개발 대상을 고른다.

현재 실제 사례와 비교 환경은 확보되지 않았다. 혼자 세 역할을 수행하는 실험으로 동작은 확인할 수 있지만 사람 간 병목 절감의 증거로 쓰지 않는다. 기존 사례가 없으면 합성 비교만 보고한다.

회사 내부 사례 대신 공개 Kubernetes 이슈 3건을 이 양식으로 복원했다: [공개 사례 복원](INTERNAL_REQUEST_PUBLIC_CASES.md).

## 3. 사례별 기록 양식

아래를 사례마다 복사한다. 자료에는 실제 고객 정보·비밀값을 넣지 않는다.

```text
사례 ID:
유형: 기존 방식 / 서비스 사용 / 합성 실험
원래 업무의 익명 식별자:
요청 유형·담당 시스템:
관측 기간·시간대:
요청자 / 처리 담당 / 판단 담당: 익명 역할 ID
공유한 자료와 공유하지 않은 자료:
처음 연락한 시각 및 근거:
서비스 요청 ID: 최초 → 재전달된 요청 순서
실행·결과 참조: 민감한 원문 대신 식별자
최종 결과: 해결 / 부분 해결 / 거절 / 진행 중 / 미해결
업무 재개 시각: 직접 관측 / 사용자 확인 / 미확인
결과 재사용: 그대로 활용 / 보충 후 활용 / 다시 작성 / 미확인
사람이 직접 작업한 분: 역할별, 미확인은 미확인
추가 질문 / 수동 재전달 / 재설명 / 수동 실행 중계 횟수:
판단 번복 / 재작업 / 오배정 횟수:
비교 조건 차이·관측 누락:
```

사건 기록:

| 시각 (UTC 권장) | 사건 | 요청·실행 ID | 현재 담당 | 근거 | 관측 유형 |
|---|---|---|---|---|---|
| 미확인 | 최초 연락 | — | 요청자 | 익명화한 도구 기록 | 실제 / 실험 / 사용자 확인 |
| 미확인 | 요청 생성·수락·질문·답변·판단·반환·재개 중 하나 | — | 역할 ID | 기록 참조 | 동일 |

대기 구간 기록:

| 시작 | 끝 | 이유 | 기다리는 주체·대상 | 근거 | 진행 상태 |
|---|---|---|---|---|---|
| 미확인 | 미확인 | 담당 탐색 / 정보 / 판단 / 권한 / 오프라인 / 기타 | 역할 ID | 기록 참조 | 종료 / 진행 중 |

수동 동작 기록:

| 시각 | 역할 | 동작 | 새 정보 추가 여부 | 횟수·소요 분 | 근거 |
|---|---|---|---|---|---|
| 미확인 | 역할 ID | 재전달 / 재설명 / 실행 중계 / 결과 재작성 | 예 / 아니오 | 미확인 | 기록 참조 |

API 재시도는 수동 왕복으로 세지 않는다. 재전달은 처리 대상을 바꿔 요청을 보내는 행동, 재설명은 이미 전달한 내용을 다시 전달하는 행동이다. 새로운 정보에 대한 질문·답변은 별도 추가 질문으로 센다. 실행 중계는 사람이 다른 사람의 에이전트 실행을 요청하거나 결과를 옮기는 행동이다.

## 4. 현재 기록에서 얻을 수 있는 시각

| 사건 | 현재 저장 필드 | 해석·한계 |
|---|---|---|
| 요청 생성·수락 | 요청 created_at / accepted_at | 생성은 서버 접수, 수락은 처리 담당자의 확인; 최초 연락·담당 탐색 완료와 동일하지 않음 |
| 담당 아님·재전달 | rejected_at / new_request_id → 새 요청 created_at | 이전 요청 연결을 따라 전체 경로 복원; 거절 시각만으로 재전달 시각 추정하지 않음 |
| 조사 작업 연결 | internal_request_investigations.created_at | 조사 Task 연결 시각; 실제 실행 시작과 다름 |
| 실행 예약·접수·시작·종료 | Execution created_at / accepted_at / started_at / finished_at | 서버 예약·러너 접수·프로세스 시작·종료 구분; 비어 있는 값 추정 금지 |
| 추가 정보 | questions asked_at / answered_at | 질문별 응답 대기; 이미 진행 중인 실행과 겹칠 수 있음 |
| 업무상 판단 | judgments asked_at / responded_at | 판단별 대기; 실행·정보 버전이 바뀐 과거 판단도 보존해서 별도로 기록 |
| 결과 반환 | returned_at | 처리 담당자가 결과를 반환한 시각; 요청자가 읽은 시각은 아님 |
| 재개 기록 | resumption.resumed_at | 사용자 확인을 저장한 시각; 실제 작업을 시작한 시각의 자동 관측이 아님 |

사람 검토와 업무상 판단은 다르다. 검토 전 대기 구간은 현재 요청 응답만으로 충분히 복원되지 않으므로 검토 행동 시각을 수동 기록한다. 최초 연락, 실제 담당 확인, 자료 권한 승인, 능동적인 사람 작업 시간도 자동 수집되지 않는다. 이번 단계에서 측정 API나 대시보드를 추가하지 않았다.

## 5. 계산과 비교 규칙

| 지표 | 계산·집계 |
|---|---|
| 전체 경과 시간 | 업무 재개 시각 − 최초 연락 시각. 실제 재개가 미확인이고 저장 시각만 있으면 “최초 연락→재개 기록 경과”로 따로 표시 |
| 제품 내 경과 시간 | 최종 재개 기록 시각 − 최초 서비스 요청 created_at. 재전달됐으면 최초 요청에서 시작; 마지막 요청만 비교하지 않음 |
| 접수 응답 대기 | 각 요청 accepted_at − created_at. 담당 아님 요청은 rejected_at − created_at을 별도 거절 응답 시간으로 표시 |
| 정보·판단 대기 | 질문별 answered_at − asked_at, 판단별 responded_at − asked_at. 미응답은 진행 중 경과와 관측 종료 시각 표시 |
| 결과 전달 이후 대기 | 재개 기록 시각 − returned_at. 사람의 독해·적용·다른 업무 대기가 포함될 수 있음 |
| 수동 중계 부담 | 재전달·재설명·실행 중계·결과 재작성 횟수와 역할별 능동 작업 분을 각각 비교 |
| 품질 | 결과 재사용 여부, 오배정·판단 번복·재작업·무단 실행·자료 노출·중복 처리 건수 |

시간은 동일 시간대·같은 기준으로 계산한다. 대기 구간이 겹치면 전체 대기에 합산하지 않는다. 합계가 필요하면 겹친 구간의 합집합을 계산하고, 이유별 시간은 중복 가능하다고 표시한다. 서버 예약부터 실행 시작까지의 시간을 전부 오프라인 대기라고 분류하지 않는다. 소유자 승인·큐·환경 오류 등 실제 근거를 확인한다.

완료 사례의 중앙값과 개별 값, 완료·진행 중·거절 건수를 함께 보고한다. 빠르게 끝난 사례만 남기지 않는다. 미확인은 0으로 채우지 않는다. 동일 사례의 반복 API 실행 시간은 자동 테스트 성능이며 실제 사람 대기 시간이 아니다.

기존 방식과 서비스의 사례 조건이 다르면 차이를 함께 적는다. 첫 5건 비교로 통계적 인과 효과나 경쟁 우위를 주장하지 않는다. 기준선 확인 후 파일럿 시작 전에 성공 기준을 고정한다. 왕복과 경과 시간이 줄어도 재작업·판단 번복이 늘었다면 개선으로 단정하지 않는다.

## 6. 결과표 — 실제 관측 후 작성

| 항목 | 기존 방식 | 서비스 사용 | 해석·누락 |
|---|---|---|---|
| 관측 / 완료 / 진행 중 / 거절 건수 | 미측정 | 미측정 | — |
| 전체 경과 시간 중앙값 | 미측정 | 미측정 | 실제 재개와 재개 기록 구분 |
| 수동 재전달·재설명·실행 중계 | 미측정 | 미측정 | 종류별 횟수 |
| 사람 능동 작업 분 | 미측정 | 미측정 | 역할별 |
| 결과 재사용·재작업 | 미측정 | 미측정 | 분모·미확인 건수 포함 |

Multica 비교도 같은 자료·역할·시나리오로 이 양식을 사용한다. 기능을 찾지 못했으면 “해당 환경에서 미확인”으로 기록하고, 제품의 기능 부재라고 단정하지 않는다. 이번 단계에서는 Multica를 실행하거나 최신 기능을 재조사하지 않았다.

다음 개발 우선순위는 이 기록에서 반복되는 대기 원인으로 정한다. 실제 사례 전에는 자동 권한 발급이나 A2A를 필수 해법으로 확정하지 않는다.
