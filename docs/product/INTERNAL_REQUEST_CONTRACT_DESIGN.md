# 사내 조사 요청 — 기존 계약 적합성 설계

작성일: 2026-10-03. 상태: 구현 전 설계안. [파일럿 범위](INTERNAL_REQUEST_PILOT.md)의 두 번째 작업이다.
후속 진행: [담당 범위 표 API](RESPONSIBILITY_DIRECTORY.md)를 구현했다. [요청 관계의 생성·수락](INTERNAL_REQUESTS.md)도 구현했다. [조사 실행·결과 반환](INTERNAL_REQUEST_INVESTIGATION.md)도 구현했다. 아래 예외 흐름은 여전히 설계안이다.
이 문서는 최초 코드 조사에 근거한 설계안이다. 후속 구현의 DB·API 변경은 위 구현 문서에 기록하며 계약 v1 실행 봉투는 변경하지 않았다. 아래 식별자 후보는 확정된 계약이 아니다.
실제 조직 정책은 미확인이다. 한 공유 워크스페이스에서 합성 자료를 쓰는 실험을 먼저 설계한다.

## 1. 설계 결론

조사 실행은 기존 `Task`·`Execution`·`LocalTarget`·`GenericResult`를 활용한다. 원래 업무의 담당자를 상대 팀으로 바꾸는 대신, 조사 요청의 수신자와 원래 업무의 담당자를 구분한다.

요청의 접수·재전달·회신은 실행 상태와 다른 의미다. 이를 `Task.status`나 에이전트의 `outcome`에 모두 넣지 않는다. 요청의 원업무 참조와 왕복 이력을 보존하는 좁은 관계가 필요하다는 설계안이다. 첫 구현 전, 기존 업무 링크를 확장하는 방식과 별도 요청 관계를 아래 불변식으로 비교한다.

첫 실험은 외부 시스템을 직접 조회하지 않고 사람이 공유 가능한 합성 자료를 선택해 보내는 읽기 전용 조사다. 상대 팀의 사설 자료에 대한 접근·공유 통제는 이후 별도 검증해야 한다.

## 2. 확인한 재사용 범위

| 기존 요소 | 재사용 | 부족한 의미 |
|---|---|---|
| `WorkItem` | 원본 정보·담당·원업무 이력 | 상대 조사 요청의 접수와 회신 관계 |
| `Task` | 조사 단계·revision·사람 검토 | 요청 수신자의 접수와 원업무 담당을 구분하는 관계 |
| `Execution` | 한 조사 시도·고정 요청·산출물·실패 | 담당 아님은 실행 실패와 다름; 재전달 이력 필요 |
| `LocalTarget` | 등록 환경에서 사용자 정의 종류 실행 | 인계 디렉터리 조사이며 임의 저장소·운영 시스템 조회가 아님 |
| `GenericResult` | 허용된 outcome·summary·로그 참조 | 근거·불확실성·다음 행동의 구조적 검증 없음 |
| `HumanRequest`와 응답 기록 | cause_key 중복 방지·응답 revision·재평가 | 지정 판단권자 검사, 조사 전용 질문/응답 의미 추가 필요 |
| `SuccessorRule` | 허용된 결과에 대한 후속 조사 | `new_work`는 새 업무 생성과 `spawned_from` 링크이며 회신·재개 보장 아님 |
| `work_item_links` | 업무 사이 참조 | 현재 `blocks`·`spawned_from`; 수신자·질문·회신 revision 없음 |

근거 코드: `src/workflow/contracts/v1.py`의 `LocalTarget`·`GenericResult`·`SuccessorRule`, `src/workflow/connector/local_tool.py`의 `_run_generic`, `src/workflow/server/worker.py`의 `_check_generic_results`, `src/workflow/server/human_api.py`, `src/workflow/domain/task_followup.py`, `src/workflow/adapters/db.py`·`repo.py`.

현재 generic 결과 판정은 봉투·ID·허용 outcome을 검사하며 `확인 필요`로 남긴다. 조사 내용이 사실이라고 검증하거나 원업무를 자동 완료하지 않는다. 일반 추가 정보 응답에는 빈 텍스트 검사와 멱등 기록이 있지만, 조사 결과에서 그 요청을 생성하는 경로까지 이미 지원한다고 간주하지 않는다.

## 3. 필요한 최소 정보

요청 관계에 필요한 정보의 의미를 먼저 고정한다. 실제 표·필드 이름은 마이그레이션 설계 때 정한다.

| 정보 | 이유 |
|---|---|
| 요청 식별자·접수 키·워크스페이스 | 재전송 중복 방지와 범위 검사 |
| 원업무 ID·요청자·조사 목적 | 원래 담당과 맥락 보존 |
| 현재 수신 멤버·조사 Task 참조 | 접수 책임과 실행 대상을 구분 |
| 요청 revision·공유 자료 참조 | 이전 담당/자료에 대한 늦은 응답 거부 |
| 담당 변경 기록·행위자·이유·시각 | 덮어쓰기 없이 재전달 추적 |
| 질문·판단 요청 참조 | 정보 대기와 판단 대기를 구분 |
| 반환 결과의 Execution·산출물 참조 | 특정 조사 시도의 결과를 회신 |
| 반환 기록·원업무 재개 확인 | 회신과 실제 활용을 별도로 측정 |

요청 하나에 활성 조사 Task는 하나만 둔다. 최초 안은 요청 하나를 원업무 안의 조사 Task 하나에 연결하는 방식이었다. 구현에서는 기존 Task 상태 집계가 원업무에 영향을 주므로 조사 전용 WorkItem과 Task를 요청 관계로 연결한다([구현 근거](INTERNAL_REQUEST_INVESTIGATION.md)). 수신자 변경 전 기존 실행이 정지하거나 결과가 보류됐음을 확인한다. 이미 실행된 Task를 새 담당으로 덮어쓰지 않고 새 조사 Task를 연결해 이전 시도를 보존한다. 병렬 조사·부서 격리·다른 워크스페이스 요청은 이 설계 범위 밖이다.

접수 책임은 멤버에게, 실행 능력은 에이전트에게 둔다. 담당표에 에이전트가 있어도 실제 사용 승인·온라인 상태·자료 접근 가능성을 따로 검사한다. 담당표는 권한을 부여하지 않는다.

## 4. 네 가지 흐름

| 흐름 | 사건과 기존 모델 대응 | 새로 필요한 검사/기록 |
|---|---|---|
| 정상 | 원업무에서 요청 → 수신자 접수 → 조사 Task 생성/실행 → generic 결과 판정 → 사람 검토 → 결과 반환 | 접수 전 실행 금지, 반환 결과 고정, 원업무와 링크 |
| 담당 아님 | 접수 전 거절 또는 조사 뒤 부적합 제안 → 사람이 이유와 후보 확인 → 요청자 재전달 선택 | 담당 변경 revision, 이전 실행 보류, 새 대상 접수; 자동 후보 확정 금지 |
| 정보 부족 | 결과/수신자가 질문 → 조사 Task에 사람 요청 → 요청자 답변 → 조건 재검사 → 새 Execution | 질문 대상·답변 자료 연결, 동일 답 재전송 한 번 처리 |
| 사람 판단 | 쟁점과 근거 → 지정 담당자에 사람 요청 → 허용/거절 → 조건 재검사 → 허용된 조사만 계속 | 지정 담당자/명시적 대체자 검사, 판단 대상 revision과 적용 범위 |

에이전트가 담당 아님·정보 부족·판단 필요를 제안할 수 있지만, 제안만으로 담당 변경·권한 확대·원업무 종료를 실행하지 않는다. 질문 작성자는 수신자, 정보 응답자는 요청자, 업무상 판단 응답자는 지정 담당자라는 실험 역할을 사용한다. 실제 조직에서의 대체자 정책은 추후 확인한다.

결과 반환은 원업무 화면에 검토된 결과 링크·요약을 표시하는 사건이다. 요청자가 ‘결과를 받고 업무를 이어감’을 명시적으로 기록하면 재개로 측정한다. 첫 버전에는 Jira 변경·원업무 자동 실행을 연결하지 않는다. 결과 거절·부분 조사도 반환할 수 있으며 업무 해결과 구분한다.

## 5. 불변식과 경쟁 처리

1. 원업무의 담당·원본·완료 판정은 조사 요청 생성이나 반환만으로 변경되지 않는다.
2. 접수 키 재전송은 같은 요청을 반환한다. 같은 키에 다른 내용이면 충돌을 반환한다.
3. 담당 변경·접수·응답·반환은 expected revision과 현재 행위자를 검사한다. 늦게 도착한 이전 담당의 결과는 보존하되 현재 회신으로 적용하지 않는다.
4. 응답 ID 재전송은 동일 내용일 때 같은 결과다. 최초 반영과 실행 예약은 원자적으로 기록하며 워커 재시작 후 실행 원인 키를 다시 검사한다.
5. 접수·실행 직전·응답 적용 뒤에 활성 멤버, 대상 등록, 에이전트 사용 조건, 공유 자료 범위를 검사한다. 조건이 바뀌면 대기를 표시한다.
6. 수신자 재지정은 실행 취소를 보장하지 않는다. 실행 중이면 재전달을 보류하고 기존 시도의 종료/보류를 확인한다. 실행 중인 다른 대상의 결과를 새 요청에 합치지 않는다.
7. 일반 `RESPOND` 권한이나 관리 역할을 업무상 판단권자로 자동 해석하지 않는다. 운영자 복구 조작이 필요하면 판단 응답과 구분해 기록한다.
8. 요청 종료 후 응답은 새 실행을 만들지 않는다. 미해결 반환은 원업무 해결로 집계하지 않는다.

## 6. ADR 후보와 선택

| 후보 | 제안 | 다른 선택을 채택하지 않는 이유 |
|---|---|---|
| 요청 관계 | 원업무·조사 Task·수신자·revision을 연결하는 좁은 기록 | `spawned_from`만으로 왕복·접수 책임을 표현하기 어려움 |
| 지정 응답자 | 사람 요청에 판단 대상과 허용 응답자 범위를 추가 | 소유자 사용 승인은 업무별 판단 권한과 다름 |
| 완료 의미 | 조사 결과 검토·반환·원업무 재개를 분리 | valid outcome만으로 사실성·문제 해결을 증명하지 못함 |

별도 범용 프로세스 엔진·모든 Task 상태 확장·A2A 전용 업무 모델은 도입하지 않는다. 위 후보는 아직 정식 ADR이 아니다. 다음 구현 설계에서 기존 링크/이벤트 확장으로 불변식이 유지된다면 별도 요청 표를 줄일 수 있다.

## 7. 구현 단위와 검증 기준

최초 구현 순서는 **담당 범위 표와 명시적 수신자 선택**부터다. 현재 담당표·웹 관리·요청 생성·수락을 구현했고, 조사 실행·검토·반환도 연결했으며 다음 단위는 예외 흐름과 원업무 재개 확인이다. 합성 시스템 이름·등록 멤버·에이전트만 사용한다. 저장소/시스템 식별자는 등록값이며 요청이 로컬 경로나 실행 명령을 정하지 못한다.

테스트를 먼저 작성할 순서:

1. 담당 후보 없음/복수 → 명시적 선택 대기. 비활성 멤버와 미등록 에이전트는 선택 불가.
2. 담당 후보 선택 → 원업무 담당 보존. 능력과 사용 승인을 검사하되 후보 등록으로 권한을 부여하지 않음.
3. 요청 접수 키·revision 경쟁 → 요청/접수가 중복되지 않음.
4. 읽기 전용 합성 조사 → 결과 검토 후 한 번 반환. 원업무는 자동 완료되지 않음.
5. 담당 아님·정보 부족·지정 판단·늦은 결과 → 위 불변식 통과.

1–2는 담당표 구현 단위, 3–4는 요청 관계와 정상 흐름 구현 단위, 5는 예외 흐름 단위다. 한 번에 전체를 구현하지 않는다. 소스 변경 단계에는 프로젝트의 전체 pytest·ruff 검증을 실행한다.

읽기 전용은 현재 도구 실행 모드와 인계 파일 변경 검사를 재사용한다. 그것만으로 호스트 전체나 외부 시스템의 접근 격리가 증명되지는 않는다. 최초 합성 실험에서 비밀 없는 자료만 제공하고, 실제 자료 연결 전 선택된 도구의 읽기 모드·파일 접근·네트워크 권한을 검증한다.

이번 설계 완료 기준인 정상·재전달·정보·판단 네 흐름의 모델 대응과 최소 변경 후보를 정리했다. 실제 사례, Multica 실행 비교, 실제 조직 정책 및 협업 효과는 여전히 미검증이다.
