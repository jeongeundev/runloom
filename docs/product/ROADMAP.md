# 제품 로드맵 — 기존 업무에서 시작하는 에이전트 자동 실행

갱신일: 2026-09-23. 제품 방향은 사용자 합의를 반영했다. 아래 버전명·세부 묶음·실험 방법은 실행 가능한 계획 제안이며 출시 날짜나 구현 완료를 뜻하지 않는다. 버전은 제품 단계로, Python 패키지·API·DB 버전 및 `phases/` 번호와 별개다.

## 1. 제품의 출발점

GitHub·Jira 등에서 이미 관리하는 업무를 쉽게 가져오거나 직접 등록하고, 기존 담당 체계와 에이전트를 연결해 준비된 업무를 추가 프롬프트 작성 없이 진행한다. 결과는 원래 업무에 반영하고, 기존 후속 업무에 연결하거나 필요한 새 업무를 생성해 실행을 이어간다.

기존 업무 도구를 교체하거나 처음부터 자연어로 모든 워크플로우를 만들게 하는 제품이 아니다. 자연어 해석은 업무 이해·입력 보충에 내부적으로 활용할 수 있다. 화면의 중심은 업무 목록·실행·결과·대기 이유다. 워크플로우 편집기나 채팅창을 필수 시작점으로 두지 않는다.

기록은 선택적인 설정 보조 자료다. 기록 없이도 업무·담당 Agent·위임 범위를 정해 시작할 수 있어야 한다. 처음부터 회사 전체 로그 분석, LLM 메모리 연결, 모델 재학습을 요구하지 않는다. 사용 중 발생하는 실행 기록은 초기부터 남기고, 기록 기반 추천·분석 기능은 그 필요성이 확인된 뒤 제공한다.

차별성 가설은 기존 업무를 다시 작성하지 않고 서로 다른 담당자의 기존 에이전트가 결과를 이어받아 실제로 실행하며, 위임된 판단까지 자동 처리해 사람의 중계를 줄인다는 것이다. 업무 가져오기·자동 배정·상태 화면 각각의 유일성을 주장하지 않는다.

## 2. 현재 위치와 버전 지도

`main`의 공개 데모는 phase 5이며 심사 기간 동결한다. `service`에는 phase 6의 종류·후속 규칙, phase 7의 n8n 입구·callback, 로컬 Agent 연결과 결과 검증 기반이 있다. `service`의 GitHub·Jira 가져오기는 fixture이고, 사전 등록한 후속 Task의 착수가 중심이다. phase 8 브랜치(미병합)에 GitHub Issues 수집·담당 연결·새 검토 Task 생성·사람 요청·응답·댓글 반영이 구현되어 대역으로 검증됐고, 실제 GitHub·Agent 왕복은 미검증이다(10절).

| 단계 | 사용자에게 약속할 가치 | 핵심 범위 | 제외·후속 |
|---|---|---|---|
| 공개 데모(기존) | 연결·인계 흐름을 체험 | 대본 에이전트·fixture·시연 | 실제 팀 효과의 증거로 사용하지 않음 |

| v0.2 / 반복 사용 | 같은 팀이 매번 다시 설정하지 않고 운영 | 재사용 설정·예외 재개 개선·운영 신뢰성·기본 집계 | 전사 프로세스 분석·광범위한 자율 판단 |
| v0.3 / 설정 추천 | 기존 기록이 있으면 설정이 쉬워짐 | 유사 업무·담당·필수 입력·후속 규칙 추천·근거와 수정 피드백 | 기록 필수 온보딩·추천의 무조건 자동 적용 |

| v1.0 / 반복 도입 가능 | 검증한 고객군이 지속적으로 도입·운영 | 지원 범위 명시·안정적 연결·운영·업그레이드·지원 절차 | 모든 도구·직무·업무 지원 약속 |

날짜 대신 아래 단계별 검증 결과로 이동한다. 반복 사용이 없으면 추천 기능을 늘리기 전에 초기 가치와 연결 부담부터 개선한다.

## 3. MVP / v0.1 — 가져온 업무가 실제로 이어진다

### 첫 사용자와 범위

제안 대상은 GitHub 또는 Jira에 업무를 관리하면서 Codex·Claude Code 등 기존 에이전트를 이미 사용하는 소규모 개발 팀이다. 제품을 개발 업무로 영구 제한하지 않되 첫 실험에서는 직무·업무 범위를 좁힌다.

첫 연동 도구는 아직 미확정이다. 파일럿 팀이 실제로 쓰는 도구를 우선하고, 동률이면 기존 Git 작업 기반을 활용할 수 있는 GitHub Issues를 먼저 검토한다. Jira와 GitHub를 동시에 구현해야 MVP가 된다고 보지 않는다. 실제 외부 업무 1종의 왕복 연동은 필요하며 fixture나 수동 복사로 대체한 검증과 구분한다.

첫 업무 유형 제안은 명확한 재현 정보가 있는 버그 수정 → 검토다. 등록된 저장소·검증 방식·담당 관계를 사용하며 범용 운영 진단 API를 전제하지 않는다. 현 진단 데모 전용 검증을 일반 버그 수정 검증으로 오인하지 않는다. 구현 전 재사용 가능한 부분과 분리해야 할 부분을 확인한다.

### 첫 사용 흐름

1. 업무 서비스를 연결하고 가져올 프로젝트·저장소·이슈 범위를 선택한다. 과거 전체 로그를 먼저 분석하지 않는다.
2. 담당자와 사용할 Agent를 연결한다. 개인 소유 Agent와 팀 공용 Agent를 모두 표현하되 담당자와 소유자를 혼동하지 않는다.
3. 지원 업무의 필수 입력·검증 기준·자동 실행 범위를 확인한다. 기존 필드는 재사용하고 누락된 필수 항목만 보충한다. 고급 KindSpec·후속 규칙 JSON을 사용자가 직접 작성하게 하지 않는 것이 목표다.
4. 지정한 범위에 새 업무가 등록·배정되면 조건을 평가해 착수한다. 최초 범위 밖 기존 백로그를 일괄 실행하지 않는다. 직접 등록 경로도 같은 판정을 사용한다.
5. 결과 요약·산출물 링크·진행 또는 확인 요청을 원래 이슈에 반영한다. 초기에는 댓글·링크 중심의 최소 왕복을 제안하며 상태 필드의 양방향 동기화는 별도 계약으로 정한다.
6. 결과가 기존 후속 업무의 입력을 채우면 연결하고, 없으면 제한된 종류의 후속 Task를 생성·배정한다. 코드 검토처럼 위임된 후속은 자동 실행한다. 모든 후속 Task를 외부 이슈로 복제할 필요는 없으며, 외부 생성 여부는 명시적 정책으로 정한다.
7. 위임 범위 밖이거나 허용된 조회·검토로도 해결하지 못하면 사람에게 요청한다. 답변 후 재평가하며 독립 업무는 계속 진행한다.

### MVP에 반드시 포함할 것

- 외부 업무 식별자·담당자·대상·원본 링크 보존, 중복 수신 방지와 명시적인 가져오기 범위.
- 지원 업무의 입력 준비 판단, 담당 Agent 연결, 실행·결과 보존, 실패와 사람 대기 구분.
- 결과 기반 기존 업무 연결과 새 후속 Task 생성의 최소 한 경로. 기존 작업을 잇는 것만으로 생성 검증을 대신하지 않음.
- 위임된 판단의 자동 실행. 처음에는 좁고 알려진 후보·정책으로 구현하며 Jev는 필수 의존이 아님.
- 결과 반영 실패를 에이전트 작업 실패와 구분하고 재전송 시 댓글·Task·Execution 중복을 막음.
- 입력·결과 버전, 착수 가능/실제 착수/종료 시각, 대기 이유, 사람 개입, 설정·판정 버전, 확인 가능한 비용 기록. 모르는 비용을 0으로 표시하지 않음.
- 연결 장애·재시작·재처리 대응, 허용 행동·필수 승인·실행 상한, 실서비스 데이터 보존을 위한 DB 변경 절차.

### MVP에서 만들지 않을 것

- 자연어 한 문장으로 임의 기업 업무 전체를 자동 구성하는 기능과 범용 워크플로우 편집기.
- 전체 서비스 로그를 통합 분석하는 플랫폼, 자동 프로세스 발견, 개인 LLM 메모리의 포괄 수집.
- 여러 업무 도구·모든 Agent·모든 직무의 동시 지원, 자동 모델 재학습.
- 고급 ROI 대시보드와 조직 전체 추천. 기본 실행 기록과 수동 집계는 초기 검증에 사용한다.

### 통과 기준

PRD의 5개 업무 시나리오(A·B 실행, A → 기존 C, B → 새 F, D·E 사람 응답 후 재개)를 지원 업무의 대역 테스트로 통과시킨다. 실제 외부 도구와 실제 Agent로 접수 → 작업 → 결과 반영 → 후속 생성·착수를 확인한다. 전체 실제 사례를 대본 성공으로 대체하지 않는다.

대표 업무에서 프롬프트 재작성·결과 복사·후속 실행 조작이 줄고, 결과가 사용 가능해야 한다. 중복 이벤트·재시작으로 중복 작업이 생기거나 위임 밖 실행이 발생하면 출시 검증 실패다. 시간 절감·오류 허용 목표와 표본은 파일럿 전에 정하고 사후에 성공 기준을 바꾸지 않는다.

## 4. v0.2 — 같은 팀의 반복 사용

진입 근거: MVP를 실제 업무에 다시 사용하는 팀이 있고, 반복 설정·대기 복구·결과 반영 문제를 구체적인 사례로 확인했다.

프로젝트별 입력·담당·위임 설정 재사용, 설정 확인·수정 UX, 연결 해제·권한 변경, 재시도·응답 후 재개, 이슈 편집 충돌 처리를 개선한다. 실행·실패·대기 사유별 기본 집계를 제공한다. 이는 MVP의 필수 신뢰성을 나중으로 미룬다는 뜻이 아니라 반복 운영의 편의성과 적용 범위를 넓히는 단계다.

두 번째 연동 도구·Agent는 실제 사용자가 요구하고 기존 계약으로 연결되는지 확인한 뒤 추가한다. 지원 도구 수를 버전 목표로 삼지 않는다.

통과 기준: 같은 프로젝트의 다음 업무가 재설정 없이 처리되고, 흔한 대기를 사용자가 개발자 도움 없이 해결한다. 반복 사용 여부와 중단 이유를 기록하며 팀 규모·업무량을 고려해 해석한다.

## 5. v0.3 — 기록이 있으면 설정을 도와준다

진입 근거: 사용자가 같은 담당·필수 입력·후속 설정을 반복 수정하거나, 신규 프로젝트 설정에 기존 사례를 찾고 있다는 증거가 있다.

허용된 업무 이력에서 유사 사례를 찾아 설정 초안을 제안한다. 출처 하나·업무 유형 하나부터 시작한다. 추천에는 근거 사례·적용 범위·예외·정보 부족을 표시하고 수락·수정·거절을 남긴다. 기록 없는 사용자의 직접 설정 경로는 유지한다. 개인 메모리는 접근 가능하고 사용자가 범위를 지정한 경우에만 선택적으로 활용한다.

우선 후보는 담당 역할, 반복 누락 입력, 후속 검토 조건이다. 전체 프로세스 자동 재구성과 모델 학습은 포함하지 않는다. 추천 단계에서 외부 실행이나 권한 변경을 일으키지 않는다.

통과 기준: 기존의 직접 설정 대비 설정 시간이 줄고, 추천 수정 부담과 오배정·재작업이 증가하지 않는다. 수락률만으로 정확도를 판단하지 않고 추천 적용 후 결과까지 연결해 본다.

## 6. v0.4 — 판단과 개선의 자동화 범위를 넓힌다

진입 근거: 특정 추천·판단이 반복 사례에서 유효했고, 오판 비용과 예외 처리를 측정할 수 있다.

업무·행동별로 추천만 표시/자동 적용/사람 결정 조건을 정한다. Jev 등 판단 모델은 기존 규칙·생성형 모델과 같은 사례로 비교하고 검증된 영역에 적용한다. confidence 단일 임계값으로 전체 업무를 허용하지 않는다.

반복되는 자료 누락·인계 대기·검토 재작업을 개선 후보로 제시하고 근거 사례를 연결한다. 패턴·정책 버전별 효과를 비교하며 실행 없는 비교 → 제한 적용 → 확대/중단을 지원한다. 중단·이전 정책 복귀가 이미 수행한 외부 행동을 취소하는 것은 아니다.

통과 기준: 사람 개입과 대기는 감소하면서 수용 가능한 결과 품질·오류·비용을 유지한다. 같은 모델이 제안하고 스스로 성공했다고 평가한 값만으로 효과를 확정하지 않는다.

## 7. v1.0 — 검증한 고객군이 반복 도입할 수 있다

진입 근거: 지원 범위 안에서 여러 실제 사용 사례가 반복되고 도입·운영 절차를 재현할 수 있다. 모든 v0.4 고급 기능을 반드시 갖춰야 v1.0이라는 뜻은 아니다.

지원 업무·도구·권한·한계를 명시하고 온보딩·연결 복구·데이터 보존·업그레이드·지원 문서를 정비한다. 팀 단위 접근 범위와 비용 관리를 실제 도입 요구에 맞춰 검증한다. 선언한 범위에서 결과를 안정적으로 제공하고 데이터 손실 없이 업그레이드할 수 있어야 한다. 전사 적용·신규 직무는 별도 검증으로 확장한다.

## 8. 벤치마킹 — 기능 복제보다 사용자 부담을 비교한다

공식 자료 확인일: 2026-09-23. 아래는 문서에서 확인한 기능과 우리 적용 가설이다. 직접 제품을 조작해 검증한 기록이나 각 회사의 창업 당시 성장 과정은 아니다. 현재 기능을 확인했다고 같은 품질·효과를 검증한 것으로 쓰지 않는다.

| 대상 | 공식 자료에서 확인한 기능 | 배울 부분 / 우리 적용 가설 | 적용 단계 |
|---|---|---|---|
| Devin | Jira 업무에서 에이전트 실행으로 이어지는 연동 | 기존 티켓에서 시작할 때 필요한 추가 입력·결과 확인·재개 부담을 비교. 단일 실행자 연결과 우리 담당자별 Agent 인계의 차이를 검증 | MVP |
| Linear Triage Intelligence | 기존 이슈를 참고해 담당·팀·라벨·관계 추천, 속성별 자동 적용 | 추천 근거와 세분화된 적용 범위. 사용자가 고친 이유를 설정 개선에 연결 | v0.3~v0.4 |
| Intercom Fin Recommendations | 미해결 대화에서 지식·외부 데이터 부족 등 개선 후보와 근거 대화 제공 | 실패율 숫자에서 끝내지 않고 반복 대기를 해결할 변경을 제안 | v0.4 |
| Zapier | 연결·템플릿·필터·테스트·실행 이력, 자연어 구성도 제공 | 계정 연결·필드 매핑·첫 실행·오류 확인의 부담을 참고. 자연어 워크플로우 생성은 우리 MVP에 복제하지 않음 | MVP~v0.2 |

### 비교 절차

1. 같은 목표·유사 난이도의 지원 업무를 준비한다. 기존 서비스+수동 Agent 실행을 기본 비교 대상으로 삼고, 가능한 경우 기존 자동화 도구 구성도 비교한다.
2. 첫 사용과 반복 사용을 분리한다. 첫 사용은 계정 연결부터 첫 유효 결과까지, 반복 사용은 준비된 업무 접수부터 후속 착수까지 잰다.
3. 사용자가 다시 작성한 정보, 복사·붙여넣기, 담당 선택, 실행 조작, 필요한 설정과 오류 복구를 기록한다. 지원하지 않는 경로는 실패 0건으로 기록하지 않고 미지원으로 표시한다.
4. 추천·분류는 기록 없는 사례, 충분한 기록, 오래되거나 상충하는 기록으로 나눠 시험한다. 당시 이용 가능했던 자료만 주며 평가 대상의 최종 결과를 입력에 섞지 않는다.
5. 원문 링크·확인일·플랜/버전·환경·지원 범위·실제 관찰·우리 적용 여부를 기록한다. 유료 기능·실계정·외부 변경이 필요한 실험은 범위를 먼저 정한다.

첫 비교 결과는 이 문서에 날짜별로 추가하고, 실행 원본은 VERIFICATION_LOG에 남긴다. 벤치마킹만을 위한 새 문서 체계를 늘리지 않는다.

| 기록할 필드 | 내용 |
|---|---|
| 비교 질문 | 예: 같은 티켓을 Agent에게 맡기기 위해 다시 작성해야 하는 정보는 무엇인가? |
| 사례와 조건 | 업무, 도구/플랜/버전, 연결 상태, 사전 설정, 담당자, 실행 환경 |
| 관찰 | 시간·조작·결과 품질·실패·복구와 근거 링크 |
| 판단 | 채택할 UX·계약, 채택하지 않을 범위, 다음 검증 |

현재 직접 사용 비교: 미수행. 문서 조사 결과만 위 표에 기록했다.

## 9. 지표와 개발 우선순위

| 지표 | 측정 정의·주의 |
|---|---|
| 첫 유효 결과까지 시간 | 연결 시작부터 사용 가능한 결과 확인까지. 설치·설정 시간 포함 |
| 인계 대기 | 후속의 필수 조건 충족 시점부터 실제 착수까지. 입력 부족·승인 대기는 별도 집계 |
| 전체 처리 시간 | 접수부터 수용 가능한 결과까지. 에이전트 종료 시각과 구분 |
| 사람 중계·예외 | 재작성·복사·배정·실행 조작과 필요한 결정·승인을 구분 |
| 품질·재작업 | 수용 여부, 오배정·중복 생성·잘못된 실행, 수정 요청과 재시도 |
| 비용 | 모델·실행의 확인 가능한 비용과 사람 설정·검토 시간. 추정은 표시 |
| 반복 사용 | 처음 성공 후 다음 실제 업무도 맡겼는지와 사용 중단 이유 |
| 추천 효과(후속) | 수락·수정·거절뿐 아니라 설정 시간과 적용 후 품질 변화 |

소규모 표본은 사례별 결과를 보여주고 일반화하지 않는다. 비교 시 업무 유형·난이도·기간·건수와 완료되지 않은 업무도 표시한다. 출시/확대 임계값은 각 파일럿 전에 PRD 또는 실험 계획에 명시한다.

고객별 업무 기록은 해당 고객의 설정과 실행 개선에 사용한다. 제품 개발을 위한 피드백·집계와 구분하며, 여러 고객의 원문을 한데 모으거나 모델 학습에 사용하는 것을 전제하지 않는다. 수집 범위·보관·접근·삭제·외부 모델 전달 정책은 실제 수집 전에 정한다.

GitHub Issues 버그 수정 → 커밋 검토 순환이 구현되어 대역 단위·e2e 테스트(가짜 GitHub·가짜 Agent)를 통과했다. 실제 GitHub·실제 Agent 전체 순환(step 16)은 아직이므로 위 MVP 통과 기준의 실연동 조건은 충족하지 않았다. 운영 절차·미검증 항목·실연동 체크리스트는 [GitHub 런북](../github/README.md).

2026-09-26: 10/2 까지의 구체 범위(측정·셀프호스트·OpenArchive 실연동)와 phase 계획은 [MVP 계획](MVP_PLAN.md)에 둔다.

1. 파일럿 도구·업무 유형을 정한다. 기본 제안은 GitHub Issues의 명확한 버그 수정 → 검토이며, 실제 팀이 Jira를 쓰면 Jira 우선으로 바꾼다.
2. PRD의 MVP 계약을 구체화한다: 가져오기 범위, 담당자 연결, 필수 입력, 허용 행동, 원본 결과 반영, 후속 생성, 사람 응답과 중복 처리.
3. 현재 코드와의 간극을 확인하고 TDD step으로 나눈다. 기존 실행 엔진을 재사용하고 전면 재작성이나 모든 도구 추상화를 먼저 만들지 않는다.
4. 실행 기록은 첫 단계부터 남긴다. MVP에서 집계는 수동으로 시작할 수 있다.
5. 실제 사용에서 반복되는 불편을 확인해 v0.2 이후 우선순위를 갱신한다. 사용자 수 증가만으로 데이터가 충분하다고 가정하지 않는다.

변경 시 제품 목적은 PRODUCT_BRIEF, 출시 범위와 단계는 이 문서, 구체적인 동작은 PRD, 기술 계약은 ARCHITECTURE/CONTRACT, 결정 이유는 ADR에 기록한다. 실행 완료는 CURRENT_HANDOFF와 VERIFICATION_LOG에 따로 남긴다.
