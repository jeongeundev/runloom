[공개 사례 K1](INTERNAL_REQUEST_PUBLIC_CASES.md#사례-k1--업그레이드-후-kube-proxy-기동-실패-재전달--우회책--원인-확정)을 셀프호스트(스키마 v24)에서 세 계정이 실제 러너·Claude CLI 로 진행한다. 목적은 **사람 사이 흐름**(판단 제안 → 수정 → 결과 뒤 판단이 사내 요청 제안 → 수락 → 질문 → 조사 → 검토 → 판단 → 반환 → 반환 후 판단 제안)의 결함과 혼란을 찾는 것이다. 조사 품질은 평가하지 않는다.

**v23 문서에서 바뀐 점(2026-10-05)**: R 이 직접 요청하는 흐름에서는 반환 뒤 제안이 뜨지 않는다 — ③ 반환 후 판단은 원업무에 결과를 낸 실행이 있어야 시작한다(`worker._returned_cause`). 그래서 판단 에이전트를 지정해 접수 판단 → 수정 실행 → ② `needs_information` 결과 뒤 판단 → 사내 요청 제안 순으로 요청이 만들어지게 한다. 요청 본문은 판단이 쓴다(아래 "요청 본문"은 비교용).

## 이번 회차의 우회와 한계

- **능력 우회**: 러너 등록 에이전트의 능력은 `code.fix`·`code.review`·`code.triage` 로 고정이다(`adapters/repo.py` 등록 경로). 조사 종류의 능력 코드를 `code.review` 로 등록해 기존 에이전트를 후보로 만든다. `list_kinds` 는 내장 종류를 먼저 돌려주므로 `code.review` 로 찾는 기존 GitHub 검토 매칭은 내장 `code_review` 를 그대로 쓴다.
- **자료 없음**: 사용자 정의 종류는 빈 인계 디렉터리에서 `Read`·`Glob`·`Grep` 만, 네트워크 없이 돈다. 에이전트는 요청 본문과 답변만 본다. K1 의 원인 확정(코드의 `!=` 비교)은 재현할 수 없다.
- **에이전트**: `runloom-sandbox` (OpenArchive 는 쓰지 않는다).
- **원업무**: runloom-sandbox #5 → `RUN-26`(`runloom` 라벨 없음 — 자동 실행 안 됨). 판단 에이전트를 sandbox 카드에 지정하면 접수 판단이 자동으로 돈다(대상: 새로 들어옴·담당 없음 업무 — sandbox 에는 RUN-26 하나, OpenArchive 카드는 지정하지 않는다).
- **수정 결과는 보장 안 됨**: sandbox 에 kube 코드가 없어 `needs_information` 이 나올 가능성이 크지만, 다른 결과면 sandbox 에 PR 이 생긴다 — 그대로 기록하고 그 결과에서 이어 간다.
