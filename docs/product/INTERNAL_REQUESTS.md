# 사내 요청 — 생성과 수락

2026-10-03. [요청 계약 설계](INTERNAL_REQUEST_CONTRACT_DESIGN.md)의 첫 접수 흐름을 구현했다. 한 공유 워크스페이스에서 원래 `WorkItem`을 유지하면서 담당표의 수신자에게 목적과 맥락을 전달한다. 이 문서는 생성과 수락을 설명한다. 후속 [조사 실행·결과 반환](INTERNAL_REQUEST_INVESTIGATION.md)을 연결했다. [담당 아님·명시적 재전달](INTERNAL_REQUEST_REROUTING.md)도 구현했다. [정보 질문·답변](INTERNAL_REQUEST_INFORMATION.md)도 구현했다. [지정 판단 담당자 응답](INTERNAL_REQUEST_JUDGMENT.md)도 구현했다. 원업무 재개 확인은 후속 범위다.

## 화면

1. **연결 → 팀·담당자**에서 담당 범위를 등록한다.
2. 업무 상세의 **다른 담당자에게 요청**에서 담당 범위와 수신자를 명시적으로 선택하고 조사 목적·공유할 맥락을 입력한다. 후보가 한 명이어도 자동 선택하지 않는다.
3. 수신자는 사이드바의 **받은·보낸 요청**(`/requests`)에서 원래 업무와 목적을 확인하고 수락한다. 이 화면에는 본인이 보냈거나 받은 요청만 표시한다.
4. 원래 업무 상세에서도 수락 대기·수락됨을 확인한다. 수락은 접수 확인이며 원업무 완료나 에이전트 실행을 의미하지 않는다.

한 공유 워크스페이스의 기존 업무 열람 범위를 사용한다. 업무별 요청 조회와 업무 상세는 해당 워크스페이스의 로그인 멤버가 볼 수 있다. 받은·보낸 요청 목록을 본인 기준으로 거르는 것이 부서별 자료 접근 격리를 구현한 것은 아니다.

## API

| 경로 | 필요 조건 | 동작 |
|---|---|---|
| `POST /work-items/{work_item_id}/internal-requests` | 로그인·`delegate` | 담당표 확인 후 요청 생성 또는 같은 접수 키 재전송 처리 |
| `GET /work-items/{work_item_id}/internal-requests` | 같은 워크스페이스 로그인 | 원업무의 요청 목록 |
| `GET /internal-requests` | 로그인 | 본인이 보냈거나 받은 요청 목록 |
| `POST /internal-requests/{request_id}/accept` | 로그인·`respond`·지정 수신자 본인 | 요청 수락 |

생성 본문:

```json
{
  "system_id": "billing",
  "request_kind": "investigation",
  "recipient_member_id": "등록된 수신자 ID",
  "expected_directory_revision": 4,
  "submission_key": "billing-investigation-1",
  "purpose": "합성 오류 기록을 보고 원인을 확인해 주세요."
}
```

수락 본문은 `{"expected_revision": 1}`이다. 응답은 `request_id`, 원업무·요청자·수신자·판단 담당자 ID, 시스템·요청 유형·선택적 에이전트, `directory_revision`, 목적, `state`, 요청 `revision`, 생성·수락 시각을 포함한다. 생성은 `pending`·revision 1, 수락은 `accepted`·revision 2다. `request_kind`는 담당 범위 분류이며 실행 종류를 지정하지 않는다.

## 중복과 조건 검사

- 생성·수락 각각은 `BEGIN IMMEDIATE` 트랜잭션으로 검사와 저장을 처리한다. 동시에 도착한 같은 요청/수락은 한 번만 기록한다.
- 접수 키는 워크스페이스·요청자별로 유일하다. 같은 키의 원업무·시스템·유형·수신자·목적이 같으면 기존 요청의 현재 상태를 반환한다. 다른 내용이면 409 `submission_conflict`다. 설정 revision은 새 요청 생성의 전제이며 이미 접수된 요청 재전송에는 다시 적용하지 않는다.
- 새 요청은 현재 담당표 revision과 후보의 존재를 확인한다. 오래된 표는 409 `stale_directory`, 후보 없음·비활성 담당자·해제된 에이전트는 422 `invalid_recipient`다.
- 수신자·판단 담당자·에이전트는 생성 시 스냅샷으로 보존한다. 이후 담당표 수정으로 기존 요청의 수신자를 바꾸지 않는다. 수락 시 스냅샷의 담당자 활성 여부와 에이전트 등록을 다시 검사한다. 담당표 항목 삭제 자체는 이미 접수된 요청을 취소하지 않는다.
- 수락은 지정 수신자만 가능하다. 관리자도 수신자를 대신해 수락할 수 없다. 다른 행위자는 403 `forbidden`, 다른 워크스페이스/없는 요청은 404 `not_found`다.
- 수락의 오래된/부적합 revision은 409 `stale_request`다. 이미 수락된 요청에 처음 수락 때의 revision 1 또는 현재 revision 2를 다시 보내면 같은 기록을 반환한다. 시각·revision을 다시 바꾸지 않는다.
- 목적은 1–4000자이며 공백만 있는 값은 거부한다. 등록 식별자를 로컬 경로나 셸 명령으로 실행하지 않는다. 쿠키 변경 요청에는 기존 Origin 검사를 적용한다.

## 저장과 검증

스키마 v18의 `internal_requests`는 원업무 참조, 접수 책임, 선택 시점의 대상, 목적, 요청 상태·revision·시각을 저장한다. 원업무 담당·상태·Task·Execution·사용 승인은 생성과 수락으로 바뀌지 않는다. v17 이전 지원 DB에는 기존 마이그레이션 뒤 빈 표·색인을 추가한다. 기존 데이터와 담당표를 보존하며 과거 요청을 추정하지 않는다.

테스트는 생성·수락 정상 흐름, 원업무/실행 불변, 같은 키의 재전송·내용 충돌, 동시 접수·동시 수락, 관리자 대신 수락 금지, 비활성 판단 담당자·해제된 에이전트 검사, 워크스페이스·로그인·Origin 경계, 화면 폼·이스케이프, DB 업그레이드·백업을 확인한다. 브라우저 조작이나 실제 조직의 두 담당자를 통한 효과 측정은 이번 검증에 포함하지 않았다. 운영 DB나 배포 환경을 직접 변경하지 않았다.

수락 후의 Task 생성·실행 조건 검사·결과 검토·반환은 [조사 실행·결과 반환](INTERNAL_REQUEST_INVESTIGATION.md)을 따른다. 지정 판단 담당자 정보는 현재 대상 기록이며, 업무상 판단 권한의 검사·응답 흐름은 후속 구현이 필요하다.
