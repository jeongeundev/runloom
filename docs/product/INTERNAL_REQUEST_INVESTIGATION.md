# 사내 요청 — 조사 실행과 결과 반환

2026-10-04. [생성·수락](INTERNAL_REQUESTS.md) 다음 단계다. 수락된 요청을 등록된 로컬 에이전트의 읽기 전용 조사 Task에 연결하고, 계약 검증과 사람 검토를 거친 최신 결과를 원래 업무에 반환한다.

## 사용 흐름

1. **받은·보낸 요청**에서 지정 수신자가 요청을 수락한다.
2. **조사 종류와 등록 범위**를 명시적으로 선택하고 **조사 시작**을 누른다. 후보는 해당 요청에 고정된 에이전트의 현재 능력·범위와 워크스페이스의 종류 등록에서 나온다.
3. **조사 작업** 링크로 실행·대기 사유와 결과를 확인한다. 소유자 사용 승인이나 온라인 러너를 기다리는 경우 기존 대기 흐름을 사용한다.
4. 기존 조사 Task 화면에서 결과를 검토·승인한다. 내용 검토는 사람이 한다. 모델 응답이나 프로세스 종료만으로 조사 완료를 판정하지 않는다.
5. 지정 수신자가 요청 화면에서 **검토된 결과 반환**을 누른다. 원래 업무에 결과 요약과 해당 산출물 링크가 표시된다.

결과 반환은 원래 업무 해결이나 완료를 뜻하지 않는다. 요청자의 업무 재개 확인과 예외 흐름은 후속 구현이다. `needs_information` 같은 허용 outcome도 사람이 검토해 반환할 수 있으며 성공으로 자동 집계하지 않는다.

## 원래 업무와 조사 업무 분리

최초 설계는 조사 Task를 원래 업무 안에 두는 안이었다. 현재 `repo._refresh_stage_work`는 Task의 실행·검토 변경을 그 Task가 속한 WorkItem 상태에 반영한다. 이 구조에서 조사 완료가 원래 업무의 완료 계산에 섞일 수 있다.

따라서 조사 전용 WorkItem과 첫 Task를 만들고 `internal_request_investigations`로 요청에 연결한다. 원래 업무는 요청의 `work_item_id`로 보존한다. 별도 조사 업무의 담당과 실행 요청자는 수신자다. 실제 에이전트 선택과 대상은 요청에 고정된 Agent 등록값을 사용한다. 이 선택은 원업무 담당·상태 보존을 우선하며 기존 업무 상태 계산을 변경하지 않는다. 임의의 `blocks`·`spawned_from` 링크로 요청의 의미를 대신하지 않는다.

## 실행 계약

- 등록된 `KindSpec.output_kind == generic_result`, `input_kinds == []`인 종류만 선택할 수 있다. 종류 이름을 실행 코드에 하드코딩하지 않는다.
- 조사 목적·공유 맥락은 기존 실행 요청 텍스트에 넣는다. 이번 단계에는 별도 공유 파일/산출물 선택을 붙이지 않았다.
- 에이전트는 요청 생성 때 고정한 같은 워크스페이스의 등록된 로컬 Agent다. 로컬 등록 ID와 `LocalTarget`은 등록값에서 만들며 외부 입력의 명령·경로를 실행하지 않는다.
- 종류의 capability code·scope key와 선택한 scope value가 Agent의 등록 능력과 정확히 일치해야 한다. scope value를 입력한다고 새 접근 권한이 생기지 않는다.
- 조사 작업 생성과 요청 연결·revision 증가·착수 대기 표시는 한 쓰기 트랜잭션이다. 생성 뒤 기존 `start_stage`를 호출하고, 소유자 승인·온라인 조건이 풀리면 워커가 이어서 시작한다. 생성 직후 프로세스가 중단돼도 착수 대기 기록을 보존한다.
- 실행 직전에 요청 대상의 활성 여부, Agent 등록·로컬 등록 ID·능력·범위를 다시 검사한다. 일반 Task 실행, 워커 재착수, 검토 재요청의 실행 생성 경로에 같은 검사를 적용한다. 조건 불일치면 실행하지 않는다. 재요청 조건이 실패하면 기존 결과를 먼저 해제하지 않는다.
- 기존 `LocalTarget` 어댑터의 읽기 모드와 인계 디렉터리 변경 검사를 사용한다. 호스트 전체·외부 시스템·네트워크의 접근 격리를 새로 구현하거나 검증한 것은 아니다. 실제 자료 연결 전 선택 도구의 접근 범위를 확인해야 한다.

## API와 중복 처리

| 경로 | 본문 | 의미 |
|---|---|---|
| `POST /internal-requests/{request_id}/investigation` | `expected_revision`, `kind`, `scope_value` | 수신자가 수락된 요청에 조사 작업 하나를 연결하고 착수 |
| `POST /internal-requests/{request_id}/return` | `expected_revision`, `execution_id` | 수신자가 검토된 최신 조사 결과를 반환 |

조사 시작은 `delegate`, 반환은 `respond`와 지정 수신자 본인 조건을 모두 검사한다. 관리자도 수신자를 대신할 수 없다. 수락 전 시작은 409 `not_accepted`; 부적합 종류·에이전트·범위는 422다.

접수 상태 `state`는 기존 `pending`·`accepted`를 유지한다. 조사 단계는 `investigation_task_id`와 `returned_at`으로 구분하며 화면에 수락 대기·수락됨·조사 작업 연결됨·결과 반환됨을 표시한다. 요청 revision은 생성 1 → 수락 2 → 조사 연결 3 → 반환 4다. 반환 뒤 추가 실행은 허용하지 않는다.

같은 종류·범위의 시작 재전송은 이미 연결한 Task를 반환한다. 최초 시작의 revision 2 또는 현재 요청 revision을 받으며 Task나 Execution을 다시 만들지 않는다. 다른 종류·범위는 409 `investigation_conflict`다. 실행 재시도는 기존 Task의 명시적 실행·검토 재요청 경로를 사용한다.

반환은 쓰기 트랜잭션에서 다음을 검사한다:

1. 지정 수신자와 요청 revision.
2. 해당 요청에 연결된 Task의 완료·검토 승인.
3. 그 Task의 최신 Execution ID와 `result_ready`, 해당 Execution의 `passed` 판정.
4. 저장된 `GenericResult`의 Execution·Task·종류 ID와 실행 요청에 고정된 허용 outcome.

요약은 요청 본문에서 받지 않고 그 결과 산출물에서 읽는다. 반환 Execution·산출물·요약·시각·행위자를 보존한다. 검토 전은 409 `result_not_reviewed`, 검증 실패는 409 `result_not_valid`다. 같은 결과의 revision 3 또는 현재 revision 4 재전송은 같은 반환 기록이며 시각과 revision을 다시 바꾸지 않는다. 다른 결과/부적합 revision은 충돌이다.

Task 검토는 기존 공유 워크스페이스의 `respond` 정책을 유지한다. 지정 수신자는 결과 반환을 확인한다. 요청의 `judgment_member_id`는 이후 업무상 판단 요청의 대상이며 이번 Task 검토로 업무상 판단권자 정책을 구현했다고 보지 않는다.

## 저장과 검증 범위

스키마 v19는 `internal_request_investigations`를 추가한다. 요청 하나에 Task 하나, Task 하나에 요청 하나만 연결하며, 반환 결과 참조와 시각·행위자가 함께 기록되도록 검사한다. 지원되는 기존 DB에는 빈 표를 추가하고 기존 요청·담당표·원업무를 보존한다.

테스트는 정상 실행 예약·워커 결과 검증·사람 검토·반환, 원업무 담당·상태 보존, 잘못된 종류·범위와 비수신자 차단, 소유자 승인 대기, 대기 중 능력 변경·검토 재요청 조건 검사, 검증 실패 결과 반환 차단, 동시 시작·반환 중복 방지, 화면 링크·이스케이프, 마이그레이션·백업을 확인한다.

테스트의 실행 결과는 합성 산출물이다. 실제 AI CLI 실행·브라우저 조작·실제 회사의 협업 효과는 이 단계에서 검증하지 않았다. 운영 DB·러너·외부 업무·배포 환경에는 변경을 직접 적용하지 않았다.
