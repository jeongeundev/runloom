# 반환 결과를 받은 뒤 원래 업무 재개 기록

2026-10-04

## 사용자 흐름

담당자가 검토된 결과를 반환하면 원래 요청자의 사내 요청 화면에 **업무 재개 기록** 입력란이 표시된다. 요청자가 반환 결과를 받고 재개한 내용을 직접 기록한다. 요청 화면과 원래 업무 패널에서 내용·시각을 확인할 수 있다.

이 기록은 사용자의 확인이다. 실행을 예약하거나 업무 상태·담당자·완료 여부를 변경하지 않는다. 이미 종료된 원래 업무도 상태 변경 없이 기록만 남길 수 있다. 실제 업무 재개를 시스템이 감지했다는 뜻은 아니다.

## 권한과 중복 처리

- 같은 워크스페이스의 실제 요청자이며 RESPOND 권한을 가진 멤버만 기록한다. 수신자나 관리자라는 이유로 대신 기록할 수 없다.
- 결과 반환 완료와 현재 요청 revision을 검사한다. 반환 전 기록은 거부한다.
- 요청별 한 번 기록하며 반환된 실행·산출물 참조, 작성자, 시각과 내용을 함께 보존한다.
- 같은 revision·내용의 재시도는 동일 기록을 반환한다. 다른 내용으로 덮어쓰기는 거부한다. 동시 요청도 쓰기 트랜잭션과 요청 ID 기본 키로 중복을 막는다.
- 별도 기록이므로 요청 revision은 증가시키지 않는다. 반환 완료 요청은 revision 4를 유지한다.

## API와 저장

`POST /internal-requests/{request_id}/resume`

```json
{"expected_revision": 4, "text": "반환된 원인을 확인하고 수정 작업을 재개했습니다."}
```

기존 텍스트 응답 계약을 사용한다. 내용은 최대 4,000자이며 공백만 있는 입력과 추가 필드를 거부한다. 응답과 목록에 `resumption`을 포함하고 기록 전에는 null이다. `resumption`에는 request_id, execution_id, artifact_id, text, resumed_by_member_id, resumed_at이 있다.

스키마 v23은 `internal_request_resumptions` 표를 추가한다. v4~v22에서 데이터를 보존해 마이그레이션하며 기존 업무 표는 변경하지 않는다.

## 검증 범위

합성 자료로 반환 전 차단, 요청자 권한, 입력·버전 검증, 재시도·충돌·동시 처리, 화면 표시와 이스케이프, 마이그레이션 및 원래 업무 상태 보존을 검증한다. 운영 DB와 실제 AI CLI에는 적용하지 않았다. 실제 조직의 대기 시간 감소는 별도 파일럿에서 검증해야 한다.

이제 담당자 선택 → 수락 → 조사 → 정보 확인·필요한 판단 → 결과 반환 → 요청자의 재개 기록까지 연결된다. [합성 통합 검증과 파일럿 기록 양식](INTERNAL_REQUEST_PILOT_RECORD.md)에 재현 명령·측정 항목을 정리했다. 다음은 실제 사례 기록이다.
