# 공개 사례 복원 — Kubernetes 이슈 3건

작성일: 2026-10-04
상태: 기존 방식 사례 3건 복원. 서비스 사용 사례·비교는 미실행.

회사 내부 사례를 확보할 수 없어 [파일럿 기록 양식](INTERNAL_REQUEST_PILOT_RECORD.md)을 공개 오픈소스 이슈에 적용했다. Kubernetes 는 SIG(분야별 담당 그룹)로 담당이 나뉘고, 담당 지정·재전달(`/sig`, `/remove-sig`)·수락(`/triage accepted`)이 라벨 이벤트로 시각과 함께 남는다. GitHub timeline API 를 읽기만 했다.

한계: 회사 내부 요청이 아니다. 지정된 판단 담당자 개념이 없고 maintainer 합의로 결정된다. 사람이 직접 작업한 시간은 알 수 없다. 원업무 재개는 요청자가 이슈에 남긴 경우만 기록했다. 3건은 재전달이 있었던 이슈를 골랐으므로 대표 표본이 아니다. 사람은 역할로만 적는다.

## 세 사례에서 보인 것과 현재 제품의 대응

| 관측 | 사례 | 현재 제품(v23) | 비고 |
|---|---|---|---|
| 요청자가 고른 첫 담당이 틀림 | K1·K2·K3 모두 | 담당 범위 표로 요청자가 후보를 고름 | 오배정 자체를 줄이는지는 미확인 |
| 재전달은 **받은 쪽**이 바로 다른 담당으로 넘기고 전문가를 호출 | K1·K2 | 받은 쪽은 반려만, **요청자가** 다른 후보를 골라 재전달 ([재전달](INTERNAL_REQUEST_REROUTING.md)) | 공개 사례보다 왕복이 한 번 더 생김 |
| 최종 수정 전에 **우회책**이 먼저 돌아가 요청자가 재개 | K1 | 반환은 요청당 한 번, 반환 후 새 질문 막힘 | 부분 결과 반환 경로 없음 |
| 요청자가 담당에게 묻는 질문 | K1(답변됨)·K2(미답변 종료) | 질문은 수신자→요청자 방향만 | 거절 뒤 후속 질문 경로 없음 |
| 한 요청이 두 담당·다른 저장소 소유자로 갈라짐 | K3 | 요청 하나에 수신자 하나 | 분기 요청은 별도 생성 필요 |
| 판단 대상이 "반환 여부"가 아니라 "어느 쪽이 고칠지" | K3 | 판단 = 결과 반환 승인·거절 ([판단](INTERNAL_REQUEST_JUDGMENT.md)) | 판단 쟁점 범위가 다름 |
| 근거 사실 정정으로 판단 번복 | K3 | 정보 변경 시 이전 판단 무효·재요청 | 대응됨 (반환 전만) |
| 조사 결과는 빠르고 판단이 느림 | K3 (8h vs 10일) | 판단 대기 상태 표시 | 판단 대기 단축 수단(알림·기한)은 없음 |

이 세 건은 우선순위의 근거가 아니라 **실험 시나리오 후보**다. 다음 단계(실제 등록 에이전트로 실행)는 K1 을 입력으로 쓴다 — 재현 정보가 공개돼 있고, 오배정·재설명·우회책·원인 확정이 모두 한 건에 있다. 이 표의 차이를 개선 대상으로 정하려면 같은 유형의 공개 사례를 더 모아 빈도를 확인해야 한다.
