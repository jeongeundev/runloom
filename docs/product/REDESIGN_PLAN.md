## 1. 왜 다시 설계하나

2026-09-29 실연동 직전 사용자 판단: "앱 사용 자체가 불편해 UX·UI 를 처음부터 손대야 할 정도로 뭐가 뭔지 모르겠다." 기능을 phase 마다 덧붙이면서 화면이 기능 단위(`/tasks`·`/operator`·`/operator/github`·`/kinds`·`/rules`·`/metrics`…)로 흩어졌고, 사용자가 해야 할 일이 보이지 않는다.

요구(사용자 말 그대로 정리):
1. **업무 가져오기가 필수** — GitHub 와 Jira. Jira 는 가져오기와 **업무 등록**(되쓰기) 둘 다.
2. **소스별 양식을 Runloom 업무 양식으로 맞춰** 등록한다.
3. 이슈만이 아니라 **PR 도 보인다**.
4. 결과가 **다시 이슈·업무로 등록**되는 흐름이 보인다.
5. **팀 단위** — 담당자(사람·에이전트)별 업무를 본다.
6. 처음부터 모든 내용을 보이지 않는다 — **한 줄 목록 + 누르면 상세**(Jira 목록 보기처럼).
7. 업무 등록 → **판단**(누가 맡을지·어떤 작업·순서) → 배정. 판단은 **로그 분석** 또는 **등록한 사내 판단 에이전트**. 업무 내용이 외부 판정 서비스로 나가면 안 된다.
8. 처음에는 판단이 **제안만** 하고, 업무 종류별로 **자동 시작을 켤지** 설정한다.
9. 자동화는 **전후 비교**가 필수 — 로그 저장과 로그 분석 모니터링.

## 2. 벤치마킹에서 가져온 것

| 무엇을 | 어디서 | Runloom 에서 |
|---|---|---|
| 가져온 항목은 먼저 거른다(수락·거절) | Linear Triage, Plane Intake | "담당 없음" 묶음 + 판단 제안 |
| 제안을 속성별로 "보여주기 / 자동 적용" | Linear Triage Intelligence | 업무 종류별 "제안만 / 자동 시작" |
| 작업 전에 계획·신뢰도를 먼저 낸다 | Devin 범위 산정 모드 | 판단 결과에 확신도·근거 |
| 칸은 상태에서 계산, 사람 할 일은 한 칸 | Agent Orchestrator(Working / Needs you / In review / Ready to merge) | "내 차례" |
| 이슈당 draft PR 1개, 전용 브랜치, 병합은 사람 | Copilot coding agent | phase 12 그대로 |
| PR 과 업무는 키 문자열로 잇는다 | Linear, GitHub for Atlassian | 브랜치·PR 제목에 원본 키 |
| 공통 필드는 작게, 상태는 값 대 값 표 | Linear·Unito·Exalate·Plane | 공통 업무 양식 + 매핑 표 |
| 자동 되먹임에 재시도 상한 | Sculptor CI Babysitter | 재작업 상한(이미 있음) |

"맡길지 말지"를 AI 가 판단해 자동 시작까지 하는 제품은 조사 범위에서 찾지 못했다. 로컬 구독 에이전트 + 규칙 기반 후속 + 판단 단계 + 전후 측정의 조합이 Runloom 의 자리다.

## 3. 흐름

```
[소스] GitHub 이슈·PR · Jira 업무 · 직접 등록 · n8n 입구
   │  가져오기(폴링) + 양식 맞추기(매핑 표)
   ▼
[업무]  담당 없음 ── 판단 업무(판단 에이전트) ──▶ 제안: 종류·담당·순서·진행 여부·확신도·근거
   │                                              │
   │   사람이 확정  ◀── 제안만(기본) ──────────────┤
   │   자동 시작    ◀── 업무 종류별로 켰을 때 ──────┘
   ▼
[배정]  담당 = 사람 또는 에이전트 → 실행 → 결과 판정 → 후속 규칙(검토·재작업·사람 차례)
   ▼
[되쓰기] 원본 댓글(한 개를 고쳐 씀) · 상태 전환 · 초안 PR · PR 링크 · 새 업무 등록(GitHub 이슈·Jira 업무)
   ▼
[기록]  업무 이벤트 · 판단 로그 · 실행 기록 → 모니터링(전후 · 판단 품질 · 담당자별)
```

판단도 업무 종류 하나다(ADR-0009 의 종류·후속 규칙). 판단 업무의 결과 갈래(outcome)가 후속 규칙으로 실제 업무를 만들고 배정한다. 새 실행 엔진을 만들지 않는다.

| **연결** | 가져올 곳(GitHub·Jira, 범위, 되쓰기) · 팀·담당자(사람·에이전트·러너) · 양식 맞추기 표 · 자동 시작(업무 종류별) · 알림 · 에이전트 허용 명령 |

## 5. 데이터 모델 변화

이름은 phase step 0 이 GLOSSARY·ARCHITECTURE 로 고정한다. 여기서는 무엇이 필요한지만.

### 5.1 공통 업무 양식

`Task` 에 원본·양식 칸을 더한다(벤치마킹 문서 "intake-mapping" 의 제안 스키마 기준).

| 칸 | 뜻 | GitHub 이슈에서 | Jira 업무에서 |
|---|---|---|---|
| 원본 종류·원본 ID·원본 키·원본 URL | 어디서 왔나 | `github` · issue id · `#61` · html_url | `jira` · `cloudId:issue.id` · `RL-12` · browse URL |
| 원본 상태 | 참고 신호(완료 판정은 계약 v1) | open/closed | `status.name` + `statusCategory`(new·indeterminate·done) |
| 제목 | | title | summary |
| 업무 종류 | Runloom 종류(버그 수정·기능·문서·판단…) | 라벨·이슈 양식 → 매핑 표 | 이슈 유형(Bug·Story·Task) → 매핑 표 |
| 우선순위 | 높음·보통·낮음 | 라벨(선택) | priority → 매핑 표 |
| 담당 | 사람 또는 에이전트 | assignee → 멤버 매핑(선택) | assignee accountId → 멤버 매핑(선택) |
| 기한 | | milestone due(선택) | duedate |
| 양식: 목표·재현 절차·기대 동작·인수 조건 | 판단·실행 입력 | 본문 절(issue forms 제목) | description(ADF) 절·사용자 필드 |
| 영역 | 저장소·에이전트 매칭 단서 | 저장소 자체 | 컴포넌트·제목 접두 `[영역/기능]` → 매핑 표 |
| 데이터 등급 | 외부 모델에 보내도 되나 | 소스 설정 기본값 | 소스 설정 기본값 |

매핑이 없거나 필수 양식 칸이 비면 업무는 "담당 없음"에서 판단 제안이 "확인 필요"로 나온다. 커스텀 필드 일반 매핑·양방향 필드 동기화·사용자 계정 자동 매칭은 하지 않는다(벤치마킹 권고).

### 5.2 소스와 매핑

- 소스 = GitHub 저장소(기존 `github_sources` 일반화) 또는 Jira 프로젝트. 소스마다 가져오기 범위(GitHub 검색 문자열 / JQL), 주기, 되쓰기 허용 목록, 데이터 등급 기본값.
- 매핑 표(워크스페이스 등록 데이터, 버전 있음): 원본 값 → Runloom 값. 종류·상태·우선순위·영역→저장소·필드→양식 칸.
- 되쓰기 기록: 원본에 쓴 것(댓글 id·상태 전환·PR 링크·새 업무 키)을 남겨 중복을 막는다. Jira 는 원격 링크만 `globalId` 멱등이고 나머지는 Runloom 기록으로 막는다.

### 5.3 팀·담당자

- **멤버**(사람 계정)와 **에이전트**를 같은 "담당" 자리에 둔다. 담당 = 멤버 id 또는 에이전트 id.
- 역할: 관리자(연결·자동 시작·매핑 설정) / 멤버(맡기기·병합 결정·응답).
- "내 차례"는 사람마다 다르다 — 사람 요청이 그 업무의 담당 멤버(없으면 관리자)에게 간다. 알림도 사람별.
- 러너는 멤버 소유(누구의 Mac)이거나 팀 소유(팀 서버).

### 5.4 판단

- 판단 업무 종류: 입력 = 업무 양식 + 로그 근거(같은 종류·영역의 과거 결과, 에이전트 부하, 선행 업무), 결과 = 고정 형태 `{종류, 담당, 선행 업무, 진행: 맡겨도 됨|확인 필요|부적합, 확신도, 근거 목록}`.
- 판단 기준: 판단 에이전트 폴더의 기준 문서 + Runloom 이 매긴 **기준 버전**(설정 번호와 같은 방식 — phase 9). 기준을 바꾸면 버전이 올라간다.
- 판단 로그: 판단마다 입력 요약(해시)·기준 버전·결과·확신도·사람 확정/변경·실제 결과(1회 통과·재작업·병합·거부)를 남긴다.
- 자동 시작 설정: 업무 종류별 끔(제안만) / 켬(확신도 기준값). 판단 기록이 기준 건수(제안 20건) 미만이면 켤 수 없다. 켜고 끈 것도 버전으로 남긴다.

## 6. 판단 단계 설계

1. **판단 에이전트는 러너에 등록한 에이전트다.** 첫 버전은 로컬 Claude Code(구독). 판단 전용 폴더(기준 문서 `.claude/agents/triage.md` 등)를 등록하고 읽기 전용 도구만 준다. 로컬 모델(Ollama·사내 LLM)은 나중(사용자 결정 2026-09-29).
2. **외부 판정 서비스는 쓰지 않는다.** 업무 내용이 나가면 안 되는 경우가 있다(사용자 판단). TypeSafe Jev 같은 판정 전용 모델은 API 전용이라 제외. 단 Claude Code 도 모델 호출은 Anthropic 으로 나간다 — "데이터 등급"(5.1)으로 업무별 허용 범위를 두고, 등급 A(로컬만)는 로컬 모델 에이전트가 생길 때까지 판단·실행을 사람에게 넘긴다.
3. **로그 근거를 입력에 넣는다.** 중앙이 계산(외부 유출 없음): 같은 종류·영역의 과거 N건 1회 통과율·재작업률·평균 시간, 담당 후보의 진행 중 업무 수, 같은 파일을 고치는 선행 업무.
4. **확신도는 로그로 보정한다.** LLM 이 말한 확신도를 그대로 믿지 않는다. 업무 종류별로 "판단이 '맡겨도 됨'이라 한 업무 중 실제 병합 비율"과 "사람과 일치율"을 모니터링에 보이고, 자동 시작 기준값은 이 수치를 보고 사람이 정한다.
5. **판단 기준의 첫 항목**(기준 v1 초안, step 에서 문서로): 명확성(목표·재현 절차·기대 동작·인수 조건), 검증 가능성(등록 검증 명령으로 확인되나), 범위(영향 모듈 수), 위험(운영 접근·비밀값·되돌리기 어려움·데이터 등급), 권한(담당 후보의 허용 명령으로 되나 — ssh 등), 과거 유사 결과, 선행 의존.
6. A2A: 지금은 필요 없다. 판단 에이전트가 수정 에이전트에게 "할 수 있나"를 묻는 형태로 나중에 확장할 수 있게 판단 결과 형태를 계약으로 둔다.

## 7. Jira 연동

벤치마킹 문서 "jira-integration" 의 권고안을 따른다.

- **인증**: API 토큰(사이트 주소 + 이메일 + 토큰 붙여 넣기) → 연결 확인 → 프로젝트 고르기. 토큰은 비밀 저장소(`secret_store`, 0600). OAuth 3LO 는 사용자가 개발자 콘솔에서 앱을 직접 만들어야 해서 1인 셀프호스트에 더 번거롭다 — Tunnel·웹훅 쓰는 사용자용 고급 경로로 미룬다.
- **가져오기**: 폴링. `GET /rest/api/3/search/jql`(옛 `/search` 제거 중), `fields` 명시, `nextPageToken` 페이지, 증분은 `updated >= <epoch ms>`. 웹훅은 공개 HTTPS 만 받아 127.0.0.1 셀프호스트에서는 못 쓴다.
- **본문**: v3 는 ADF(JSON). 가져올 때 ADF → 텍스트·절 추출, 쓸 때 짧은 Markdown → ADF 변환기(제목·문단·목록·코드·링크만).
- **되쓰기**(`write:jira-work` 범위): 댓글(한 개를 고쳐 씀), 상태 전환(전환 id 는 업무마다 조회, 매핑 표의 상태로), 원격 링크(PR — `globalId` 로 멱등), 새 업무 생성(연결 설정의 기본 이슈 유형·필수 필드 기본값, createmeta 로 필수 필드 확인), 이슈 링크(원인 업무와 "relates").
- **PR 표시**: 브랜치 `task/<원본 키>`·PR 제목에 `RL-12` → GitHub for Atlassian 앱이 설치된 Jira 는 개발 패널에 PR. 설치 안 됐으면 원격 링크로 대신.
- 미확인: OAuth 콜백 `http://127.0.0.1` 허용, 리프레시 토큰 절대 만료, Data Center 페이지 방식.

## 8. GitHub 확장

- 이슈와 **PR 을 함께 가져와** 업무 옆에 보인다(업무가 연 PR, 원본 이슈에 연결된 PR). PR 만 있는 업무(리뷰 요청)는 나중.
- 이슈 양식(issue forms) 제목으로 양식 칸을 채운다.
- 되쓰기에 **새 이슈 등록**(후속 규칙이 만든 업무를 원본 쪽에도).
- GitHub App 권한: Issues RW, Pull requests RW, Metadata R(현재와 같음). 브랜치 이름에 원본 키.

## 9. 에이전트 허용 명령

러너가 에이전트를 사용자 계정으로 띄우므로 터미널에서 되는 연결(ssh 등)은 원칙적으로 에이전트에서도 된다. 지금 막는 것은 `connector/claude.py` `ALLOWED_TOOLS` 고정과 환경 허용 목록(`SSH_AUTH_SOCK` 없음). 러너 로컬 등록에 **허용 명령 목록**(`--allow "Bash(ssh opensql-node-*)"` 형태)과 넘길 환경 이름을 선언하게 하고, 화면에는 선언된 것만 보인다(값·명령은 러너 로컬 — 중앙은 이름만). 판단 기준의 "권한" 항목이 이 목록을 본다.

## 10. 모니터링

phase 9 의 `task_events`·설정 번호·기준선·`/metrics` 를 넓힌다.
- 전후: 기존 지표 + Jira 이력 기준선(생성 → 해결).
- 판단 품질: 판단 로그로 계산(5.4).
- 담당자별: 완료·진행·내 차례 대기·알림 → 응답 시간.
- 버전 비교: 매핑 표·판단 기준·자동 시작 설정 버전별.
- 원칙 유지: 시스템이 남긴 기록으로만, 건수 함께, 인과 단정 안 함.

## 11. 접근 모델

지금 셀프호스트는 고정 워크스페이스 + 운영자 토큰 로그인 하나다([ADR-0016](../adr/0016-selfhost-docker-fixed-workspace.md)). 팀 단위로 가려면 계정이 필요하다. 첫 버전 제안: 관리자가 만든 **초대 링크**로 멤버가 이메일·비밀번호 계정을 만든다(외부 인증 없음, 셀프호스트). GitHub·Jira 사용자와 멤버의 연결은 선택(담당 매핑용). demo 모드와 `main` 은 그대로.

## 12. phase 제안

순서는 "모델 → 팀 → 화면 → 소스 → 판단 → 모니터링". 화면을 먼저 바꾸면 새 모델이 없어 다시 고쳐야 하고, Jira 를 먼저 붙이면 공통 양식 없이 GitHub 전용 칸이 늘어난다.

| 순서 | phase | 내용 |
|---|---|---|
| 1 | `13-task-model` | 공통 업무 양식 칸, 소스·매핑 표 일반화(GitHub 를 새 모델로 옮김), 담당 = 멤버 또는 에이전트, 되쓰기 기록 |
| 2 | `14-team` | 계정·초대·역할, 사람별 "내 차례"·알림, 러너 소유자 |
| 3 | `15-work-ui` | 업무 목록(담당자별 묶음·필터·목록/보드)·상세 패널·연결 화면·시작하기. 기존 기능 화면 정리 |
| 4 | `16-jira` | 토큰 연결·프로젝트 선택·JQL 폴링·매핑·되쓰기·ADF·PR 링크, Jira 기준선 |
| 5 | `17-triage` | 판단 업무 종류·결과 형태·기준 버전·로그 근거·판단 로그·제안 UI·자동 시작 설정 |
| 6 | `18-monitor` | 판단 품질·담당자별·버전 비교 화면 |
| 함께 | (작은 step) | 에이전트 허용 명령(9절)은 13 또는 17 에 넣는다 |

그 뒤 실연동(13절). 일정은 phase 당 하네스 실행 반나절~하루 기준으로 1주 이상 — 10/2 목표는 이 재설계로 넘어간다(사용자 확인 필요).

## 13. 실연동 환경

- **저장소**: Runloom `service` 를 복사한 새 비공개 저장소(제안 `jeongeundev/runloom-sandbox`). Runloom 본 저장소(공모전 심사 ~10/5)와 OpenArchive(공모전 출품작 — 쓰기 금지)는 쓰지 않는다.
- **Jira**: 사용자 계정으로 무료 Jira Cloud 사이트를 새로 만든다. 지인 회사 Jira 화면은 **형식만** 참고한다(내용은 옮기지 않는다): 이슈 유형 버그·작업, 회사가 정한 한국어 상태 이름(대기·진행 중·리뷰중·종료), 해결 칸, 기한, 제목 접두 `[영역/기능]`, 담당자별 묶음 보기.
- 연습 업무: sandbox 저장소의 실제 개선거리를 GitHub 이슈와 Jira 업무로 나눠 만든다(버그·기능·문서, 양식이 빈 것·부적합한 것 포함 — 판단 제안 확인용).
- 기록: [VERIFICATION_LOG](../VERIFICATION_LOG.md) 의 실연동 틀.
