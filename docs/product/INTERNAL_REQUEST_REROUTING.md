# 담당 아님과 명시적 재전달

2026-10-04. [조사·결과 반환](INTERNAL_REQUEST_INVESTIGATION.md)에 이어 잘못된 담당자에게 보낸 요청을 정정하는 흐름을 구현했다.

수신자가 수락 전에 ‘담당 아님’ 사유를 입력하면 요청이 반려된다. 요청자는 받은·보낸 요청 화면에서 같은 시스템·요청 종류에 등록된 다른 담당 후보를 선택한다. 새 요청은 원래 목적·원업무·요청자를 유지하고, 최신 담당표에서 판단 담당자와 에이전트를 다시 고정한다. 새 수신자의 수락을 기다린다. 반려 사유는 새 수신자에게도 표시된다.

원래 요청의 수신자·목적·판단 담당자·에이전트를 덮어쓰지 않는다. 이전 요청과 새 요청을 양방향으로 연결한다. 원업무 담당·완료 상태를 변경하거나 실행을 생성하지 않는다. 수락 이후의 담당 변경, 실행 취소·조사 인계, 후보 추천은 이번 범위에 포함하지 않았다.

## API와 상태

- `POST /internal-requests/{id}/not-responsible`: `expected_revision`, `reason`. 응답 권한과 지정 수신자 검사. 빈 사유·추가 필드를 거부한다.
- `POST /internal-requests/{id}/reroute`: `expected_revision`, `expected_directory_revision`, `recipient_member_id`. 위임 권한과 원래 요청자 검사. 같은 수신자·미등록 후보·비활성 멤버·미등록 에이전트·오래된 담당표를 거부한다.
- 반려 시 기존 요청 revision은 1에서 2로 증가한다. 공개 응답 `state`는 `rejected`이며 DB의 기존 접수 상태는 보존한다. 수락 API는 반려 기록이 있으면 거부한다.
- 재전달 시 새 요청 revision은 1이다. 원래 요청에는 `new_request_id`, 새 요청에는 `previous_request_id`와 `previous_rejection_reason`이 표시된다.
- 같은 사유의 반려 재시도, 같은 수신자의 재전달 재시도는 이미 기록된 결과를 반환한다. 재전달 재시도는 기존 접수와 마찬가지로 변경된 담당표를 재검증하지 않는다. 다른 사유·수신자로 재시도하면 충돌한다.

반려와 재전달은 각각 `BEGIN IMMEDIATE` 트랜잭션이다. 수락과 반려가 경합하면 하나만 성공한다. 반려 요청당 새 요청은 한 개만 연결된다. 새 수신자가 다시 반려하면 그 요청에서 같은 절차를 반복할 수 있다.

## 저장과 검증

스키마 v20은 `internal_request_rejections`를 추가한다. 원래 요청 ID가 기본키이며 사유·반려 시각·새 요청 ID를 저장한다. 반려자는 변경되지 않는 원래 요청의 수신자로 식별한다. 새 요청 ID는 UNIQUE 외래키다. v19에서 기존 테이블을 재생성하지 않고 추가하며, 기존 v4~v18 마이그레이션도 v20까지 이어진다.

합성 요청으로 API·화면, 사유 이스케이프, 권한·revision 검사, 중복·동시 접수, 수락/반려 경합, 원업무 보존, 마이그레이션과 기존 조사 흐름을 검증한다. 실제 회사의 재전달 시간이나 병목 감소 효과는 아직 측정하지 않았다. 운영 DB·러너에 적용하지 않았다.
