# 사내 요청 병목 파일럿 — 첫 제품 범위

작성일: 2026-10-03
상태: 사용자와 합의한 제품 방향을 바탕으로 한 범위 초안. 실제 사례·사용성·효과 검증은 진행 전이다.
현재 구현 조사: `service` 브랜치. 이 문서는 코드 계약을 변경하지 않으며, 새 phase 실행 지시가 아니다.

## 1. 문제와 근거

사용자가 전달한 친구의 경험: 스타트업에서 사람이 많은 회사로 이직한 뒤, 업무량 외에도 담당자에게 요청하고 권한·판단을 기다리는 데 시간이 소요된다. 오류가 발생하면 여러 담당자를 태그하지만 확인 후 다른 사람의 담당 업무로 밝혀지는 경우도 있다.

직접 인터뷰·원본 Jira 사진·요청 기록은 아직 확보하지 않았다. 빈도, 평균 대기 시간, 비용은 모른다. 위 경험은 문제를 탐색할 근거이며 효과나 시장 수요의 증명은 아니다.

첫 대상은 **한 회사에서 담당 범위와 권한이 나뉜 두 팀 사이의 오류 조사 요청**이다. 요청자가 정확한 담당자를 모르는 경우를 포함한다. 기업 간 협업은 확장 방향이다.

제품 가설: 담당 확인 → 맥락 전달 → 허용된 조사 → 필요한 사람 판단 → 결과 회신을 연결하면 재전달·재설명·수동 실행 중계를 줄일 수 있다. 실제 권한 발급이나 필수 승인 자체의 대기를 반드시 없앤다고 주장하지 않는다.

## 2. 첫 사용 흐름

기존 Jira 이슈 또는 직접 등록한 업무에서 오류 조사 요청을 만든다. 담당 범위 표로 처리 후보를 확인하고, 사람이 선택한 상대 팀의 에이전트가 자신의 환경에서 허용된 조사를 수행한다. 정보 부족·담당 아님·사람 판단 필요를 구분해 반환하고, 요청자가 결과를 받아 원래 업무를 이어간다.

첫 파일럿의 처리 범위는 읽기 전용 조사와 결과 전달이다. 운영 데이터 변경·배포·권한 발급은 실행하지 않는다. 승인 필요 사례는 등록한 담당자의 판단을 받아 조사·요청 흐름을 계속하는 것으로 검증한다. 결과의 `승인`은 특정 조사 요청에 대한 결정이며 운영 변경 허가로 확대 해석하지 않는다.

| 역할 | 원하는 결과 |
|---|---|
| 요청자 | 담당자 이름을 몰라도 접수하고, 대기 이유와 다음 담당을 확인한다 |
| 받는 팀 담당자 | 업무 범위·조사 에이전트·판단 담당자를 명시하고 필요한 요청만 처리한다 |
| 조사 에이전트 | 고정된 실행 방식과 허용 자료로 조사하고 근거·불확실성을 반환한다 |
| 판단 담당자 | 쟁점과 근거를 보고 답하고, 자신의 응답 이후 진행을 확인한다 |

## 3. 검증용 시나리오와 실제 사례 수집

아래는 **가상 시나리오**다. 실제 회사·오류·권한·처리 시간을 관측한 기록이 아니다.

개발팀 A가 “결제 버튼을 누르면 500 오류가 발생한다”는 업무를 접수한다. 최초 후보는 화면을 담당하는 개발팀이다. 허용된 자료를 조사하면 결제 API의 오류 응답이 확인된다. 운영팀 B에 오류 시각·요청 식별자·재현 절차·조사 결과를 전달한다. B의 에이전트가 로컬 검증 자료에서 원인을 조사하고 응답한다. 신규 예외 판단은 B 담당자에게 요청한다. A는 결과를 보고 원래 업무를 계속한다.

합성 로그·테스트 저장소만으로 흐름을 검증할 수 있다. A에게 B의 내부 자료 접근을 허용하지 않는다. 초기 공유 워크스페이스에 두 역할을 만들었다고 실제 부서 간 데이터 격리가 검증됐다고 말하지 않는다.

실제 사례 기록 양식:

| 항목 | 기록할 내용 |
|---|---|
| 원본 | 익명화한 제목·내용·도구·원본 식별자 |
| 담당 경로 | 최초 요청 대상, 실제 담당, 담당이 바뀐 이유 |
| 시간 | 접수·담당 확인·인계·응답·작업 재개 시각, 모르면 `미확인` |
| 왕복 | 추가 질문, 재설명, 재전달, 사람이 에이전트를 실행한 횟수 |
| 대기 원인 | 담당 불명확·입력 부족·판단·실제 권한 부족·상대 실행 환경 오프라인 |
| 결과 | 해결·부분 해결·거절·미해결, 판단 수정·재작업 여부 |
| 공유 제한 | 상대 팀에 보낼 수 있는 정보와 보낼 수 없는 정보 |

사용자에게 실제 사례 하나를 요청했다. 회신 전에는 가상 사례로 범위 정리와 구현 대조를 진행한다. 실제 효과 판정은 실제 사례 없이 완료하지 않는다.

## 6. 요구사항과 수용 기준

### P0 — 두 역할의 조사 요청 한 줄기

1. **원래 업무 보존**: 요청을 만들 때 원본 링크·요청자·조사 목적을 보존한다. 같은 접수 키를 재전송해도 업무·요청이 중복 생성되지 않는다.
2. **담당 범위 표**: 담당 시스템/저장소, 요청 종류, 처리 대상, 사람 판단 담당자를 등록한다. 후보가 없거나 여러 명이면 명시적 선택을 기다린다. 첫 버전은 사람이 후보를 확인하며, 자동 담당 확정은 하지 않는다.
3. **요청 접수와 거절**: 받는 쪽은 접수·정보 부족·담당 아님을 구분한다. 담당 아님이면 이유와 후보를 남기며 원본과 기존 조사 기록을 보존한다. 재전달은 사용자 선택으로 한다.
4. **읽기 전용 조사**: 등록한 환경과 사전 고정된 어댑터로만 실행한다. 외부 요청이 실행 명령·로컬 경로를 정하지 못한다. 읽기 전용은 지침만으로 보장했다고 판단하지 않는다.
5. **사람 판단과 재개**: 판단이 필요하면 쟁점·근거·응답 대상·대기 원인을 기록한다. 지정한 담당자 또는 명시적 대체자가 응답할 수 있다. 응답·실행 허용 조건을 다시 검사한 후 원래 요청을 계속한다.
6. **결과와 작업 재개**: 조사 결과에는 근거·불확실성·다음 행동이 있다. 결과 검증과 사람 결정을 구분한다. 처음에는 원업무에 결과 링크·요약을 보여주고 수동으로 적용한다. 자동 재개는 명시적으로 허용된 후속 조사 단계에 한정한다.
7. **대기와 중복 관리**: 정보·담당·판단·접근 부족·오프라인 대기를 구분한다. 중복 응답·이벤트·재시작으로 중복 실행이나 중복 재개가 발생하지 않는다. 거절·미해결이면 원업무를 해결된 것으로 표시하지 않는다.

등록된 능력, 에이전트 사용 승인, 자료 접근 권한, 업무상 판단 권한은 서로 다른 의미다. 부족한 접근 권한은 진단 결과로 반환하고, 사람 응답 텍스트만으로 새 권한을 부여하지 않는다.

### P1 — 첫 흐름 검증 후

- 기존 Jira 업무에 조사 결과를 회신하는 최소 경로(현재 기능의 지원 여부를 확인하고 부족한 경우 추가).
- 근거를 붙인 담당 후보 추천과 변경 이유 기록. 모델의 자기 confidence만으로 품질을 판정하지 않는다.
- 다른 저장소를 담당하는 조사 대상 연결, 상대 팀 단위 요청 접근·자료 공유 범위.
- 실제 A2A 상대가 준비되면 요청·질문·응답·상태를 현재 업무에 연결한다. A2A가 사용자 위임이나 권한 발급을 자동 해결한다고 가정하지 않는다.

### 이번 범위 밖

- 기업 간 협업, 전사 다중 워크스페이스 운영, 범용 워크플로우 편집기.
- 자동 권한 발급·상대 계정 공유·운영 변경·배포 자동화.
- 모든 AI 앱 탐지, 임의 채팅 메모리 수집, 전사 담당 자동 학습.
- 기존 PRD·ARCHITECTURE·계약을 이번 문서만으로 대체하거나 전면 재설계.

## 7. 기존 계약에 대응시키는 방법

현재의 `WorkItem`은 원래 업무, `Task`는 조사 단계, `Execution`은 조사 시도, `outcome`은 에이전트가 주장하는 조사 결론으로 사용 후보를 검토한다. 조사 결과가 형식상 유효하다고 원래 업무가 해결된 것으로 보지 않는다. 현재 코드 수정의 PR 병합 완료 규칙을 조사 업무에 적용하지 않는다.

다음 사건은 기존 단계 상태만으로 충분히 표현되는지 별도 설계한다: 접수, 담당 아님과 재전달, 정보 추가, 지정 사람 판단, 응답 반환, 원업무 재개. 전부 새 `Task.status`로 추가하지 않는다. 요청의 발생 원인·현재 대상·원업무 참조를 보존할 수 있는지 확인한다.

조사가 원업무의 단계로 끝나는 단순 흐름은 기존 계약을 우선 활용한다. 다른 업무·다른 팀에 요청했다가 돌아오는 사례가 기존 선행/후속 모델로 표현되지 않으면 좁은 요청 관계를 설계한다. 새 코드 식별자·DB 표·API는 아직 확정하지 않는다.

## 8. 검증과 효과 측정

| 검증 사례 | 통과 조건 |
|---|---|
| 담당 명확·조사 가능 | 조사 결과가 원업무에 연결되고 허용된 후속만 진행 |
| 잘못된 담당 | 이유·후보·기존 자료를 보존해 재전달; 해결로 오표시하지 않음 |
| 정보 부족 | 질문과 답을 같은 요청에 연결; 답 재전송으로 중복 실행 없음 |
| 사람 판단 필요 | 지정한 판단 담당자만 응답 가능; 다른 멤버의 결정 거부 |
| 접근 부족·오프라인 | 대기 원인 표시; 자동 권한 확대 없음; 복구 뒤 조건 재검사 |
| 공유 제한 | 허용 자료만 요청/응답에 포함; 상대 내부 자료·비밀값 노출 없음 |

합성 사례는 동작만 증명한다. 같은 컴퓨터의 두 계정·두 러너는 실제 두 팀 협업 가치나 자료 격리의 증명이 아니다. 실제 환경에서는 상대 시스템의 권한 검사도 확인한다.

접수·담당 확정·조사 시작·추가 질문·답변·사람 판단 요청/응답·결과 반환·원업무 재개를 기록한다. 경과 시간과 실제 사람 작업 시간을 구분하고, 오프라인 대기와 판단 대기를 합치지 않는다. 모르는 시각은 `미확인`, 재현 실험 시간은 `실험`으로 표시한다.

실제 파일럿 제안: 같은 요청 유형의 기존 사례 5건과 서비스 사용 사례 5건부터 탐색한다. 통계적 인과 효과로 해석하지 않는다. 도입 전 사례가 부족하면 동일 합성 사례 비교만 수행하고 실제 절감 주장은 보류한다.

잠정 제품 가설(관측 기준선이 나온 뒤 파일럿 시작 전에 고정): 수동 재전달·재설명 횟수가 기준선보다 줄고, 담당 확정부터 원업무 재개까지의 중앙값이 줄며, 사용자가 결과를 다시 작성하지 않고 활용할 수 있다. 감소율의 숫자는 기준선 확인 전 임의로 확정하지 않는다. 무단 실행·자료 노출·중복 실행/재개가 한 건이라도 발생하면 해당 흐름 적용을 중단하고 수정한다. 오배정·판단 번복·재작업을 함께 보고한다.

## 9. 구현 작업 순서

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 실제 사례와 Multica 실행 비교 | 사례 출처·수동 단계·대기 원인·비교 한계가 기록됨 |
| 2 | 요청 의미와 기존 모델 적합성 설계 | 정상·재전달·정보·사람 판단 4개 흐름을 기존 계약에 대응, 필요한 변경만 ADR 후보로 정리 |
| 3 | 담당 범위 표와 명시적 선택 | 후보 없음/복수·비활성 담당 처리 테스트; 자료 권한과 분리 |
| 4 | 두 역할의 접수·조사·결과 반환 | 읽기 전용 실제 어댑터 1종; 단계·원업무 연결·중복 검증 |
| 5 | 정보 질문·담당 아님·지정 사람 판단 | 각 경우 대기·응답·재개; 일반 멤버의 무단 판단 거부 |
| 6 | 실제 업무 입구·회신·측정 | Jira를 쓸 실제 대상이 있으면 연동 확인, 실제 2명 사용 기록 |
| 7 | 독립 에이전트 연결 | 실제 상대가 있을 때 A2A 인증·요청 범위·자료 공유·복구 검증 |

새 기능은 TDD. 도메인은 인프라 import 금지, 중앙과 connector는 contracts만 공유, 비밀은 SecretStore/환경에서 관리. `service`에서 새 phase 계획을 만들 때 이 문서의 P0 중 하나의 검증 가능한 흐름으로 나눈다. 구현 후 프로젝트의 pytest·ruff 검증을 수행한다.
