# 지정 판단 담당자의 응답

2026-10-04. [정보 질문·답변](INTERNAL_REQUEST_INFORMATION.md)에 이어 검토된 조사 결과의 반환 여부를 지정 담당자에게 판단받는 흐름을 구현했다.

## 사용자 흐름

수신자가 조사 Task에서 결과를 검토·승인한 뒤, 받은·보낸 요청 화면에서 판단할 쟁점을 입력한다. 요청 생성 시 담당 범위 표에서 고정한 `judgment_member_id`에게 판단 요청이 전달된다. 요청자·수신자와 다른 사람도 판단 담당자가 될 수 있다. 판단 요청을 받은 담당자의 목록에 해당 요청과 근거가 표시된다.

판단 담당자는 쟁점, 조사 결과 요약·산출물, 추가 질문·답변을 보고 승인 또는 거절과 사유를 남긴다. 지정 담당자만 응답하며 관리 역할이나 원래 요청자라는 이유로 대신 응답할 수 없다. 승인 후에도 수신자가 결과 반환을 명시적으로 실행한다. 승인·거절 자체는 원업무 담당·완료, 에이전트 실행, 시스템 권한을 변경하지 않는다.

판단 요청을 보낸 요청은 최신 근거에 대한 지정 담당자의 승인 전까지 반환을 막는다. 거절하면 반환할 수 없다. 판단 요청을 보내지 않은 요청의 기존 반환 흐름은 유지한다. 어떤 경우에 판단을 반드시 요청해야 하는지 회사 정책으로 자동 판정하는 기능은 포함하지 않았다.

## 판단 근거와 이력

판단은 특정 `Execution`과 결과 산출물·요약, 질문 ID·버전 목록에 고정된다. 질문 추가 또는 답변으로 정보가 변경되면 이전 승인을 반환에 재사용할 수 없다. 미응답 판단의 근거가 변경돼도 이전 판단에 응답할 수 없다. 새로운 근거에 새 판단을 요청하며 이전 이력은 보존한다. 같은 결과·정보에 대해 다른 접수 키로 다시 요청하여 거절을 덮어쓰는 것은 막는다.

응답 시 최신 조사 결과가 여전히 계약 검증과 Task 검토를 통과했는지 확인한다. 반환 시 결과·정보 일치와 지정 담당자의 활성 상태를 다시 검사한다. 판단 담당자가 비활성화되면 반환을 막는다. 대체 담당자·예외 승인 정책은 추측하지 않으며 별도 후속 설계가 필요하다.

현재 조사 Task는 사람 검토 승인으로 마감된다. 거절 이후 새 조사가 필요하면 원업무에서 새 요청을 생성한다. 마감된 조사 Task 재개·같은 요청의 조사 교체는 이번 범위에 포함하지 않았다. 추가 정보만으로 쟁점이 달라진 경우에는 같은 결과와 새 정보를 근거로 새 판단을 요청할 수 있다. 시스템이 기존 결과에 새 정보를 자동 반영했다고 해석하지 않는다.

## API·저장

- `POST /internal-requests/{id}/judgments`: 요청 `expected_revision`, `submission_key`, `execution_id`, `issue`. 응답 권한과 지정 수신자를 검사한다. 검토된 최신 결과·반환 전 상태·정보 답변 완료·활성 판단 담당자가 필요하다.
- `POST /internal-requests/{id}/judgments/{judgment_id}/respond`: 판단 `expected_revision`, `decision`(`approve` 또는 `reject`), `reason`. 응답 권한과 지정 판단 담당자를 검사한다.
- 요청 응답에 `judgments` 배열을 포함한다. 접수 키와 내부 JSON 열은 숨기고 정보 버전 목록을 제공한다. 지정 담당자의 목록에는 실제 판단 요청이 생성된 뒤부터 표시한다.
- 판단 버전은 미응답 1, 응답 완료 2다. 요청의 수락·조사 revision은 변경하지 않는다. 같은 접수 키·내용 및 같은 판단·사유의 재시도는 기존 기록을 반환한다. 다른 내용으로 덮어쓰기는 충돌한다. 기록 재시도는 근거가 변경돼도 기존 기록만 반환하며 현재 반환 허용 여부는 별도로 검사한다.
- 쟁점·사유는 최대 4,000자이며 공백만 있는 입력·추가 필드를 거부한다. 접수 키는 최대 128자다.

스키마 v22은 `internal_request_judgments`를 추가한다. 판단 ID, 요청·실행·산출물 참조, 결과 요약, 정보 버전, 쟁점, 요청자·지정 담당자, 요청·응답 시각, 결정·사유·응답자·판단 버전을 보존한다. 요청별 접수 키와 실행·정보 버전 조합을 각각 UNIQUE로 둔다. 요청·응답·반환은 쓰기 트랜잭션으로 검사한다. v4~v21에서 기존 데이터를 보존해 v22까지 마이그레이션한다.

## 검증 범위와 다음 작업

합성 자료로 정상 승인·반환, 세 사람의 역할 분리와 목록, 관리자 대체 응답 차단, 정보 변경 시 이전 판단 무효화, 거절과 재요청 충돌, 비활성 담당자, 입력·버전·결과 참조 검사, 중복·동시 요청 및 응답, 화면·이스케이프·판단 근거 표시, 마이그레이션과 원업무 보존을 검증했다. 실제 AI CLI·조직 정책·업무 대기 시간 감소는 검증하지 않았다. 운영 DB·러너에는 적용하지 않았다.

반환 결과를 받은 요청자의 [업무 재개 기록](INTERNAL_REQUEST_RESUMPTION.md)이 연결됐다. 업무 재개와 업무 완료는 별도로 유지한다.
