# 제품 개요 — 기존 에이전트를 업무에 연결

갱신일: 2026-09-23
상태: 실서비스 제품 방향 확정([ADR-0011](../adr/0011-task-driven-work-cycle.md)). 수용 기준은 [PRD](../PRD.md), 현재 구현과 전환 설계는 [ARCHITECTURE](../ARCHITECTURE.md)에 둔다. 10/2 까지의 범위는 [MVP 계획](MVP_PLAN.md). 공모전 절은 2026-09-27 [보관 자료](../archive/2026-09-27-contest-and-history/PRODUCT_BRIEF-contest.md)로 옮겼다.

## 제품 방향

기존 업무 서비스에서 업무를 가져오거나 직접 등록하면 담당자의 기존 에이전트가 준비된 업무를 실행하고, 결과를 원래 업무에 반영하며 다음 업무를 연결·생성하는 서비스. 위임된 판단은 AI가 수행하고, 범위 밖이거나 해결하지 못한 경우 사람에게 요청한다.

첫 경험은 기존 업무의 가져오기·배정·실행이다. 자연어로 모든 워크플로우를 생성하거나 과거 로그를 먼저 분석하는 것을 요구하지 않는다. 기록이 있으면 설정을 돕고, 사용 중 쌓인 기록에서 추천·개선을 제공하는 기능은 단계적으로 추가한다([ADR-0013](../adr/0013-existing-tasks-first-staged-rollout.md)). Jev는 구현 후보이며 미채택이다. MVP에서 v1.0까지의 범위·진입 근거·벤치마킹은 [ROADMAP](ROADMAP.md)을 따른다.

업무 목록에서 각각의 실행 조건을 평가한다. 5개 중 2개가 준비되었다면 그 2개는 진행하고, 나머지는 필요한 입력·결정·권한·의견 조율을 기다린다. 결과 기반 후속 업무 생성과 사람 응답 후 재개는 제품의 핵심 동작이다. 모든 기업 업무를 처음부터 지원한다는 뜻은 아니며, 한 업무 사례에서 전체 순환을 먼저 검증한다.

## 문제와 해결 가설

후속 단계에서는 기업·개인이 허용한 업무 이력과 접근 가능한 LLM 메모리에서 반복 작업·필수 입력·담당 관계·대기·예외를 찾아 설정 후보를 제안한다. 과거 이력과 실행 없는 비교로 확인한 뒤 허용 범위에 적용한다. 이는 모델 재학습과 다르며, 과거 행동이나 메모리를 실행 권한으로 취급하지 않는다. 이 분석은 처음 사용하기 위한 선행 조건이 아니다.

도입 후에는 인계 대기·사람 중계·처리 시간·재작업·비용을 도입 전 기준과 비교한다. 효과가 없는 패턴은 수정·중단하고 적용 버전을 추적한다. 관측한 개선을 곧바로 자동화의 인과적 효과라고 단정하지 않는다.

A → B → C 업무에서 A가 끝나 B를 시작할 수 있어도, 사람이 업무를 확인하고 에이전트에 내용을 전달해 실행할 때까지 기다리면 C도 밀린다. 사용자는 이를 핵심 병목으로 지적했다.

기존 에이전트를 업무 흐름에 한 번 연결해두고 실행 가능한 순간에 자동 착수시키면, 수동 전달과 실행 중계, 후속 업무의 착수 대기를 줄일 수 있다는 가설이다. 정보 전달뿐 아니라 실제 실행 시작까지 제품 책임에 포함한다.

모든 병목을 해결한다고 주장하지 않는다. 필수 판단·권한·입력이 없거나 실행 환경이 오프라인이면 작업을 시작할 수 없다. 병목의 빈도·손실 규모와 실제 절감 효과는 아직 측정하지 않았다.

## 사용자와 에이전트

- 사용자 방향: 기존 에이전트를 사용하는 개인과 협업 팀. 비개발자도 연결 코드를 직접 작성하지 않고 사용할 수 있는 경험을 지향한다.
- 등록 대상: 개인 에이전트, 팀 공용 에이전트, 사내 에이전트. 특정 소유 유형에 한정하지 않는다.
- 에이전트 소유자와 업무 담당자는 구분한다. 담당자가 팀 공용 에이전트를 활용할 수도 있다.
- 연결 대상은 모델 이름만이 아니라 실제 작업을 수행할 수 있는 실행 환경이다. 기존 스킬·MCP·프로젝트 설정을 활용한다는 주장은 대상별 실험으로 확인해야 한다.
- 첫 MVP는 현재 사용 중인 컴퓨터에 연결 프로그램을 두는 방식으로 합의했다. 연결 프로그램이 웹 서비스의 업무를 받아 지정한 작업 폴더에서 기존 설정을 활용한 새 작업을 실행하고 상태·결과를 전달한다. 컴퓨터가 꺼져 있거나 연결이 끊기면 새 업무는 대기한다. 이미 열린 대화창이나 대화 기억을 자동 승계하는 방식은 첫 연결 범위에 포함하지 않는다.

로컬 에이전트의 등록 단위는 실행 도구 + 작업 폴더 하나다. API 에이전트는 별도 주소·인증·능력 정보로 연결하는 설계를 검토하며 작업 폴더를 필수로 요구하지 않는다. 같은 도구도 폴더별로 별도 에이전트로 등록할 수 있다. Git 저장소인 폴더는 이후 업무와 변경 이력을 연결하는 기반이 되지만, Git 필수 등록이나 커밋·푸시·PR 자동화까지 합의한 것은 아니다.

사용자는 Git 작업의 병렬 실행에 worktree 활용을 제안했다. 독립적인 코드 업무별 worktree를 유지하는 것은 assistant의 구체화 제안이다. 등록 폴더를 기준 저장소로 삼는다. 선행 업무가 완료되면 결과 버전을 보존하고 후속 업무는 그 버전의 별도 worktree에서 시작하며 작업 요약·검증 결과·남은 사항을 함께 전달하는 순서에 합의했다. 기준 브랜치 병합은 사용자 확인 후 진행한다. 결과 버전의 보존·전달 방법과 worktree 정리 정책은 미결이다.

## 핵심 경험

1. 기존 에이전트의 실행 환경·작업 폴더를 연결한다. 허용한 범위에서 설정·스킬·도구 정보를 자동 파악해 업무 설명을 제안하고, 사용자가 이름·소유 구분·업무 설명을 확인·수정해 등록한다. 읽어오지 못한 정보는 보충하며 실제 연결 가능 여부를 확인한다. 이 등록 흐름은 사용자 합의이며 자동 파악의 기술적 범위는 검증 전이다.
2. 업무를 직접 등록하거나 GitHub·Jira 등 기존 업무 도구에서 가져와 목록으로 본다. 목표·역할·담당자·수행할 작업·대상·필요 자료·완료 기준을 파악한다. 알려진 정보는 재사용하고 필요한 누락 정보만 요청한다.
3. 업무 담당자와 사용할 에이전트를 연결한다. 입력·선행 조건·권한·위임 범위·실행 환경이 충족된 업무부터 자동 실행하며, 직접 실행 설정은 사용자 조작을 기다린다. 서로 독립적인 업무를 하나의 체인 때문에 대기시키지 않는다.
4. 사람의 결정·승인·권한 제공·의견 조율이 필요하면 무엇을 누가 해결해야 하는지 표시한다. 응답 후 해당 업무의 조건을 다시 평가해 자동 실행을 재개한다. 위임 범위 안의 판단은 에이전트가 수행한다.
5. 결과와 검증 근거를 보존하고 다른 업무의 입력에 연결한다. 필요한 후속 업무가 이미 있으면 재사용하고, 없으면 생성한다. 담당 역할·대상·필요 자료를 확인해 담당자의 에이전트에 배정하고 같은 실행 판단을 반복한다. 모호한 담당자나 허용 범위를 결과만으로 확정하지 않는다.
6. 결과 제출·형식 검증·업무 품질 검증·사람 승인을 구분해 표시한다. 후속 작업이 허용된 검토·분석이면 먼저 진행할 수 있고, 승인이 필요한 외부 반영이면 기다린다. 생성된 업무의 원인과 결과 버전을 추적할 수 있게 한다.

사용자는 직접 에이전트를 선택하는 방식과 업무 내용에 따라 시스템이 자동 선택하는 방식이 모두 필요하다고 확인했다. 두 방식을 첫 MVP 기능으로 다룬다. 선택 기준·알고리즘은 미결이다. 자동 선택한 대상과 이유를 표시·기록하고, 직접 실행 업무는 사용자 조작을 기다리며 자동 실행 업무는 조건 충족 시 별도 승인 없이 시작한다. 적합한 대상을 정할 수 없으면 보류하고 정보 또는 선택을 요청한다. 이 확인 절차는 사용자 합의다. 직접 실행과 자동 실행도 모두 지원한다는 사용자 결정을 반영한다. 에이전트 선택과 실제 실행 시점은 별개로 설계하며, 실행 기본값과 세부 조건은 미결이다.

## 기존 서비스와 차별성 가설

공식 문서 확인일: 2026-09-19. 아래는 문서 조사이며 연결 실험이나 전체 시장 조사 결과가 아니다.

| 대상 | 확인한 겹치는 기능 | 추가 비교가 필요한 부분 |
|---|---|---|
| [Jira](https://support.atlassian.com/jira-software-cloud/docs/collaborate-on-work-items-with-ai-agents/) | 에이전트 선택 실행, 상태 전환에 따른 실행, 외부 에이전트 연동 | 각 소유자의 기존 실행 환경 등록·설정 보존 과정 |
| [Devin](https://docs.devin.ai/integrations/jira) | Jira 할당·라벨·상태 조건으로 Devin 세션 실행, 결과 반영 | 서로 다른 소유자·종류의 기존 에이전트를 연결하는 경험 |
| [n8n](https://blog.n8n.io/agent-to-agent-protocol/) | 워크플로우 자동화와 A2A 커뮤니티 노드를 통한 통신 | 사용자가 작성해야 하는 연결 코드와 구성 단계 |
| [Paperclip](https://github.com/paperclipai/paperclip) | 기존 에이전트 연결, 업무 관리·조율, Claude Code·Codex·HTTP 등 지원 표방 | 분산된 개인·사내 실행 환경 연결의 편의성과 기존 설정 활용 |

‘외부 에이전트 연결’이나 ‘티켓 자동 실행’ 자체가 시장에 없다고 주장하지 않는다. Jira에 등록된 외부 에이전트가 있다는 사실만으로 임의의 담당자 실행 환경까지 그대로 연결된다고 가정하지도 않는다.

차별성 가설은 기존 업무·담당 체계와 서로 다른 담당자의 기존 에이전트를 연결하고, 실행 가능 판단 → 실행 → 결과 인계 → 후속 업무 연결·생성 → 재실행 → 필요한 사람 응답 후 재개의 순환에서 사람의 중계를 줄인다는 것이다. 업무 자동 생성 건수 자체를 성과로 보지 않는다. 등록·설정 비용, 인계 대기 시간, 사람의 재작성·전달·실행 횟수, 재작업률, 전체 처리 시간을 실제 대안과 비교한다. 시장 유일성은 검증되지 않았다.

## 기술의 위치

- n8n: 현재 입구·callback 연동을 구현했다. 실서비스에서의 역할은 업무 순환을 지원하도록 정하며, 입구·출구만을 영구 제약으로 두지 않는다. 에이전트 실행 책임은 현재 Runloom에 있고, 변경 시 중복되지 않게 설계한다.
- A2A: 요청·상태·결과·질문 교환을 통일할 후보. 자동 실행의 필수 조건이 아니다.
- 웹훅: 이벤트 전달 방식. 실제 에이전트 실행과 완료 확인은 별도 연결이 필요하다.
- GitHub·Jira 등 업무 도구: 기존 업무를 가져오는 제품 입력 경로다. 현재 가져오기 화면은 fixture 기반이며 실제 연동·담당자 매핑·결과 반영 범위는 후속 구현 대상이다.

기술 선택은 첫 연결 대상과 사용자 흐름을 기준으로 결정한다. 기존 자동화 기능을 재사용해도 무방하며, 특정 프로토콜 채택을 제품 가치로 대신 설명하지 않는다.

## 현재 구현과 다음 검증

`service`에는 등록된 업무 사이의 결과 기반 착수, 종류·후속 규칙, 기존 로컬 에이전트 연결, n8n 입구·callback이 있다. 목록 전체의 독립적 실행 판단, 조직 담당 관계에 따른 배정, 결과 기반 새 업무 생성, 일반적인 사람 요청·응답 후 재개는 아직 구현하지 않았다. 기존 데모의 성공을 이 순환의 검증 완료로 표시하지 않는다.

다음 검증은 5개 업무 중 준비된 2개 실행 → 결과로 기존 업무 연결·새 업무 생성 → 담당 에이전트 실행 → 사람 응답 후 재개다. 구체적인 기대 결과는 PRD의 실서비스 수용 기준을 따른다.

## 유지하는 장기 방향과 미결 사항

포괄적인 목표에서 전체 작업을 분해하는 기능, 새 에이전트 생성, 에이전트 간 자유로운 질문·답변은 장기 검토 대상이다. 결과에서 필요한 후속 업무를 연결·생성하는 기능 및 사람의 응답 후 재개와는 구분한다. 후자의 두 기능은 현재 실서비스 제품 기준에 포함한다.

담당자·역할과 Agent의 연결, 입력 해석·후속 업무 제안의 주체, 권한과 위임 정책, 기존 업무 중복 판정, 외부 업무 도구 동기화는 후속 기술 설계 대상이다. 구체적인 필드와 구현 순서는 ARCHITECTURE에서 현재 계약과 구분해 정한다.

## 이력

이전 누적 초안은 [보관 자료](../archive/2026-09-19-before-agent-registration/README.md)에 원문으로 남겼다. 그 안의 n8n 필수 채택, 되묻기 중심 데모, 공모전 일정·구성 관련 표현을 현행 요구사항으로 자동 복원하지 않는다.
