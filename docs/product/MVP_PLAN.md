# MVP 계획 — 실제 업무 순환과 셀프호스트 배포 (2026-10-02 목표)

갱신일: 2026-09-26
상태: 2026-09-25~26 사용자 합의를 정리한 계획. [ROADMAP](ROADMAP.md) 3절 MVP / v0.1 을 대체하지 않고 10/2 까지의 범위·순서로 구체화한다. ROADMAP 과 달라지는 점은 12절에 적는다. 구현 완료를 뜻하지 않는다.

## 1. 제품 정의

> Runloom 은 업무를 등록받아 담당자(에이전트나 사람)에게 배정하고, 담당자 환경에서 실행한 결과를 판정해 다음 업무로 등록한다. 이 순환이 사람의 전달 없이 돌아가게 하고, 그 효과를 측정한다. 바깥 서비스 연결은 n8n 같은 도구에 맡긴다.

순환: **등록 → 배정 → 실행 → 결과 판정 → 등록 → 배정 → …** 사람은 사람 차례(초안 수정·승인·결정)에서만 끼어든다.

Jira 도 보드·배정·Automation(완료 시 후속 생성)을 가진다. Jira 에서는 실행과 "완료" 처리를 사람이 해야 순환이 한 칸 돈다. Runloom 은 배정받은 담당자가 자기 환경에서 실제로 실행하고, 결과의 내용(outcome)과 검증으로 다음 업무를 등록한다.

판별 질문: **n8n 을 꺼도 Runloom 은 등록·배정·실행·인계를 한다.** n8n 노드는 Runloom 을 부르는 얇은 클라이언트일 뿐 기능이 아니다.

## 2. 이웃 도구와의 경계

| 도구 | 맡는 일 | Runloom 과의 관계 |
|---|---|---|
| Jira · GitHub Issues · Linear | 사람이 보는 업무 보드, 전체 진행 기록 | Runloom 은 여기서 업무를 가져오고 결과·새 업무를 되쓴다. 보드가 없는 개인·소규모 팀은 Runloom 화면만 쓴다 |
| n8n | 바깥 서비스 연결(Gmail·캘린더·폼·채용 사이트)과 정해진 처리(Code 노드) | 입구(업무 등록 API)·출구(callback·알림 웹훅)로 붙는다. 흐름 전체를 n8n 에 그리지 않는다 |
| 벤더 에이전트 (Linear+Cursor/Codex, Copilot coding agent, Codex cloud) | 이슈 하나를 벤더 클라우드의 에이전트가 처리 | Runloom 은 담당자 환경(PC·VM·라이선스 DB)에서 실행하고, 결과에 따라 다음 업무로 이어지며, 벤더를 섞고, 사람을 담당자로 둔다 |

n8n 만으로 구성하면 바깥 연결은 쉽지만 "내 구독 에이전트가 내 환경에서 일하고 서로 주고받는" 부분을 노드로 다시 만들어야 한다. Runloom 만으로 구성하면 바깥 연결이 없어 사람이 입력·등록을 대신한다. 그래서 개발자 사례(GitHub 연결 내장)는 Runloom 단독, 지원자·채용자 사례는 n8n 과 함께 쓴다.

## 3. 사용자가 등록하는 것

순서도가 아니라 업무 분장표와 인수인계 규칙이다([ADR-0009](../adr/0009-registered-kinds-and-succession-rules.md)).

| 등록 단위 | 내용 | 예 |
|---|---|---|
| 업무 종류 | 받는 입력, 내는 결과물, 결과 갈래(outcome) | `서류 검토`: 지원서 → 평가서, `합격`/`불합격`/`애매` |
| 담당자 | 누가 어떤 업무를 어느 범위에서 맡나 (능력 + 범위) | 백엔드 면접관의 에이전트: `서류 검토 · 직무=backend` |
| 후속 규칙 | 이 업무가 이 결과로 끝나면 다음은 무엇인가 | `서류 검토` 가 `합격` → `면접 질문 정리` |

**에이전트 담당자 = 러너에서 등록하는 "폴더 + 역할 + 권한".** 폴더가 프로젝트 맥락(`CLAUDE.md`·`.claude/settings.json`·스킬·`.mcp.json`)을, 역할이 그 폴더 안의 일(`.claude/agents/<역할>.md` → `--agent`)을, 권한이 허용 도구·권한 모드를 정한다. 구독 하나로 역할이 다른 에이전트를 여럿 둔다. 폴더·역할 이름은 러너의 로컬 설정에서만 오고, 중앙에는 에이전트 ID 와 능력만 알린다(실행 인자는 어댑터가 고정한다는 규칙 유지).

**러너**는 각자의 PC·VM 에 설치하는 연결 프로그램이다(GitHub Actions self-hosted runner 와 같은 구조). **템플릿**은 업무 종류 + 후속 규칙 + 곁들일 n8n 워크플로우 JSON 묶음이며, 가져온 뒤 담당자만 등록하면 쓴다.

## 4. 담당 방식 세 가지

| 방식 | 예 | Runloom 의 가치 |
|---|---|---|
| 에이전트만 | 코드 검토, 형식 검사 | 사람 개입 없이 끝남 |
| 에이전트 초안 → 사람 수정 | 공고 초안, 면접 질문지, 이력서 | 사람이 초안에서 시작하고, 수정을 마치는 순간 다음 단계가 시작됨 |
| 사람만 | 회의, 로그인이 필요한 사이트 게시 | 거의 없음. 기존 보드에 둔다 |

대부분의 실제 업무는 두 번째다. **사람이 결과물을 수정하는 단계**를 정식 단계로 다뤄야 한다(현재 사람 단계는 재개·에이전트 선택·종료 응답뿐 — 7절).

## 5. 사용 장면

| 사례 | 들어오는 곳 | 에이전트끼리 | 사람 차례 | 나가는 곳 | 필요한 코어 |
|---|---|---|---|---|---|
| **개발자** ([OpenArchive](https://github.com/jeongeundev/OpenArchive)) | 이슈에 라벨 | 수정(`task/*` 브랜치, 검증) → 검토 → 필요 시 재작업 | "검토 통과, diff 확인" 알림 | 사람이 push·PR·병합 | **지금 있음**(phase 8) + 10/2 범위 |
| 기술 블로그 | PR 병합(n8n GitHub 트리거) | 글 초안 → 검토 → 재작업 | 초안 확인·수정 | 병합하면 게시 | 쓰기 가능한 종류, 재작업 규칙, 사람 수정 |
| 지원자 | 공고 URL(n8n 폼) → 코드로 자격 판정(n8n Code) | 이력서 맞춤 작성 → 평가(프로필에 없는 경험 검사) → 재작업 | 수정본 확인 | 사람이 직접 제출, 메일 감시 → 캘린더(n8n) | 위 + 템플릿. 미충족 사유 누적 → 공부 우선순위 |
| 채용자 | 지원서 접수·파싱(n8n) | 직무별 면접관 에이전트가 1차 검토 → 합격이면 면접 질문 정리 | 면접관 확인·수정 | 일정 선택 메일 → 캘린더(n8n) | 위 + 사람 담당자·알림, 지원자 개인정보 정책 |

모든 사례는 같은 지표 화면(6절)으로 본다.

## 6. 측정 설계

원칙: 사람이 보고한 숫자가 아니라 **시스템이 남긴 기록**에서 계산한다. 지표 정의는 [ROADMAP](ROADMAP.md) 9절을 따르고, 여기서는 수집 방법과 비교 방법을 정한다.

### 6.1 기록

업무 단위 이벤트를 한 흐름으로 모은다: 업무 생성(출처) · 착수 가능 · 배정 · 실행 시작/종료 · 판정 · 재작업 · 사람 요청/응답 · 완료/종료. 각 이벤트에 시각·담당자·업무 종류·**규칙/설정 버전**을 남긴다. 현재 `executions`·`execution_events`·`task_verdicts`·`human_requests`·`human_responses` 에 상당 부분이 있으므로 새 저장소를 만들기보다 빠진 시각·버전을 보충하는 것이 먼저다(구체는 phase 설계에서 확인).

### 6.2 지표

| 무엇을 | 지표 | 원천 |
|---|---|---|
| 병목 | 인계 대기: 후속의 조건 충족 → 실제 착수 | 판정 시각, 후속 실행 시작 |
| 속도 | 접수 → 사람 차례, 접수 → 완료 | 업무 생성·사람 요청·종료 |
| 사람 부담 | 사람 개입 횟수, 알림 → 응답 시간 | 사람 요청/응답 |
| 품질 | 1회 통과율, 재작업 횟수, 사람 거부 비율 | 판정·재작업·사람 응답 |
| 비용 | 에이전트 실행 시간, CLI 가 보고한 비용, 한도 도달 | 실행 기록. 모르는 비용은 0 이 아니라 "모름" |
| 신뢰성 | 실패율, 실패 사유 분포, 재실행 | 실행 실패·관찰 |

### 6.3 전후 비교

- **과거 이력 기준선**: OpenArchive 의 이슈·PR 이력(이슈 열림 → 첫 커밋 → PR → 병합)을 GitHub 에서 가져와 도입 전 기준선으로 쓴다. 기준선은 자동화 시작 전 데이터라 나중에 만들 수 없으므로 먼저 확보한다.
- **버전 비교**: 모든 실행에 규칙·설정 버전이 찍히므로 "평가 기준을 바꾼 뒤 재작업률" 같은 비교를 한다. 측정 → 다음 과제 설계의 순환이다.
- **수동 처리 모드**: 업무를 등록하되 사람이 처리하고 완료만 표시해 같은 형식의 기준선을 만든다(선택).

중앙값과 건수(n)로 보여주고, 업무 난이도·기간·미완료 건을 함께 표시한다. 관측한 개선을 인과적 효과로 단정하지 않는다.

### 6.4 위치

- Runloom: 이벤트 기록, 지표 화면, 지표 API(JSON/CSV), 실행별 원시 로그(마스킹).
- n8n(선택 예시): 지표 API 를 읽어 주간 리포트, 알림 웹훅을 받아 메신저로. 제품 기능이 아니라 붙이는 쪽의 예시로 둔다.
- 문서: 런북 — 지표가 나빠지면 무엇을 확인하고 어떻게 재실행하나.

## 7. 코어의 현재 상태 (2026-09-25 코드 조사)

| 틀의 요소 | 지금 | 빈칸 |
|---|---|---|
| 업무 종류 | 등록 가능(`/kinds`) | 사용자 종류는 읽기 전용(인계 디렉터리, `{outcome, summary}`), 완료는 항상 사람 검토, 검증 스크립트가 종류에 묶이지 않음 |
| 후속 규칙 | 앞으로 넘기기 가능(`/rules`) | 재작업이 규칙으로 표현되지 않음(`task_followup.py` 가 `changes_requested` 문자열 비교, 상한은 GitHub 소스 설정), 결과 기반 새 업무 생성은 `bug_fix → code_review` 한 경로 |
| 에이전트 담당자 | 구독 CLI 등록, 능력 + 범위 선택 | 역할(`--agent`) 지정 불가, 사용자 종류는 프로젝트 지침을 읽지 못함(작업 폴더가 인계 디렉터리), API 에이전트는 진단 전용, A2A 없음 |
| 사람 담당자 | 요청에 응답(운영자, 웹) | 사람을 담당자로 둘 수 없음, 결과물 수정 단계 없음, 알림 없음 |
| 템플릿 | 없음 | 묶음 가져오기·내보내기 |
| 측정 | 2026-09-27 phase 9 완료(대역 검증): `task_events`(상태 변화·막힘·착수 가능), 설정 번호·러너 폴더 커밋·CLI 보고 비용/토큰, `/metrics` 화면·`/metrics.json`·`/metrics.csv`, GitHub 이력 기준선 가져오기([ADR-0015](../adr/0015-measurement-events-and-baseline.md)) | 실제 OpenArchive 기준선 가져오기(사용자 지시 후), 실제 순환 데이터로 도입 후 지표 채우기, v6 이전 실행은 비용·커밋 모름 |
| 배포 | 이전 공모전용 VM 구성(systemd), 로컬 데모 기동기 | 제품용 한 명령 셀프호스트 없음 |
| 팀 | 익명 세션 + 운영자 토큰 | 계정·멤버·권한 |

## 8. 배포 경로 — n8n 을 벤치마킹

n8n 은 1인 사이드 프로젝트로 시작해(2019) 셀프호스트로 사용자를 모은 뒤 약 1년 반 뒤(2021) 클라우드를 붙였다([Wikipedia](https://en.wikipedia.org/wiki/N8n)). Runloom 도 같은 순서로 간다.

1. **셀프호스트 우선**: 한 명령으로 중앙 서버·워커를 띄우고, 러너는 호스트에서 네이티브로 돈다(구독 CLI 가 호스트에 로그인돼 있으므로). 원격 접속이 필요하면 Cloudflare Tunnel.
2. **러너 프로토콜 고정**: 현재 계약 v1 을 러너 프로토콜로 문서화하고 호환을 지킨다.
3. **호스팅 제어면은 나중**: 수요와 약관(9절)을 확인한 뒤. 러너 하나로 셀프호스트·호스팅 양쪽을 지원하는 구조(GitLab Runner, Tailscale/Headscale)가 최종 형태다.

같은 계열 사례: 중앙 조율 + 사용자 인프라 실행 — [Buildkite](https://buildkite.com/about/company/)(보안 제약으로 클라우드 CI 를 못 쓰는 팀에서 출발, 사용자 수 과금), [Prefect hybrid](https://medium.com/the-prefect-blog/the-prefect-hybrid-model-1b70c7fd296), [Dagster+ Hybrid](https://docs.dagster.io/deployment/dagster-plus/hybrid). 실행량 과금은 사용자가 컴퓨팅을 부담하는 구조에서 반발을 부른다([GitHub self-hosted runner 과금 보류](https://github.com/orgs/community/discussions/182186)). 실행 위치를 벤더 쪽으로 옮기는 것([Trigger.dev v3](https://trigger.dev/blog/v3-developer-preview-launch))은 Runloom 의 존재 이유와 반대 방향이다.

이전 공모전용 VM 구성(ADR-0006·0008)은 이어서 쓰지 않는다. 10/2 배포는 셀프호스트다. 셀프호스트 패키징 결정은 새 ADR 로 남긴다.

## 9. 구독 에이전트와 약관

확인일 2026-09-26, Anthropic 공식 문서 기준.

- 허용: 사용자가 수정하지 않은 Claude Code 에 자기 구독으로 로그인해 쓰는 것, 플랫폼이 Claude Code 를 띄워주는 경우 포함([Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). `claude -p`·Agent SDK·서드파티 앱 사용은 구독 한도에서 차감된다([도움말, 2026-06-15](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)).
- 금지: 서드파티가 Claude 로그인을 자기 앱에 넣는 것, 사용자 구독 자격증명으로 요청을 대신 보내는 것, 자격증명·세션 토큰을 수집·저장·중개하는 것, 사용료 대납·재판매.
- 회색지대: 소비자 약관은 API 키이거나 명시적으로 허용된 경우가 아니면 봇·스크립트 등 자동화된 접속을 금지한다([Consumer Terms](https://www.anthropic.com/legal/consumer-terms)). 한도는 "일반적인 개인 사용"을 전제한다. 2026년에 서드파티 에이전트의 구독 사용 정책이 차단(4/4) → 별도 크레딧(5/13) → 보류(6/15)로 바뀌었다([VentureBeat](https://venturebeat.com/technology/anthropic-reinstates-openclaw-and-third-party-agent-usage-on-claude-subscriptions-with-a-catch)).
- 헤드리스 러너(예: OpenSQL VM): `claude setup-token` 으로 만든 1년 토큰을 `CLAUDE_CODE_OAUTH_TOKEN` 으로 쓸 수 있다([Authentication](https://code.claude.com/docs/en/authentication)). 토큰은 사용자가 러너 머신에 직접 두고 중앙에 보내지 않는다.

설계 규칙: 공식 CLI 를 수정 없이 호출하고 자격증명을 다루지 않는다 / 사람 게이트를 기본으로 둔다 / 에이전트별 API 키 모드를 대안으로 둔다 / "구독이라 무료"를 핵심 약속으로 쓰지 않는다 / 상업 출시 전 Anthropic 에 사용 형태를 확인한다.

## 10. 10/2 범위

목표: **Runloom 단독으로 OpenArchive 의 실제 이슈를 순환 처리하고, 셀프호스트로 배포하며, 도입 전후를 지표로 보여준다.**

| 묶음 | 내용 |
|---|---|
| 측정 | 업무 단위 이벤트 보충(시각·규칙/설정 버전), 지표 화면, 지표 API(JSON/CSV), OpenArchive GitHub 이력 기준선 가져오기 |
| 셀프호스트 | 한 명령 설치·실행(서버·워커), 러너는 호스트 네이티브, 데이터 보존·백업, 설치 문서. 선택: Cloudflare Tunnel |
| 실제 저장소 | 알림 웹훅(사람 차례·실패 → 등록 URL, Discord 웹훅 호환), 검증 프로필이 넘길 환경변수를 러너 로컬 등록에서 선언(OpenArchive 검증의 `DATABASE_URL`), worktree 에 없는 실행 환경(`backend/.venv`, `node_modules`) 사용 방법, OpenArchive 등록과 실연동 기록 |

통과 기준:
- OpenArchive 실제 이슈 3건 이상이 이슈 → 수정 → 검토 → 사람 차례 알림까지 사람의 전달 없이 진행되고, 기록이 [VERIFICATION_LOG](../VERIFICATION_LOG.md)에 남는다. 실패·재작업도 그대로 기록한다.
- 지표 화면에서 기준선과 도입 후 수치가 건수와 함께 나란히 보인다.
- 빈 디렉터리에서 설치 문서대로 한 명령 설치가 재현되고, 재시작 뒤 데이터가 보존된다.
- 토큰·비밀값이 DB·로그·응답·중앙에 남지 않는다.

10/2 이후로 미룸: 담당자 = 폴더 + 역할 등록, 쓰기 가능한 사용자 종류, 사람 수정 단계, 재작업·후속 생성 규칙 범용화, 템플릿, n8n 예시(블로그·지원자·채용자), API 키 모드, A2A, 팀 로그인, 호스팅 제어면.

## 11. phase 계획 (제안)

| 순서 | phase | 내용 | 이유 |
|---|---|---|---|
| 1 | `9-measure` | 이벤트 보충, 지표 집계·화면·API, GitHub 이력 기준선 | 기준선은 도입 전 데이터라 가장 먼저 |
| 2 | `10-selfhost` | 한 명령 설치·실행, 데이터 보존·백업, 설치 문서, 새 ADR. 접근 모델 재검토 — 익명 세션·운영자 토큰([ADR-0005](../adr/0005-access-model-anonymous-session-operator-token.md))은 공모전의 무로그인 공개 웹 요구에서 나왔고, 실서비스는 공개 URL 이 필요 없는 로컬 셀프호스트다 | 실제 사용 데이터가 처음부터 배포된 곳에 쌓이게 |
| 3 | `11-real-repo` | 알림 웹훅, 검증 환경 선언, OpenArchive 등록·실연동 3건 이상 | 10/2 의 증거 |

일정 위험: 9/26~10/2 에 세 phase 와 실연동. 늦어지면 Cloudflare Tunnel·CSV 내보내기·n8n 리포트부터 뺀다. 측정과 실연동은 빼지 않는다.

이후(제안): 담당자 등록(폴더 + 역할 + 권한, API 키 모드) → 쓰기 가능한 종류 + 사람 수정 단계 → 재작업·후속 생성 규칙 범용화 → 템플릿 + 블로그·지원자 예시(n8n) → 채용자 예시(사람 담당자·직무 라우팅) → A2A·팀 로그인·호스팅 제어면. 사용량 한도 대기([ADR-0007](../adr/0007-usage-limit-wait-policy.md), `3-limit-wait`)는 실사용에서 한도에 걸리는 빈도를 보고 당긴다.

## 12. 위험·미결과 기존 문서와의 차이

위험·미결:
- 구독 정책 변동(9절). 구독 한도 도달 시 대기 동작.
- OpenArchive 검증은 무겁다: `scripts/check.sh` 가 backend pytest(실제 pgvector DB 필요)·frontend lint·test·build 를 모두 돈다. 업무 종류별로 더 좁은 검증 명령이 필요할 수 있다. 에이전트가 닿는 DB 는 테스트용으로 한정한다.
- OpenArchive 는 자체 하네스(`phases/`)가 있다. 이슈 하나 단위의 작은 수정은 Runloom, 여러 단계짜리 기능은 하네스로 나누는 것을 제안한다.
- 지원자·채용자 사례의 개인정보(지원서·이력서)를 에이전트에 넘기는 정책은 그 사례 전에 정한다.
- 경쟁: [Paperclip](https://github.com/paperclipai/paperclip)(기존 에이전트 연결·업무 조율 표방), Copilot coding agent 의 self-hosted runner 지원. 표본이 작아 효과를 일반화하지 않는다.

ROADMAP 3절과 달라지는 점:
- 기본 지표 화면과 기준선을 MVP 에 넣는다(ROADMAP 은 "수동 집계로 시작 가능"). 고급 ROI 대시보드·조직 전체 추천 제외는 유지한다.
- 배포 형태를 셀프호스트 우선으로 정한다(ROADMAP 은 배포 형태를 정하지 않음).
- 첫 실제 저장소를 OpenArchive 로 정한다(ROADMAP 은 파일럿 도구·업무 미확정, 기본 제안은 GitHub Issues 버그 수정 → 검토로 같다).
