# UI 디자인 가이드

갱신일: 2026-09-22 (phase 7-n8n-gateway docs-sync — `/sources` 입구 화면·사이드바 `입구`·체인 화면 callback 한 줄)
상태: 제안. 화면 스택은 [ADR-0002](adr/0002-server-stack-python-fastapi-sqlite.md)의 Jinja2 서버 렌더링 + CSS + 소량 JavaScript다. Tailwind·웹폰트·외부 CDN·아이콘 라이브러리를 쓰지 않는다. 상태명·문구는 [GLOSSARY](GLOSSARY.md), 상태와 이유의 대응은 [PRD 3절](PRD.md)을 그대로 쓴다. 경로·문구는 구현된 템플릿(`src/workflow/server/templates/`)과 e2e(`tests/e2e/test_scenario.py`)에 맞춘다.

## 참고 화면과 대응

## 디자인 원칙

1. 도구처럼 보인다. 랜딩(`/`)은 로고·한 줄 설명·4단계·`서비스 바로 가기` 한 화면뿐이고, 앱(`/tasks` 이하)에는 마케팅 문구가 없다 — 첫 앱 화면이 곧 에이전트·업무 목록이다.
2. 상태와 이유는 항상 한 쌍이다. 배지 옆에 PRD 3절의 이유 문구를 붙이고, 접수와 시작을 시각적으로 구분한다.
3. 근거가 결론보다 먼저 보인다. 결과 카드와 뷰어는 검증 결과·근거 원문·산출물을 위에, 에이전트의 요약 문장을 아래에 둔다.
4. 심사자는 처음 왔고 2분 있다. 모든 화면에 다음 행동 버튼이 하나 있고, 빈 목록에는 빈 상태 문장과 그 버튼이 있다.

| 운영자 | `/operator` | 운영자 | 토큰 입력. 에이전트 등록·수정·삭제(능력 코드 text + 내장 datalist, scope 키 입력), 연결 코드 발급·취소, 병합 확인 대기 목록, 모든 세션 업무, 진단 예산 사용량 |

## 심사자 첫 방문 흐름

순서는 `tests/e2e/test_scenario.py` 의 주 경로(test_12~21, phase 5 step 9)와 같다. 문구는 화면이 실제로 보이는 것이며, 공개 데모는 세 Agent 모두 대본([ADR-0008](adr/0008-public-demo-scripted-agents.md))이다.

1. 랜딩(`/`). 세션을 만들지 않는다. 배너, 한 줄 설명, 4단계(에이전트 등록 → 업무 가져오기 → 워크플로우 자동 구성 → 자동 실행), 버튼 `서비스 바로 가기`.
2. 서비스 바로 가기 → 업무 홈(`/tasks`). 세션 쿠키가 발급된다. 등록한 에이전트가 없으므로 `먼저 에이전트를 등록하세요.` 안내와 `에이전트 등록` 버튼, `업무 가져오기`는 비활성(`에이전트를 먼저 등록하세요`). 업무 목록은 `아직 업무가 없습니다.`, 워크플로우 구역은 없다.
3. 에이전트 등록(`/agents/register`). 카탈로그 3개 — 운영 진단 데모(`agent-ops-demo`, API)·개인 Codex(`agent-codex-mac`)·Claude Code(`agent-claude-mac`) — 를 ops → codex → claude 순으로 `등록`. 카드마다 `시연용 · 대본 재생`. 홈에 카드 3개가 등록 순서대로, 로컬 2개는 `연결됨 · 마지막 확인 {시각}`, `업무 가져오기`가 활성이 된다.
4. 업무 가져오기(`/tasks/import`). GitHub Issues 탭(기본)에 fixture 이슈 `#41`~`#44`가 전부 체크돼 있고 배정 미리보기는 `#41` `operations.diagnose · daily-report`, `#42` `code.modify · demo-report-repo`(`blocked by #41`), `#43`·`#44` `맡을 에이전트 없음 · …`. 상단 `시연 데이터입니다 — 실제 GitHub·Jira 에 연결하지 않습니다.`. `가져와서 워크플로우 구성` → 워크플로우 화면.
5. 워크플로우 확인(`/chains/{chain_id}`). 순서·담당·이유가 한 화면에 있다.
   - 노드 1 `#41` 진단 · 담당 운영 진단 데모 · `실행 직접` · `자동 완료` · `실행 가능 · agent-ops-demo 선택됨` · 이유에 `체인의 첫 업무 — 선행 없음`.
   - 노드 2 `#42` 코드 수정 · 담당 개인 Codex(`시연용 · 대본 재생`) · `선행 완료 시 자동` · `검토 후 완료` · `대기 · 선행 대기` · 이유에 `선행 #41 (operations.diagnose) → code.modify 인계`와 `일치 후보 2개 — 먼저 등록한 agent-codex-mac`(등록 순서 동률 규칙). 시작 전에는 `담당 변경`으로 Claude Code 로 바꿀 수 있다.
   - 사람 단계 `검토 승인 (사람) · 병합은 운영자 확인` · `대기 · 선행 대기`.
   - `워크플로우에 넣지 않은 이슈` `#43`·`#44`와 이유. 동작 영역은 `워크플로우 시작` 하나. 홈 워크플로우 구역은 `0/2 완료 · 시작 전`.
6. 시작. `워크플로우 시작`을 누르면 노드 1이 `실행 요청됨`, 동작 영역이 `2단계 중 1단계 실행 요청됨`으로 바뀌고 3초마다 갱신된다(`data-poll="1"`).
7. A 완료. 노드 1이 `실행 요청됨 → 실행 중 → 완료 · 판정 근거: n/n`. 업무 상세는 결과 카드 `인계 가능`, 메타 끝 `대본 재생 (실제 모델 호출 없음)`, 뷰어 `진단 결과`(provenance `fake-fixture-script`), 브레드크럼에 `워크플로우 {title}` 칩.
8. B 자동 착수. A 완료 직후 워커가 노드 2를 사람 조작 없이 `대기 → 실행 요청됨 → 실행 중 → 확인 필요 · 검토 대기`로 옮긴다. 사람 단계도 `확인 필요 · 검토 대기`와 `검토하기` 링크, 진행 한 줄 `2단계 중 2단계 확인 필요`, 폴링 정지(`data-poll="0"`). 연결 프로그램이 오프라인이면 `대기 · 연결 끊김, 마지막 확인 {시각}`이다.
9. 검토 승인. `#42` 상세의 결과 카드 `검토 가능` + `대본 재생 (실제 모델 호출 없음)`, 산출물 칩 `diff`·`테스트 전`·`테스트 후`·`보고서`·`Codex JSONL`(Claude 를 먼저 등록한 세션이면 `Claude JSONL`). `완료 승인`을 누르면 노드 2는 `완료 · 검토 승인 · 병합: 운영자 확인 대기`, 사람 단계는 `완료 · 병합: 운영자 확인 대기`, 진행 한 줄 `2단계 모두 완료`, 홈은 `2/2 완료 · 2단계 모두 완료`.
10. 병합은 운영자 확인. 심사자 세션에는 `병합: 운영자 확인 대기`까지만 보이고, 병합 확인은 운영자 화면(`/operator`)에서만 한다(ADR-0005). 확인 뒤 사람 단계는 `완료 · 병합 확인됨`.

직접 등록 경로(`직접 등록` → `/tasks/new?example=diagnose`, 시연 업무 A·B 미리 채움)는 남아 있다. 동률 기본 선택(`prefer`)은 가져오기에만 있어 직접 등록한 B 는 접이식 행이 `자동 선택 · 미선택 · 후보 2개 — 선택 필요`이고(선행이 있으면 상태는 `대기 · 선행 대기`가 먼저, 없으면 `확인 필요 · 후보 2개 — 선택 필요`) `/tasks/{task_id}/select`로 담당을 골라야 한다. 시연 예시 A의 완료 방식만 기본값과 다르게 자동 완료로 채운다. 자동 완료가 가능한 유일한 업무 종류이고, 그래야 사람 조작 없는 인계가 화면에 보인다.

1. 브레드크럼 `agent-ops-demo / 일일 보고서 실패 진단` + 종류 라벨 칩(`.kind-chip`, 예 `진단`·`검토`). 우측에 연결 업무 칩 `선행 · {상태}`/`후속 · {상태}`와 뷰어 접기 버튼.
2. 요청 말풍선. `Task.request` 전문, 등록 시각. 배경 `--bg-bubble`, 반경 12px.
3. 접이식 행 `자동 선택 · agent-ops-demo · operations.diagnose 일치 후보 1개`. 펼치면 CONTRACT 9절의 선택 기록 표. `reason` 문자열은 그대로 출력한다.
4. 접이식 행 `완료 기준 · 자동 완료 · 결과가 ready_for_handoff이고 근거 검증 통과`. 펼치면 기준 항목 목록.

8. 상태 줄. 상태 배지 + 이유. 예 `실행 중 · 재현 테스트 작성, 수정 전 실행 실패 확인`, `대기 · 연결 끊김, 마지막 확인 10:12:03`, `확인 필요 · 검토 대기`.
9. 동작 영역. 상태에 따라 하나만 보인다.
   - `실행 가능`: 버튼 `실행`, 링크 `에이전트 직접 선택`.
   - `확인 필요`(검토 대기 또는 판정 불가): textarea `검토 의견`과 버튼 `완료 승인`, `수정 요청`, `종료`. 승인 뒤에는 코드 수정 업무만 "병합: 운영자 확인 대기"를 같은 자리에 남긴다(사용자 정의 종류는 `완료 · 검토 승인` 뿐). 선행 승인 전에 후속이 이미 돌 수 있으므로 브레드크럼의 `후속 · {상태}` 칩이 승인 화면에서도 갱신된다.
   - `확인 필요`(후보 0개 또는 2개 이상): 에이전트 선택 목록과 버튼 `확정`.
   - 그 외: 비어 있다.

## 결과 카드

PR 카드 형식. 테두리 카드, 첫 줄에 outcome 배지와 대상, 둘째 줄에 요약 한 줄, 셋째 줄에 모노스페이스 메타.

| 종류 | 첫 줄 | 셋째 줄 메타 |
|---|---|---|
| 진단 | 배지 + `daily-report · daily-0920-0900` | `response_path_changed` · `근거 5 · 첨부 8 · 검증 6/6 통과` |
| 코드 수정 | 배지 + `demo-report-repo · fix-daily-0920` | `9b7e4d2` ← `3f9c2e1` · `3 files` · `+21 -8` · `vp-pytest exit 0` |
| 결과 봉투(`generic_result`, 사용자 정의 종류) | 배지(outcome 코드 그대로, 예 `approved`) + `{scope 값} · {task_id}` | `결과 봉투 · {kind} · 산출물 {n}` — 둘째 줄은 `summary`. 커밋·병합 문구 없음. 뷰어는 `결과 봉투`(outcome → summary → 산출물 ID 목록) |

outcome 표시 라벨. 코드 값은 GLOSSARY, 라벨은 여기서만 정한다.

| outcome | 라벨 | 배지 색 |
|---|---|---|
| `ready_for_handoff` | `인계 가능` | `--state-done` |
| `ready_for_review` | `검토 가능` | `--state-attention` |
| `needs_information` | `정보 필요` | `--state-attention` |
| 그 외(사용자 정의 종류의 `outcomes`) | 코드 그대로 | `--state-attention` |

증감 수는 `+21` `--state-done`, `-8` `--state-failed` 모노스페이스. 카드 우측에 `뷰어에서 열기` 아이콘 버튼.

## 오른쪽 열 — 산출물 뷰어

- 헤더: 산출물 이름, `kind` 배지, 크기, 버튼 `원문 보기`, `복사`, `다운로드`.
- 기본 내용. 진단이면 `진단 결과`, 코드 수정이면 `검증 요약`. 칩을 누르면 개별 산출물로 바뀐다.
- `진단 결과` 렌더링 순서: 검증 결과(통과·미충족 항목) → `summary` → `findings`(claim과 근거 칩) → `diagnosis` 표 → `repair_request` → `missing_information`. `needs_information`이면 `missing_information`을 맨 위로. 두 칸 비교 `변경 전 응답 / 변경 후 응답`을 `findings` 아래에 두고 `old_path`·`new_path` 값을 강조한다.
- `검증 요약` 렌더링 순서: `verification`(프로필, 종료 코드, 결과 커밋) → 두 칸 비교 `수정 전 테스트 / 수정 후 테스트`(각 로그 마지막 20줄) → 생성된 `보고서` → `summary`.
- 근거 칩 `evidence_id@version · location`은 모노스페이스. 누르면 바로 아래에 첨부 원문의 해당 값 또는 줄 범위를 펼친다. 원문은 서버가 첨부에서 잘라 준다. 모델 문장을 원문 대신 넣지 않는다.
- `diff`는 `<pre>`에 추가 줄 `--bg-done`, 삭제 줄 `--bg-failed`. 로그는 `<pre>` 모노스페이스 13px, 줄 번호 표시.
- 두 칸 비교는 참고 화면의 Before/After 카드와 같다. 각 칸 위에 12px 라벨, 안에 테두리 상자, 아래에 한 줄 설명.

## 상태 표시

배지는 연한 배경 알약 + 점 + 한글 상태 텍스트다. 점의 채움은 의미를 갖는다. 빈 점은 상대 쪽에서 아직 확인된 사실이 없다는 뜻, 채운 점은 확인된 사실이다.

| 사용자 상태 | 점 | 글자·점 색 | 배경 | 이유 문구 예 |
|---|---|---|---|---|
| `대기` | 빈 점 | `--state-wait` | `--bg-wait` | 선행 대기 / 자동 실행 대기 / 후속 규칙 없음: code_change → review — 규칙을 등록하거나 직접 실행 / 연결 끊김, 마지막 확인 10:12:03 |
| `실행 가능` | 빈 점 | `--state-ready` | `--bg-wait` | agent-ops-demo 선택됨 |
| `실행 요청됨` | 빈 점 | `--state-inflight` | `--bg-inflight` | 접수 확인 / 접수 대기 |
| `실행 중` | 채운 점, 맥동 | `--state-inflight` | `--bg-inflight` | 마지막 진행 메시지 |
| `확인 필요` | 채운 점 | `--state-attention` | `--bg-attention` | 검토 대기 / 후보 2개, 선택 필요 / 선행 outcome needs_information 은 규칙 대상 아님 — 확인 필요 / 허용되지 않은 outcome … — 허용: … / 시작 여부 불명, 재실행하지 않음 |
| `완료` | 채운 점 | `--state-done` | `--bg-done` | 판정 근거 / 검토 승인 |
| `실패` | 채운 점 | `--state-failed` | `--bg-failed` | 실패 코드·메시지 |

내부 Execution 상태(`queued`, `accepted`, `running`…)는 실행 블록 안에서만 보조 텍스트로 보인다. 에이전트 연결 상태는 `연결됨`(채운 점, `--state-done`)과 `연결 끊김`(빈 점, `--state-wait`) 둘이고 항상 "마지막 확인 {시각}"을 붙인다.

대본 라벨 `시연용 · 대본 재생`(`.tag-scripted`)은 배지가 아니다 — 12px/400 `--text-muted` 회색 텍스트를 Agent 이름 옆에 붙인다(홈·에이전트 목록·등록·상세·워크플로우 노드의 담당). `agents.demo_scripted=1` 일 때만 보이며 상태 점·배경을 갖지 않아 상태 배지와 헷갈리지 않는다. 결과 카드는 그 Agent 가 만든 결과일 때 메타 끝에 `대본 재생 (실제 모델 호출 없음)`을 붙인다. `mock`·`simulation` 같은 다른 표현을 쓰지 않는다.

callback 한 줄(`.callback-line`, `<p class="small" data-callback-state="대기|전송됨|실패">`)도 배지가 아니다 — 체인 화면 브레드크럼 아래 12~13px `--text-muted` 한 줄로, 출처가 `n8n` 이고 `callback_url` 이 있을 때만 있다. 문구는 네 가지뿐이다: `callback · {host} · 대기(사람 차례가 되면 보냄)` / `callback · {host} · 대기 · 재시도 {n}회 · {last_error}`(전송 실패 뒤 물러나 기다리는 중) / `callback · {host} · 전송됨 {n분 전}` / `callback · {host} · 실패 {n}회 · {last_error}`(5회 실패 후 중단). `host` 는 `callback_url` 의 `netloc` 만이고 URL 전체·전송 본문은 화면에 찍지 않는다. `webhook`·`알림` 같은 다른 표현을 쓰지 않는다.

## 컴포넌트

- 카드: `background: var(--bg-card); border: 1px solid var(--border); border-radius: 10px; padding: 16px 20px`. 그림자 없음.
- 버튼: 기본 `background: var(--text); color: #fff`, 보조 `background: #fff; border: 1px solid var(--border-strong)`, 종료·거절 `color: var(--state-failed); border: 1px solid currentColor`. 높이 36px, 가로 여백 14px, 반경 8px. 비활성은 사유를 옆 문구로 표시한다.
- 입력: `border: 1px solid var(--border-strong); border-radius: 8px; padding: 9px 12px`. 포커스 `outline: 2px solid var(--accent); outline-offset: 1px`. 라벨 위, 도움말 아래 12px.
- 배지·칩: 높이 24px, 반경 6px, 12px/500. 산출물 칩은 테두리 + 파일 아이콘 + 이름.
- 접이식 행: 왼쪽 chevron, 13px `--text-muted`, 펼치면 아래에 표. 상태는 `<details>`로 구현해도 된다.
- 오류 알림: 카드 상단 인라인, `--bg-failed`. API 오류 본문의 `message`를 그대로, `code`는 모노스페이스 12px. 429는 `details.resets_at`을 "다시 가능: {시각}"으로 붙인다.
- 빈 상태: 한 문장 + 버튼 하나.

## 타이포그래피

| 용도 | 스타일 |
|---|---|
| 브레드크럼·카드 제목 | 15px / 600 / `--text` |
| 뷰어 문서 제목 | 20px / 600 |
| 본문·요청 말풍선 | 14px / 400 / `--text-body` / 행간 1.6 |
| 목록 보조·시각·이유·접이식 행 | 12~13px / `--text-muted` |
| ID, 커밋, 경로, 능력 코드, 로그, diff, 증감 수 | `--mono` 13px |

시각은 `2026-09-20 10:12:03 KST` 절대 시각으로, 목록과 "마지막 확인"만 `12분 전`을 쓴다. 서버는 UTC 저장, 템플릿에서 Asia/Seoul 변환.

## 실시간 갱신

- 상태 줄, 실행 블록, 결과 카드, 산출물 칩, 동작 영역, 왼쪽 목록의 상태를 `data-live` 조각으로 두고 3초마다 교체한다. 입력 중인 textarea가 있는 조각은 교체하지 않는다.
- 상태 줄 옆에 "마지막 갱신 10:12:03". 실패하면 "갱신 실패, 재시도 중"으로 바꾸고 화면을 멈추지 않는다.
- 업무가 `완료`·`실패`이면 10초로 늦춘다. 후속 업무 칩의 상태도 같은 조각에 넣어 페이지를 옮기지 않아도 B 착수가 보인다.

## 애니메이션과 아이콘

- 허용: 조각 교체 시 opacity 0.2s, `실행 중` 점 1.2s 맥동, 슬라이드 오버 0.2s. `prefers-reduced-motion`이면 맥동을 끈다. 그 외 금지.
- 아이콘은 인라인 SVG 소수만: chevron, 파일, 복사, 열기, 다운로드, 검색, 목록. `stroke-width: 1.5`, 16px, 둥근 배경 상자로 감싸지 않는다.
