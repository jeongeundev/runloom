# 벤치마크: 로컬 코딩 에이전트 + 업무 보드 제품 (2026-09-29)

조사 범위: 사용자 PC 에서 도는 Claude Code / Codex 등을 업무(카드·이슈) 단위로 돌리는 제품. 1차 출처(공식 문서·공식 README·공식 블로그·GitHub API)만 사용했다. 문서에 없으면 "확인 못 함" 으로 적었다. 스타 수·릴리스 날짜는 2026-09-29 GitHub API(`gh api repos/...`) 기준.

## 요약

이 범주의 제품은 거의 모두 **"업무 1건 = 워크스페이스 1개 = git worktree + 브랜치 1개 + 에이전트 세션 1개"** 라는 같은 뼈대를 쓴다. 차이는 (1) 업무가 어디서 오는지, (2) 보드의 칸을 사람이 옮기는지 사실(세션·PR·CI·리뷰 상태)에서 자동으로 계산하는지, (3) 결과 이후의 되먹임(리뷰 코멘트·CI 실패 → 같은 에이전트에게 다시 보냄)을 자동화하는지에 있다. 가장 가까워 보였던 **Vibe Kanban 은 운영사 Bloop 이 2026-04-10 폐업**했고, 클라우드 쪽(칸반 이슈·프로젝트·조직)은 30일 뒤 제거되어 지금은 커뮤니티 유지 로컬판이다. GitHub 이슈를 필터로 끌어와 보드 첫 칸에 넣는 제품은 **Kanban Code**(프로젝트별 `gh` 검색 필터) 와 **Conductor**(워크스페이스 생성 시 GitHub/Linear 이슈 선택) 정도이고, Vibe Kanban·Claude Squad·Sculptor 는 수동 입력만 문서화되어 있다. Jira 를 업무 입구로 쓰는 제품은 없었다(Paperclip 은 Jira 를 "에이전트가 쓰는 도구" 로만 연결). 결과 처리에서는 **Agent Orchestrator(AO)** 와 **Kanban Code** 가 PR·CI·리뷰 상태로 카드 칸을 자동 결정하고, **Sculptor 의 CI Babysitter**·**AO** 가 CI 실패·리뷰 요청을 같은 에이전트에게 자동으로 되돌린다. 사람 승인 단계를 1급 개념으로 둔 곳은 **Paperclip**(Reviewers/Approvers, execution policy) 하나다. 권한 면에서는 모두 "worktree 는 격리가 아니라 작업 분리일 뿐, 에이전트는 사용자 권한으로 로컬 셸을 그대로 쓴다" 는 입장이다(Conductor 는 문서에 명시).

## 제품별 상세

### 1. Vibe Kanban (BloopAI)

**상태 먼저**: Bloop 은 2026-04-10 폐업을 발표했다. "The Vibe Kanban project will live on, open source and community maintained", 원격 서비스("kanban issues, comments, projects and organisations")는 30일 뒤 종료되고 "a fully local architecture" 로 전환 ([blog/shutdown](https://www.vibekanban.com/blog/shutdown)). README 상단에도 "Vibe Kanban is sunsetting" ([README](https://github.com/BloopAI/vibe-kanban)). 폐업 후에도 v0.1.45 가 2026-09-19 에 나왔다(버그 수정 위주, [releases](https://github.com/BloopAI/vibe-kanban/releases)). 아래 문서 내용 중 이슈·보드 부분이 현재 로컬판에서 그대로 동작하는지는 **확인 못 함**(문서가 클라우드 시절 기준일 수 있음).

1. **업무 입구**: 이슈는 수동 생성 — 칸 머리의 "+" 또는 필터 바의 "New Issue" ([issue-management](https://vibekanban.com/docs/issue-management.md)). GitHub/Linear/Jira 이슈 가져오기는 문서에 없음; GitHub 연동 문서는 PR 생성만 다룬다 ([github-integration](https://vibekanban.com/docs/integrations/github-integration.md)). 에이전트가 MCP 서버의 `create_issue`(부모 이슈 지정 가능)·`start_workspace` 로 이슈를 만들고 실행을 시작할 수 있다 ([vibe-kanban-mcp-server](https://vibekanban.com/docs/integrations/vibe-kanban-mcp-server.md)).
2. **데이터 모델**: title, description(리치 텍스트, "serves as the prompt sent to coding agents"), priority(Urgent/High/Medium/Low), assignee, tags; 하위 이슈(부모 자동 완료 안 됨) ([issue-management](https://vibekanban.com/docs/issue-management.md)). 외부 형식 매핑: 해당 없음(가져오기 없음).
3. **PR 표시**: 워크스페이스 사이드바에 "pull request status badges" ([interface](https://vibekanban.com/docs/workspaces/interface.md)). Git 패널은 저장소·현재/대상 브랜치·미커밋 수·ahead/behind·충돌 표시 ([git-operations](https://vibekanban.com/docs/workspaces/git-operations.md)). CI 체크·리뷰 상태의 앱 내 표시는 확인 못 함("PRs appear on GitHub displaying ... CI checks" 라고만 씀).
4. **배정·실행**: 이슈 하나에 워크스페이스 여러 개(병렬 실행) ([issue-management](https://vibekanban.com/docs/issue-management.md)). 워크스페이스 생성 시 저장소(여러 개 가능)·대상 브랜치·에이전트·작업 설명 선택, "a git worktree - a separate working directory with its own branch", 설정 시 setup script 실행, dev server 버튼 ([creating-workspaces](https://vibekanban.com/docs/workspaces/creating-workspaces.md)). 에이전트 프로필(Settings → Agents)로 변형 저장: Claude Code `dangerously_skip_permissions`, Amp `dangerously_allow_all`, Gemini/Qwen `yolo`, Cursor `force` ([agent-configurations](https://vibekanban.com/docs/settings/agent-configurations.md)). worktree 위치는 확인 못 함. 컨테이너 실행 없음(문서상 언급 없음).
5. **결과 처리**: 통합/나란히 diff, 파일 트리; 줄에 코멘트 → "Comments are collected and submitted together when you send a message in the chat" ([reviewing-code](https://vibekanban.com/docs/reviewing-code.md)). PR 생성 대화상자(AI 설명·제목 자동·기본 브랜치·Draft 토글), merge, rebase, 충돌 파일 목록 ([git-operations](https://vibekanban.com/docs/workspaces/git-operations.md)). 워크스페이스 상태 "Running / Idle / Needs Attention" ([interface](https://vibekanban.com/docs/workspaces/interface.md)). 결과 판정 후 후속 이슈 자동 생성은 확인 못 함(MCP 로 에이전트가 만들 수는 있음).
6. **첫 실행·화면**: `npx vibe-kanban` → 에이전트·IDE·알림 선호 설정 → GitHub/Google 로그인(건너뛰기 가능) → 개인 조직·첫 프로젝트 자동 생성 → 이슈 생성 → 워크스페이스 생성 → 에이전트 즉시 실행 → 검토 → PR 또는 로컬 merge ([getting-started](https://vibekanban.com/docs/getting-started.md)). 보드: 앱 바 / 카드 그리드 / 생성 버튼 / 오른쪽 상세 패널; 칸 To do·In progress·In review·Done, 숨김 Backlog·Cancelled ([getting-started](https://vibekanban.com/docs/getting-started.md), [issue-management](https://vibekanban.com/docs/issue-management.md)). 워크스페이스 화면은 4패널(워크스페이스 목록 / 대화 / 변경·로그·미리보기 / Git·터미널·메모) ([interface](https://vibekanban.com/docs/workspaces/interface.md)).
7. **라이선스·성숙도**: Apache-2.0, 28,214★, 최근 릴리스 v0.1.45(2026-09-19) (GitHub API).

### 2. Conductor (conductor.build)

1. **업무 입구**: "Workspaces can be created from branches, pull requests, GitHub issues, or Linear issues" (⌘⇧N 또는 New workspace 옆 `...`) ([workflow](https://www.conductor.build/docs/concepts/workflow)). 2026-02-26 "Open from Linear" — Linear 이슈에서 Conductor 워크스페이스를 연다 ([changelog 0.36.5](https://www.conductor.build/changelog/0.36.5-open-from-linear-bug-fixes)). 이슈 선택 UI 의 검색·필터 방식, 동기화 여부는 확인 못 함 ([issue-to-pr](https://www.conductor.build/docs/guides/issue-to-pr)). Jira 는 문서에서 못 찾음.
2. **데이터 모델**: 별도 업무 모델 없이 워크스페이스가 단위. 이슈에서 만들면 에이전트가 "the issue title, description, and context" 를 받음 ([issue-to-pr](https://www.conductor.build/docs/guides/issue-to-pr)). 필드 매핑 상세는 확인 못 함.
3. **PR 표시**: Checks 탭 = "git status, CI, deployments, comments, and todos before you merge"; GitHub 리뷰 스레드 포함; "unresolved todos or failed checks" 면 merge 를 막거나 말림 ([checks](https://www.conductor.build/docs/reference/checks)). GitHub 리뷰 코멘트가 Diff Viewer 에도 뜸 ([diff-viewer](https://www.conductor.build/docs/reference/diff-viewer)).
4. **배정·실행**: 워크스페이스마다 git worktree·브랜치·터미널; Claude Code, Codex, Cursor, OpenCode ([workflow](https://www.conductor.build/docs/concepts/workflow)). setup/run script, `CONDUCTOR_PORT`, `.context` 폴더(커밋 안 되는 메모·인계). "Isolation is development-focused, not a security boundary ... with your user permissions" ([workspaces-and-branches](https://www.conductor.build/docs/concepts/workspaces-and-branches)). Plan/Fast 모드, 추론 수준 ([agent-modes](https://www.conductor.build/docs/concepts/agent-modes)). 권한 우회 플래그는 문서에서 확인 못 함.
5. **결과 처리**: ⌘⇧D Diff Viewer, 줄 코멘트가 작성창 첨부가 됨, `Review` 로 에이전트 리뷰, ⌘⇧P PR 생성(에이전트가 diff 로 PR 본문 작성), GitHub Actions 감시, 끝나면 archive(History 에서 복원) ([workflow](https://www.conductor.build/docs/concepts/workflow)). "Conductor recommends actions" — 다음 할 일(Create PR·피드백 대응·체크 수정·merge)을 제안 ([diff-viewer](https://www.conductor.build/docs/reference/diff-viewer)). 후속 업무 자동 생성·알림은 확인 못 함.
6. **첫 실행·화면**: 설치 후 "Open project"(로컬) / "Open GitHub project" / "Quick start" 중 선택, 터미널의 GitHub 자격 사용, 워크스페이스 자동 생성 ([first-workspace](https://www.conductor.build/docs/first-workspace)). 화면: 사이드바(워크스페이스) + 채팅 작성창 + 터미널 + 파일 + Diff Viewer + Checks 탭 ([first-workspace](https://www.conductor.build/docs/first-workspace)). 칸반 보드는 없음(문서상 사이드바 목록).
7. **라이선스·성숙도**: Mac 앱. Free($0, 로컬 워크스페이스·자기 구독/키), Pro $50/월(클라우드 워크스페이스·멀티플레이어·API·모바일), Teams $60/인/월, Enterprise ([pricing](https://www.conductor.build/pricing)). 소스 공개 여부·버전은 확인 못 함.

## Runloom 에 가져올 점

1. **보드 칸을 "사실에서 계산" 하고 사람 차례를 한 칸으로 모은다** — AO 의 Working / **Needs you** / In review / Ready to merge. Runloom 의 여러 상태·outcome 을 사용자에게 그대로 보이지 말고, "지금 내가 해야 할 일"(사람 차례·판정 실패·변경 요청·러너 끊김)을 한 칸에 모으면 첫 화면이 한 질문("뭘 봐야 하지?")에 답한다. (AO, Kanban Code 의 Waiting 칸)
2. **업무 입구 = 프로젝트별 저장된 GitHub 검색 필터 하나** — Kanban Code 는 `assignee:@me label:bug` 같은 `gh` 검색식을 프로젝트 설정에 두고 백로그를 자동으로 채운다. Runloom 의 "업무 가져오기" 를 저장소 선택 + 필터 문자열 1개로 줄이고, 이슈 본문을 그대로 첫 프롬프트로 쓰면 Jira 도 같은 틀(JQL 한 줄)로 붙일 수 있다. (Kanban Code, Conductor 의 "이슈에서 워크스페이스 만들기")
3. **카드 하나에 이슈·실행·PR 을 선택적 링크로 붙이고 중복을 재조정기로 막는다** — "card = 1급 객체, 세션·worktree·PR·이슈는 있을 수도 없을 수도" 모델은 fix → review → rework 로 이어지는 Runloom 후속 업무를 "같은 카드의 다음 단계" 로 보여 줄지, 별도 카드로 보여 줄지 결정할 때 기준이 된다. (Kanban Code)
4. **PR 요약은 카드에 짧게, merge 준비 체크리스트는 상세에** — 카드에는 PR 상태·실패 체크 이름·미해결 코멘트 수만(AO 는 원시 로그를 의도적으로 뺀다), 상세에는 git·CI·리뷰 스레드·todo 를 한 탭에 모아 "merge 해도 되는가" 를 판단하게 한다. (AO, Conductor Checks 탭, Sculptor PR 버튼)
5. **자동 되먹임에 재시도 상한과 "같은 실패에 두 번 안 쏨" 규칙** — Sculptor CI Babysitter: 워크스페이스가 한가할 때만, 새 실패 run 에만, 상한(기본 3) 넘으면 사람에게 넘기고, merge·close 는 절대 자동으로 안 함. Runloom 의 rework 후속 규칙과 "사람 차례" 전환 조건을 이 문장들로 명시하면 사용자가 자동화 범위를 이해하기 쉽다. (Sculptor, AO 의 nudge)
6. **사람 검토 단계를 업무 필드로 드러낸다** — Paperclip 은 이슈마다 Reviewers/Approvers 와 execution policy 를 두고, In Review 에서 "Run review" 와 승인·반려를 이슈 화면 안에서 끝내며 기록을 Activity 에 남긴다. Runloom 의 "사람 차례" 를 숨은 규칙이 아니라 카드에 보이는 "검토자: 나" 로 표시하는 방식. (Paperclip)
7. **첫 실행은 3단계 마법사 + 의존성 점검** — Sculptor(이름 → Claude CLI·git 점검 → 저장소 추가), Kanban Code(기존 세션 스캔 → 프로젝트 추가 → 훅 설치). Runloom 은 "러너 연결됨? → 저장소·필터 선택 → 첫 업무 가져와 실행" 3단계로 줄이고, 러너·`claude`·`gh` 준비 상태를 첫 화면에서 점검해 보여 주면 된다. (Sculptor, Kanban Code)

참고로 권한 면에서는 조사한 제품 모두 로컬 에이전트를 사용자 권한으로 돌리고(worktree 는 격리가 아님, Conductor·AO 문서에 명시), 권한 우회를 프로필 옵션(Vibe Kanban `dangerously_skip_permissions`, Paperclip 기본 true)으로 둔다. Runloom 이 러너에서 실행 파일·인자를 고정하는 방식은 이들보다 보수적이다.
