# ADR-0022: 업무 화면 — 한 줄 표·오른쪽 상세 패널·연결 화면·직접 작업과 PR 신호

결정일: 2026-09-30 (phase 16 step 0). 근거: [재설계 계획](../product/REDESIGN_PLAN.md) 4절(화면)·10절(직접 작업)·13절(phase 제안 4 `16-work-ui`), 목업 3판(비공개), [ADR-0020](0020-work-items-and-stages.md)(업무·단계, 업무 상태 계산), [ADR-0021](0021-team-accounts-and-roles.md)(역할 × 동작, 맡긴 사람, 받는 사람). 기본값은 [phase 16 README](../../phases/16-work-ui/README.md) "계획 기본값" 9가지(사용자 결정 2026-09-30)이며 이 문서로 구현 기준을 고정한다. 적용 범위는 `service` 브랜치. 이 시점에는 구현이 없다 — 아래 이름·주소·표는 step 1~10 이 만들고, 바꿀 때는 이 ADR·[ARCHITECTURE](../ARCHITECTURE.md) "업무 화면 — phase 16"·[UI_GUIDE](../UI_GUIDE.md)·[GLOSSARY](../GLOSSARY.md)·테스트를 같이 고친다. 이름·주소·시그니처의 기준은 ARCHITECTURE 쪽이다(README 와 다르면 ARCHITECTURE).

**이 ADR 은 ADR-0020 결정 4 의 "`직접 작업 중` 은 값만 예약한다 — 신호는 16-work-ui 이후" 를 채운다.** 신호는 [내 세션에서 작업] 버튼과 업무 키가 든 PR 이다(브랜치 push·Claude Code 훅은 아님).

계기(README "조사로 확인한 현재"): 사이드바에 기능 단위 탐색 10개가 흩어져 사용자가 할 일이 안 보인다. 홈은 에이전트 카드·체인 카드·업무 카드 목록과 빠른 필터 두 개뿐이고 담당자별 묶음·보드·표가 없다. 업무 상세는 전체 페이지라 목록으로 돌아가면 맥락을 잃는다. 담당·우선순위를 바꾸는 화면·경로가 없고, 맡기기는 GitHub 이슈(`/tasks/{id}/delegate`)와 직접 등록(`/select` → `/run`) 두 갈래다. 사람이 자기 세션에서 연 PR 을 업무에 붙일 곳이 없어 `직접 작업 중` 을 계산할 수 없다.

## 결정

1. **업무 화면 = `/tasks` 의 한 줄 표.** 칸 8개: 키(원본 키가 있으면 원본 키 + 원본 표시, 없으면 `RUN-n`) · 제목 · 담당 · 우선순위 · 종류 · 상태 · 다음 할 일 · 업데이트. 묶기는 담당자(맨 위 "담당 없음", 그다음 사람, 그다음 에이전트) 또는 상태. 빠른 필터 4개: 전체 · 내 차례(로그인한 멤버가 받는 사람) · 담당 없음 · 에이전트 작업 중. 보기는 목록 / 보드. 필터·묶기·보기·열린 업무·끝난 업무 범위는 주소 쿼리(`q`·`group`·`view`·`open`·`closed`)에 남는다 — 값은 열거형으로만 받고 모르는 값은 기본값이다. "다음 할 일" 칸은 열린 사람 요청 질문 → 직접 작업 → PR → 상태 이유 순이다(판단 제안 칸은 18-triage). 기본 목록은 끝나지 않은 업무 + 최근 14일 안에 끝난 업무다.
2. **상세는 오른쪽 패널.** 목록은 그대로 두고 오른쪽에 패널이 열린다. 주소는 `/tasks?open=RUN-12` — 새로 고침·링크 공유도 같은 상태다. 서버가 `open` 을 보고 패널을 함께 렌더하므로 JS 없이도 열린다. JS 는 행을 누를 때 패널 조각(`/work/{key}/panel`)을 불러와 끼우고 `history.pushState` 로 주소만 바꾼다. `/work/RUN-12` 는 `/tasks?open=RUN-12` 로 303. 알림·원본 댓글의 상세 링크도 업무 주소로 바꾼다. 단계 상세 `/tasks/{task_id}`(3열 셸·산출물 뷰어·라이브 조각)는 그대로 남아 패널의 진행 타임라인에서 링크한다.
3. **보드는 보기 전용.** 칸 6개: `대기`(`새로 들어옴` 포함) · `에이전트 작업 중` · `직접 작업 중` · `내 차례` · `PR · 검토` · `완료`. `종료` 는 보드에 없다(목록의 상태 묶음에서 본다). 끌어 옮기기 없음 — 업무 상태는 계산값이다(ADR-0020 결정 4). 카드를 누르면 패널.
4. **담당을 에이전트로 고르면 곧 맡기기.** 패널의 담당 선택에서 에이전트를 고르면 그 업무의 가장 최근 미마감 단계에 그 에이전트를 지정(`select_agent(mode="manual")`)하고, GitHub 지시 전 이슈면 지시를 기록하고, 바로 착수를 시도한다(`POST /work/{key}/assignee` — 지금의 delegate·select·run 을 한 경로로). 지금 못 시작하면 담당·선택은 저장되고 대기 사유가 단계에 남는다(지금 [에이전트에게 맡기기] 와 같다). 사람을 고르면 배정만, "없음" 은 담당 해제. 활성 실행이 있거나 끝난 업무는 담당을 바꿀 수 없다(409). 우선순위도 패널에서 바꾼다. 필요 동작은 `delegate` — 관리자·멤버 모두. 맡긴 사람은 누른 멤버(ADR-0021 결정 5). 기존 `/tasks/{id}/delegate`·`/select`·`/run` 은 주소·동작을 유지하고 같은 내부 함수를 쓴다.
5. **연결 화면으로 모은다.** `/connect` 탭 5개: 가져올 곳(`sources` — GitHub 연결·저장소·러너 붙이기·기준선, n8n 입구) / 팀·담당자(`team` — 멤버·초대, 에이전트, 러너) / 업무 종류·규칙(`kinds`) / 알림(`notify`) / 고급(`advanced` — 연결 코드 수동 발급, 에이전트 수동 등록). 탭 본문은 기존 템플릿 내용을 옮겨 재사용하고 권한은 기존 화면 그대로다. 옛 GET 주소(`/sources`·`/operator`·`/operator/github`·`/operator/notifications`·`/team`·`/agents`·`/kinds`)는 새 탭으로 303. 모든 POST 경로와 GitHub App 만들기·콜백·설치 setup 경로는 주소를 바꾸지 않는다(GitHub 에 등록된 URL·기존 폼). 지표 화면은 이름만 **모니터링**(`/monitor`, `/metrics` → 303, `/metrics.json`·`/metrics.csv` 그대로).
6. **사이드바**: 업무(내 차례 수) · 모니터링 · 연결 · 시작하기 · 내 설정, 아래 로그인 멤버·로그아웃. "최근" 목록과 `+` 는 없앤다 — 업무 화면이 목록이고 업무 등록은 업무 화면 도구 막대의 버튼이다.
7. **시작하기** `/start`: 가져올 곳 연결 → 러너 붙이기 → 팀원 초대(선택) → 첫 업무 맡기기. 각 항목의 완료는 DB 에서 계산한다(순수 함수). 필수 세 항목이 다 끝나면 사이드바에서 숨긴다(주소는 계속 열린다).
8. **직접 작업 = 버튼 + PR 신호.** 패널 [내 세션에서 작업] → 담당 = 누른 멤버(다른 멤버가 담당이어도 바뀐다), 업무 상태 `직접 작업 중`(이유 = 멤버 표시 이름), 키가 든 브랜치 이름(`RUN-15-url-filter`)을 복사해 준다. 에이전트 실행 중이면 누를 수 없다. 직접 작업 중에는 워커가 그 업무의 단계를 자동 착수하지 않는다. [직접 작업 그만두기]·[에이전트에게 넘기기](= 그만두기 + 결정 4 의 에이전트 담당). GitHub 동기화가 소스 저장소의 PR 목록을 읽어 **head 브랜치 이름이나 제목에 업무 키가 든 PR** 을 업무에 붙인다(업무 PR): 열림 → `PR · 검토`, 병합 → `완료`, 병합 없이 닫힘 → 무시(직접 작업이면 `직접 작업 중` 으로 돌아간다). Runloom 이 연 PR 은 따로 저장하지 않는다(지금의 `task_pull_requests` 그대로). 브랜치 push 만으로는 감지하지 않는다. 직접 작업은 Runloom 결과 판정을 거치지 않는다 — 완료는 PR 병합으로만(REDESIGN_PLAN 10절, 계약 v1).
9. **스키마 v12 는 ALTER + 새 표 + `work_item_events` 재생성.** `work_items.direct_member_id`·`direct_started_at`·`direct_branch`, 새 표 `work_pull_requests`(감지 PR 전용 — Runloom PR 은 `task_pull_requests`), `github_sources.pull_cursor`, `work_item_events.type` 에 `priority_changed`·`direct_started`·`direct_stopped`·`pull_request_linked` 추가. `work_item_events` 는 다른 표가 참조하지 않아 CHECK 를 넓히려 재생성한다(행·id 보존). `tasks` 재생성 금지(ADR-0020)는 그대로. v11 → v12 는 한 트랜잭션이고 실패하면 v11 그대로다.

## 하지 않는 것

- 판단 제안·확신도·자동 시작(18-triage), Jira(17-jira), 모니터링 지표 확장(19-monitor).
- Claude Code 훅 상태 보고(REDESIGN_PLAN 10절 2 — 다음 phase 로 미룸, 사용자 결정 2026-09-30).
- 보드 끌어 옮기기, 브랜치 push 감지, 여러 행 선택·일괄 변경, 목록 안 인라인 편집(담당·우선순위는 패널에서).
- 새 JS 프레임워크·번들러·CDN·아이콘 라이브러리(ADR-0002). 소량 인라인 JS 와 `static/` 의 파일 하나까지.
- 직접 작업을 Runloom 결과 판정·완료 판정으로 처리하기, [검증만 돌리기](REDESIGN_PLAN 10절 — 뒤로).
- 매핑 표 편집 화면(연결 화면의 새 탭 — 17-jira 에서 소스와 함께).
- `tasks` 재생성, `tasks.status` CHECK 변경, 종류 이름 분기.

## 대안

- **상세를 전체 페이지로(지금 `/work/{key}`).** 구현이 가장 단순하지만 목록으로 돌아갈 때 필터·스크롤·묶음 접기 같은 맥락을 잃고, 여러 업무를 차례로 훑는 일(담당 없음 묶음 정리)이 느리다. 기각.
- **보드 끌어 옮기기.** 업무 상태는 단계·사람 요청·PR 에서 계산하는 값이라 칸을 옮기는 것이 하나의 행동과 1:1 로 대응하지 않는다(`PR · 검토` → `완료` 로 끌면 병합하는가?). 끌기가 할 수 있는 일을 패널 버튼이 이미 한다. 기각.
- **에이전트 담당 = 배정만(맡기기는 따로 누름).** 한 번 더 눌러야 하고 "담당 에이전트인데 아무것도 안 움직이는" 상태가 생긴다 — 에이전트 담당은 곧 일을 시킨다는 뜻으로 읽힌다. 기각.
- **옛 화면 유지 + 연결 화면 추가.** 같은 폼이 두 곳에 있어 화면이 두 벌이 되고 사이드바를 줄일 수 없다. 옛 GET 은 303 으로 넘기고 POST 주소만 남긴다. 기각.
- **브랜치 push 감지.** 폴링마다 저장소 브랜치 목록을 읽어야 하고(요청 수), push 한 사람이 누군지 알 수 없어 "직접 작업 중 · 이름" 을 채울 수 없다. PR 은 작성자가 있고 목록 한 번으로 상태까지 온다. 기각.
- **Claude Code 훅 포함.** 사용자 전역 설정(`~/.claude/settings.json`)을 고치는 일이라 설치·제거·기존 훅 보존을 따로 검증해야 한다. 버튼 + PR 신호로 먼저 쓰고 다음 phase 에서 붙인다. 기각(미룸).
- **업무 PR 표를 Runloom PR 과 합치기(공용 표).** `task_pull_requests` 는 대기열·재시도·검토 실행을 가진 단계 단위 표라 칸이 다르다. 감지 PR 만 새 표에 두고 화면·상태 계산에서 둘을 함께 읽는다. 기각.

## 결과

- 처음 화면은 업무 한 줄 목록이고, 할 일(내 차례)과 담당 없는 업무가 묶음으로 보인다. 담당 지정 = 맡기기라 GitHub 이슈·직접 등록·체인 업무 모두 같은 자리에서 시작한다.
- 옛 주소는 넘어가므로 북마크·문서 링크가 깨지지 않는다. GitHub 에 등록된 App URL 은 바뀌지 않는다.
- 사람이 자기 세션에서 처리한 업무도 PR 로 `PR · 검토` → `완료` 가 되어 모니터링의 "직접 처리 대 에이전트 처리" 비교(19-monitor)의 재료가 생긴다.
- GitHub 요청이 소스마다 tick 당 최대 2회(PR 목록 페이지) 늘어난다. App 권한은 지금과 같다(Pull requests RW 가 이미 있다).
- 알림·원본 댓글 링크가 업무 주소가 된다. 이미 보낸 댓글·알림의 옛 단계 주소도 계속 열린다.
- **업그레이드**: 스키마 v12. 러너 프로토콜(계약 v1)은 바뀌지 않는다 — 러너 재기동은 필요 없다(step 10 이 SELFHOST 에 적는다).
