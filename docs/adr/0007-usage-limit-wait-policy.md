# ADR-0007: 사용량 한도 도달 시 리셋까지 대기 후 새 Execution 으로 재시도

결정일: 2026-09-20. 사용자 확정. **적용 시점: 심사 기간(2026-09-21 ~ 10-05) 이후, `phases/3-limit-wait` 실행 시.** 그 전까지는 ARCHITECTURE "상태·재접속·완료" 절의 현재 문장("사용량 한도는 실패로 기록하고 다른 엔진으로 자동 대체하지 않는다")이 그대로 유효하며, 다른 phase 는 이 ADR 을 근거로 코드를 바꾸지 않는다.

**결정**: 로컬 에이전트가 사용량 한도(구독 창 5시간·7일)에 걸려 실행이 실패하면, Agent 의 `on_usage_limit` 정책이 `wait`(기본) 일 때 Task 를 마감하지 않고 `대기`(사용량 한도, 리셋 시각, 재시도 n/N)로 둔다. 리셋 시각이 지나면 **새 Execution**(`attempt_no + 1`, 같은 요청·같은 인계 자료·같은 `base_commit`) 을 만든다. 정책이 `fail` 이면 지금처럼 `실패` 로 마감한다. `fallback`(다른 Agent 로 이어서) 은 값만 예약하고 이번에는 구현하지 않는다.

**이유**: 등록 대상 에이전트의 대부분은 API 종량제가 아니라 개인 구독형이며, 한도는 고장이 아니라 예정된 시각에 회복되는 상태다. 이를 `실패` 로 마감하면 운영자가 리셋 뒤 손으로 다시 시작해야 하고, 자동 실행(A 완료 → B 착수)의 이점이 사라진다. Codex 는 매 turn 의 `rate_limits.primary.resets_at`(5시간 창)·`secondary.resets_at`(7일 창)을 알려주므로 "5시간 기다리기" 가 아니라 "리셋 시각까지 기다리기" 로 설계할 수 있다(2026-09-20 `~/.codex/sessions/` rollout 기록에서 확인. `codex exec --json` stdout 에 같은 값이 있는지는 미확인).

**규칙 — 바뀌지 않는 것**:
- 같은 Execution 을 되살리지 않는다. 재시도는 항상 새 Execution 이며 `process_stopped=true` 로 이전 프로세스 종료를 확인한 실패에서만 만든다.
- 재시도 start_key 는 실패한 Execution ID 에서 파생(`retry:{execution_id}`)한다. `UNIQUE(task_id, start_key)` 로 실패 1건당 재시도는 정확히 1건이다.
- 재시도는 `base_commit` 부터 다시 시작한다. worktree 의 미커밋 변경(한도 도중 남은 부분 수정)은 버린다. 이전 시도의 diff 를 다음 시도에 넘기지 않는다.
- 무제한 재시도 금지. 재시도 최대 6회, 리셋 시각을 모르면 1시간 뒤, 리셋까지 6시간을 넘기면(7일 창 도달) 기다리지 않고 `실패` 로 마감하되 리셋 시각을 이유에 적는다. 값은 서버 설정(`Limits`)이다.
- 다른 엔진·다른 Agent 로 자동 대체하지 않는다(ADR-0001·ADR-0004 유지).
- 진단(A, API 에이전트)은 범위 밖이다. 그쪽 한도는 이 제품의 예산 429 이며 "모델 호출 예산" 절을 따른다.

**트레이드오프**: 대기 중 Task 는 최대 6시간 `대기` 에 머문다. 리셋 시각을 stdout 에서 못 읽으면 1시간 간격 재시도로 실패 Execution 기록이 최대 6건 쌓인다. 정책이 Agent 단위라 "이 업무만 급하니 기다리지 말라" 는 표현이 없다 — Task 단위 정책은 필요가 확인되면 추가한다. 연결 프로그램이 Codex 의 rollout 파일에서 리셋 시각을 읽는 경로는 Codex 내부 형식에 의존하므로 보조 수단으로만 쓰고, 없으면 `None` 으로 둔다.
