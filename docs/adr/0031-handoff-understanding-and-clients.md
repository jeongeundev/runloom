# ADR-0031: 제품 역할 — 이해한 상태로 이어받는 인계 계층, API 우선, 웹 기본 · IDE 앱 선택

결정일: 2026-10-21. 사용자 정리(2026-10-19~21 대화): "단순하게 앞 순서 에이전트가 일이 끝났으니 다음 순서 작업자의 에이전트가 자동 실행되게 하는 거라기보다는, 이 작업의 이해·판단을 하기 위한 결정에 필요한 이해도 줄여보자", "모두가 깔아 쓰지 않아도 되게 — 편하게 쓰고 싶으면 앱, 아니면 웹", "앱은 단순히 보는 게 아니라 IDE 형태". 계기는 Claude Code 작업이 끝날 때마다 HTML 리포트를 만들어 IDE 형태 macOS 앱(Swift·SwiftUI·libghostty·WKWebView)의 웹뷰에 띄우는 개인 작업 방식이다. 이 문서는 방향과 순서를 고정하며 구현은 없다.

## 배경

- [ADR-0011](0011-task-driven-work-cycle.md) 이후 제품의 병목 정의는 "A 가 끝나도 사람이 확인해 에이전트에 전달·실행할 때까지 B·C 가 밀린다"였고, 해법은 실행 시작까지의 자동화였다. [ADR-0023](0023-cross-member-delegation.md) 이 이를 사람 사이 인계로 넓혔다.
- 작업이 크고 중요할수록 받는 사람은 앞 작업을 이해해야 판단할 수 있다. 문서화를 요청하면 읽을 양이 늘어 이해 자체가 새 병목이 된다. 자동 착수만으로는 이 대기를 줄이지 못한다.
- 지금의 인계 자료는 에이전트용이다 — `handoff_bundle`(`handoff.json`, 선행 결과·규칙 `handoff_kinds` 산출물·근거 원문)과 결과 봉투의 요약·검증 근거. 사람이 읽고 판단하기 위한 형태는 없다.
- [Multica](https://github.com/multica-ai/multica)(2026-10-19 확인)는 중앙 서버 + 로컬 daemon + 웹·Electron 데스크톱·모바일·CLI 로, 이슈를 에이전트에게 배정·실행·리뷰 상태로 옮기는 범위가 Runloom 과 거의 겹친다. 의도·실행 로그·결정·diff 를 이슈에 묶지만 받는 사람의 이해를 돕는 형태와 파일·코드 화면은 없다.
- 사람용 기능은 대부분 `server/web.py` 의 HTML 폼으로만 있다(2026-10-21 기준 템플릿·리다이렉트 응답 103곳). JSON API 는 러너(`machine_api.py`)·n8n 입구(`inbound_api.py`)·사람 응답(`human_api.py`) 등에 한정된다.

## 결정

1. **제품 역할.** Runloom 은 팀 안에서 일이 사람에서 사람으로(각자의 에이전트를 거쳐) 넘어가는 지점을 맡는다. 다음 사람과 그 에이전트가 앞 작업을 **이해한 상태로**, 기다리지 않고 바로 이어받게 한다. 하는 일은 셋이다.
   - **넘기기** — 가져오기·배정·조건 충족 시 담당자 에이전트 착수(지금 구현).
   - **이해시키기** — 인계 리포트(결정 2).
   - **판단 받기** — 사람이 결정할 지점을 리포트 앞에 세우고, 결정을 기록한 뒤 이어서 진행한다. 지금의 사람 요청·대기·재평가를 그대로 쓴다.
   Runloom 은 에이전트·이슈 트래커·워크플로우 빌더·IDE 자체가 아니다. 웹·앱·CLI 는 이 역할을 쓰는 화면이다. Runloom·n8n 역할 구분(Runloom = 독립 서비스, n8n = API 로 붙는 쪽)은 그대로다.
2. **인계 리포트.** 단계가 끝나 다른 사람(또는 나중의 나)에게 넘어갈 때 같은 내용을 두 형태로 낸다.
   - 사람용: 무엇이 왜 바뀌었는지(다이어그램 포함), 결정한 것과 근거, **정하지 않고 남긴 것**, 받는 사람이 결정·확인할 것. HTML 한 장.
   - 에이전트용: 바뀐 파일·결정과 근거·남은 일·지킬 제약. 기존 `handoff_bundle` 을 확장하며 새 묶음을 따로 만들지 않는다.
   - 리포트의 주장마다 근거(diff·테스트 결과·커밋·산출물)를 붙인다. 모델이 쓴 리포트를 근거 없이 사실로 표시하지 않는다(AGENTS.md 완료 판정 규칙과 같은 원칙).
   - 혼자 쓸 때도 같다 — 어제의 나에게서 오늘의 나에게 넘기는 인계로 본다.
3. **API 우선.** 사람용 기능(업무 목록·상태, 배정·시작, 인계 리포트 조회, 결정 응답)을 JSON API 로 연다. 웹 폼과 API 는 같은 도메인 로직을 쓴다 — 화면마다 규칙을 따로 두지 않는다. 웹·앱·CLI·n8n·에이전트는 모두 이 API 의 클라이언트다.
4. **웹이 기본, 앱은 선택.** 아무것도 깔지 않아도 웹에서 보드·배정·진행 상태·리포트·결정까지 모두 할 수 있어야 한다. 팀원 중 누구도 앱 설치를 강제받지 않는다.
5. **앱은 IDE 형태다.** 단순 뷰어가 아니라 화면을 나눠 파일 트리·문서/코드 보기·diff·터미널(사용자의 로그인 셸과 설정 그대로 — herdr·tmux 등이 그 안에서 돈다)·웹뷰(보드·리포트·브라우저)를 띄운다. 앱 안에 러너가 들어가 그 컴퓨터가 실행 환경이 된다. 웹과의 차이는 **로컬 파일과 터미널**이다 — 리포트 항목에서 해당 파일·diff 로 바로 간다. 웹을 감싸기만 한 앱은 만들지 않는다(웹보다 나은 점이 없어 유지 이유가 사라진다 — n8n 데스크톱 앱은 2023년 지원 중단, 저장소 2025-08 보관).
6. **순서.** ① 사람용 기능의 JSON API → ② 인계 리포트(생성·보관·API 조회·웹 표시) → ③ API 를 감싼 CLI(에이전트가 "내 다음 업무와 인계 내용"을 직접 가져감) → ④ IDE 앱. 앱을 마지막에 두는 이유: ①~③ 이 있어야 앱이 붙을 곳이 생기고, ①~③ 만으로 웹·에이전트·n8n 쪽 가치가 먼저 생긴다. 각 단계는 별도 phase 로 설계한다.

## 미결

- **앱 기술.** 제안은 Swift + SwiftUI + libghostty + WKWebView(macOS 전용) — 러너가 이미 Mac 기준이고 다른 OS 팀원은 웹으로 참여한다. 대안은 Electron/Tauri + xterm.js(크로스 플랫폼, 터미널 품질·무게 손해). ④ 착수 전에 정한다.
- **리포트를 누가 만드는가.** 보내는 쪽 러너(실제 diff·테스트 결과를 가짐)가 단계 끝에 만드는 안과, 받는 쪽 에이전트가 받는 사람에 맞춰 만드는 안. ② 설계에서 정한다.
  → [ADR-0033](0033-handoff-report.md) 에서 정함.
- **리포트 형식과 보관.** HTML 의 생성 방식(템플릿 + 데이터 / 모델 생성), 다이어그램 표현, 산출물 kind 이름, 결정 기록의 위치.
  → [ADR-0033](0033-handoff-report.md) 에서 정함.
- **API 인증.** 웹은 세션 쿠키. 앱·CLI 는 멤버별 토큰이 필요하며 비밀값 규칙(AGENTS.md)을 따른다. ① 설계에서 정한다.
  → [ADR-0032](0032-human-api-and-member-tokens.md) 에서 정함.

## 결과

- 제품 개요·PRD·로드맵의 제품 정의에 "이해 비용"과 위 구성을 더한다. 기존 순환·수용 기준은 바꾸지 않는다.
- 다음 phase 는 ① 사람용 JSON API 다. 설계 전 범위(어느 화면 기능부터 여는지)를 정한다.
- ③ API 를 감싼 CLI 는 [ADR-0034](0034-cli.md) 에서 정함.
- 차별성은 "배정·실행"이 아니라 "이해·판단을 거친 인계"에 둔다. 배정·실행 자체는 Multica·Jira·Devin 도 한다.
