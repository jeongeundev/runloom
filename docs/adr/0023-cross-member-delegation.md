# ADR-0023: 사람 사이 인계 — 다른 멤버의 에이전트에게 맡기기·소유자 승인·꺼진 러너 대기·검증만 다시

결정일: 2026-09-30 (phase 17 step 0). 근거: [재설계 계획](../product/REDESIGN_PLAN.md) 5.3절(팀·담당자)·13절, [ADR-0021](0021-team-accounts-and-roles.md)(팀·러너 소유자·내 차례), [ADR-0022](0022-work-screen-and-direct-work.md)(업무 화면·담당 = 맡기기), [ADR-0018](0018-real-repo-cycle.md)(러너 로컬 등록 `--env`·검증 프로필), [ADR-0014](0014-github-task-cycle.md)(준비 판정·후속 결정). 기본값은 [phase 17 README](../../phases/17-team-handoff/README.md) "계획 기본값" 10가지(사용자 결정 2026-09-30)이며 이 문서로 구현 기준을 고정한다. 적용 범위는 `service` 브랜치. 이 시점에는 구현이 없다 — 이름·표·경로·시그니처의 기준은 [ARCHITECTURE](../ARCHITECTURE.md) "사람 사이 인계 — phase 17" 이다(README 와 다르면 ARCHITECTURE).

계기: Runloom 의 핵심 가치는 내 에이전트 사이가 아니라 **사람 사이의 병목**을 줄이는 것이다(사용자 정리, 2026-09-30). 다른 멤버의 에이전트(그 멤버 Mac 의 러너)로 작업이 바로 가야 하고, 결과는 받아야 할 사람에게만 "내 차례"로 가야 한다. phase 15 가 러너 소유자를 만들었지만 에이전트 소유자를 비교하는 코드가 없고, 소유자가 자기 Mac·구독 사용을 통제할 방법(승인·거절)이 없다. 꺼진 러너에게 맡긴 일은 순환 종류만 기다리고 소유자는 모른다. 받는 쪽 에이전트는 업무 제목·양식 칸·맡긴 사람의 지시를 받지 못한다.

## 코드 조사로 README 와 달라진 사실 (2026-09-30, `feat-17-team-handoff` d17dad2)

1. `human_requests.code`·`human_responses.action` 에는 CHECK 가 없다 — 사람 요청 코드 `owner_approval`·동작 `approve`·`decline`·`reverify` 는 표를 바꾸지 않고 들어간다. 반면 `notifications.event` 에는 CHECK 가 있어(`NOTIFICATION_EVENTS` 3개) 새 알림 사건 3개를 넣으려면 `notifications` 를 재생성해야 한다. 이 표를 참조하는 표는 없다(`grep "REFERENCES notifications"` 0건). `work_item_events` 도 CHECK 가 있어 지시 메모 이벤트 종류를 더하려면 v12 처럼 재생성한다(참조 0건).
2. 준비 판정의 `input_missing`(`request_required and not request_text.strip()`)은 `task_cycle.request_text` 를 본다. 요청문 머리에 `# RUN-n 제목` 을 붙이면 이 검사가 늘 통과해 버린다. 그래서 **판정용 문구(`request_text`)는 그대로 두고**, 실행 요청에 싣는 문구만 새 함수(`execution_request_text`)로 만든다.
3. 순환이 아닌 종류는 첫 단계를 사람이 누를 때만 시작한다 — 워커가 다시 시도하는 경로는 선행 결과가 있는 후속(`_spawn_successors`)뿐이다. "꺼진 러너가 켜지면 시작"을 비순환 종류에도 하려면 "사람이 맡겼는데 아직 실행이 없음"을 저장할 곳이 필요하다 → `tasks.start_pending_at`(ALTER ADD COLUMN — 재생성 아님). 순환 종류도 같은 칸으로 "사람이 맡겼으니 `manual_mode` 를 빼고 착수"를 표시한다(지금은 `start_manually` 호출 순간에만 뺀다 — 러너가 꺼져 있다 켜지면 `manual_mode` 소스의 업무는 다시 멈춘다).
4. 웹 경로는 알림을 쌓지 못한다 — `Worker._notify` 는 워커 메서드이고 웹이 만드는 `Worker`(`run_cycle_task`)에는 비밀 저장소가 없어 아무것도 쌓지 않는다. 맡긴 순간의 알림(`delegated_to_you`)·거절 알림(`delegation_declined`)을 위해 알림 행 만들기를 모듈 함수로 꺼낸다.
5. 검증만 다시에 필요한 산출물(diff·수정 전/후 테스트 로그·검증 로그)은 모두 에이전트 없이 러너가 결과 커밋에서 다시 만들 수 있다. 에이전트 산출물(도구 stdout·stderr)과 사용량만 빈다. 러너는 이전 결과 봉투(`code_change_result`)를 입력으로 받아 outcome·요약을 잇는다.
6. 실행이 `running` 이 되어도 `tasks.status` 가 `실행 요청됨 · 접수 대기` 로 남는 원인: `machine_api.post_event` → `repo.append_event` 는 `executions` 만 바꾸고, 워커 `_start_ready_tasks` 는 활성 실행이 있으면 `_resume` 만 보고 넘어간다. 두 곳에서 단계 상태를 다시 계산한다.

## 결정

1. **맡기기 정책은 에이전트마다.** `agents.delegation_policy` = `run`(바로 실행, 기본) | `owner_approval`(소유자 승인 뒤 실행). 에이전트 소유자 = 그 러너의 소유자(`agents.connector_id` → `connectors.owner_member_id`, ADR-0021 결정 10). 소유자가 없으면(v11 이전 러너·API 에이전트) "공용" — 활성 관리자 전원이 소유자 역할을 한다. 정책은 소유자 본인(`attach_runner`)과 관리자(`remove_any_runner`)가 바꾼다 — 러너 해제와 같은 권한 규칙.
   - 맡긴 사람 ≠ 소유자이면 소유자에게 정보 알림 `delegated_to_you`("김OO 가 opensql 에게 맡김")가 간다. 승인 요청이 생기는 맡기기는 승인 요청 알림(`human_request`)이 이 정보를 싣고 가므로 `delegated_to_you` 를 따로 보내지 않는다 — 같은 사람에게 한 번의 맡기기로 두 번 가지 않게.
   - `owner_approval` 이고 맡긴 사람 ≠ 소유자이면, 승인 전에는 그 단계에 실행을 만들지 않는다. 패널 맡기기·옛 `/tasks/{id}/delegate|select|run`·워커 자동 착수·[다시 맡기기]로 생긴 단계·후속 단계 모두 같다. 맡긴 사람이 없는 착수(트리거 라벨·자동 후속)도 "소유자가 아님"으로 본다.
   - 승인을 기다리는 동안 업무는 `내 차례`, 이유 "김OO 가 맡김 · 이OO 승인 대기". 받는 사람은 소유자(공용이면 활성 관리자 전원). 사람 요청 코드 `owner_approval`, 동작 `approve`[승인]·`decline`[거절](메모 선택). 승인·거절은 소유자와 관리자만 한다(`respond` + 소유자 비교).
   - 승인하면 곧 착수한다(러너가 꺼져 있으면 결정 2 의 대기). 같은 단계·같은 에이전트·같은 맡긴 사람의 승인은 그 단계 안에서 유지된다(검토 요청으로 인한 재작업은 다시 묻지 않는다). 새 단계(후속 검토·[다시 맡기기])는 새로 묻는다.
   - 거절하면 그 단계의 선택을 지우고(선택 기록 `needs_selection` · "이OO 가 거절 — 메모") 업무 담당을 비운다(`담당 없음` 묶음). 맡긴 사람에게 알림 `delegation_declined`. 업무를 닫지 않는다. 같은 에이전트에게 사람이 다시 맡기면 새 승인 요청이 생기고, 워커가 자동으로 다시 묻지는 않는다.
   - 담당을 다른 것(멤버·없음·다른 에이전트)으로 바꾸거나 정책을 `run` 으로 바꾸거나 업무가 끝나면 열린 승인 요청을 닫는다(동작 `withdraw`, 시스템 응답).
   - 자기 에이전트에게 맡기면(맡긴 사람 = 소유자, 공용이면 맡긴 사람이 활성 관리자) 정책과 관계없이 바로 실행한다.
2. **꺼진 러너에게 맡기기 — 허용하고 알린다.** 담당 후보 한 줄: `이름 · <소유자 표시 이름>의 Mac · 켜짐|꺼짐`(소유자 없으면 `공용`). 꺼진 에이전트에게 맡기면 담당·선택은 저장하고 실행은 만들지 않는다. 단계 이유 "이OO의 러너 꺼짐 · 켜지면 시작"(공용이면 "공용 러너 꺼짐 · 켜지면 시작"), 업무 상태 `대기`. 소유자에게 알림 `runner_offline_waiting` 한 번(업무 × 에이전트 중복 키). 러너가 다시 붙으면 워커가 착수한다 — **순환이 아닌 종류도 같다**. 판정은 종류 이름이 아니라 에이전트 연결 상태(`agent_online` 과 같은 기준)로 한다.
3. **[검증만 다시]** — 결과 커밋이 있는 수정 검증 실패 요청(`fix_verification_failed`)에 동작 `reverify` 를 더한다. 에이전트를 돌리지 않는다. 같은 러너(이전 실행의 Agent — 같은 로컬 등록)가 같은 결과 커밋을 깨끗한 체크아웃에서 등록된 검증 프로필로 다시 검증하고, 결과는 평소 판정(`_code_result_checks`)·후속 결정을 거친다. 계약: `ExecutionRequest.verify_only_commit`(선택), `ClaimRequest.capabilities`(선택, 러너가 `"verify_only"` 를 보고). 보고하지 않는 옛 러너에는 배정하지 않고 "연결 프로그램 업데이트 필요 — 검증만 다시 미지원"으로 기다린다. null 은 직렬화에서 뺀다. 기존 `resume` 버튼 이름은 [답하고 다시 맡기기](동작 그대로 — 에이전트를 이전 결과 위에서 다시 돌린다).
4. **인계 맥락.** 패널 담당 폼에 선택 칸 "지시 메모"(최대 2000자). 서버가 실행 요청의 `request` 문자열 앞에 `# <RUN-n> <업무 제목>`·"## 업무 양식"(양식 칸 제목·값, 빈 칸 제외)·"## 맡긴 사람 지시 (이름)"을 붙인다. 계약 칸은 바꾸지 않는다. 메모는 업무 칸(지금 유효한 메모)과 업무 이벤트 `handoff_note`(타임라인)로 남는다. 순환·비순환 모두 같은 함수를 지난다. 준비 판정의 입력 검사는 머리 없는 원문을 그대로 본다(조사 사실 2).
5. **저장소별 보기.** 묶기에 `repo`, 도구 막대에 저장소 필터 `repo=<owner/name>`(열거형 — 워크스페이스 GitHub 소스의 저장소만, 모르는 값은 무시). 저장소가 없는 업무는 "저장소 없음" 묶음(마지막). 기본 묶기는 담당자 그대로. 저장소는 조회 때 원본에서 계산하고 칸을 새로 두지 않는다.
6. **목록 키 칸 = `RUN-n` 먼저.** 원본 키는 옆에 흐리게 짧게(`owner/name#3` → `name#3`).
7. **상대 `PYTHONPATH` 풀기.** 러너가 도구·검증 프로세스를 띄울 때 등록된 `--env PYTHONPATH` 의 상대 항목을 그 프로세스의 cwd(worktree 또는 임시 체크아웃) 기준 절대 경로로 바꾼다. 다른 변수는 그대로다. 등록 화면·SELFHOST 에 안내한다.
8. **단계 상태 결함 수정.** 실행 이벤트를 받으면(`machine_api.post_event`) 그 단계의 `tasks.status` 를 다시 계산하고, 워커도 활성 실행이 있는 순환 단계를 그냥 넘기지 않고 다시 계산한다. 재현 테스트를 먼저 쓴다.
9. **한 Mac 에 러너 두 대.** `install-runner.sh --name <이름>`(영소문자·숫자·하이픈)이면 launchd label·plist·로그·러너 홈을 이름으로 나눈다. `--name` 이 없으면 지금과 같다(업그레이드 호환).
10. **스키마 v13.** ALTER: `agents.delegation_policy`(기본 `run`), `connectors.capabilities_json`, `executions.verify_only`(기본 0), `tasks.start_pending_at`, `work_items.handoff_note`·`handoff_note_by_member_id`. 재생성: `notifications`(사건 CHECK 확장), `work_item_events`(종류 CHECK 에 `handoff_note`). `human_requests` 는 그대로(코드 CHECK 없음). `tasks` 는 재생성하지 않는다. 실패하면 v12 그대로.

11. **같은 저장소를 등록한 러너가 여럿일 때의 매칭(step 11 e2e 에서 추가).** 자동 매칭(ADR-0017, `all_open` 소스)은 수정 Agent 후보가 둘이면 "수정 Agent 2개 — 설정에서 하나 고르세요" 로 막고 사람이 맡긴 Agent(`tasks.chosen_agent_id`)를 보지 않았다 — 두 멤버가 각자 러너로 같은 저장소를 등록하면 다른 멤버의 에이전트에게 맡길 수 없었다. 이제 ① `all_open` 소스에서 사람이 그 단계에 맡긴 Agent 가 있으면 수정 Agent 는 그것이고 검증 프로필도 그 등록에서 정한다(`filtered` 는 담당자 규칙 그대로 — ADR-0014). ② 검토 Agent 설정이 비어 있으면 검토 단계의 수정 Agent 가 검토 능력을 가지면 그것을 고른다 — 검토는 수정 결과 커밋이 있는 러너에서만 돈다(`review_repository_mismatch`). 설정값은 그대로 우선한다. 판정은 순수 함수 `github_match.match_source(..., chosen_agent_id, pair_agent_id)` 가 한다.

**ADR-0021 결정 5(받는 사람 규칙)에 우선 규칙이 붙는다**: 업무에 열린 `owner_approval` 요청이 있으면 받는 사람은 그 에이전트의 소유자다(소유자가 없거나 비활성이면 활성 관리자 전원). 그 밖은 ADR-0021 그대로(담당 멤버 → 맡긴 사람 → 활성 관리자 전원).

## 하지 않는 것

- Jira(18-jira), 판단 제안·자동 시작(19-triage), 모니터링 확장(20-monitor).
- 다른 Mac 에서 하는 실연동(이번 실연동은 같은 Mac 의 두 번째 멤버 계정 + `--name b` 러너, phase 뒤 사용자).
- 에이전트 사용량 한도·요금 통제, 러너 전용 venv 설치, Claude Code 훅 상태 보고, 보드 끌기, 여러 행 일괄 변경.
- 새 역할(역할은 관리자·멤버 두 개 그대로, 동작 표에 새 동작 없음), 승인 위임(대리 승인자), 승인 만료 시간.
- 검증만 다시에서 검증 명령을 바꾸거나 고르게 하기 — 러너에 등록된 프로필만 쓴다.
- `tasks` 재생성, `tasks.status` CHECK 변경, 종류 이름 분기.

## 대안

- **누구 것이든 바로 실행.** 가장 빠르지만 소유자가 자기 Mac·구독 사용을 통제할 수 없다 — 다른 사람이 내 에이전트를 무제한 돌린다. 기각.
- **항상 소유자 승인.** 통제는 확실하지만 없애려던 사람 사이 병목이 다시 생긴다(맡길 때마다 소유자를 기다린다). 에이전트마다 고르게 하고 기본은 바로 실행. 기각.
- **꺼진 에이전트 선택 막기.** 실수는 줄지만 맡긴 사람이 러너가 켜질 때를 기억했다가 다시 맡겨야 한다 — 사람 사이 병목이 맡긴 사람 쪽으로 옮겨 간다. 허용하고 켜지면 시작, 소유자에게 알림. 기각.
- **버튼 이름만 바꾸기([답하고 다시 판정] → [다시 맡기기]).** 환경 원인(상대 `PYTHONPATH` 등) 검증 실패마다 에이전트를 다시 돌려 사용량이 들고, 같은 문제를 푼 diff 가 매번 바뀐다. 결과는 그대로 두고 검증만 다시 하는 동작이 따로 필요하다. 기각.
- **계약 칸으로 제목·지시 전달(`ExecutionRequest.title`·`note`).** 러너 프롬프트 조립·계약 fixture·옛 러너 호환이 함께 바뀌어 변경이 커진다. 요청문(`request`)에 절로 붙이면 러너는 바뀌지 않는다. 기각.
- **`work_items` 에 저장소 칸.** 원본(`github_sources.repository_full_name`)에서 계산할 수 있고, 칸을 두면 소스 저장소가 바뀔 때 두 곳을 맞춰야 한다. 기각.
- **러너 전용 venv 설치.** 편집 설치가 검증 하위 프로세스에 섞이는 문제를 뿌리부터 막지만 `install-runner.sh`·업그레이드·launchd 경로가 모두 바뀐다. 이번 원인(상대 `PYTHONPATH` 가 cwd 에 따라 호스트 설치를 잡음)은 상대 경로 풀기로 막는다. 기각(미룸).
- **승인 대기를 업무 상태 새 값(`승인 대기`)으로.** 보드 칸·필터·`WORK_STATUSES` CHECK(`work_items` 재생성)가 모두 바뀐다. 사람이 할 일이므로 `내 차례` + 이유로 충분하다. 기각.
- **승인 정보를 새 표(`delegation_approvals`)에.** 사람 요청 표가 이미 질문·응답·응답자·낙관적 잠금·알림을 가진다. 코드 CHECK 도 없어 표 변경 없이 들어간다. 기각.

## 결과

- 다른 멤버의 에이전트에게 맡기면 그 멤버에게 알림이 가고, 정책이 `owner_approval` 이면 그 멤버의 `내 차례` 가 된다. 결과·검토·PR 뒤의 `내 차례` 는 지금처럼 맡긴 사람에게 간다.
- 꺼진 러너에게 맡긴 일은 모든 종류에서 켜지면 시작한다. 순환 종류의 대기 문구가 "연결 끊김, 마지막 확인 …" 에서 "이OO의 러너 꺼짐 · 켜지면 시작" 으로 바뀐다.
- 검증만 다시는 에이전트 사용량 없이 판정을 다시 받는다. 실행 횟수에는 들고(`executions.verify_only = 1`) 사용량은 NULL 이다.
- **업그레이드**: 스키마 v13(백업 먼저). 러너 프로토콜에 선택 칸이 생긴다 — 서버를 먼저 올리고 **러너도 재설치**한다(새 러너는 `capabilities` 를 늘 보내므로 옛 서버와는 422). 옛 러너는 검증만 다시를 받지 않을 뿐 나머지는 그대로 동작한다.
- phase 8·11·12·14·15·16 의 GitHub 순환(수집 → 맡기기 → 수정 → 검토 → 초안 PR → 병합 추적 → 업무 완료), 사람별 내 차례, 직접 작업·PR 신호는 정책이 `run`(기본)이면 흐름이 그대로다.
