# ADR-0024: Jira 소스 — 토큰 연결·폴링 가져오기·상태 옮기기(세 순간)·후속 이슈 등록

결정일: 2026-10-01 (phase 18 step 0). 근거: [재설계 계획](../product/REDESIGN_PLAN.md) 7·13·14·16절, [Jira 연동 조사](../research/2026-09-29-jira-integration.md)(1차 출처), [ADR-0020](0020-work-items-and-stages.md)(업무·단계·매핑 표·"Jira 는 전용 표를 나란히"), [ADR-0017](0017-github-app-connection.md)(비밀 저장소), [ADR-0014](0014-github-task-cycle.md)(준비 판정·outbox), [ADR-0018](0018-real-repo-cycle.md)(초안 PR), [ADR-0022](0022-work-screen-and-direct-work.md)(업무 상태·직접 작업·PR 신호), [ADR-0023](0023-cross-member-delegation.md)(맡기기·매칭). 기본값은 [phase 18 README](../../phases/18-jira/README.md) "사용자 결정" 6가지(2026-09-30)와 "계획 기본값" 14가지이며 이 문서로 구현 기준을 고정한다. 적용 범위는 `service` 브랜치. 이 시점에는 구현이 없다 — 이름·표·경로·시그니처의 기준은 [ARCHITECTURE](../ARCHITECTURE.md) "Jira 소스 — phase 18" 이다(README 와 다르면 ARCHITECTURE).

계기: 팀은 업무를 Jira 로 관리한다(REDESIGN_PLAN 14절). Jira 업무가 Runloom 업무 목록에 들어와 에이전트(다른 멤버의 에이전트 포함 — phase 17)에게 맡겨지고, 팀원이 Jira 만 봐도 상태가 따라와야 한다. 지금 제품은 원본 종류가 `github`·`n8n`·`manual` 뿐이고, 원본 조회·매칭·지시 대기·초안 PR·목록 저장소 칸이 GitHub 이슈 행(`source_issues`)을 전제한다.

## 코드 조사로 README 와 달라진 사실 (2026-10-01, `feat-18-jira` 7de3284)

README "조사로 확인한 현재" 는 맞았다. 아래는 더 들어가 확인한 사실이다.

1. **`work_items` 재생성은 FK 가 켜진 트랜잭션 안에서 안 된다.** v13 DB 사본으로 실험했다: `BEGIN IMMEDIATE` 안에서 새 표 → `INSERT … SELECT` → `DROP TABLE work_items` → `RENAME` 은 `PRAGMA defer_foreign_keys=ON` 을 켜도 COMMIT 에서 `FOREIGN KEY constraint failed` 로 실패한다(DROP 의 암묵 DELETE 가 자식 행 — `work_item_events`·`work_item_links`·`tasks.work_item_id`·`work_pull_requests` — 만큼 지연 위반을 세고, 이름 바꾼 새 표의 행은 그 수를 줄이지 않는다). SQLite 공식 12단계 절차대로 **트랜잭션 밖에서 `PRAGMA foreign_keys=OFF`** 를 건 뒤 재생성하고 `PRAGMA foreign_key_check` 로 확인하면 행·칸·자식 FK 가 모두 보존된다(자식 표의 `REFERENCES work_items` 는 글자 그대로라 새 표를 가리킨다 — 재생성 뒤 없는 업무 id 로 이벤트를 넣으면 FK 오류, 확인함). `init_schema` 는 지금 FK 가 켜진 연결로 `BEGIN IMMEDIATE` 하므로 v14 에서 바꾼다. 빈 DB 는 `_SCHEMA` executescript 안에서 빈 표를 재생성하므로 FK 가 켜져 있어도 된다(확인함).
2. **`task_pull_requests.issue_number` 는 `INTEGER NOT NULL`** 이다. Jira 업무의 초안 PR 에는 GitHub 이슈 번호가 없다 → 이 표도 재생성해 NULL 을 허용한다(이 표를 참조하는 표는 없다 — `grep "REFERENCES task_pull_requests"` 0건).
3. **초안 PR 전송도 GitHub 이슈 행을 읽는다.** `worker._deliver_pull_requests` 는 PR 제목을 `get_source_issue_by_task` 의 스냅숏 제목으로 만들고, `_apply_pull_request_state` 는 병합 때 그 이슈 행으로 `record_issue_merge`(기준선)를 쓴다. 이슈 행이 없으면 둘 다 예외다 — 대기열만 고치면 안 된다.
4. **수정/검토 매칭의 갈림은 "이 단계에 원본 행이 붙어 있는가" 다.** `_match_facts(fix=intake.assignee_ids is not None)` 에서 `assignee_ids` 는 `source_issues.task_id == 이 단계` 일 때만 None 이 아니다(검토 단계는 None). 그래서 Jira 스냅숏 행도 업무가 아니라 **첫 단계(`task_id`)에 붙인다**(`source_issues` 와 같은 모양). 업무는 `tasks.work_item_id` 로 따라간다.
5. **`all_open` 의 매칭 규칙이 Jira 에 맞다.** `match_source` 는 `intake == "all_open"` 일 때만 사람이 맡긴 Agent(`chosen_agent_id`)를 수정 Agent 로 쓰고, 담당자 연결이 없으면 `code.fix {repository_id}` 후보가 하나일 때 그것을 쓴다. `filtered` 는 GitHub 담당자 규칙이라 Jira 에서는 늘 "담당 대기"로 막힌다.
6. **준비 판정의 `not_delegated` 사유 문구**는 "실행 지시 전 — [에이전트에게 맡기기] 또는 `runloom` 라벨" 이다. Jira 에는 라벨 지시가 없지만 문구를 바꾸면 GitHub 테스트 단정이 바뀐다 — 그대로 둔다(업무 목록 이유는 `work_status` 의 "지시 전 — [에이전트에게 맡기기]" 라 목록에는 라벨 말이 없다). 알려진 한계로 남긴다.
7. **GitHub 소스에는 삭제 경로가 없다**(`DELETE FROM github_sources` 0건, 멈춤만). 그래서 Jira 프로젝트 설정이 연결 저장소를 FK 로 가리켜도 된다. 연결 저장소를 멈추면(`enabled=false`) 그 프로젝트 업무의 초안 PR 은 GitHub 업무와 같이 `github_not_connected` 로 사람 요청이 된다.

## 결정

1. **인증 = API 토큰 붙여 넣기, 호출 기준 주소는 "확인 뒤 저장".** 입력은 사이트 주소·이메일·토큰. 사이트 주소는 `https://<이름>.atlassian.net` 형식만(소문자로 바꾸고 끝 `/` 하나만 지운 뒤 정규식 `^https://[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?\.atlassian\.net$` — 다른 호스트·경로·포트·사용자 정보·쿼리 거부, SSRF 방지). 확인 순서: ① `GET {site}/_edge/tenant_info` → `cloudId`(UUID 형식만 받는다) ② `GET https://api.atlassian.com/ex/jira/{cloudId}/rest/api/3/myself`(Basic) ③ ②가 401 이면 `GET {site}/rest/api/3/myself` ④ 성공한 쪽을 `api_base = 'gateway' | 'site'` 로 저장. 이후 모든 호출은 저장한 기준 주소로만 만든다(두 호스트는 코드 상수 + 검증된 사이트 이름·cloudId 만). 둘 다 401 → "이메일·토큰이 맞지 않습니다", 403 → "권한(스코프)이 부족합니다". 근거: scoped 토큰은 `api.atlassian.com/ex/jira/{cloudId}` 로만 된다고 문서에 있고(조사 2.1), unscoped 토큰이 그 주소로도 되는지는 문서로 확인하지 못했다 — 둘을 다 받으려면 실제로 된 쪽을 기록하는 것이 가장 단순하다. OAuth 3LO·웹훅·Data Center 는 하지 않는다(사용자가 앱을 직접 만들어야 하고 공개 HTTPS 가 필요 — 조사 1.1·2.6).
2. **토큰은 비밀 저장소에만.** `adapters/secret_store.py` 에 새 고정 이름 `JIRA_API_TOKEN = "jira_api_token"`(0600 파일, `NAMES` allowlist). DB(`jira_connections`)에는 사이트 주소·cloudId·기준 주소 종류·이메일·accountId·표시 이름만. 응답·로그·템플릿·백업·Codex 프로세스 환경에 토큰을 넣지 않는다. 이것은 ADR-0017 이 GitHub App 비밀에 쓴 방식과 같고, AGENTS.md 비밀값 규칙("환경변수 또는 비밀 저장소에서만")에 맞는다 — 조사 문서 열린 질문 2 는 이것으로 닫는다. 이메일은 비밀이 아니다(연결 화면에 보인다).
3. **연결은 워크스페이스에 하나, 프로젝트는 여럿.** 프로젝트 설정 한 행 = 프로젝트 id·키·이름, 연결 저장소(`github_sources.source_id`, 필수 — 사용자 결정 3), 가져올 이슈 유형(이름 목록, 비우면 전부), 시작점(`from_now` 지금부터 | `all_open` 열린 업무 전부 — 프로젝트를 추가할 때만 고르고 뒤에 바꾸지 않는다), 세 순간의 Jira 상태 이름(각각 비우면 그 순간은 옮기지 않음), 후속 이슈 유형(비우면 후속을 Jira 에 만들지 않음), 켜짐. 후보(이슈 유형·상태 이름)는 `GET /rest/api/3/project/{key}/statuses` 한 번으로 받아 행에 저장하고(`choices_json`), [목록 새로 고침] 으로 다시 받는다 — 화면을 그릴 때 Jira 를 부르지 않는다. 끊기 = 토큰 파일 삭제 + `disconnected_at`. 업무·프로젝트 행은 남는다. 다시 연결할 때 프로젝트 행이 있으면 같은 cloudId 만 받는다(다르면 409 `jira_site_mismatch`).
4. **가져오기 = 폴링.** `GET /rest/api/3/search/jql`(옛 `/search` 금지), `fields=summary,description,status,issuetype,priority,labels,created,updated,project`, `nextPageToken` 페이지, `maxResults=100`. JQL 은 프로젝트 **id** 와 숫자만 넣는다(사용자 문자열을 JQL 에 넣지 않는다): 커서 없음(`all_open` 첫 바퀴) `project = <id> AND statusCategory != Done ORDER BY updated ASC, key ASC`, 커서 있음 `project = <id> AND updated >= <cursor_ms> ORDER BY updated ASC, key ASC`(따옴표 없는 epoch ms, 포함 경계 — 다시 받은 이슈는 digest 로 흡수). 이슈 유형 거르기는 JQL 이 아니라 받은 뒤 코드에서 한다. `from_now` 의 첫 커서 = 프로젝트를 추가한 시각. 페이지를 다 저장한 뒤에만 커서를 전진한다(GitHub 과 같다). 간격 60초(`GITHUB_SYNC_INTERVAL_SECONDS` 와 같은 값), 429 는 `Retry-After`(최소 60초)만큼 그 프로젝트를 쉰다. 401 은 연결에 `auth_failed_at` 을 쓰고 다시 연결할 때까지 모든 Jira 호출(가져오기·전송)을 멈춘다.
5. **업무로.** 새 이슈는 (이슈 유형이 고른 것이거나 전부) 이고 상태 범주가 `done` 이 아니고 (`all_open` 이거나 `created >= start_at`) 일 때만 받는다. 이미 받은 이슈의 변경은 범위와 무관하게 반영한다. 업무 칸: `source_type='jira'`, `source_id` = 프로젝트 설정 id(`jps-…`), `source_item_id` = issue id(문자열, 이동해도 안 바뀜), `source_key` = `SHOP-12`(이동하면 갱신), `source_url` = `{site}/browse/SHOP-12`, `source_state` = Jira 상태 이름. 본문(ADF)은 텍스트로 바꿔(문단·제목 `#`·목록·코드·링크·줄바꿈만, 모르는 노드는 안의 글만) 요청·양식 칸 읽기(`form_sections`)에 넘긴다. 종류·우선순위는 매핑 표(`field_mappings`, `source_type='jira'`) — 입력값 = 라벨 + 이슈 유형 이름 + 우선순위 이름. 기본 행 `('jira', 'kind', '*', 'bug_fix')`(새 워크스페이스·v14 마이그레이션 모두). 종류가 매핑되지 않으면 받지 않는다(GitHub 과 같다). 첫 단계 = 매핑 종류의 등록 봉투, 요구 능력 범위 = 연결 저장소의 `workflow_repository_id` 또는 저장소 이름(매칭이 채운다 — `snapshot_to_task_spec` 과 같은 규칙), `run_mode` = 연결 저장소 설정. 제목·본문이 바뀌면 GitHub `upsert_source_issue` 와 같이 첫 단계 revision + 1 과 업무 제목·요청 갱신. 한 Jira 이슈는 업무 하나 — `work_items(source_id, source_item_id) WHERE source_type = 'jira'` 부분 UNIQUE 인덱스로 DB 가 막는다.
6. **원본 열림/닫힘 = 상태 범주.** `status.statusCategory.key == 'done'` 이면 `closed`, 그 밖(`new`·`indeterminate`)은 `open`. 기존 두 값 판정(`task_readiness` 의 `source_closed`, `task_followup` 의 `hold_code="source_closed"`)에 그대로 넣는다 — 새 대기 코드 없음. 다시 열리면 이어간다. 이미 도는 실행은 끊지 않고 Runloom 업무를 닫지 않는다(사용자 결정 5). **Jira 상태는 완료 판정 근거가 아니다** — 업무 완료는 지금처럼 PR 병합 신호(계약 v1).
7. **원본 조회 일반화 — `source_type` 분기는 `task_cycle.origin` 한 곳.** `origin_source(conn, task) -> (source_issues 행, 설정)` 을 `origin(conn, task) -> Origin` 으로 바꾼다. `Origin` = `issue`(GitHub `source_issues` 행 — GitHub 원본만, `views._origin`·원본 댓글 표시가 쓴다), `config`(실행 설정), `state`(`open`|`closed`|None), `own`(원본 행이 이 단계에 붙어 있음 = 수정 단계), `origin_key`(요청문 머리의 원본 키 — Jira 만). Jira 업무의 `config` = **연결 저장소의 `GitHubSourceConfig` 를 `intake="all_open"`·`trigger_label=None` 으로 본 사본**(`domain/jira_intake.run_config`) — 실행 설정(검증 프로필·검토 Agent·기본 수정 Agent·`run_mode`·재작업 상한·로컬 저장소 id)은 연결 저장소의 것이고, 지시는 [맡기기]로만 받는다(결정 9). 부르는 곳 7곳(`max_rework_rounds`·`source_match`·`task_facts`·`execution_request_text`·`worker._followup_context`·`_create_followup_task`·`_queue_pull_request`, 화면 `cycle_context`·단계 묶음)은 모두 `origin` 을 쓴다. 화면의 GitHub 원본 카드(`_origin`)는 `origin.issue` 가 있을 때만 — Jira 업무는 패널의 원본 키 링크와 Jira 반영 상태(결정 11)로 보인다. 준비 판정의 담당·지시 사실도 같은 곳에서 고른다: `task_cycle.task_intake(conn, task)` = 이 단계에 붙은 Jira 행이 있으면 `jira_sync.task_intake_facts`, 아니면 `github_sync.task_intake_facts`.
8. **에이전트 매칭 — Jira 업무의 첫 단계는 수정 단계.** Jira 첫 단계의 `IntakeFacts` 는 `assignee_ids=()`(빈 튜플 — None 이 아니다: 원본이 붙은 수정 단계), `bindings={}`, `source_state` = 결정 6, `delegated` = 지시 기록 유무, `run_mode` = 운영자 지시면 `auto`(GitHub `intake_facts` 와 같은 규칙). 그래서 `_match_facts(fix=True)` 가 되고 `config.intake == "all_open"` 이라 `auto_match=True`, 수정 Agent = 맡긴 Agent(`chosen_agent_id`) → 기본 수정 Agent → `code.fix {repository_id}` 후보 하나. 요구 능력 범위 `repository_id` 는 지금처럼 `config.workflow_repository_id` 가 없으면 매칭 결과(`match.workflow_repository_id` — 러너가 보고한 GitHub 저장소가 연결 저장소와 같은 로컬 등록)로 채운다. 같은 업무의 검토 단계는 Jira 행이 없어 `fix=False`(검토 매칭, `pair_agent_id`) — GitHub 과 같다. `github_match`·`task_readiness` 는 바꾸지 않는다.
9. **맡기기 전엔 실행하지 않는다.** Jira 업무는 들어오면 `새로 들어옴`(담당 없음), [에이전트에게 맡기기](또는 [내 세션에서 작업]) 뒤에만 착수한다. 지시 기록은 Jira 스냅숏 행의 `delegated_at`·`delegated_by`(`operator` | `followup`) — `source_issues` 와 같은 모양. `hand_work_to_agent` 는 그 단계에 Jira 행이 있으면 같은 트랜잭션에서 `operator` 로 기록한다. `work_item_facts.delegated` 는 지금의 GitHub 조건 **또는** "업무의 단계에 붙은 Jira 행 중 `delegated_by IS NULL` 이 있음" 이면 거짓. `intake_facts` 의 `needs_delegation` 은 Jira 에서 늘 참이다(소스 설정이 아니라 원본 종류의 규칙 — `all_open` 과 같다). 라벨 지시(`trigger_label`)는 Jira 에 두지 않는다. Runloom 이 만든 후속 이슈를 받은 업무는 `followup`(이미 워커가 만든 단계 — 다시 지시를 기다리지 않는다).
10. **초안 PR·PR 감지·업무 완료.** Jira 업무의 실행 대상 저장소 = 프로젝트의 연결 저장소(사용자 결정 3). 브랜치 `runloom/<RUN-n>`·PR 제목 `<RUN-n> <업무 제목>` 그대로 — Jira 키를 브랜치·PR 제목에 넣지 않는다(개발 패널 연동은 범위 밖). 대기열(`_queue_pull_request`)은 `origin.own and origin.config is not None` 일 때 연결 저장소(`config.source_id`·`config.repository_full_name`)로 행을 만들고, `issue_number` 는 GitHub 원본이면 이슈 번호, 아니면 NULL(`task_pull_requests` 재생성 — 사실 2, `enqueue_pull_request(..., issue_number: int | None)`). 전송(`_deliver_pull_requests`)은 PR 제목을 업무 제목(`work_items.title`)으로 만들고(GitHub 업무는 지금처럼 이슈 제목 — 둘은 같다, 업무 제목이 이슈 제목에서 온다), 본문 첫 줄은 `issue_number` 가 있을 때만 `Fixes #N`, 없고 업무에 원본 키가 있으면 `원본: SHOP-12 — https://x.atlassian.net/browse/SHOP-12`(`pull_request.origin_line`). `_apply_pull_request_state` 의 기준선 기록(`record_issue_merge`)은 GitHub 이슈 행이 있을 때만(사실 3). PR 감지(`RUN-n` 키)·병합 → `완료` 는 지금 GitHub 소스 PR 동기화가 그대로 한다 — 연결 저장소가 `github_sources` 이고 감지는 워크스페이스 업무 키로 찾는다.
11. **상태 옮기기 = 세 순간 = 업무 상태 전이.** `repo.set_work_status` 가 새 상태를 쓸 때(값이 바뀌어 `status_changed` 이벤트를 남길 때) `to` 가 다음이면 그 순간이다:

    | 순간 | 들어가는 업무 상태(`to`) | 뜻 |
    |---|---|---|
    | `start` | `에이전트 작업 중` 또는 `직접 작업 중` | 에이전트 실행 착수 또는 [내 세션에서 작업]·키 든 브랜치 push |
    | `review` | `PR · 검토` | Runloom PR(`PR 여는 중`·`PR 확인`) 또는 감지 PR 열림 |
    | `done` | `완료` | PR 병합(또는 단계가 모두 완료로 마감) |

    `종료`(PR 이 병합 없이 닫힘·실패 마감)·`내 차례`·`대기`·`새로 들어옴` 은 옮기지 않는다. **한 업무 × 한 순간 = 한 번**(중복 키 `transition:<work_item_id>:<moment>`) — PR 이 닫혔다 다시 열려도, 재작업으로 `에이전트 작업 중` 에 다시 들어가도 다시 보내지 않는다(Jira 상태가 앞뒤로 흔들리지 않게. Jira 는 사람이 옮긴 상태가 기준이다). 훅 위치를 `set_work_status` 로 정한 이유: 업무 상태 쓰기가 이 한 곳뿐이라(`refresh_work_status`·`_refresh_stage_work`·`refresh_open_work_statuses` 모두 거친다) 같은 트랜잭션에 행을 넣으면 놓치는 전이가 없고 커서가 필요 없다. 넣는 함수는 `INSERT … SELECT` 하나(`repo.queue_jira_transition`)로, 업무가 Jira 프로젝트 설정 행에 JOIN 되고 그 순간의 상태 이름이 설정돼 있고 프로젝트가 켜져 있고 원본 이슈 id 가 있을 때만 행이 생긴다 — `set_work_status` 에 원본 종류 분기 문이 생기지 않는다. 순간 판정은 순수 함수(`domain/jira_intake.moment_for`). 연결이 끊겨 있어도 행은 쌓이고 다시 연결하면 나간다. 목표 상태 이름은 행에 적어 둔다(뒤에 설정을 바꿔도 이미 생긴 행은 그대로).
12. **전송·실패 분류.** 전송은 트랜잭션 밖(GitHub 댓글 outbox 와 같은 claim fence — `attempts + 1`, claim 만료 120초, 백오프 30·2^(n-1)초 최대 1시간). 상태는 `pending`·`sending`·`delivered`·`unknown`·`failed`·`skipped` — 기존 `SourceDelivery.state` 다섯에 `skipped` 를 더한다. 전환 전송: ① 같은 업무에 더 늦게 생긴 전환 행이 있으면 앞 행은 `skipped`(옛 순간을 뒤늦게 보내 상태를 되돌리지 않는다) ② `GET /issue/{id}?fields=status` — 이미 목표 이름(대소문자 무시)이면 보내지 않고 `delivered`, 상태 범주가 `done` 인데 순간이 `done` 이 아니면 `skipped`("Jira 에서 이미 완료 범주") ③ `GET /issue/{id}/transitions` 에서 `to.name` 이 목표와 같은(대소문자 무시) 첫 전환 ④ `POST /issue/{id}/transitions`. 이슈는 id 로 부른다(키는 이동하면 바뀐다). 전환은 ②의 확인 때문에 다시 보내도 중복이 없어 `unknown` 을 쓰지 않는다(응답을 잃으면 `pending` 으로 돌아가 ②부터).

    | 결과 | 상태 | 화면 문구(마지막 오류) |
    |---|---|---|
    | 2xx·이미 목표 상태 | `delivered` | `반영됨` |
    | 목표로 가는 전환 없음 | `failed`(재시도 없음) | `전환 없음 — 현재 상태 <이름>` |
    | 400(전환 화면 필수 칸 등) | `failed` | `전환에 입력할 칸이 있음 — Jira 에서 옮기세요` |
    | 403 | `failed` | `권한 없음 — 이 이슈를 옮길 수 없음` |
    | 404 | `failed` | `이슈를 찾을 수 없음` |
    | 401 | `pending`(시도 수 되돌림 없음) + 연결 `auth_failed_at` | `Jira 토큰 확인 필요 — 다시 연결` |
    | 429 | `pending`(`Retry-After`, 최소 60초) 후 그 바퀴 중단 | `Jira 요청 한도 — 잠시 뒤` |
    | 5xx·연결 오류·timeout | `pending`(백오프) | `Jira 응답 없음 — 다시 시도` |

    화면: 업무 패널에 "Jira 반영" 줄 — `상태 → 진행 중 · 반영 대기|반영됨|반영 불확실|반영 실패 — <문구>`(`skipped` 는 보이지 않는다). 업무 상태와 따로다(GitHub 댓글 반영 표시와 같은 방식).
13. **후속 이슈 등록.** 후속 규칙이 새 업무(`placement == "new_work"`)를 만들 때(`repo.create_followup_once`) 원인 업무가 Jira 원본(원본 이슈 id 있음)이고 그 프로젝트에 후속 이슈 유형이 설정돼 있고 켜져 있으면, 같은 트랜잭션에서 `create_issue` 행 하나(중복 키 `create_issue:<새 work_item_id>`, `INSERT … SELECT` — 결정 11 과 같은 방식). 전송: `POST /rest/api/3/issue` — 같은 프로젝트(id), 이슈 유형 = 설정 이름을 `choices_json` 의 id 로 바꾼 것(없으면 `failed` "이슈 유형 <이름> 없음 — 목록 새로 고침"), `summary` = 새 업무 제목(255자에서 자름), `description` = 짧은 Markdown → ADF(아래), `labels` = `runloom`, `runloom-<RUN-n>`. 성공하면 한 트랜잭션에서 새 업무의 `source_item_id`·`source_key`·`source_url` 을 채우고 행 `delivered`(`result_issue_id`·`result_issue_key`). 그 뒤 링크: `GET /rest/api/3/issueLinkType` 에서 이름이 `Relates`(대소문자 무시)인 유형 → `POST /rest/api/3/issueLink`(inward = 원인 이슈, outward = 새 이슈). 유형이 없거나 링크가 실패해도 이슈는 이미 있으므로 다시 만들지 않고 `note` 에만 남긴다("링크 유형 Relates 없음 — 링크 생략"). POST 응답을 잃으면(연결 오류·timeout·5xx) `unknown` → 다음 바퀴에 JQL `project = <id> AND labels = "runloom-RUN-<n>"`(값은 고정 형식이라 따옴표 안전)으로 찾아 있으면 `delivered`(여럿이면 id 가 가장 작은 것 + `note`), 없으면 `pending`. 400 → `failed`(`필수 칸 — <Jira 첫 오류 문구 200자>`), 401·403·404·429 는 결정 12 표와 같다. 본문:

    ```
    Runloom 후속 업무 RUN-13 — SHOP-12 의 결과로 생겼습니다.

    <새 업무 요청, 앞 2000자>

    Runloom 업무: <공개 주소>/work/RUN-13      (공개 주소가 없으면 이 줄 없음)
    ```

    **중복 업무 금지**: 다음 동기화가 이 이슈를 받으면 `(source_id, source_item_id)` 로 그 업무를 찾아 스냅숏 행을 붙인다(`delegated_by='followup'`, `task_id` = 그 업무의 첫 단계). 붙인 업무는 Jira 제목·본문 변경을 업무 입력으로 받지 않는다(Runloom 이 쓴 본문이 업무 요청과 다르다 — 받으면 첫 바퀴에 revision 이 오른다). 생성 POST 는 닿았는데 기록 전에 죽은 경우에도 새 업무가 생기지 않게: 라벨 `runloom-RUN-<n>` 이 붙은 처음 보는 이슈는 새 업무를 만들지 않는다 — 같은 워크스페이스의 RUN-n 업무가 같은 프로젝트의 원본 이슈 id 없는 Jira 업무이면 그 업무에 붙이고(원본 칸 채움 + 그 업무의 `create_issue` 행 `delivered`), 아니면 건너뛴다.
14. **Markdown → ADF 는 후속 이슈 본문에만**(문단·`- ` 목록·``` 코드 블록·`[글](http(s)://…)` 링크와 맨 URL). 새 의존성 없음. ADF → 텍스트는 가져오기에만(결정 5).
15. **요청문 머리에 원본 키.** `compose_request(..., origin_key: str | None = None)` — 값이 있으면 `# RUN-12 쿠폰 오류` 바로 아래 줄에 `원본: SHOP-12`. `origin_key` 는 `Origin.origin_key`(Jira 만 값, GitHub 은 None) — **GitHub 업무 요청문은 바이트 단위로 그대로**(17 테스트 유지).
16. **목록 저장소 칸.** `list_work_rows.repository` = GitHub 원본은 그 소스 저장소, Jira 원본은 프로젝트 연결 저장소(`jira_projects.github_source_id` → `github_sources.repository_full_name`), 그 밖은 None. JOIN 만 바꾸고 칸을 두지 않는다. 키 칸은 `RUN-n` 먼저, 원본 키 `SHOP-12` 는 옆에 흐리게 그대로(`short_source_key` 는 `owner/name#n` 만 줄인다). 출처 표시 `SOURCE['jira'] = "Jira"`.
17. **스키마 v14 = Jira 전용 표 4개를 나란히**(ADR-0020): 연결(`jira_connections`, 워크스페이스당 1행), 프로젝트 설정(`jira_projects`), 이슈 스냅숏(`jira_issues`, 첫 단계에 붙음), outbox(`jira_deliveries`, 전환·후속 생성). `work_items.source_type`·`field_mappings.source_type` CHECK 에 `'jira'`, `task_pull_requests.issue_number` NULL 허용 — 세 표는 재생성한다. `work_items` 는 자식 FK 때문에 트랜잭션 밖 `PRAGMA foreign_keys=OFF` 로(사실 1), `tasks` 는 재생성하지 않는다(ADR-0020). 세부는 ARCHITECTURE.
18. **연결 화면.** `/connect?tab=sources` 의 GitHub 칸 옆 Jira 칸(`manage_connections`): 붙여 넣기 → 확인 → 프로젝트 찾기·추가(연결 저장소·시작점) → 프로젝트별 설정(이슈 유형·세 상태 이름·후속 이슈 유형·켜짐) → 저장, 끊기. 경로는 `/operator/jira/…`(GitHub 의 `/operator/github/…` 와 같은 자리). 외부 문자열(Jira 제목·상태 이름·프로젝트 이름·표시 이름)은 자동 이스케이프로만 출력(`|safe` 금지).

## 하지 않는 것

진행 댓글, PR 원격 링크·개발 패널·브랜치·PR 제목의 Jira 키, OAuth 3LO, 웹훅, Jira Data Center, Jira 담당자 ↔ 멤버 매핑, Jira 기준선(19·20), 매핑 표 편집 화면(API 만 — `mapping_api` 가 `jira` 를 받는다), 컴포넌트별 저장소, 삭제·권한 상실 감지(bulkfetch), 판단 제안(19-triage), 모니터링 확장(20-monitor), 실제 Jira·GitHub 호출(모든 step 은 httpx `MockTransport`·가짜 클라이언트로 검증, 실연동은 phase 뒤 사용자가 Jira Cloud 사이트·토큰을 만든 뒤 1회).

## 결과

- 좋은 점: Jira 업무가 GitHub 업무와 같은 순환(맡기기 → 수정 → 검토 → 초안 PR → 병합 → 완료)을 탄다. 원본 종류 분기는 원본 조회 한 곳(`task_cycle.origin`·`task_intake`)과 소스 경계 모듈(`jira_sync`·`jira_delivery`)에만 있고, 종류 이름 분기는 늘지 않는다. 되쓰기 두 가지는 업무 상태 쓰기·후속 생성과 같은 트랜잭션에 기록돼 놓치지 않는다.
- 비용: v14 마이그레이션은 FK 를 끄고 `work_items` 를 재생성한다(`foreign_key_check` 로 확인, 실패하면 13 그대로). 한 순간은 한 번만 옮기므로 Jira 에서 사람이 상태를 되돌린 뒤 같은 순간이 다시 와도 따라가지 않는다. 이슈 유형 거르기·라벨 조정은 받은 뒤 코드에서 하므로 큰 프로젝트의 `all_open` 첫 바퀴는 페이지가 많다.
- 실연동 때 확인할 것: unscoped·scoped 토큰 각각의 기준 주소, `project/{key}/statuses` 응답 모양, 한국어 상태 이름 전환, 후속 이슈 필수 칸(회사 Jira 는 화면 필수 칸이 있을 수 있다 — 400 이면 `failed`), `Relates` 유형 이름.
