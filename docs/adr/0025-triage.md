# ADR-0025: 판단 — 담당 없는 업무에 종류·담당·순서 제안, 판단 로그, 자동 시작

결정일: 2026-10-01 (phase 19 step 0). 근거: [재설계 계획](../product/REDESIGN_PLAN.md) 3·5.4·6·11·13·15·16절, [ADR-0009](0009-registered-kinds-and-succession-rules.md)(종류·후속 규칙은 등록 데이터), [ADR-0015](0015-measurement-events-and-baseline.md)(설정 번호), [ADR-0018](0018-real-repo-cycle.md)(기준 커밋 보고), [ADR-0020](0020-work-items-and-stages.md)(업무·단계), [ADR-0022](0022-work-screen-and-direct-work.md)(업무 상태·직접 작업), [ADR-0023](0023-cross-member-delegation.md)(맡기기 정책·소유자 승인·꺼진 러너 대기), [ADR-0024](0024-jira-source.md)(Jira 업무 → 연결 저장소). 기본값은 [phase 19 README](../../phases/19-triage/README.md) "사용자 결정" 3가지(2026-10-01)와 "계획 기본값" 14가지이며 이 문서로 구현 기준을 고정한다. 적용 범위는 `service` 브랜치. 이 시점에는 구현이 없다 — 이름·표·경로·시그니처의 기준은 [ARCHITECTURE](../ARCHITECTURE.md) "판단 — phase 19" 이다(README 와 다르면 ARCHITECTURE).

계기: 업무가 들어오면(GitHub·Jira) 지금은 사람이 하나씩 열어 "누가 맡을지·어떤 작업인지·먼저 할 것이 있는지"를 정한다. 판단 단계는 이 일을 러너의 로컬 에이전트에게 **제안**하게 하고, 기록이 쌓여 믿을 만해지면 업무 종류별로 **자동 시작**을 켤 수 있게 한다. 업무 내용은 외부 판정 서비스로 보내지 않는다(REDESIGN_PLAN 6절 2).

## 코드 조사로 README 와 달라진 사실 (2026-10-01, `feat-19-triage` c122b94 = `service` c5f1d31 + 설계)

README "조사로 확인한 현재" 는 맞았다. 아래는 더 들어가 확인한 사실이고, 결정 몇 개를 바꾼 근거다.

1. **중앙은 기본 브랜치 커밋을 안다.** 러너는 claim 마다 등록별 `origin/HEAD` 커밋을 `registration_heads` 로 보내고 `repo.update_registration_heads` 가 그 값을 `agents.base_commit` 에 쓴다(ADR-0018 결정 2). 그래서 판단 요청에 체크아웃할 커밋을 **중앙이 고정해 넣는다** — 러너가 따로 fetch·계산하지 않는다(결정 6). 값이 아직 없으면(보고 전) 판단을 시작하지 않는다.
2. **수정·검토 Agent 칸은 표 칸이 아니라 소스 설정 JSON 이다.** `default_fix_agent_id`·`review_agent_id` 는 `GitHubSourceConfig`(`github_sources.config_json`)의 칸이고 저장 경로는 `PUT /github/sources/{id}`(`github_api`, `MANAGE_CONNECTIONS`, 낙관적 잠금 `expected_revision`, 저장 때 `config_revision` +1)다. README 기본값 14 의 `github_sources.triage_agent_id` 표 칸 대신 **같은 JSON 의 `triage_agent_id`** 로 둔다(결정 3). 형제 칸과 같은 검증(`_agent_problem`)·같은 저장·같은 설정 번호를 그대로 쓰고 스키마를 바꾸지 않는다. FK 는 형제 칸에도 없다 — 쓸 때 등록 여부·능력·정책을 다시 본다.
3. **판단 단계가 그대로 들어가면 깨지는 곳이 여섯 군데 있다.** ① `work_actions.open_stage` 는 "마감 전 단계 중 최신" 이라 판단 단계(나중에 만들어짐)를 고른다 ② `repo.work_item_facts` 의 `assigned` 는 어느 단계든 `chosen_agent_id` 가 있으면 참이라 판단 단계의 판단 Agent 를 담당으로 센다 ③ `work_status` 는 실행 중 단계가 있으면 `에이전트 작업 중` 이다 ④ `repo.create_execution` 끝의 `_fill_work_assignee` 가 담당 없는 업무에 실행 Agent 를 담당으로 채운다 ⑤ `worker._reflect_failures` 는 실패한 실행마다 `stage_failed` 사람 요청(`내 차례`)과 `task_failed` 알림을 만든다 ⑥ `repo.list_metric_facts` 는 모든 단계·실행을 지표에 넣는다. 그 밖에 `work_actions._running`(업무에 실행 중 단계가 있으면 담당 바꾸기 409)·패널 `running` 도 판단 실행을 센다. 모두 결정 2 의 한 함수로 판단 단계를 빼고 본다.
4. **실행 실패는 결과 판정과 다른 길이다.** 결과(`result_ready`)는 `_check_*_results` 가 판정하고, 실패(`failed`·`unknown`)는 `_reflect_failures` 가 마감한다. 판단은 둘 다 새 `_judge_triage` 가 먼저 처리하고 `_reflect_failures` 는 판단 단계를 건너뛴다(결정 9).
5. **`work_item_links(blocks)` 는 착수를 막지 않는다.** 링크를 읽는 곳은 패널(`views.work_panel_context` "연결 업무")뿐이고, 준비 판정은 `predecessor_task_id`(체인·폼 선행)만 본다(`insert_work_item_task` 주석 "준비 판정은 아직 `predecessor_task_id` 를 본다"). 그래서 판단이 정한 선행 업무는 **링크만** 남긴다 — 선행이 끝날 때까지 막는 규칙은 범위 밖(README "하지 않는 것").
6. **직접 등록 업무도 저장소 값이 있다 — 하지만 판단 Agent 칸과 이어지지 않는다.** `/tasks` 직접 등록은 첫 단계 요구 능력에 `scope_value`(예: `repository_id`)를 받는다. 그러나 판단 Agent 는 저장소 카드(GitHub 소스 설정)에 있고, 직접 등록·n8n 업무는 원본 칸이 없어 `task_cycle.origin` 이 설정을 돌려주지 않는다. scope 값으로 소스를 거꾸로 찾는 규칙을 새로 만들지 않는다 — **직접 등록·n8n 업무는 판단하지 않는다**(자동도 버튼도 없음, 결정 4).
7. **판단 결과의 제안 종류 칸 이름.** 모든 결과 봉투에서 `kind` 는 "이 실행의 종류" 다(`GenericResult.kind` — 판정 `ids_match` 가 요청 kind 와 대조한다). README 기본값 3 의 `kind` 를 그대로 쓰면 뜻이 둘이 된다 → 제안 종류는 **`proposed_kind`** 로 둔다(결정 7).
8. **`_tx` 는 겹칠 수 없다**(`BEGIN IMMEDIATE` 를 그대로 연다). 판단 단계·선택 기록·실행·판단 로그를 한 트랜잭션에 쓰려면 `create_execution` 의 안쪽을 트랜잭션 없는 함수로 나눠 함께 쓴다(결정 8).
9. **대기열에서 끝나지 않는 실행을 정리하는 장치가 없다.** `_observe` 는 `accepted` 뒤 시작 없음(`unknown`)과 heartbeat 상실 관찰만 한다. `queued` 로 남거나 `running` 인 채 러너가 사라진 판단은 판단 로그 `running` 으로 남아 워크스페이스의 "한 번에 1건" 자리를 막는다 → 판단 실행에만 기한을 둔다(결정 9).
10. **알림 사건은 표 CHECK 다.** `notifications.event` 에 새 사건을 넣으려면 표를 재생성해야 한다(v13 선례). README 기본값 1 의 "다른 멤버의 Agent 를 판단 Agent 로 고르면 소유자에게 알림 1회" 는 이번에 하지 않는다(결정 3) — 판단 Agent 는 맡기기 정책이 `run`(소유자가 다른 사람의 실행을 이미 허락함)인 Agent 만 고를 수 있고, 저장소 카드와 에이전트 상세에 보인다.

## 결정

1. **판단 = 내장 종류 `triage`, 그 업무의 한 단계(Task).** 봉투: `kind="triage"`, `label="판단"`, `capability_code="code.triage"`, `scope_key="repository_id"`, `input_kinds=[]`, `output_kind="triage_result"`, `outcomes=["ready", "needs_check", "unsuitable"]`(= 진행 여부 세 값), `instructions=""`, `builtin=True`. 사용자 정의 종류는 결과가 `{outcome, summary}` 고정이고 인계 폴더에서 돌아 저장소를 못 읽는다 — 그래서 내장이다(사용자 결정 2). 판단 단계는 **업무 상태·맡기기 대상·후속 규칙의 대상이 아니다**: 판단이 도는 동안 업무는 `새로 들어옴`(이유 `판단 중`), 판단은 후속 규칙을 만들지 않고(규칙 등록에서 `triage_result` 종류를 from·to 로 거부), 업무를 완료·종료하거나 `내 차례` 를 만들지 않는다. 판단 단계는 업무 패널 진행 타임라인에는 `판단` 단계로 보인다(기록).
2. **판단 단계는 결과 형태로 가른다 — 한 함수.** `domain/execution_policy.py` 에 `TRIAGE_OUTPUT_KIND = "triage_result"` 와 `is_triage_kind(spec: KindSpec) -> bool`(= `spec.output_kind == TRIAGE_OUTPUT_KIND`). 종류 이름 `triage` 로 분기하지 않는다(ADR-0009). DB 행만 있는 곳은 같은 상수로 `json_extract(k.spec_json, '$.output_kind')` 를 비교하는 SQL 조각 하나(`repo._TRIAGE_STAGE`)와 `repo.is_triage_task(conn, task_id) -> bool` 을 쓴다. 쓰는 곳(사실 3): `open_stage`(판단 단계를 빼고 최신 — 그래서 판단 단계가 기존 첫 단계 **뒤에** 만들어져도 맡길 단계가 되지 않는다), `agent_candidates`(`open_stage` 를 쓰므로 자동), `work_item_facts`(단계 사실·`assigned` 에서 빼고 판단 사실을 따로), `create_execution`(`_fill_work_assignee` 건너뜀), `_reflect_failures`(건너뜀), `list_metric_facts`(빼고 — 판단 지표는 20-monitor), `work_actions._running`·패널 `running`(빼고 — 판단 중에도 사람이 맡길 수 있다), 종류 선택 목록(직접 등록 폼·매핑 값·후속 규칙·판단 후보 종류에서 빼고). 업무의 대표 종류(`work_items.kind`)는 첫 단계 종류 그대로다 — 판단 단계는 업무를 만들지 않고 기존 업무에 단계로 붙으므로 `kind` 를 바꾸지 않는다. 실행 정책 표는 `BUILTIN_POLICIES["triage"] = ExecutionPolicy("triage", "triage", "triage_result", (), "triage", cycle=False)`(target `triage`·판정기 `triage` 추가).
3. **판단 Agent = 저장소 카드의 `triage_agent_id`(소스 설정 JSON).** `GitHubSourceConfig.triage_agent_id: NonEmptyStr | None = None`(사실 2). 저장 = `PUT /github/sources/{id}`(`MANAGE_CONNECTIONS`). 검사: 이 워크스페이스 Agent·`code.triage {repository_id}` 능력(저장소 id 를 알 때 — 형제 칸과 같은 `_agent_problem`)·**맡기기 정책 `run`**(아니면 422 `triage_agent_policy` "판단 에이전트는 맡기기 정책이 '바로 실행'인 에이전트만 고를 수 있습니다" — 자동 판단마다 승인 요청이 쌓이지 않게). 자동 매칭하지 않는다 — 비워 두면 그 저장소는 판단하지 않는다(버튼도 없음). Jira 업무는 프로젝트의 연결 저장소 칸을 쓴다(`task_cycle.origin(...).config` 가 연결 저장소 설정의 사본 — `triage_agent_id` 가 그대로 따라온다). 소유자 알림은 하지 않는다(사실 10). 정책이 나중에 `owner_approval` 로 바뀌면 판단을 시작하지 않고 이유를 보인다(결정 5).
4. **판단 대상 업무.** 업무 상태 `새로 들어옴` · 담당 없음 · 직접 작업 없음 · 끝나지 않음 · 원본 종류 `github`|`jira` · 판단 단계가 아닌 열린 단계 있음 · `task_cycle.origin(열린 단계)` 의 `config` 가 있고 `state != "closed"`(Runloom 이 만든 후속 새 업무는 원본 이슈가 없어 `state` None — 대상) · 그 설정에 판단 Agent 있음. 직접 등록·n8n 업무는 판단하지 않는다(사실 6).
5. **판단을 시작할 수 있는 판단 Agent**(자동·버튼 공통, 하나라도 아니면 이유 문구로 거절): 워크스페이스 Agent · 로컬 · 러너에 붙음(`connector_id`) · `code.triage {repository_id}` 능력(요구 능력을 `select_agent(mode="manual", chosen_agent_id=판단 Agent)` 로 검사 — 기존 선택 함수 재사용, 결과 기록을 판단 단계의 선택 기록으로 저장) · 맡기기 정책 `run` · 러너 켜짐(`views.agent_online`) · 러너 마지막 claim 의 `supported_kinds` 에 `triage`(옛 러너면 "러너 업데이트 필요 — 판단 미지원") · `base_commit` 있음(사실 1). 저장소 id(`repository_id`)는 설정의 `workflow_repository_id`, 없으면(App 소스) `task_cycle.match_for_source(...).workflow_repository_id`(17 의 자동 매칭 결과 — 러너가 보고한 GitHub 저장소가 같은 로컬 등록). 판단 실행은 소유자 승인·꺼진 러너 대기 경로(`owner_approval`·`start_pending_at`)를 타지 않는다.
6. **체크아웃 = 판단 Agent 의 `base_commit`(origin 기본 브랜치 끝, 중앙이 고정).** 요청 target 은 새 모양 `TriageTarget{local_registration_id, base_commit}`. 러너는 그 커밋의 **깨끗한 임시 체크아웃**(`_in_clean_checkout` — `code_review` 와 같은 방식)에서 `READONLY_TOOLS`(Read·Glob·Grep)만 주고 `--json-schema` 로 구조화 출력을 받는다. HEAD·파일이 바뀌면 `readonly_violation`, 커밋이 없으면 `commit_missing`(다른 기기 커밋은 가져오지 않는다), 끝나면 체크아웃을 지운다. 러너는 fetch 하지 않는다(claim 의 기준 커밋 보고가 이미 한다). 결과에 본 커밋 **`inspected_commit`** 을 러너가 체크아웃 HEAD 로 채우고, 중앙은 `== target.base_commit` 을 확인한다. Codex 어댑터도 같은 `launch_readonly`(`--sandbox read-only` + 출력 스키마)라 판단을 지원한다 — 지원하지 못하는 어댑터는 `unsupported_kind` 로 끝낸다(조용히 다른 형태로 내지 않는다).
7. **결과 형태 `TriageResult`(계약 v1 확장, `extra="forbid"`).** `contract_version`, `execution_id`, `task_id`, `inspected_commit`(40 hex), `proceed: "ready"|"needs_check"|"unsuitable"`, `confidence: 0.0~1.0`, `proposed_kind: KindId | None`, `assignee: {type: "member"|"agent", id} | None`, `predecessors: [WorkKey]`(최대 5, 중복 없음), `reasons: [{criterion, note}]`(1~7개, `criterion` ∈ `clarity`·`verifiability`·`scope`·`risk`·`permission`·`history`·`dependency` 중복 없음, `note` 1~200자), `missing_information: [str]`(최대 10, 각 1~200자). 제약: `ready` 면 `proposed_kind`·`assignee` 필수이고 `missing_information` 은 빈 배열, `needs_check` 면 `missing_information` 1개 이상(사람이 확인할 것 — README "또는 reasons 1개 이상" 은 `reasons` 가 늘 1개 이상이라 제약이 되지 않으므로 확인할 것을 반드시 적게 한다), `unsuitable` 은 `assignee` 없어도 된다. 모델 출력의 글(`note`·`missing_information`)은 저장·표시만 하고 명령·경로로 쓰지 않는다. 산출물 kind `triage_result` 를 `ARTIFACT_KINDS` 끝에 더한다.
8. **후보 목록 `TriageCandidates` — 판단 시점에 고정하고 그 안에서만 받는다.** 중앙이 판단을 시작할 때 계산해 요청문에 글로 넣고 판단 로그 행(`candidates_json`)에 저장한다. 판정은 **저장된 후보**로 한다(다시 계산하지 않는다). 칸: `kinds: [{kind, label}]`(워크스페이스 종류 중 판단 종류가 아니고 `input_kinds` 가 비어 업무를 시작할 수 있는 것, 그리고 `scope_key == "repository_id"` 이거나 열린 단계 종류인 것), `current_kind`(열린 단계 종류), `members: [{member_id, display_name, open_work}]`(활성 멤버, `open_work` = 담당인 끝나지 않은 업무 수), `agents: [{agent_id, name, owner_name, online, open_work, kinds}]`(워크스페이스 Agent 중 후보 종류 하나 이상을 이 저장소 범위로 맡을 수 있는 것 — `kinds` 는 맡을 수 있는 후보 종류, `select_agent(mode="manual")` 로 계산), `predecessors: [{work_key, title, status}]`(같은 연결 저장소의 끝나지 않은 다른 업무, 최근 30건). 판정 실패(전부 판단 로그 `failed`, 코드 `triage_invalid`, 메시지 = 하위 사유 + 설명): `ids_mismatch`(execution_id·task_id), `commit_mismatch`(`inspected_commit` ≠ 요청 `base_commit`), `kind_not_candidate`, `assignee_not_candidate`(멤버·Agent 가 후보 밖), `assignee_cannot_take_kind`(Agent 의 `kinds` 에 `proposed_kind` 없음), `predecessor_not_candidate`. 봉투를 읽지 못하면 `result_unreadable`.
9. **판단 로그 = 판단마다 한 행, 시작할 때 만든다.** README 기본값 6 은 결과 때 행을 만들게 했지만, 후보 목록을 판단 시점에 고정해야 하고(결정 8) "도는 판단" 을 한 곳에서 세야 하므로 **판단 단계·실행과 같은 트랜잭션에서 `running` 행**을 만든다(사실 8). 상태: `running` → `proposed`(판정 통과) | `failed`(판정 실패·실행 실패·기한 초과) → (다시 판단 때) `superseded`. 칸: 업무·업무 `revision`·단계·실행·판단 Agent·계기(`auto`|`manual`)·누른 멤버, 기준 버전, 입력 해시(요청문 원문 UTF-8 의 sha256 — 원문은 실행 요청에 이미 있어 따로 저장하지 않는다), 후보 JSON, 결과 JSON·`proceed`·`confidence`·`proposed_kind`, 실패 코드·메시지, 사람 처리(아래 결정 11)와 그 사람·시각·실제로 정한 담당·종류. "실제 결과"(병합·재작업) 칸은 두지 않는다 — 20-monitor 가 기존 이벤트로 계산한다. 같은 업무에 `running` 은 하나(부분 UNIQUE 인덱스). 실행 실패·`unknown` 은 판단 단계를 `실패` 로 마감하고 잠금을 풀되 **사람 요청·`task_failed` 알림을 만들지 않는다**(`_reflect_failures` 는 판단 단계를 건너뛴다). 판단 실행 기한: 만든 지 `TRIAGE_DEADLINE_SECONDS = 3600` 초가 지나도 `queued`·`accepted`·`running` 이면 서버가 `fail_execution(code="triage_deadline")` 으로 끝내고 위와 같이 `failed`(사실 9).
10. **`superseded` 규칙.** 새 판단을 시작하는 트랜잭션에서 같은 업무의 **사람 처리가 없는** `proposed`·`failed` 행을 모두 `superseded` 로. 사람이 처리한 행(`accepted`·`changed`·`dismissed`·`auto_started`)은 그대로 둔다 — 자동 시작 자격 건수가 줄지 않는다.
11. **사람 처리 기록 = 맡기기·배정 트랜잭션 안에서.** 판단 제안(최신 행이 `proposed` 이고 처리 없음)이 있는 업무의 담당이 `repo._assign_work_item` 에서 없음 → 멤버·에이전트로 정해지면, 같은 트랜잭션에서 그 행에 처리를 쓴다: 정한 담당이 제안 담당과 같고 열린 단계 종류가 `proposed_kind` 와 같으면 `accepted`, 아니면 `changed`(제안 담당이 없던 판단도 `changed`). `_assign_work_item` 은 패널 담당 select(멤버 배정·에이전트 맡기기 `hand_work_to_agent`)·[제안대로 맡기기]·[내 세션에서 작업](`start_direct_work`) 모두가 거친다 — 한 곳에 둔다. 워커의 자동 매칭(`_fill_work_assignee`)은 사람 처리가 아니다(기록하지 않음). [무시] = `dismissed`(제안을 접는다, 업무 이유는 `담당 없음` 으로). 자동 시작은 `auto_started`(결정 13). 처리는 한 행에 한 번(조건부 UPDATE `handling IS NULL`).
12. **[제안대로 맡기기].** 최신 `proposed` 행, 처리 없음, 업무가 여전히 판단 대상(결정 4 의 상태 조건)일 때만(아니면 409 `triage_stale`). 순서(한 요청): ① 제안 종류 ≠ 열린 단계 종류이면 그 단계에 실행이 한 번도 없을 때만 종류를 바꾼다 — 요구 능력(`{code: 새 종류 capability_code, scope: {scope_key: 이 저장소 id}}`)·`target`(`work_actions.target_for`)·`selection_mode` 다시, 그 단계가 업무의 첫 단계면 `work_items.kind` 도(`repo.change_stage_kind`, 업무 이벤트 없음 — 기록은 판단 로그의 `final_kind`). 실행이 있으면 409 `stage_started` "이미 시작한 단계는 종류를 바꿀 수 없습니다" ② 선행 업무마다 `work_item_links(blocks, 선행 → 이 업무)`(이미 있으면 그대로 — 착수를 막지 않는다, 사실 5) ③ 담당이 에이전트면 기존 맡기기(`work_actions.hand_to_agent` — `assign_work` 의 에이전트 가지를 그대로 옮긴 함수, 소유자 승인·꺼진 러너 대기 그대로), 멤버면 배정만(phase 16 결정 — 사람은 배정만). 처리 기록은 결정 11 이 ③ 안에서 쓴다. `proceed == unsuitable` 인 제안에는 이 버튼을 그리지 않는다(사람이 담당 select 로 정한다).
13. **자동 시작.** 업무 종류별 설정 `{enabled, threshold}`(기본 꺼짐, 기준값 0.8, 범위 0.50~1.00 소수 둘째 자리) — 바꿀 때마다 새 버전 행 + `sessions.config_revision` +1(phase 9 와 같은 방식). **켤 수 있는 조건**(자격): 그 종류를 `proposed_kind` 로 제안한 판단 로그 중 `state = 'proposed'` 이고 사람 처리가 `accepted` 또는 `changed` 인 행이 `AUTOSTART_MIN_HANDLED = 20` 건 이상(`superseded`·`dismissed`·`auto_started`·`failed` 는 세지 않는다 — 사람이 실제로 담당을 정한 판단만). 20건 미만이면 켜기 409 `triage_autostart_locked`("판단 기록 n/20 — 20건이 되면 켤 수 있습니다"), 끄기·기준값 바꾸기는 언제나 된다. 켜져 있으면 워커가 `proposed` 판단 중 처리 없음 · 그 업무의 최신 판단 · 업무가 여전히 판단 대상 · `proceed == "ready"` · 제안 담당이 **에이전트** · `confidence >= threshold` · 그 종류(`proposed_kind`) 설정이 켜짐 · 자격 충족 인 것을 [제안대로 맡기기]와 같은 함수(`work_actions.accept_triage(..., member_id=None)`)로 맡긴다. 맡긴 사람 = 없음(`requested_by_member_id` NULL — 정책 `owner_approval` 인 담당 Agent 면 기존대로 승인 요청이 열린다), 업무 이벤트 `assigned` 의 `data` 에 `"triage": {"triage_id", "criteria_version"}` 를 더하고 타임라인 표시는 `자동 시작 · 판단 v<기준 버전>`, 판단 로그 `auto_started`. 한 판단은 한 번만(처리 칸 조건부 UPDATE 로 두 tick·재시작에도 멱등). 확신도는 모델이 말한 값이다 — 이 값을 믿을 만한지는 20-monitor 의 판단 품질 화면을 보고 사람이 기준값을 정한다(REDESIGN_PLAN 6절 4).
14. **자동 판단 — 워크스페이스에 한 번에 1건, 판단 Agent 의 러너가 빌 때만.** 워커 tick 의 `_start_waiting_stages` **뒤**에 `_triage_new_work`: 워크스페이스마다 `running` 판단이 이미 있으면 0건, 아니면 대상(결정 4) 중 **그 업무에 판단 로그 행이 하나도 없는**(실패 코드 `usage_limit` 행은 없는 것으로 본다) 업무를 오래된 순(`created_at`, `key_number`)으로 보고, 판단 Agent 가 시작 가능(결정 5)하고 **그 러너가 빔**(러너에 `queued`·`accepted`·`running` 실행이 없고 `connectors.current_execution_id` 가 NULL)이고 그 Agent 가 쉬는 중이 아닌 첫 업무 하나를 시작한다. 자리가 `_start_waiting_stages` 뒤인 이유: 같은 tick 에 착수되는 수정·검토·승인 뒤 단계가 먼저 러너를 차지해야 한다(수정·검토 실행이 우선 — 사용자 결정 1). README 기본값 10 의 "그 업무 `revision` 의 행이 없음" 을 "그 업무의 행이 없음" 으로 바꾼다 — 같은 기본값이 "업무 내용이 바뀌어도(`revision` 증가) 자동으로 다시 판단하지 않는다" 고 하는데 `revision` 조건이면 내용이 바뀔 때마다 자동 판단이 다시 걸린다. 그래서 자동 판단이 한 번 돈(실패 포함) 업무에는 다시 걸지 않고, 다시 판단은 [다시 판단]만 한다. `revision` 은 행에 기록만 한다(20-monitor 가 "판단 뒤 내용이 바뀐 업무" 를 볼 수 있게). 자동 시작 자리는 `_judge_triage` 바로 뒤 `_autostart_triaged` — 같은 tick 의 `_advance_cycle` 이 맡긴 단계를 바로 착수한다.
15. **사용량 한도.** 판단 실행이 `usage_limit` 로 실패하면 판단 로그 `failed`(코드 `usage_limit`) + 그 판단 Agent 의 자동 판단을 `TRIAGE_USAGE_PAUSE_SECONDS = 3600` 초 쉰다(워커 메모리 `dict[agent_id, 시각]` — 재시작하면 풀림, 3-limit-wait 는 범위 밖). 사용량 한도 실패는 판단 실패가 아니므로 결정 14 의 대상 조건에서 빼고 쉬는 시간이 끝나면 그 업무를 다시 대상에 넣는다. 그 밖 실패는 판단 로그 `failed` + 패널 "판단 실패 · 이유 · [다시 판단]".
16. **기준 문서 = Runloom 이 저장, 버전 행.** 판단 기준 v1 은 [triage-criteria-v1.md](../product/triage-criteria-v1.md)(에이전트가 읽는 지시문, REDESIGN_PLAN 6절 5 의 7 항목). 코드 상수 `domain/triage_criteria.TRIAGE_CRITERIA_V1` 이 그 파일 내용과 **바이트 단위로 같다**(테스트가 확인). 스키마 v15 가 워크스페이스마다 v1 행을 시드하고(새 워크스페이스는 `create_session`), 설정 화면에서 고치면 새 버전 행(본문이 같으면 버전을 올리지 않음, 1~8000자, 낙관적 잠금 `expected_version` — 다르면 409 `stale_criteria`) + `config_revision` +1. 판단 전용 러너 폴더를 등록하지 않는다(사용자 결정 2 — REDESIGN_PLAN 6절 1 의 "판단 전용 폴더" 를 대신한다).
17. **요청문.** `domain/triage.compose_triage_request` 가 만든다: `# 판단: RUN-n 제목`(Jira 면 다음 줄 `원본: SHOP-12`) → `## 판단 기준 (v<n>)` 본문 → `## 업무`(업무 양식 칸 — `FORM_LABELS` 순, 요청 원문, 지금 종류) → `## 후보`(종류·담당·선행 후보 — 결정 8, 담당 줄은 `member:<id>`·`agent:<id>` 표기) → `## 로그 근거 (Runloom 계산)`(결정 18) → `## 답하는 법`(고정 문구 — 후보 밖 값은 실패, 저장소는 현재 폴더에서 읽기만). 지시 메모(`handoff_note`)·사람 응답은 넣지 않는다(담당이 정해지기 전이라 없다).
18. **로그 근거(중앙 계산, 순수 함수).** 후보 종류마다 같은 대표 종류(`work_items.kind`)의 최근 `HISTORY_LIMIT = 20` 건 끝난 업무(`closed_at` 최신순): 건수 n, 1회 통과(업무 `완료` 이고 그 종류 단계의 실행이 한 번 — 재작업 없이 병합), 재작업(그 종류 단계 실행 두 번 이상), 중앙 소요 시간(`완료` 업무의 `created_at → closed_at`). 담당 후보별 진행 중 업무 수(결정 8 의 `open_work`), 같은 저장소 열린 업무(선행 후보). 언제나 건수를 같이 적고, 0건이면 "기록 없음". 인과를 단정하는 문구("이 담당이 더 낫다" 등)는 쓰지 않는다 — 숫자만.
19. **업무 상태 이유.** 업무 상태는 `새로 들어옴` 그대로이고 `담당 없음` 자리에 판단 사실을 보인다: 도는 중 `판단 중`, 제안(처리 없음) `판단 제안 · <진행 여부 이름> <확신도 0.00>`(진행 여부 이름: `ready` 맡겨도 됨 · `needs_check` 확인 필요 · `unsuitable` 부적합 — 예 `판단 제안 · 맡겨도 됨 0.86`), 실패 `판단 실패 · <실패 이름>`(예 `판단 실패 · 후보 밖 제안`, `판단 실패 · 사용량 한도`), 무시·다시 판단 전 처리됨 → `담당 없음`. 판단 사실은 그 업무의 가장 최근 판단 로그 행 하나로 정한다.
20. **러너 프로토콜.** 러너 `SUPPORTED_BUILTIN_KINDS` 에 `triage`. 서버는 판단을 시작하기 전에 판단 Agent 러너의 마지막 claim `supported_kinds` 에 `triage` 가 있는지 보고(결정 5), `repo.claim_execution` 도 결과 형태가 `triage_result` 인 종류의 실행은 마지막 claim 의 `supported_kinds` 에 그 종류가 있는 러너에만 준다(러너가 옛 판으로 돌아간 경우 — `verify_only` 와 같은 두 번째 검사). 옛 러너는 판단만 못 하고 나머지는 그대로다. 업그레이드 순서는 서버 → 러너(14·16절과 같다), 셀프호스트 v15 업그레이드에 **러너 재설치** 포함.
21. **스키마 v15 = 표 셋 + 시드 둘.** 판단 기준(버전) 표 `triage_criteria`, 판단 로그 표 `triage_logs`, 자동 시작 설정(버전) 표 `triage_autostart`, 기존 로컬 Agent 에 `code.triage {repository_id}` 능력(`code.fix` 의 범위와 같은 값), 워크스페이스마다 내장 종류 `triage` 행과 판단 기준 v1 행. 새 칸·재생성 없음 — **`tasks` 는 그대로**(ADR-0020), `github_sources` 도 그대로(결정 3). 워크스페이스에 사용자 정의 종류 `triage` 가 이미 있으면 마이그레이션을 중단한다(v8 → v9 선례). 세부는 ARCHITECTURE.
22. **화면.** 업무 패널 "판단" 절(속성 다음, 지금 할 일 앞): 제안(진행 여부·확신도·제안 종류·담당·선행·근거·모자란 정보·기준 버전) + [제안대로 맡기기]·[무시], 실패 이유, [판단 받기](판단 없음)/[다시 판단](있음) — 버튼은 판단 대상이고 판단 Agent 가 정해졌고 `DELEGATE` 권한일 때만, 시작할 수 없으면 이유 문구. 목록 행에 판단 배지(`판단 중`·`판단 제안`·`판단 실패`). 연결 화면에 탭 `판단`(`MANAGE_CONNECTIONS` 만 보임): 기준 본문 편집·버전 이력(번호·누가·언제·이전 본문 보기), 종류별 자동 시작(자격 n/20·켬/끔·기준값·변경 이력). 저장소 카드에 판단 에이전트 select(후보 = 그 저장소 `code.triage` 능력·정책 `run`)와 매칭 줄 `판단 에이전트`(설정 | 없음). 외부 문자열(업무 제목·판단 근거·모자란 정보·기준 본문)은 자동 이스케이프로만(`|safe` 금지).

## 하지 않는 것

데이터 등급, 에이전트 허용 명령(REDESIGN_PLAN 9절), 판단 품질·담당자별·버전 비교 화면(20-monitor), 판단 "실제 결과" 집계 칸, 로컬 모델(Ollama 등), 외부 판정 API·중앙 LLM 호출, A2A(판단 에이전트가 수정 에이전트에게 묻기), 업무 내용 변경 시 자동 재판단, 선행 업무 완료까지 착수 막기, 사용량 한도 대기열(3-limit-wait), 판단 Agent 소유자 알림, 직접 등록·n8n 업무 판단, 판단 Agent 자동 매칭, Claude Code 훅, 실제 Claude·GitHub·Jira 호출(모든 step 은 가짜 러너·가짜 도구·`MockTransport` 로 검증, 실연동은 phase 뒤 사용자 지시).

## 결과

- 좋은 점: 판단은 새 실행 엔진 없이 기존 단계·실행·러너·읽기 전용 체크아웃 위에 얹힌다. 판단 단계를 가르는 곳은 결과 형태 한 함수(와 같은 상수의 SQL 조각)뿐이고 종류 이름 분기는 늘지 않는다. 사람 처리가 맡기기 트랜잭션과 같이 기록돼 "제안대로 했는가" 를 놓치지 않고, 그 기록이 자동 시작의 자격이 된다. 업무 내용은 러너의 로컬 에이전트만 본다.
- 비용: 판단 단계는 업무 단계 목록에 섞여 있으므로 단계를 세는 새 코드는 언제나 `is_triage_kind` 를 거쳐야 한다(빠뜨리면 업무 상태가 틀린다 — e2e 가 지킨다). 확신도는 모델의 말이라 보정 전에는 자동 시작 기준으로 약하다. 판단마다 구독 사용량을 쓴다(자동 판단은 워크스페이스에 1건·러너가 빌 때만).
- 실연동 때 확인할 것: 판단 시간·구독 사용량, 명확한 버그·양식이 빈 업무·운영 접근이 필요한 업무 세 건의 진행 여부(`맡겨도 됨`·`확인 필요`·`부적합`), 모델이 후보 밖 값을 내는 빈도(`triage_invalid`).
