# ADR-0027: 결과 뒤 판단 — 상주 판단 에이전트가 다음 행동을 제안하고 사람이 한 번 눌러 확정한다

결정일: 2026-10-04 (phase 22 step 0). 근거: [ADR-0009](0009-registered-kinds-and-succession-rules.md)(종류·후속 규칙은 등록 데이터), [ADR-0020](0020-work-items-and-stages.md)(업무·단계), [ADR-0023](0023-cross-member-delegation.md)(맡기기 정책), [ADR-0025](0025-triage.md)(판단), [사내 요청](../product/INTERNAL_REQUESTS.md)·[조사·반환](../product/INTERNAL_REQUEST_INVESTIGATION.md)·[담당 범위 표](../product/RESPONSIBILITY_DIRECTORY.md), [Multica 진행 방식 조사](../research/2026-10-04-multica-how-work-flows.md). 기본값은 [phase 22 README](../../phases/22-next-step/README.md) "사용자 결정" D1~D4(2026-10-04)와 "계획 기본값" 10가지이며 이 문서로 구현 기준을 고정한다. 적용 범위는 `service` 브랜치. 이름·표·경로·시그니처의 기준은 [ARCHITECTURE](../ARCHITECTURE.md) "결과 뒤 판단 — phase 22" 이다(README 와 다르면 ARCHITECTURE).

## 계기

Runloom 의 사이클은 **업무 등록 → 배정 → 에이전트 작업 → 결과에 따라 업무 등록** 이다. 지금은 두 곳에서 끊긴다.

1. **배정 판단이 접수 때 한 번뿐이다.** 판단(phase 19)은 `새로 들어옴`·담당 없음 업무만 본다. 결과가 나온 뒤 후속 규칙에 맞는 것이 없으면 아무 일도 일어나지 않고(`worker._apply_followup` 의 `none`), `needs_information` 은 사람 요청으로 멈춘다.
2. **바깥 담당을 모른다.** 판단 후보는 워크스페이스 멤버·에이전트뿐이다. 담당 범위 표와 사내 요청(21)은 사람이 손으로만 쓰고, 요청이 만들어져도 받는 사람에게 알림이 없으며, 반환된 결과는 원래 업무로 이어지지 않는다.

Multica 는 이 자리를 squad 리더 LLM(자유 텍스트 지시, 권한 전부 열림, 댓글로 인계)이 메운다. Runloom 은 **프로젝트에 상주하는 판단 에이전트가 판단 시점에 고정한 후보(종류·멤버·에이전트·담당 범위) 안에서만 다음 행동 하나를 제안**하고, 사람이 [제안대로] 를 한 번 눌러 확정한다. 판단은 기존 내장 종류 `triage`·판단 로그·판단 Agent·읽기 전용 체크아웃 위에 얹는다 — 새 실행 엔진·새 내장 종류·그래프가 없다.

## 사용자 결정 (2026-10-04)

1. **D1 언제** — 결과 뒤 판단은 세 경우에만 돈다: ① 후속 규칙에 맞는 것이 없는 결과(판정 통과) ② `needs_information` ③ 사내 요청 반환. 판정 실패·실행 실패는 지금처럼 사람에게 간다.
2. **D2 무엇을** — 다음 행동은 네 가지: 같은 업무의 다음 단계·재작업 / 새 업무 / 외부 담당에게 사내 요청 / 사람에게 돌려보내기. "완료" 는 제안하지 않는다(PR 병합·사람이 정한다).
3. **D3 어떻게** — 판단은 제안까지. 사람이 [제안대로] 한 번 누른다. 결과 뒤 판단의 자동 시작은 없다. 접수 판단의 자동 시작 자격 건수에 섞지 않는다. 판단이 만든 사내 요청의 요청자는 [제안대로] 를 누른 멤버다.
4. **D4 받는 쪽** — 받는 사람의 수락·검토는 그대로. 요청 생성 때 받는 사람에게 알림, 반환되면 원래 업무의 결과 뒤 판단이 자동으로 이어진다(재개 기록 기능은 그대로).

## 코드 조사로 README 와 달라진 사실 (2026-10-04, `feat-22-next-step` `70a05e7` = `service` `aae864a` + step 파일)

README "조사로 확인한 현재" 의 위치·이름은 맞았다. 아래는 더 들어가 확인한 사실이고, 결정 몇 개를 바꾼 근거다.

1. **조사 C3 는 KeyError 가 아니라 계약 검증 오류로 먼저 터진다.** `domain/triage.startable_kinds` 가 입력이 있는 종류를 빼므로 지금 단계 종류가 `input_kinds` 를 가지면(예: `code_review`) `assemble_candidates` 가 만든 `TriageCandidates` 가 "kinds 에 current_kind 가 있어야 합니다" 로 `ValidationError` 를 낸다(`compose_triage_request` 의 `labels[current_kind]` 까지 가지 않는다). 접수 판단에서도 이미 생길 수 있다 — 검토 Agent(`review_agent_id`)가 비어 있는 `new_work` 후속 업무는 첫 단계가 `code_review` 이고 담당 없음·`새로 들어옴` 이라 자동 판단 대상이 되고, `request_triage` 가 워커 tick 안에서 예외를 낸다. 결정 4 가 고친다(지금 종류는 입력과 무관하게 후보에 넣고 `startable` 표시로 가른다).
2. **업무 순환 종류의 "규칙 없음" 은 `_after_fix` 한 곳뿐이다.** `_after_review` 의 "검토 outcome … 은 후속 대상 아님" 은 내장 `code_review` 의 outcome 이 `approved`·`changes_requested`·`needs_information`(계약 Literal)이라 닿지 않는다. 그리고 `none` 이면서 `hold_code` 가 없는 결정은 규칙 없음만이 아니다 — `검토 승인`(따로 처리)·`이미 재작업을 시작한 검토`·`decide_followup` 이 덮는 `이미 처리한 후속 …` 도 같은 모양이다. 그래서 README 의 "결정이 `none` 이고 `hold_code` 가 없을 때" 대신 **규칙 없음에 새 `hold_code` `no_rule`** 을 붙이고 그것만 시작 지점으로 본다(결정 6).
3. **`_cycle_followups` 는 같은 결과를 매 tick 다시 본다.** 판정은 `finish=False` 라 Task 가 마감되지 않고, 끝나지 않은 Task 의 `result_ready` 실행은 tick 마다 `decide_followup` 을 다시 지난다(지금은 `cause_key`·`start_key` 로 멱등). 결과 뒤 판단 시작도 매 tick 다시 불리므로 **원인당 판단 하나를 표가 지킨다**(부분 UNIQUE, 결정 9). 이 반복 덕분에 "기다렸다가 시작"·"시작할 수 없으면 대체 경로" 를 재시작에 안전하게(메모리 없이) 다시 계산할 수 있다.
4. **담당표 revision 은 워크스페이스 설정 번호 전체다.** `internal_request_store._create` 의 `expected_directory_revision` 은 `sessions.config_revision` 과 비교하고, 이 번호는 종류·규칙·저장소·매핑·판단 기준·자동 시작·담당표 어느 것을 바꿔도 오른다. README 계획 기본값 7 의 "담당표 revision = 판단 시점 값 — 바뀌었으면 409 `stale_directory`" 를 그대로 쓰면 판단 기준 하나만 고쳐도 모든 사내 요청 제안이 막힌다. 그래서 **판단 시점에 저장한 담당 범위 항목과 지금 항목이 같은지**(같은 시스템·요청 종류·받는 사람에 판단 담당·조사 에이전트가 같고 `entry_problem` 이 없음)를 보고, 같으면 지금 번호로 만든다(결정 7).
5. **규칙 없이 이어 붙인 단계는 착수되지 않는다.** 사용자 정의 종류의 입력 인계(`_spawn_successors`)는 `get_rule(선행 종류, 후속 종류)` 가 있어야 묶음을 만들고(없으면 `대기 · 후속 규칙 없음`), 결과에서 시작하는 내장 종류(`code_review`, `starts_from_result`)는 `_cycle_followups` 의 규칙 결정으로만 착수한다. 결과 뒤 판단은 규칙에 맞는 것이 없을 때 도는 것이므로 README 계획 기본값 4 의 "입력 종류가 원인 실행의 산출물로 채워지는 종류" 를 다음 단계 후보로 넣으면 만든 단계가 멈춘다. 그래서 **다음 단계·새 업무 후보는 입력이 없는 종류만**, 이전 결과는 새 단계의 요청 글로 넘기고, 같은 단계 재작업은 기존 **검토 [수정 요청]**(`/tasks/{id}/review` `request_changes` — 이전 결과 + `review_comment` 지적 산출물을 입력으로 새 실행) 경로를 쓴다(결정 7).
6. **알림 행은 Task 없이도 쌓인다.** `notifications.task_id` 는 NULL 을 허용하지만 `worker.enqueue_event_notification` 은 Task 를 읽어 제목·업무 주소·받는 사람을 정한다. 사내 요청은 Task 가 없으므로 요청 알림은 업무 제목·`/requests` 주소로 쓰는 별도 함수로 둔다(결정 10).
7. **러너 능력은 계약 상수가 곧 보고값이다.** `connector/client.claim` 은 `capabilities` 로 `contracts.v1.RUNNER_CAPABILITIES` 를 늘 싣고, 서버는 `connectors.capabilities_json` 에 저장한다(`verify_only` 선례). 그리고 `claim_execution` 은 `verify_only` 실행을 그 능력을 보고한 러너에만 준다. 결과 뒤 판단 실행도 같은 두 번째 검사가 필요하다 — 옛 러너가 `mode` 가 있는 `TriageTarget` 을 받으면 `extra="forbid"` 로 요청을 읽지 못한다(결정 3).
8. **null 칸을 직렬화에서 빼는 장치가 이미 있다.** `contracts.v1._OmitUnknownMeasure`(`_MEASURE_FIELDS` 가 None 이면 뺀다)를 `ExecutionRequest.verify_only_commit`·`ClaimRequest.capabilities` 가 쓴다. `TriageTarget.mode`·`TriageResult.next_action` 도 이것으로 옛 모양을 지킨다(결정 2).
9. **판단 로그를 읽는 기존 코드는 "업무의 최신 행" 을 전제한다.** `latest_triage`·`work_item_facts.triage`·`list_work_rows` 배지·`autostart_candidates`·`triage_handled_counts`·`auto_triage_works`·`start_triage` 의 `superseded`·`dismiss_triage`·`_record_triage_handling`·`list_triage_facts`(모니터링)·`views.triage_panel` 이 모두 원인 구분 없이 업무의 판단 로그를 본다. 결과 뒤 판단 행이 같은 표에 들어가면 이 열한 곳이 **`cause = 'intake'` 로 거른다** — 그래야 접수 판단의 동작·자동 시작 자격 건수·판단 품질 지표가 그대로다(결정 9).
10. **`human_requests.code` 는 CHECK 가 없고 `human_api` 의 허용 응답 기본값이 `resume`·`close` 다.** `next_step_human` 은 표 변경 없이 값만 쓰고, `resume` 에 답 글을 요구하는 `_INFORMATION_CODES` 에만 더한다.

## 결정

1. **같은 판단, 원인 셋.** 내장 종류 `triage`·판단 단계·판단 실행·표 `triage_logs`·판단 Agent(저장소 카드 `triage_agent_id`)·판단 기준·기본 브랜치 끝의 읽기 전용 체크아웃을 그대로 쓴다. 판단 로그에 원인 `cause` ∈ `intake`(접수 판단, 기존 행 전부)·`after_result`(①②)·`request_returned`(③)와 원인 참조 `cause_execution_id`(executions — `intake` 면 NULL, 결과 뒤 판단은 늘 있음)·`cause_request_id`(internal_requests — `request_returned` 만)를 둔다. 결과 뒤 판단(`after_result`·`request_returned`)을 묶어 **`next_step` 판단** 이라 부른다. 원인 실행이 속한 Task 를 **원인 Task** 라 부른다. `trigger` 는 결과 뒤 판단이면 늘 `auto`(사람이 시작하는 버튼은 없다 — [다시 판단]도 없다).
2. **계약 확장(옛 모양 유지).**
   - `TriageTarget.mode: Literal["next_step"] | None = None` — None = 접수 판단. `TriageTarget` 이 `_OmitUnknownMeasure`(`_MEASURE_FIELDS = ("mode",)`)를 이어받아 None 이면 직렬화에서 빠진다. 그래서 접수 판단 요청은 바이트 단위로 지금 모양이고 옛 러너가 받는다. README 의 `"intake" | "next_step"`(기본 `intake`) 대신 None 을 쓰는 이유는 기존 장치(사실 8)를 그대로 쓰기 위해서다.
   - `TriageResult.next_action: NextAction | None = None` — 같은 방식으로 None 이면 빠진다(접수 판단 결과·저장된 `result_json` 모양 그대로). 계약 검증: `next_action` 이 있으면 `proposed_kind` None·`assignee` None·`predecessors` 빈 배열이어야 하고(접수 판단 칸을 비운다), `proceed == "ready"` 의 "`proposed_kind`·`assignee` 필수" 는 `next_action` 이 없을 때만 적용, `proceed == "unsuitable"` 이면 `next_action.type == "human"`(부적합이면 사람에게 돌려보낸다), `needs_check` 는 지금처럼 `missing_information` 1개 이상. `proceed`·`confidence`·`reasons`·`missing_information` 은 두 모드 공통.
   - `NextAction` = `type` 으로 가르는 네 모양(`Field(discriminator="type")`, 모두 `extra="forbid"`):
     - `NextStage{type: "stage", kind: KindId, assignee: TriageAssignee, rework: bool}` — `rework=false` 면 같은 업무의 새 단계, `true` 면 원인 Task 재작업(그때 `kind` 는 원인 Task 종류, `assignee` 는 원인 실행의 Agent `agent:<id>` 여야 한다 — 판정이 본다).
     - `NextNewWork{type: "new_work", kind: KindId, title: 1~120자, assignee: TriageAssignee}` — `spawned_from` 으로 잇는 새 업무.
     - `NextInternalRequest{type: "internal_request", system_id: Identifier, request_kind: Identifier, recipient_member_id: NonEmptyStr, purpose: 1~2000자}` — 담당 범위 후보 중 하나에게 사내 요청.
     - `NextHuman{type: "human", question: 1~500자}` — 사람에게 돌려보내기.
     글 칸(`title`·`purpose`·`question`)은 공백만이면 422. 저장·표시만 하고 명령·경로로 쓰지 않는다.
   - 접수 판단 결과에 `next_action` 이 오면 판정 실패(`next_action_forbidden`), 결과 뒤 판단 결과에 없으면 실패(`next_action_missing`).
3. **러너 능력 `after_result_triage`.** 계약 상수 `RUNNER_CAPABILITY_AFTER_RESULT_TRIAGE = "after_result_triage"`(step 1). 러너가 `mode=next_step` 을 실행할 수 있게 되는 step 2 에서 `RUNNER_CAPABILITIES` 에 더한다 — claim 이 이 튜플을 그대로 보고한다(사실 7). 중앙은 판단 Agent 러너의 마지막 claim `capabilities_json` 에 이 값이 있을 때만 결과 뒤 판단을 시작하고(없으면 이유 `러너 업데이트 필요 — 결과 뒤 판단 미지원` → 결정 6 의 대체 경로), `claim_execution` 도 `json_extract(e.request_json, '$.target.mode') = 'next_step'` 인 실행을 그 능력을 보고한 러너에만 준다(`verify_only` 와 같은 두 번째 검사). 옛 러너는 결과 뒤 판단만 못 하고 접수 판단·나머지는 그대로다. 업그레이드 순서는 서버 → 러너, 셀프호스트 v24 에 러너 재설치 포함.
4. **후보 확장 — 판단 시점에 고정하고 그 안에서만 받는다.** `TriageCandidates` 에 기본값이 있는 칸 둘과 표시 하나(저장된 v23 이전 후보 JSON 도 그대로 읽힌다):
   - `TriageKindCandidate.startable: bool = True` — 그 종류로 새 단계·새 업무를 시작할 수 있는가(판단 종류 아님·`input_kinds` 없음·`scope_key == "repository_id"`). 지금 종류(`current_kind`)는 입력과 무관하게 늘 `kinds` 에 들어가고 시작할 수 없으면 `startable=False` — 사실 1 의 C3 를 고친다(접수 판단의 `startable_kinds` 도 같은 규칙으로 바꾼다: 지금 종류는 늘 포함. 접수 판단 판정은 지금처럼 `kinds` 안이면 받는다).
   - `responsibilities: list[TriageResponsibilityCandidate] = []`(최대 `RESPONSIBILITY_CANDIDATES_MAX = 50`, 담당표 순서, `entry_problem` 이 None 인 항목만) — `{system_id, request_kind, recipient_member_id, recipient_name, judgment_member_id, agent_id: str | None}`. README 의 `has_agent` 대신 `agent_id` 를 저장한다 — [제안대로] 때 항목이 바뀌었는지 비교해야 한다(결정 7). 요청문에는 `조사 에이전트 있음|없음` 으로만 쓴다. 키 `(system_id, request_kind, recipient_member_id)` 중복 422.
   - `cause: TriageCause | None = None` — `{cause: "after_result"|"request_returned", execution_id, task_id, kind, agent_id, outcome, request_id: str | None}`. 결과 뒤 판단이면 늘 있고 `kind == current_kind`, `request_returned` ⇔ `request_id` 있음. 접수 판단이면 None.
   결과 뒤 판단의 `kinds` = 지금 종류(원인 Task 종류) + `startable` 종류(등록부 순서), `members`·`agents` 는 접수 판단과 같은 규칙(에이전트의 `kinds` = 맡을 수 있는 후보 종류 — 지금 종류는 원인 Task 의 요구 능력, 나머지는 `{scope_key: repository_id}`), `predecessors` 는 빈 배열, `responsibilities` 는 위. 접수 판단은 `responsibilities` 빈 배열·`cause` None(지금 그대로).
5. **요청문 `compose_next_step_request`(`domain/next_step.py`).** 접수 판단의 절 모양을 따른다: `# 다음 단계 판단: RUN-n 제목`(Jira 면 `원본:` 줄) → `## 판단 기준 (v<n>)` → `## 업무`(지금 단계 종류·양식 칸·요청 원문) → `## 이전 결과`(원인 실행의 종류·outcome·판정·결과 봉투의 `summary`, 검토 결과면 `missing_information`) → `## 사람 응답`(원인 Task 의 최근 응답 3개, 있을 때) → `## 반환된 사내 요청`(③ 만 — 시스템·요청 종류·받은 사람·목적·반환 요약) → `## 후보`(다음 단계 종류·담당·사내 요청 담당 범위) → `## 로그 근거 (Runloom 계산)`(접수 판단과 같은 계산) → `## 답하는 법`(결과 뒤 판단 고정 문구). 외부 글(양식·요청·결과 요약·응답·목적·반환 요약)은 접수 판단처럼 펜스 안에, 제목·이름은 한 줄로. 길이: 결과 요약·반환 요약·목적 `PRIOR_TEXT_MAX = 2000` 자, 응답 하나 `RESPONSE_TEXT_MAX = 1000` 자에서 자른다(`…(생략)`). 모양은 ARCHITECTURE.
6. **시작 지점·순서·대체 경로(워커).**
   - **① 규칙 없는 결과**: 업무 순환 종류는 `decide_followup` 이 `FollowupDecision("none", …, hold_code="no_rule")` 를 낸 결과(사실 2 — `_after_fix` 의 규칙 없음에 `hold_code` 를 더한다. `_HOLD_LABELS` 에 넣지 않으므로 상태 쓰기는 지금 그대로 없음). 사용자 정의 종류는 `generic_result` 결과가 판정 통과(`verdict outcome == "passed"`)·실행 `result_ready`·해제 안 됨·Task 끝나지 않음·그 Task 를 선행으로 둔 Task(`predecessor_task_id`) 없음·사내 조사 Task(`internal_request_investigations.task_id`) 아님인 것(DB 조회 `repo.generic_results_awaiting_next_step`).
   - **② `needs_information`**: `decide_followup` 이 `request_human` 이고 `request_code ∈ NEEDS_INFORMATION_CODES = ("fix_needs_information", "review_needs_information")`.
   - **③ 반환**: `internal_request_investigations.returned_at` 이 있고 그 요청에 `request_returned` 판단이 없는 요청. 원인 실행 = 요청이 판단으로 만들어졌으면(`created_by_triage_id`) 그 판단의 `cause_execution_id`, 아니면 원래 업무의 맡길 단계(`repo.open_stage`)의 활성 실행. **원인 실행이 `result_ready`·해제 안 됨·원인 Task 끝나지 않음일 때만** 시작한다 — 아니면 ③ 판단을 하지 않는다(반환은 지금처럼 패널에 보이고 재개 기록은 그대로).
   - **시작 조건**(`next_step_runs.next_step_route` — 접수 판단 `triage_route` 의 판단 Agent 검사와 같은 함수를 나눠 쓴다): 원인 Task 의 원본 설정(`task_cycle.origin(원인 Task).config`)이 있고 원본이 닫히지 않음, 판단 Agent 있음, 저장소 id, Agent 가 워크스페이스·로컬·러너, `code.triage` 능력, 정책 `run`, 러너 켜짐, 러너 `supported_kinds` 에 판단 종류, 러너 `capabilities` 에 `after_result_triage`, `base_commit` 있음. 접수 판단의 업무 조건(`새로 들어옴`·담당 없음)은 보지 않는다. 직접 등록·n8n·조사 업무는 원본 설정이 없으므로 이유 `연결 저장소가 없는 업무는 판단하지 않습니다` — 지금 동작.
   - **처분 `domain.next_step.disposition`**(순수, 원인마다 매 tick): 그 원인의 판단 행이 `running` 이거나 `proposed`(처리 없음·`accepted`)면 `hold`(아무것도 하지 않는다). `failed`·`superseded` 이거나 `dismissed` 면 `fallback`. 행이 없으면 시작 조건의 이유가 있으면 `fallback`, 원인이 생긴 지 `NEXT_STEP_WAIT_SECONDS = 3600` 초가 넘었으면 `fallback`, 아니면 `queue`. 원인 시각 = ①② 그 실행의 판정 `task_verdicts.decided_at`, ③ `returned_at`. 기다림 상한은 판단 자리(워크스페이스 1건·러너 빔)를 못 얻어 원인이 조용히 멈추지 않게 하고, v24 로 올린 직후 오래된 결과·반환이 한꺼번에 판단에 걸리지 않게 한다.
   - **`fallback`(대체 경로)**: ② 는 지금 그대로 원래 사람 요청(`_request_human(code, reason, cause_key="{code}:{execution_id}")` + 원인 Task `확인 필요`). ① 은 아무것도 하지 않는다(지금 그대로 — 결과는 `확인 필요 · 검토 대기` 로 사람 검토를 기다린다). ③ 은 요청이 판단으로 만들어졌으면 원인 Task 에 `next_step_human` 사람 요청(질문 `사내 요청 결과가 돌아왔습니다 — 다음 단계를 정해 주세요: <반환 요약 첫 줄 120자>`, `cause_key = "next_step_human:request:<request_id>"`), 사람이 만든 요청이면 아무것도 하지 않는다(요청자가 이미 안다).
   - **같은 원인에 사람 요청이 둘 생기지 않는다**: 결과 뒤 판단 행이 `accepted` 면 `hold` 라 대체 경로가 열리지 않고, `human` 행동의 요청(`cause_key = "next_step_human:<triage_id>"`)은 `accepted` 에서만 생긴다. 대체 경로의 요청은 `cause_key` 로 멱등(`create_human_request_once`)이고, ② 의 원래 요청이 열리면 `decide_followup` 이 그 `cause_key` 를 이미 처리한 원인으로 보아 `none`(`이미 처리한 후속`) — 결과 뒤 판단 시작 지점이 아니다.
   - **README 계획 기본값 7 의 "[무시] = 원래 사람 요청(없으면 `next_step_human` 과 같은 일반 확인 요청)" 을 바꾼다**: [무시] 는 `dismissed` 만 기록하고, 다음 tick 의 처분이 위 대체 경로를 따른다(② 원래 요청, ③ 판단이 만든 요청이면 `next_step_human`, ① 없음). ① 에 일반 확인 요청을 열지 않는 이유: [무시] 를 누른 사람이 이미 패널에 있고, 원인 Task 는 지금도 `확인 필요 · 검토 대기` 로 사람 검토를 기다린다 — 같은 사람에게 `내 차례` 를 하나 더 만들 뿐이다.
   - **tick 순서**: `… _check_generic_results → _judge_triage → _autostart_triaged → _advance_cycle → _spawn_successors → _start_waiting_stages → _triage_after_results → _triage_new_work → _reflect_failures → …`. ①②(업무 순환)는 `_advance_cycle`(`_cycle_followups` → `_apply_followup`)이 처분을 계산해 `queue` 인 원인을 이번 tick 의 메모리 목록 `_next_step_queue` 에 담고(tick 머리에서 비운다 — 다음 tick 에 다시 계산되므로 재시작에 안전), `_triage_after_results` 가 그 목록 + DB 조회(① 사용자 정의 종류·③)를 원인 시각 오래된 순으로 본다. 워크스페이스마다 `running` 판단(접수·결과 뒤 합쳐)이 있으면 0건, 아니면 시작 조건 이유 없음·판단 Agent 쉬는 중 아님·러너 빔(`repo.runner_idle`)인 첫 원인 하나를 시작한다. `_triage_new_work` 앞이라 **결과 뒤 판단이 접수 판단보다 먼저** 자리를 차지하고(진행 중 업무가 막혀 있다), `_start_waiting_stages` 뒤라 수정·검토 착수가 러너를 먼저 차지한다(ADR-0025 결정 14 와 같은 이유).
7. **[제안대로](`work_actions.accept_next_step`)·[무시](`dismiss_next_step`).** 권한 `team.DELEGATE`. 조건: 그 행이 그 업무의 최신 결과 뒤 판단(`cause != 'intake'`)·`proposed`·처리 없음이고 **원인이 그대로**(원인 실행 `result_ready`·해제 안 됨·원인 Task 끝나지 않음, ③ 은 요청이 반환된 채) — 아니면 409 `next_step_stale`. 처리 기록 `handling = 'accepted'`·`handled_by_member_id`·`handled_at` 은 조건부 UPDATE(`handling IS NULL`)로 한 번(두 번 누름·경합에 멱등). 행동별(DB 쓰기는 처리 기록과 한 트랜잭션, 맡기기·착수는 그 뒤 기존 함수):
   - `stage`, `rework=false`: 원인 Task 를 `완료`(이유 `다음 단계로 넘김`)로 마감·잠금 해제, 같은 업무에 새 단계(종류 = 제안 종류, `predecessor_task_id` NULL — 규칙 없이 이은 선행은 착수되지 않는다(사실 5), 요구 능력 `{capability_code, {scope_key: 저장소 id}}`, `target = target_for(spec, 담당 Agent 또는 None)`, 요청 글 = `next_step.stage_request_text`(원래 업무 요청 + 이전 결과 요약 + 판단 근거)). 그 뒤 담당이 에이전트면 `hand_to_agent(member_id=누른 멤버)`(소유자 승인·꺼진 러너 대기 그대로), 멤버면 `assign_work_item`(배정만). 원인이 `needs_information` 이어도 `완료` 다 — 사람이 다른 단계로 넘기기로 정한 것이고, 같은 단계에서 답을 넣어 다시 하려면 `rework=true` 를 쓴다.
   - `stage`, `rework=true`: 원인 Task 에 기존 검토 [수정 요청] 과 같은 일 — `review_comment` 지적 산출물(`comment` = `next_step.rework_note` — 판단 근거·모자란 정보·③ 이면 반환 요약)을 저장하고, 이전 입력 + 이전 결과 + 지적을 입력으로 원인 실행을 해제하고 새 실행(같은 Agent·이전 target, 코드 수정이면 `base_commit` = 이전 결과 커밋). 웹 `task_review` 의 `request_changes` 본문을 `stage_runs.request_changes` 로 옮겨 둘이 같이 쓴다(동작 그대로). README 의 "`needs_information` 이면 사람 응답 `resume` 과 같은 재착수" 를 이 경로로 정한다 — 업무 순환·사용자 정의 종류 모두에 같은 경로가 있고(사실 5), `resume` 은 사람 요청·응답 행이 있어야 하며 사용자 정의 종류에는 자동 재착수가 없다.
   - `new_work`: 원인 Task 를 `완료`(이유 `새 업무로 넘김`)로 마감, `create_followup_once(placement="new_work")` 와 같은 쓰기(새 업무 + 첫 단계 + `spawned_from` 링크 + 원인 업무의 맡긴 사람 복사 + Jira 원인이면 후속 이슈 생성 대기 — 트랜잭션 안쪽을 `_create_followup` 으로 나눠 같이 쓴다, `cause_execution_id` = 원인 실행, `to_kind` = 제안 종류). 그 뒤 새 업무에 `hand_to_agent`/`assign_work_item`.
   - `internal_request`: `internal_request_store` 의 생성 경로 그대로(`_create`) — 요청자 = 누른 멤버, `submission_key = "next_step:<triage_id>"`, 목적 = 제안 `purpose`, `created_by_triage_id` = 판단. 담당표 검사(사실 4): 판단 시점의 후보 항목과 지금 항목(같은 키)의 `judgment_member_id`·`agent_id` 가 같고 `entry_problem` 이 None 이면 지금 `config_revision` 을 `expected_directory_revision` 으로 넘긴다. 항목이 없어졌거나 달라졌으면 409 `stale_directory`, 활성이 아니면 422 `invalid_recipient`(store 그대로). 원인 Task 는 그대로(잠금 유지, `확인 필요`) — 업무 이유는 `사내 요청 대기 · <받는 사람>`(결정 11). 같은 트랜잭션 뒤 `internal_request_received` 알림.
   - `human`: 원인 Task 에 `next_step_human` 사람 요청(질문 = 제안 `question`, `cause_key = "next_step_human:<triage_id>"`) + `human_request` 알림(지금 사람 요청과 같다). 응답 `resume` 은 지금 사람 요청처럼 답과 함께 그 단계를 다시 하게 하고(업무 순환 종류 — `_resume`), 사용자 정의 종류는 사람이 [실행] 한다.
   - [무시](`dismiss_next_step`): `handling = 'dismissed'`, 업무 상태 재계산. 대체 경로는 결정 6.
   - 실패 응답: 404 `not_found`, 409 `next_step_stale`·`stale_directory`·`kind_unavailable`(제안 종류가 등록부에서 지워짐)·`work_closed`(끝난 업무), 422 `invalid_recipient`. 맡기기·재작업 단계의 기존 오류는 그대로 지난다(422 `invalid_field` 맡을 수 없는 에이전트, 409 `execution_conflict`·`request_incomplete`·`investigation_blocked`·`no_open_stage`). 처리 기록 뒤 맡기기·재작업이 실패하면 처리는 `accepted` 로 남고 새 단계·새 업무는 담당 없이 남는다 — 사람이 패널 담당 select·검토로 잇는다(접수 판단과 달리 다시 누를 수 없다 — 원인 Task 를 이미 마감했으므로).
8. **판정(`_judge_triage`).** 원인으로 판정기를 고른다: `intake` 는 지금 `triage.validate`(+ `next_action_forbidden`), 결과 뒤 판단은 `next_step.validate_next_step`. 둘 다 실패면 판단 로그 `failed` 코드 `triage_invalid`(메시지 = 하위 사유 + 설명 — 접수 판단과 같다). 결과 뒤 판단 하위 사유(위에서부터 첫 실패): `ids_mismatch`, `commit_mismatch`, `next_action_missing`, `kind_not_candidate`(`stage`·`new_work` 종류가 `kinds` 밖), `rework_mismatch`(`rework=true` 인데 종류 ≠ 지금 종류 또는 담당 ≠ `agent:<cause.agent_id>`), `kind_not_startable`(`rework=false` 인 `stage` 의 종류 = 지금 종류이거나 `startable=False`, `new_work` 종류가 `startable=False`), `assignee_not_candidate`, `assignee_cannot_take_kind`, `responsibility_not_candidate`(`(system_id, request_kind, recipient_member_id)` 가 `responsibilities` 밖). 통과면 `record_triage_proposed`(원인 Task·업무 상태 재계산) + `next_step_proposed` 알림. 실행 실패·기한 초과·사용량 한도 쉼은 접수 판단과 같다(`TRIAGE_DEADLINE_SECONDS`·`TRIAGE_USAGE_PAUSE_SECONDS` 공용). 실패한 결과 뒤 판단은 다시 돌리지 않는다 — 다음 tick 처분이 대체 경로로 간다.
9. **스키마 v24.** `triage_logs` 재생성(칸 셋·CHECK·부분 UNIQUE 둘, 기존 행 `cause = 'intake'`), `notifications` 재생성(사건 CHECK 두 값 추가), `internal_requests.created_by_triage_id`(NULL 허용, 부분 UNIQUE). `human_requests` 는 그대로(사실 10). 표·칸·CHECK·인덱스는 ARCHITECTURE. 판단 로그를 읽는 기존 열한 곳은 `cause = 'intake'` 로 거른다(사실 9) — 업무마다 `running` 판단 하나(`ux_triage_logs_running`)는 원인을 가리지 않고 그대로. 결과 뒤 판단을 시작하는 트랜잭션은 같은 업무의 처리 없는 결과 뒤 판단 `proposed`·`failed` 를 `superseded` 로(접수 판단 행은 건드리지 않는다), 접수 판단은 같은 업무의 처리 없는 접수 판단만(지금 그대로).
10. **알림(v24).** 새 사건 둘. `internal_request_received` — 받는 사람 = 요청의 `recipient_member_id` 한 명, 판단이 만든 요청·사람이 만든 요청·재전달(`reroute`)로 새로 생긴 요청 모두, `dedupe_key = "internal_request_received:<request_id>"`, 문구 `[Runloom] 요청 받음 — <원래 업무 제목>: <요청자 이름> · <system_id>/<request_kind> · <목적 첫 줄 80자>`, 링크 `<public_url>/requests`, `task_id` NULL(사실 6 — 새 함수 `enqueue_request_notification`). `next_step_proposed` — 받는 사람 = `turn_recipients_of(원래 업무)`, `dedupe_key = "next_step_proposed:<triage_id>"`, 문구 `[Runloom] 다음 단계 제안 — <업무 제목>: <행동 한 줄> · 확신도 0.82`, 링크 = 업무 주소, `task_id` = 원인 Task(기존 `enqueue_event_notification`). 같은 요청·판단에 한 번(`dedupe_key` UNIQUE). 웹훅이 없으면 쌓지 않는다(지금 그대로).
11. **업무 상태·화면.** `WorkItemFacts.next_step: NextStepFact | None` = 그 업무의 최신 결과 뒤 판단 행이 원인이 그대로이고 `running`(→ `에이전트 작업 중` · `다음 단계 판단 중`) 이거나 `proposed`·처리 없음(→ `내 차례` · `다음 단계 제안 · <행동 이름>`) 이거나 `accepted`·행동 `internal_request`·그 요청이 반환·반려 전(→ `대기` · `사내 요청 대기 · <받는 사람>`)일 때. `work_status` 는 열린 사람 요청·PR·직접 작업 뒤, 단계 `확인 필요` 앞에서 이 사실을 본다. 행동 이름: `stage` `다음 단계`(재작업이면 `재작업`) · `new_work` `새 업무` · `internal_request` `사내 요청` · `human` `사람 확인`. 업무 패널에 "다음 단계 제안" 절(`data-panel-section="next_step"`, 판단 절 뒤·지금 할 일 앞: 원인·행동·근거·모자란 정보·확신도·기준 버전·[제안대로]·[무시]·처리됨·실패 이유), 목록 배지(`다음 단계 판단 중`·`다음 단계 제안`·`사내 요청 대기`), `/requests` 의 판단이 만든 요청에 `판단 제안으로 생성`. 외부 문자열은 자동 이스케이프로만.

## 하지 않는 것

결과 뒤 판단의 자동 시작·자동 시작 자격 건수 반영, 결과 뒤 판단의 [다시 판단]·사람이 시작하는 버튼, 프로젝트(저장소)별 판단 기준·한 화면 등록(phase 23), 받는 사람 수락·검토·반환 생략, 조사 업무 안에서의 판단, 판단이 업무 완료·종료를 정하기, 판정 실패·실행 실패의 판단, 규칙 없이 이은 단계에 산출물 인계(이전 결과는 글로 넘긴다), 결과 뒤 판단 품질의 모니터링 지표(이번에는 `cause = 'intake'` 만 센다), 워크스페이스 사이 요청, A2A, Claude Code 훅, 실제 Claude·GitHub·Jira·Discord 호출(모든 step 은 가짜 러너·가짜 도구·`MockTransport` 로 검증, 실연동은 phase 뒤 사용자 지시).

## 결과

- 좋은 점: 결과가 규칙 밖으로 나가거나 정보가 모자라도 사이클이 조용히 멈추지 않는다 — 판단 에이전트가 후보 안에서 다음 행동 하나를 제안하고 사람은 한 번 누른다. 바깥 담당(담당 범위 표)이 후보에 들어오고, 요청은 받는 사람에게 알림으로 닿으며, 반환은 원래 업무의 판단으로 이어진다(RUN-26 장면). 새 실행 엔진·새 내장 종류·종류 이름 분기가 없다 — 판단 단계는 `is_triage_kind`, 원인은 판단 로그 칸이다. 판단을 시작할 수 없거나 실패·무시하면 지금 동작(사람 요청)으로 돌아간다.
- 비용: 판단 로그를 읽는 코드는 언제나 원인을 가려야 한다(빠뜨리면 접수 판단 배지·자동 시작이 틀린다 — 사실 9 의 열한 곳을 테스트가 지킨다). 결과 뒤 판단마다 구독 사용량을 쓴다(워크스페이스 1건·러너가 빌 때만). [제안대로] 의 맡기기·재작업이 실패하면 처리 기록만 남아 사람이 손으로 잇는다. 셀프호스트 v24 는 러너 재설치가 필요하다.
- 실연동 때 확인할 것: RUN-26 장면(수정 에이전트 `needs_information` → 사내 요청 제안 → 받는 사람 알림·수락·조사·검토·반환 → 반환 뒤 판단 → 재작업)이 실제 Claude 로 도는지, 판단 시간·구독 사용량, 모델이 후보 밖 값을 내는 빈도(`triage_invalid`), 재작업 실행이 `review_comment` 지적 산출물을 실제로 읽는지, 기다림 상한(3600초) 안에 판단 자리를 얻는지.
