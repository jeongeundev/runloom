# Phase 25 — 인계 리포트: 단계가 끝나면 근거가 붙은 리포트를 만들고, 받는 사람이 이해·판단한 뒤 이어받는다

작성일: 2026-10-22. 상태: 설계 완료, 실행 전. **`main` 에서 실행하고 `--pr` 로 `main` 행 PR 을 연다**([ADR-0030](../../docs/adr/0030-pr-ci-review-flow.md)). 근거: [ADR-0031](../../docs/adr/0031-handoff-understanding-and-clients.md) 결정 2(인계 리포트)·6(순서 ②)·미결 "리포트를 누가 만드는가"·"리포트 형식과 보관".

## 왜

ADR-0031 은 Runloom 의 역할을 "다음 사람과 그 에이전트가 앞 작업을 **이해한 상태로** 바로 이어받게 하는 것"으로 넓혔다. 지금 인계 자료는 에이전트용(`handoff_bundle` — 선행 결과·산출물·근거 원문)뿐이고, 사람이 읽고 판단할 형태가 없다. 결과 봉투의 `summary` 한 줄로는 무엇이 왜 바뀌었는지, 무엇을 정하지 않고 남겼는지, 받는 사람이 무엇을 결정해야 하는지 알 수 없다.

이 phase 가 끝나면 단계 결과가 판정을 통과할 때마다 그 단계를 실행한 에이전트가 별도 실행으로 **원본 리포트**(주장마다 근거 — 커밋·diff·검증 로그·업무 원문·PR·산출물)를 만든다. 받는 사람은 업무 패널에서 리포트를 읽고, "결정·확인할 것" 항목에 답을 남기고, 원하면 자기 에이전트에게 **맞춤 풀이**를 시킨다. 다음 단계 에이전트는 착수할 때 그 순간의 최신 리포트와 결정 답을 함께 받는다.

## 범위

- 포함: 원본 리포트 생성(러너)·저장·판정, 다음 단계 claim 대기, 받는 러너에게 리포트·결정 답 전달, 결정 답, 맞춤 풀이, 다시 만들기, 사람용 JSON API, 웹 패널·리포트 페이지, 셀프호스트 업그레이드 문서.
- 제외: 직접 작업(에이전트 실행 없는 업무)의 리포트(③ CLI), CLI·IDE 앱(ADR-0031 ③④), 새 알림 종류, 리포트 켜기/끄기 설정.

### 구조
D1. 만드는 쪽 → 보내는 쪽 원본 + 받는 쪽 맞춤 풀이. [사용자]
D2. 원본 → 결과 뒤 별도 실행. 근거는 작업 증명 기록(PR·커밋·이슈/Jira 원문·diff·검증 로그·산출물). [사용자]
D3. 원본 실행 에이전트 → 그 단계를 실행한 Agent(같은 러너). [사용자]
D4. 대상 → 판정 통과(`passed`)한 실행 결과 전부: 다음 사람에게 넘어가는 결과(후속 규칙·리뷰 뒤 재작업·판단 제안·사내 요청 반환), 마지막 단계, 정보 필요, 접수 판단 단계(결과 뒤 판단 단계는 제외 — 원인 단계 리포트와 중복, D4 는 D-4 검사 뒤 사용자 답으로 좁힘). 실행 실패·판정 불통과는 제외. 종류 무관(내장·사용자 정의). (검사 후) [사용자]
D5. 직접 작업(에이전트 실행 없음) → 리포트 없음, ③ CLI 에서. 직접 작업 중이라도 실행 결과가 있으면 4 를 따른다. [사용자 + 근거 4]
D6. 리포트 1개 = 원인 실행 1개. 재작업 결과는 새 리포트, 패널은 최신, 이전은 '자세히'. [조정값]
D7. 보낸 사람 = 원인 단계 Agent 의 주인 멤버, 받는 사람 = 다음 단계 담당 멤버(없으면 업무 담당). 담당이 에이전트면 그 에이전트의 주인 멤버, 주인 없는 공유 에이전트면 업무 담당 멤버, 그도 없으면 관리자만. (검사 후·D-4 검사 후) [사용자]
D8. 맞춤 풀이 → 받는 사람이 [내게 맞춰 풀기] 를 눌렀을 때만, 자기 Agent 중 선택(기본: 다음 단계 Agent), 맞춤 풀이를 할 수 없는 Agent(API 연결형·러너가 `handoff_report` 미선언)는 목록에서 빼고, 남는 Agent 가 없으면 버튼 숨김(API 는 422 + 사유) (D-4 검사 후 [사용자]). 근거는 원본만(원본 주장 ID 인용). 팀에 공개, 만든 사람 표시. (리포트, 만든 사람)당 최신 하나. 원본을 다시 만들면 옛 풀이에 '옛 리포트 기준'. (검사 후) [사용자]

### 동작
D9. 착수 대기 → 다음 단계 실행은 claim 순간 원인 리포트가 '작성 중'이면 가져갈 수 없음(최대 30분). 모든 착수 경로(자동·재작업·판단 제안 수락·사람 [시작])가 이 한 곳을 지난다. 실패·시간 초과·리포트 불가면 리포트 없이 착수. [사용자 + 조정값(30분)]
D10. 리포트 불가 → 원인 Agent 삭제·API 연결형·러너 능력 미선언이면 대기 없이 '리포트 없음(사유)'. [사용자(묶음 2)]
D11. 같은 러너 대기열 → 리포트 작업이 그 러너의 다음 실행보다 먼저. [사용자(묶음 2)]
D12. 실패 → 자동 재시도 없음, '리포트 없음(사유)' + [리포트 다시 만들기](보낸 사람·받는 사람·관리자), 같은 Agent 가 다시 씀. 이미 착수한 다음 단계에는 사람용으로만. [사용자]
D13. 결정 항목 → 항목마다 [확인함] / [다르게 정함 + 한 줄]. 답할 수 있는 사람 = 받는 사람·관리자. 착수를 막지 않음(막는 판단은 기존 사람 요청). (검사 후) [사용자]
D14. 리포트·결정 답 전달 → 묶음에 굳히지 않고 claim 순간의 최신을 붙인다. 자동 즉시 착수면 답은 사람 기록으로만 남고, 사람 [시작]·재작업 때 반영. (검사 후) [사용자]
D15. 결과 뒤 판단 → 리포트를 기다리지 않고 동시에. [사용자(묶음 6)]
D16. 원인 결과가 대체된 뒤 도착한 리포트 → 그 실행에 붙여 보관. [사용자(묶음 4)]

### 기술
D17. 실행 모델 → 전용 테이블 `handoff_reports`(원인 실행·상태·임대·결과) + 러너 claim 응답의 '리포트 작업'. Task·종류·업무 상태·보드·측정·모니터링을 건드리지 않는다. [사용자]
D18. 리포트 실행 환경 → 결과 커밋의 깨끗한 읽기 전용 체크아웃, 쓰기·커밋 금지(판단 선례). 원인 단계 실행 승인을 그대로 쓰고 능력 검사·소유자 재승인 없음. [사용자(묶음 3)]
D19. 형식 → 모델은 절별 주장+근거 ID JSON, 서버가 근거 확인 후 Jinja 템플릿. 에이전트용도 같은 JSON. [사용자]
D20. 판정 → 스키마 위반·크기 초과 = 실패. 근거 ID 미확인 = 그 주장에 '근거 확인 안 됨'. [사용자(묶음 4)]
D21. 근거 종류 → 이 실행·묶음의 artifact_id, base..result 커밋, 업무에 연결된 PR(있을 때만 — bug_fix→code_review 시점엔 없음), 업무 원문(이슈·Jira·사내 요청), 검증 로그. (검사 후) [사용자]
D22. PR 근거 수집 → 중앙이 리포트 작업 직전 GitHub App 으로 PR 본문·커밋·리뷰 코멘트 읽기(쓰기 없음), 러너는 로컬 git. 읽기 실패면 PR 근거 없이 'PR 읽기 실패' 표시. Jira 는 이미 가진 원문만. [사용자 + 묶음 7]
D23. 받는 쪽 러너 호환 → 리포트·결정 답은 `handoff_bundle` 계약을 바꾸지 않고 별도 파일로, 받는 러너가 능력을 선언했을 때만. [사용자(묶음 5)]
D24. 다이어그램 → Mermaid 텍스트, static 에 둔 mermaid.js(CDN 없음), `securityLevel: 'strict'`, 실패 시 텍스트. [사용자 + 묶음 8]
D25. 화면 안전 → 모든 텍스트 이스케이프. [사용자(묶음 8)]
D26. 저장 → 리포트 JSON 을 산출물 kind `handoff_report` 로 저장, HTML 은 조회 때 렌더. kind 는 종류·규칙 폼 선택지에서 숨김. 결정 답은 DB 행. 맞춤 풀이 결과도 원본과 같이 `handoff_report` 산출물로 저장하고 `handoff_reports` 행(`job_type=tailored`)이 가리킨다(D36 과 맞춤 — D-4 검사 뒤 정정). [조정값(이름) + 묶음 9]
D27. 러너 프로토콜 → claim capabilities 에 리포트 능력, 보내는·받는 러너 모두 재설치. 스키마 +1. 업그레이드 전 결과는 리포트 없음. [사용자(묶음 12)]
D28. 비밀값 → GitHub 토큰은 중앙에만, 러너·요청문에 넣지 않음. [근거: AGENTS.md CRITICAL]
D29. API → 리포트 조회(JSON·HTML)·결정 답·맞춤 풀이 요청/조회·다시 만들기를 /api/v1 에, 웹 폼과 같은 도메인 로직. 읽기 전용 토큰은 조회만. [근거: ADR-0031 결정 3, ADR-0032]
